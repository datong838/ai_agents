## 0. 本文从何而来（沟通结论摘要）

本清单汇总此前就「v0.1 试用版」与「目标态 AOS」的对齐结论，避免选型再次摇摆。


| 议题                                        | 结论                                                                  |
| ----------------------------------------- | ------------------------------------------------------------------- |
| 0.1 要不要钉钉/企微/飞书                           | **不要**。抛弃外部 IM；改为 **Local-First 桌面工作站**（对标数据主权 / Foundry Client 切片） |
| 安装平台                                      | **Windows · macOS · Linux 均可部署安装**（见 10 §0.2 / 11 §2.2）             |
| 代码改在哪                                     | **自有目录**（desktop/overlay/adapter）；**禁止 Dify 上游内大改**                 |
| 产品工程名                                     | **AOS 本地工作站** · 目录 `mybuddy-v01/`                                   |
| Dify / OpenOcta 能否当永久 Ontology / Workshop | **不能**。只覆盖问答 Agent + 本地壳；须有替换阶梯                                     |
| Apollo / 工作台 Module / Action 写回           | **工作量大**；Apollo 可最后做；**Module + Action 才是「玩业务闭环」**，不可永远缺失           |

| 方案措辞                                      | **禁止**写死个别客户/行业定制名词；示例用通用 `OBJ-`* / 企业知识库                           |

## 1. 目标态 vs 0.1 试用态（能力边界）

```text
目标态（01～09 / AOS）
  L1 数据集成 · Connectors / Pipeline / Dataset/MediaSet
  L2 Ontology · Object/Link/Action/Function · OKF · Wiki
  AIP · k-LLM · Logic / Chatbot · Draft · Lineage · HITL
  L3 工作台 · Module/Widget · Selection · 知识图谱 · Buddy
  Apollo · Hub-Spoke · Ferry · OPS-001~009

0.1 试用态（企业客户 · Local-First）
  L1′  本机上传企业文档（≈ MediaSet 代用品）
  L2′  本机 Dify Dataset RAG（≠ Ontology；左栏业务对象可为 mock）
  AIP′ OpenOcta Agent + Skill 调 Dify；无 Draft 写回
  L3′  Tauri 三栏（左对象 · 中 Chat · 右溯源）≈ UI-002 预览壳
  OPS′ 本机 Docker Compose + OpenOcta 单二进制；不做 Apollo
```

**话术红线：** 0.1 可说「本机可追溯问答 / 数据不出厂」；不可说已建成 Ontology / Workshop 工厂 / Apollo。

## 2. 已备开源 / 框架（覆盖到哪）


| 组件               | 状态                          | 覆盖目标态的角                                         |
| ---------------- | --------------------------- | ----------------------------------------------- |
| **Dify**         | `mybuddy-v01/dify` 上游克隆     | 文档知识库 · Chat/Workflow · Citations → **AIP′ 问答** |
| **OpenOcta**     | `mybuddy-v01/openocta` 上游克隆 | 本机 Agent · Skill/Tool → **AIP′ 运行时壳**           |
| **Tauri**        | 方案已定，桌面工程待建                 | Local-First Client → **L3′ Buddy 预览**           |
| **可选 adapter**   | `/v1/buddy/ask` 契约层         | 换脑不换 UI 的稳定钉                                    |
| **claudeskills** | 仓库平级                        | 工程方法（切分评测/Prompt/安全），**不是**产品层替代                |


### 2.1 开发组织铁律（写入 10 / 10a）

**新起/用好我们自己的目录开发，不要在 Dify 里大改。**

- 主代码：`mybuddy-v01/desktop` · `openocta-overlay` · `adapter` · `docs`  
- 上游 `dify/` / `openocta/`：配置与 API 引擎，gitignore，非日常开发仓  
- `claudeskills/`：按需捞取方法与脚本，不进交付包

### 2.2 跨平台安装铁律

**自有桌面与启动交付物须在 Windows / macOS / Linux 均可安装运行。**

- 打包：Tauri 多目标（`.msi`/`.exe` · `.dmg`/`.app` · AppImage/deb 等）  
- 脚本：`scripts/win|mac|linux`；Compose + OpenOcta 按各 OS 文档起服  
- 禁止默认「只做 Windows」

**明确不够用的断言：**

- Dify Dataset ≠ Ontology Object/Link/Action  
- OpenOcta ≠ 工作台 Module 工厂  
- docker compose 本机 ≠ Apollo Hub-Spoke / Ferry

## 4. 与「怎么玩业务」相关的优先级（沟通结论固化）


| 能力                     | 相对工作量    | 能否最后做        | 没有时业务怎么玩               |
| ---------------------- | -------- | ------------ | ---------------------- |
| **Apollo（E）**          | 大        | **可以最后做**    | 业务照玩；用 Compose/手工运维顶交付 |
| **工作台 Module（D）**      | 中～大      | **不该压到最后**   | 只能问答；看不清业务台面           |
| **Action 写回（B5 + G1）** | 中（单场景可控） | 0.1 可后；闭环必尽早 | 只能建议；人去外系统改            |


**建议建设顺序（目标态视角）：**

```text
本机 Buddy 问答（已定 0.1）
  → 一个固定业务 Module（列表+详情）
  → 1～2 个 Action（可先 Draft）
  → L1 真接入 / 真 Ontology
  → Workshop 画布工厂
  → Apollo 子集
```

11 缺失的开源方向组件 补充如下：

针对你当前“拿 Dify + OpenOcta 拼凑 MVP”与“未来对标 Palantir AOS 目标态”之间的巨大鸿沟，我为你梳理了缺失的核心开源组件清单。

这些组件可以作为你未来 AOS（Agent Operating System）的“积木”。在当前的 MVP 阶段，你不需要全部用上，只需将它们的设计理念或核心算法，通过二开“塞进” Dify 或 OpenOcta 里。

### 一、 核心架构缺口与开源组件推荐

#### 1. 数据摄入与本体建模层（L1 Pipeline / Ontology）

**缺口**：Dify 目前只能做简单的 RAG（基于文档切片），无法处理复杂的异构数据（如肽的批次号、合成设备日志、ERP 状态），也无法建立 Palantir 核心的“对象（Object）”模型。

- **推荐组件：OpenFoundry**
  - **简介**：这是一个非常新的 Rust 微服务架构开源项目，被社区称为 Palantir Foundry 的极客版替代方案 。
  - **可参考点**：虽然它极早期不适合商用，但其 **[Architecture.md](http://Architecture.md)**​ 极其精良。重点关注它的四大边界划分：**Platform（平台层）**、**Data Engine（数据引擎）**、**Ontology（本体论建模）**、**ML-AIP（AI 智能体）**。
  - **二开迁移**：借鉴它的 Ontology 层设计，在 Dify 的 Metadata（元数据）中强行扩充“对象属性”（如：肽 ID、纯度、状态），而不是只存 Text Chunk。
- **推荐组件：OpenMetadata**
  - **简介**：标准化的数据治理与元数据管理平台 。
  - **可参考点**：如何用 Schema 定义企业内的各种数据表，以及数据血缘追踪。
  - **二开迁移**：在 MVP 中，你可以用 OpenMetadata 管理湃肽的非结构化文档元数据，将其作为 Dify 之外的“轻量级 LDM（逻辑数据模型）”展示给客户看，体现专业性。

#### 2. 高级知识图谱与复杂推理层（L2 Knowledge / KG-RAG）

**缺口**：肽工艺涉及复杂的化学反应路径、上下游依赖。纯文本的 RAG 会出现“幻觉”和遗漏。你需要 GraphRAG（图检索增强生成）。

- **推荐组件：LightRAG**
  - **简介**：港大开源的轻量级 GraphRAG 。它将文档转化为图结构（实体-关系-属性），成本极低但能处理多跳推理（例如：“找出和 PT-888 肽使用相同催化剂且有纯度异常的批次”）。
  - **可参考点**：它的图索引算法和查询时的“增量检索”逻辑。
  - **二开迁移**：**这是 MVP 阶段的重点！**​ 不要直接用 LightRAG 替换 Dify（太重），而是写一个简单的 Python 脚本，利用 LLM 抽取湃肽 PDF 中的“实体（Enzyme, Temperature）”和“关系（causes, requires）”，生成一个 JSON 图谱，前端可视化展示给客户，证明你达到了“Palantir 级别的关联分析”。
- **推荐组件：Youtu-GraphRAG (腾讯优图)**
  - **简介**：腾讯开源的图检索框架，支持动态 Schema 引导 。
  - **可参考点**：它的 Schema 演化机制。当湃肽新增了一种新肽时，系统如何自动更新图谱 Schema。

#### 3. 智能体执行与自动化层（L3 Action / Agentic Workflow）

**缺口**：OpenOcta 目前擅长“问答”，但不擅长“办事”。Palantir 的核心是 Agent 能直接调用 API 操作外部系统。

- **推荐组件：AutoGen (微软)**
  - **简介**：经典的 Multi-Agent（多智能体）对话框架。
  - **可参考点**：GroupChat（群聊模式）和 Nested Agent（嵌套代理）。
  - **二开迁移**：在 OpenOcta 中引入 AutoGen 的思想。例如，当客户问“帮我查一下昨天的异常批次并生成报告”时，OpenOcta 内部拆解为两个 Agent：Agent-A 负责查数据库（Tool Use），Agent-B 负责写 Word 报告（Code Interpreter），最后汇总输出。
- **推荐组件：Mage AI**
  - **简介**：现代的数据管道（Data Pipeline）和编排工具 。
  - **可参考点**：可视化拖拽的数据流（Dataflow）。
  - **二开迁移**：把 Dify 的 Workflow 看作是 Mage 的 Pipeline。未来你可以开发一个“Pipeline 导入导出”功能，让 Agent 生成的 Workflow 能直接变成企业级的数据调度任务。

#### 4. 应用与可视化层（L4 Workshop）

**缺口**：Dify 的界面是“后台管理风”，不是 Palantir 那种炫酷的 Workshop 操作台。

- **推荐组件：Apache Superset**
  - **简介**：顶级的 BI 可视化开源工具。
  - **可参考点**：它的 Dashboard 拖拽布局和图表联动。
  - **二开迁移**：在 Tauri 桌面壳的右侧面板，嵌入 Superset 的渲染引擎。让 Agent 的分析结果不仅是一段话，而是一个可交互的柱状图或关系拓扑图。
- **推荐组件：OpenCTI**
  - **简介**：威胁情报知识图谱平台 。
  - **可参考点**：它的“实体-关系-证据链”可视化展示。
  - **二开迁移**：借鉴其前端图谱渲染（Force-directed graph）技术，用来展示“肽-工艺-设备”之间的复杂关系。

### 二、 二开实施路线图（如何利用这些组件）

#### 阶段一：MVP 交付（当前 - 3周后）

- **策略**：隐藏高级组件，用“伪功能”占位。
- **操作**：
  - **L2 层**：用 Dify 的 RAG 兜底。但前端界面（Tauri）加一个“知识图谱”Tab，用 ECharts 画一个简单的静态拓扑图（手动把 PDF 里的几个核心肽连起来），告诉客户：“这是我们的底层图谱雏形，二期会接入 LightRAG 自动生成”。
  - **L3 层**：OpenOcta 只做问答。但在回答末尾加一句：“我已为您准备好调用 ERP 接口的方案（展示 AutoGen 风格的伪代码），二期可自动执行”。

#### 阶段二：AOS 原形搭建（未来 3-6个月）

- **策略**：取其精华，去其糟粕。不要大而全，要小而美。
- **操作**：
  1. **数据层**：放弃 Dify 自带的向量库，引入 **OpenFoundry 的数据引擎理念**，自建一个小型的 Neo4j 或 Postgres 来存储肽的 Object 属性。
  2. **知识层**：引入 **LightRAG**​ 的核心逻辑，作为 Dify 的一个外部 Tool。当问题复杂时，Dify 调用 LightRAG 查图，再返回结果。
  3. **应用层**：用 **Superset**​ 的 React 组件重写 Tauri 的前端展示面板，彻底摆脱 Dify 的 UI 束缚。

### 三、 避坑指南

1. **不要盲目 All in**：OpenFoundry 虽然架构最像 Palantir，但它极早期，千万别在湃肽项目里直接用它的代码，否则会导致项目失控。
2. **GraphRAG 是必选项**：对于生物医药（肽、蛋白），单纯的文本 RAG 是不够的。**LightRAG 是目前开源界性价比最高的 GraphRAG 解决方案**，强烈建议在 MVP 的后端默默接入它做辅助计算。

**下一步建议**：

你可以先去 GitHub Star 一下 **OpenFoundry**​ 和 **LightRAG**，把它们的 Architecture 文档读一遍。然后我们制定一个“**LightRAG 二开接入 Dify**”的具体 API 接口规范，这能成为二期可选增强能力的底牌。
