## 0. 一句话结论

| 问题 | 结论 |
| --- | --- |
| aos-platform **现在有没有**区分使用者？ | **有登录身份**（Bearer / OIDC `sub`），**有租户字段**（`org_id` + `project_id`），部分写路径已按两字段过滤 |
| **有没有**像 Dify 那样「切工作区 = 整站换世界」？ | **没有。** Web 客户端写死 `X-Org-Id: dev-org` / `X-Project-Id: dev-project`；无工作区切换器；多数列表/读路径未强制按工作区隔离验收 |
| 标准企业版多人登录够不够？ | **身份层够起步，隔离层不够交付。** 多人同 `dev-org/dev-project` 会看到同一套业务资源，仅靠 Marking/角色做细粒度，**不等于工作区隔离** |
| 集团 / 多租户怎么做？ | **Org = 租户硬边界**；**Project = 工作区（≈ Dify Workspace）**；Hub+多 Spoke 在 Org 之上再加 **部署/数据主权** 边界，不替代工作区 |

## 1. 问题陈述（对照 Dify）

### 1.1 Dify 截图里的策略（我们要学的「体验」）

```text
登录用户（栖月汇）
    └── 当前工作区：「栖月汇的工作区」← 左上角切换
            └── Studio / Agents / 知识库 / 集成 … 全部只显示该工作区资源
```

要点：

1. **工作区是一等公民** — 不是筛选器，而是整站上下文。  
2. **切工作区 = 换资源宇宙** — App、知识库、集成与用户列表一并切换。  
3. **同一用户可属多个工作区** — 成员关系在工作区上，不在「全局扁平资源」上。  
4. **工作区内仍可有多创建者** — 「创建者」过滤 ≠ 跨工作区可见。

### 1.2 AOS 应对齐的部署形态（你表里的四档）

| 形态 | 谁用 | 隔离诉求 | 与本方案关系 |
| --- | --- | --- | --- |
| Local-First 工作站 | 试用 / 单机主权 | 默认可单 Org + 单 Project | 字段保留，UX 可隐藏切换器 |
| **单机房私有化** | **标准企业** | **一家公司多用户 + 多部门工作区** | **本方案主战场（P0）** |
| Hub + 多 Spoke | 集团 / 多租户 | Org 间硬隔离 + Spoke 数据主权 | P1：Org 边界 + Apollo；工作区模型不变 |
| 气隙 / Ferry | 高安全 | 包级隔离 + 单向摆渡 | 工作区随 Bundle 元数据携带；不新造实体 |

**关键误区：** 「单 Spoke / 单机房」≠「不用隔离」。标准企业版仍是 **多用户 + 多工作区**；只是通常 **一个 Org**，不是 SaaS 多客户混部。

## 2. 现状诊断（诚实口径）

### 2.1 已有（可复用）

| 能力 | 落点 | 说明 |
| --- | --- | --- |
| Principal | `aos_api/auth.py` | `subject` · `org_id` · `project_id` · `roles` · `markings` |
| Claims / 头 | OIDC + `X-Org-Id` / `X-Project-Id` | 与 [60](60-生产IdP联调手册.md) 一致 |
| T-CROSS 模型 | Org / Project / Environment | 方案层已决：业务表带两字段 |
| 部分写路径 | Draft / Module / Action 等 | SQL `WHERE org_id AND project_id` |
| Authz | OpenFGA + Markings | 对象级 / 标记级（[61](61-OpenFGA生产模型扩展.md)） |
| 日志 | `org_id` / `project_id` 强制字段 | T-CROSS §3.2 |

### 2.2 缺口（相对「整站隔离」）

| 缺口 | 现象 | 风险 |
| --- | --- | --- |
| **G1 客户端写死上下文** | `apps/web/src/api/client.ts` 固定 `dev-org` / `dev-project` | 无法切工作区；演示即生产假象 |
| **G2 无工作区一等 UX** | 壳无「当前工作区」切换器（对标 Dify 左上角） | 用户感知不到隔离 |
| **G3 读路径未门禁统一** | 部分 list/get 未强制 `project_id` 过滤或未测跨区拒访 | **水平越权** |
| **G4 无 Membership 产品面** | 用户↔工作区成员关系依赖 IdP 手工 claim，无「我的工作区」API/页 | 标准企业运维难 |
| **G5 存储前缀未产品化** | MinIO 等可有 `org/project/` 前缀，未强制验收 | 对象存储串租 |
| **G6 Dev Token 过宽** | `Bearer dev` + 头可任意改 org/project | 开发便利；**生产必须关**（已有开关） |

**结论：** 不是「完全没有多租户设计」，而是 **横切字段未产品化成「整站工作区上下文」**。标准企业版若直接上多人，**默认会共池**。

## 3. 实体识别模型（从身份到边界）

> 命名约定：**对外产品文案可用「工作区」**；契约与库表继续用 **`project_id`**（与 T-CROSS 一致），避免第三套 ID。

### 3.1 实体清单

```text
┌─────────────────────────────────────────────────────────────┐
│ Identity Plane（IdP · Keycloak 等）                          │
│   User（sub） · Group/Role（可选） · Org claim / Realm        │
└───────────────────────────┬─────────────────────────────────┘
                            │ OIDC Access Token
┌───────────────────────────▼─────────────────────────────────┐
│ AOS Control Plane                                           │
│   Organization（org_id）     ← 租户 / 公司 / 集团客户单元      │
│   Project / 工作区（project_id）← ≈ Dify Workspace           │
│   Membership（user×project） ← 角色：owner/admin/editor/viewer│
│   Environment（rc/beta/stable）← Apollo Channel，与工作区正交 │
└───────────────────────────┬─────────────────────────────────┘
                            │ Principal 注入每个请求
┌───────────────────────────▼─────────────────────────────────┐
│ Resource Plane（一律带 org_id + project_id）                 │
│   Ontology · Dataset · MediaSet · Pipeline · Draft ·        │
│   Workshop Module/Widget · AIP Agent/Logic · Wiki ·         │
│   Connector 配置 · 密钥 ref · 通知通道 · 分析 Notebook …      │
└─────────────────────────────────────────────────────────────┘
```

| 实体 | ID | 含义 | 隔离强度 |
| --- | --- | --- | --- |
| **User** | `sub`（JWT） | 自然人 / 服务账号 | 认证边界 |
| **联系方式（产品）** | `email:…` / `phone:…` → subject | 管理员加人用邮箱/手机识别；见 [168](168-成员自然人识别-邮箱手机号方案.md)；**验证码后置** | 映射到 Membership |
| **Organization** | `org_id` | 公司或集团客户租户 | **硬边界**（跨 Org 默认不可见） |
| **Project（工作区）** | `project_id` | 部门 / 业务线 / 产品线工作区 | **硬边界**（跨 Project 默认不可见） |
| **Membership** | `(user, project_id, role)` | 谁能进哪个工作区、何角色 | 准入 |
| **Environment** | channel | 发布轨道 | 与工作区正交；不替代隔离 |

### 3.2 与 Dify 概念映射

| Dify | AOS | 备注（含产品 UI 中文展示名） |
| --- | --- | --- |
| 登录用户 | User `sub` | 同；UI 展示名：**用户** / 头像旁显示姓名 |
| **工作区** | **Project（`project_id`）** | 契约名 Project；**产品 UI 一律称「工作区」**（切换器、面包屑、设置页） |
| （隐式租户 / 云上多客户） | **Organization（`org_id`）** | 私有化常一 Org；SaaS/集团多 Org；**产品 UI 称「组织」**（管理面；单 Org 部署可隐藏） |
| App / 知识库 / 集成 | Module · Ontology · Dataset · AIP … | 资源一律挂工作区；UI 沿用既有中文：**模块** · **本体** · **数据集** · **AIP** 等 |
| 工作区内「创建者」 | `created_by` + Membership 角色 | 区内过滤，非跨区；过滤器 UI 称**「创建者」**；成员角色 UI：**所有者** / **管理员** / **编辑者** / **查看者** |

### 3.3 标准企业版 vs 集团多租户（实体怎么摆）

| 场景 | Org | Project（工作区） | 用户登录后 |
| --- | --- | --- | --- |
| **标准企业 · 单机房** | **1 个**（如 `acme`） | **多个**（销售 / 供应链 / 沙箱…） | 选工作区 → 整站只见该区 |
| **集团 · 多子公司同部署** | **多个**（每子公司一 Org） | 每 Org 下多个 Project | 先 Org（或 IdP Realm）再工作区 |
| **Hub + 多 Spoke** | Hub 管元数据；Spoke 带 `org_id` | 工作区定义可在 Hub，数据在 Spoke | 控制面切换工作区；数据面不跨 Spoke 串读 |
| **Local-First** | 默认 `local-org` | 默认 `default`（可隐藏切换） | 单人/小队试用 |

**已决：** 不因「标准企业只有一家公司」而删除 `org_id`；单 Org 部署仍走同一代码路径（T-CROSS §5）。

### 3.4 已决产品规则（数据 · 插件 · 案例 · 工程口径）

#### 3.4.1 历史开发数据 → 唯一「测试工作区」

| 项 | 已决 |
| --- | --- |
| 性质 | 现有种子 / ensure-seed / 开发过程写入的数据 = **测试数据**，不是交付资产 |
| 归属 | 一律归入组织内固定工作区：**「测试工作区」**（契约建议 `project_id=test` 或 `dev-test`；UI 名必须是中文 **测试工作区**） |

#### 3.4.2 插件目录共用 · 工作区配置私有

| 层 | 范围 | 示例 | 隔离 |
| --- | --- | --- | --- |
| **平台插件目录（共用）** | Org 内或整站可读的「可选用」能力清单 | 可选大模型 Provider 插件、数据采集 / Connector / Pipeline 插件、解析器、Widget 等 | **不按工作区复制插件包**；目录对有权用户可见 |
| **工作区已配置实例（私有）** | 挂在当前 `project_id` 上的启用与参数 | **已配置大模型**（密钥 ref、默认路由、温度等）、已启用的采集链路实例、连接凭据 | **按工作区隔离**；切区后只见本区配置 |

```text
平台：可选插件目录（共用）
        │ 安装/启用到工作区
        ▼
工作区 A：已配置大模型 · 已配采集链路 …
工作区 B：另一套已配置大模型 · 另一套链路 …
```

**已决：** 「能选什么」共用；「本区选了什么、怎么配」私有。密钥 / Vault ref 只绑定工作区级配置，禁止跨区复用明文或 ref 偷渡。

## 4. 整站隔离（从识别到每一层）

「整站」= **任何业务请求进入后，上下文不可被客户端随意伪造，且读写存储全链路带同一边界。**

### 4.1 请求上下文（强制）

```text
1. 认证：Bearer JWT（生产禁 Bearer dev）
2. 解析 Principal.subject / roles / markings
3. 解析 org_id / project_id：
   - 优先 JWT claims（不可被头静默覆盖升级）
   - 可选：用户显式「切换工作区」后由 BFF 换发含新 project_id 的会话令牌
   - X-Org-Id / X-Project-Id：仅 Dev 或与 claim 一致时允许；生产冲突 → 403
4. Membership 校验：subject 必须是该 project 成员，否则 403 WORKSPACE_FORBIDDEN
5. 下游所有查询/写入注入 (org_id, project_id)；禁止「无过滤全表扫描」业务 API
```

**安全已决（相对现状加强）：**

| 规则 | 说明 |
| --- | --- |
| **R-ISO-01** | 生产：`project_id` **以服务端会话 / 令牌为准**，禁止仅靠浏览器改 Header 越权进其他工作区 |
| **R-ISO-02** | 跨 Org 访问 → **404 或 403**（不泄露资源是否存在，产品可选统一 404） |
| **R-ISO-03** | 列表 API 默认 `WHERE org_id=? AND project_id=?`；缺过滤 = **缺陷** |
| **R-ISO-04** | 对象存储 Key / 向量集合 / Wiki 空间前缀必须含 `org_id/project_id` |
| **R-ISO-05** | Audit / App Log 每条带 `org_id` · `project_id` · `actor_id` |

### 4.2 分层隔离矩阵

| 层 | 隔离手段 | 验收 |
| --- | --- | --- |
| **UI 壳** | 顶栏「当前工作区」；切换后全站刷新上下文；面包屑含工作区名 | 切区后列表内容变化且不可「返回看见他区 ID」 |
| **BFF / aos-api** | Principal + Membership；统一依赖注入 | 用 A 区 Token 读 B 区 rid → 拒 |
| **元数据库** | 所有业务表双字段 + 复合索引 `(org_id, project_id, …)` | 迁移扫描：无双字段表进门禁黑名单 |
| **图 / Ontology** | 分支、对象、链接挂 Project；跨区 Link **禁止**（或显式「跨区只读联邦」二期） | 邻接查询不漏他区 |
| **对象存储** | `s3://…/{org}/{project}/…` | 预签名 URL 不可猜扫他区前缀 |
| **向量 / 检索** | collection 或 payload filter 含双 ID | 检索结果无他区 hit |
| **AIP / Draft** | Draft 队列按工作区；审批人须为本区角色 | Inbox 不串区 |
| **Workshop** | Module/Widget 安装与画布属工作区 | 工作室列表按区 |
| **密钥** | Vault path 含 org/project；secret ref 不可跨区解析 | 他区 ref → 拒绝 |
| **Apollo** | Channel/Spoke 资产带 `org_id`；Promote 不跨 Org | T09 已述；本方案不削弱 |
| **可观测** | 日志/指标标签带双 ID；看板可按工作区过滤 | 排障不串租 |

### 4.3 与 Marking / OpenFGA 的关系（不要混为一谈）

| 机制 | 解决什么 | 不解决什么 |
| --- | --- | --- |
| **Org / Project 隔离** | **租户 / 工作区硬边界**（有没有资格看见这片宇宙） | 宇宙内细粒度「这份密件」 |
| **OpenFGA** | 宇宙内对象级 viewer/editor/owner | 替代工作区边界 |
| **Markings** | 标签级读脱敏 / 写拒绝 | 替代工作区边界 |

**组合顺序（已决）：**  
`认证 → 工作区 Membership →（OpenFGA 关系）AND（Markings）→ 业务结果`。

## 5. 产品体验（对标 Dify，落到 AOS 壳）

### 5.1 壳交互（P0）

| 元素 | 行为 |
| --- | --- |
| 左上 / 顶栏 **工作区切换器** | 展示当前工作区名称；下拉「我的工作区」列表 |
| 切换 | 调用 `POST /v1/me/workspace/switch`（或等价）→ 更新会话 → **整站路由重载或清空查询缓存** |
| 无成员工作区 | 不出现在列表；深链他区 URL → 统一「无权限 / 不存在」页 |
| Local-First 单区 | 可配置隐藏切换器，仍保留后端字段 |

### 5.2 最小 API（建议契约，实现刀另开）

| API | 作用 |
| --- | --- |
| `GET /v1/me` | 扩展：返回 `org` · `currentProject` · `projects[]`（仅成员） |
| `GET /v1/workspaces`（或 `/v1/projects`） | 当前 Org 下我可进入的工作区 |
| `POST /v1/workspaces/{id}/enter` | 切换当前工作区（服务端会话） |
| `GET/POST /v1/workspaces/{id}/members` | 成员管理（admin） |
| 既有业务 API | 全部消费 Principal 的 `org_id`/`project_id`，**禁止**客户端传任意资源所属区覆盖 |

### 5.3 管理面（标准企业运维）

| 能力 | 说明 |
| --- | --- |
| 创建工作区 | Org admin |
| 邀请成员 / 绑 IdP Group | 映射到 Membership 角色 |
| 工作区停用 | 只读或拒绝进入；数据保留 |
| 审计 | 进入工作区、成员变更、跨区拒绝记 Audit |

## 6. 分阶段落地（不一次做爆）

### 6.1 阶段划分

| 阶段 | 目标 | 形态 | DoD（摘要） |
| --- | --- | --- | --- |
| **P0** | **标准企业可用的工作区隔离** | 单 Org · 多 Project | 切换器 + 会话；核心 CRUD/列表双字段强制；跨区拒访单测；关 Dev 越权头 |
| **P1** | 成员与管理面 | 同上 | Members API/页；IdP Group→工作区角色；Audit |
| **P2** | 存储与检索强制前缀 | 同上 | MinIO/向量/Wiki 前缀门禁；迁移工具 |
| **P3** | 集团多 Org / Hub+Spoke | 多 Org | Org 切换或 Realm；Spoke 绑定 Org；控制面不串数据面 |

### 6.2 P0 实现刀建议（文档级，**本文件不编码**）

1. **方案回写**：本文件挂索引；T-CROSS §5 增补「工作区 = Project 产品名」一句。  
2. **安全收紧**：生产忽略或校验 Header 与 claim 一致（R-ISO-01）。  
3. **上下文门面**：Web 去掉写死 `dev-org/dev-project`；从 `/v1/me` 注入；开发种子默认写入 **测试工作区**。  
4. **壳切换器**：最小 UI（可先简易下拉，不追求 Dify 视觉 1:1）；列表含「测试工作区」（可标为可删）。  
5. **隔离门禁测试**：固定夹具 OrgA/Prj1 vs Prj2；list/get/write 越权用例进 pytest。  
6. **盘点漏网表**：脚本扫 SQL/仓储无 `org_id`+`project_id` 谓词的读路径 → 台账销项。  
7. **插件边界**：盘点「目录 vs 已配置实例」；大模型已配置项必须带 `project_id`。  
8. **禁演示壳**：实现刀自检无新增演示页/临时分支；正式案例等产品方微信商城工作区规格。

### 6.3 明确非目标（本期）

| 非目标 | 原因 |
| --- | --- |
| ❌ 另造 `workspace_id` 与 `project_id` 双轨 | 分裂契约 |

| ❌ 行级「个人私有盘」替代工作区 | 个人草稿可用 `created_by`，边界仍是工作区 |

| ❌ **演示专用页面 / 临时分支逻辑** | **R-PROD-01～04**；案例用正式工作区配置，不用演示壳 |
| ❌ 把测试种子写进默认/隐藏共池 | 一律进 **测试工作区**，可删 |
| ❌ 按工作区复制整份插件包目录 | 目录共用；仅「已配置实例」按区隔离 |

## 7. 验收标准

| # | 标准 |
| --- | --- |
| A1 | 用户 U 为工作区 P1 成员、非 P2：P2 列表为空或拒访；已知 P2 资源 ID 直链 → 403/404 |
| A2 | 切换工作区后，Workshop / Ontology / Draft / Data 主列表均只反映新区 |
| A3 | 生产关闭 `AOS_AUTH_ALLOW_DEV`；伪造 `X-Project-Id` 不能进入无成员工作区 |
| A4 | 新建资源落库必含当前 `org_id`+`project_id`；禁止客户端指定他区 ID 写入 |
| A5 | Audit 可查：进入工作区、拒绝跨区、成员变更 |
| A6 | Local-First 单区模式：无切换器亦可工作；字段仍写入默认 Org/Project |
| A7 | 文档与话术：标准企业版 =「单 Org + 多工作区」；集团 =「多 Org」；不与 Marking 混谈 |
| A8 | 开发种子 / 历史测试数据仅出现在 **测试工作区**；可一键或运维删除该区而不影响产品能力 |
| A9 | 插件目录（可选大模型 / 采集链路等）跨工作区可见；**已配置大模型**等实例严格按当前工作区隔离 |
| A10 | 产品 UI/API **无**演示临时页或 `if demo` 主路径；正式案例仅通过正常工作区配置承载（含待交付的微信商城案例） |

## 8. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 历史开发数据散落 | **迁入 / 种子写入固定「测试工作区」**；开发结束后允许删除该工作区（§3.4.1） |
| 插件与配置边界不清 | **目录共用 · 已配置实例按区**（§3.4.2）；密钥 ref 绑工作区 |
| 演示逻辑渗进产品 | **R-PROD-01～04**；案例走正式工作区（微信商城案例待产品方交付，§3.4.3） |
| 漏网 API 未过滤 | 中央仓储基类 / 中间件强制；CI 扫描 + 越权单测 |
| 与 OpenFGA 元组未带 project | 元组 key 含 `project:{id}` 或 object 名带前缀（对齐 61） |
| 性能：每请求 Membership | 会话缓存 + 短 TTL；变更成员时吊销 |
