0产品全景

AOS（AI Ontology System）是对标 Palantir Foundry 的自研平台。核心思路：先建本体，再搭应用，最后注入智能。整个系统由三大产品层 + 模型管理 + 运维交付构成。

①
数据层 — Foundry 数据 → 本体
把外部系统数据接入、清洗、加工、物化为本体。包含数据源同步、管道构建、本体管理。
②
应用层 — Workshop 本体 → 应用
在已有本体之上，用低代码画布搭业务应用。包含工作台、画布编辑器、组件注册表、变量管理器、事件配置。
③
智能层 — AIP 应用 + AI
给应用注入 AI 能力：对话助手、逻辑编排、智能体、工具面板。含评测门控、人在回路、决策谱系。
④
模型管理 — 三层栈 AI 基础设施
管理 LLM 供应商连接、路由策略、模型目录、容量配额。是 AIP 智能层的底层依赖。
⑤
运维交付 — Apollo 多环境管理
中心 Hub 管理多个 Spoke 边缘环境，灰度发布、版本管理、气隙交付、资产打包。
一句话理解：数据层把脏数据变成可信本体 → 应用层把本体变成可操作的应用 → 智能层让应用能自主决策 → 模型层提供 AI 算力 → 运维层把整套系统交付到不同环境。
0.1三层栈架构与数据流向

理解 AOS 的关键是理解数据如何在三大产品层之间流动。以下是一个完整链路：

[数据层] 外部数据源（MySQL/Kafka/Salesforce…） ↓ 数据链接器选择连接器，配置同步任务 [数据层] 数据集 (Dataset) ↓ 管道构建：Join → Filter → Transform → 输出 [数据层] 本体 (Ontology) — Object Type / Link Type / Action Type ↓ 本体管理：定义实体、属性、关系、动作 [应用层] Workshop 应用 ↓ 画布编辑器拖入 Widget → 绑定 Object Type → 配置变量 → 配置事件 [智能层] AIP 逻辑编排 ↓ 逻辑画布编排：Input → Get Property → Use LLM → Apply Action [智能层] Agent 执行 ↓ Agent 调用工具 → 生成 Draft → 人工审批 → 写回本体 [运维层] 交付到 Spoke 环境
关键概念：每一层都是独立可用的。你可以只用数据层做 ETL，也可以只用应用层搭管理界面。但完整价值需要三层贯通：数据 → 本体 → 应用 → AI 决策 → 写回数据。
0.2快速上手路径

如果你是第一次使用 AOS，按以下顺序操作：

1
接入数据源
进入 数据源 → 数据链接器，选择连接器类型（MySQL/REST/GraphQL…），配置连接参数，创建同步任务将外部数据拉入数据集。
2
构建管道加工数据
进入 管道 → 管道构建，在 DAG 画布上拖入数据源节点和变换算子（Filter/Join/Expression），配置输出到本体 Object Type。
3
定义本体结构
进入 本体 → 本体管理，创建 Object Type（如 Order/Customer），定义属性、Link Type（关系）、Action Type（写回操作）。
4
搭建业务应用
进入 工作台 → 创建应用，4 步向导创建 Module，然后在画布编辑器中拖入 Widget 组件，绑定 Object Type 和变量。
5
注入 AI 能力
进入 AIP → 逻辑画布 编排 AI 决策流；在 AIP → 对话机器人 创建 Agent 绑定工具和提示词；在 AIP → Draft 审批台 审批 AI 写操作。
6
配置模型基础设施
进入 模型管理 → 供应商 接入 LLM API Key，在 模型管理 → 路由 配置任务路由策略。

1.1管道构建

侧边栏 「管道与数据治理」 分区。管道是数据从原始到可信的加工流水线——类似 Spark / Airflow 的 DAG 编排，但可视化操作。

搭建查看当前管道的搭建状态和日志排查管道执行失败

2

管道的核心价值：不是写 SQL，而是把数据加工过程可视化、可追溯、可协作。每个节点的输出都可以预览，数据沿袭图可以追溯任何字段的来源。
1.2本体 · 数字孪生

侧边栏 「本体 · 数字孪生」 分区。本体（Ontology）是 AOS 的核心——它把业务实体（订单/客户/设备）、关系、动作建模为一等公民，而不是普通的数据库表。

为什么需要本体？数据库表只描述"数据长什么样"，本体还描述"实体之间什么关系"和"可以对实体做什么操作（Action）"。这让 AI 能理解业务语义，而不只是 SQL 查询。
页面用途什么时候用
本体管理本体总入口，收藏的 Object Type、最近修改、按业务域分组日常维护本体时从这里出发
对象探索图谱可视化，展示 Object Type 之间的关系拓扑向业务方展示数据模型全貌；检查关系是否合理
本体提案本体变更的审批流程（类似 Git PR）修改 Object Type / Link Type 后提交审批
图谱健康度检查本体的一致性、连通性、孤立节点本体治理巡检
活知识 Wiki本体的"活知识库"——业务规则、SOP、操作手册为 Agent 提供业务上下文；记录领域知识
Wiki 索引Wiki 的目录导航页（分支树 + 卡片 + 搜索）浏览和查找 Wiki 文档
分支管理本体的版本控制分支（类似 Git branches）多人协作修改本体时隔离工作
本体的三大核心概念
Object Type 实体
业务实体的定义。例如 Order 有 order_no、amount、status 等属性。不只是 schema——还含主键、显示标题、索引策略。
→ 在 Workshop 中被 Widget 绑定
Link Type 关系
实体之间的关系。例如 Order → Customer (N:1)、Order → OrderItem (1:N)。定义基数、方向、约束。
→ 在对象探索图谱中可视化
Action Type 动作
对实体可执行的操作。例如 confirmShipment、cancelOrder、refundOrder。不是 CRUD API——是有业务语义的写操作。
→ 在 AIP Logic 中被 Apply Action 块调用

3智能层 — AIP 应用层

侧边栏 「AIP 决策引擎」 分区。AIP（AI Intelligent Platform）是给应用注入 AI 能力的层。分为 4 个子分组：应用层、逻辑编排层、智能体、评测与治理。

3.0.1 AIP 助手 即问即答

用途：权限感知的 LLM 聊天界面，基于产品文档和本体知识回答问题。

什么时候用：需要快速了解平台功能、查阅文档、获取操作指引时——类似内嵌的 ChatGPT，但了解你的业务数据。

关键特性：返回答案附带引用来源；底部展示建议问题引导深入探索。

3.1AIP 逻辑画布 核心编排工具

这是 AIP 最核心的工具——一个可视化逻辑编排器，把 AI 决策流程拆解为可连接的逻辑块（Block）。

为什么需要逻辑画布？直接写 Prompt 让 LLM 自由决策不可控。逻辑画布让你像搭管道一样编排 AI 决策流：先拿什么数据、再调什么模型、满足什么条件走哪条路、最后怎么写回——每一步都可见、可调试、可审计。
10 种逻辑块（Block）详解

每种 Block 对应 AI 决策流程中的一个具体步骤。以下是每个 Block 是什么、在哪一步用、解决什么问题：

IN
1. Input（输入）
流程第一步。声明本次操作的目标对象，如 order : Order。所有后续 Block 从此变量读取数据。
GP
2. Get Property（取属性）
Input 之后。从本体对象提取字段值，如 order.status / order.amount，注入上下文供后续分析。
CV
3. Create Variable（建变量）
需要计算派生值时。用 DSL 表达式创建中间变量，如 is_vip = customer.tier == "gold"。
LLM
4. Use LLM（调模型）核心
需要 AI 判断时。配置 prompt / model / temperature，调用大模型做分类、抽取、生成、风险评估。是 AI 决策的核心环节。
TL
5. Use Tool（调工具）
需要调外部能力时。调用已注册的 Capability 工具（查库、调 API、执行计算）。
TF
6. Transform（变换）
需要集合操作时。用 DSL 过滤/映射/聚合列表数据，如 filter(orders, o → o.amount > 500)。
AA
7. Apply Action（执行动作）写回
需要改变系统状态时。对本体对象执行 Action（修改状态、创建工单、发通知）。支持 dryRun 模式——先生成提案不落库。
EX
8. Execute（执行子流程）
需要嵌套或通知时。执行子逻辑流、语义搜索、或触发通知（email/webhook）。
BR
9. Branch（分支）条件路由
需要走不同路径时。根据条件 DSL 分叉，如高风险→升级流程，低风险→自动放行。不是独立块——通过边的 condition 实现。
HO
10. Handoff（汇聚交接）合并
分支执行完毕后。合并多路上下文，输出决策摘要+产物+待确认项，传递给下游 Agent 或人工审批台。
典型编排示例：风险分诊
[Input] order : Object · Order ↓ [Get Property] order.status / amount / currency / region ↓ [Use LLM] 风险评估 (model=私有-中, temp=0.3, max=512) ↓ ↓ (双路分支) ├─ [Branch · high] → [Apply Action] escalate_to_supervisor └─ [Branch · low] → [Write Back] update_status → shipped ↓ ↓ 汇聚 [Handoff] 上下文交接 (decision + artifacts + open_questions)
数据流模型：每个 Block 从 ExecutionContext 读取输入变量，执行后写回同一 Context。下游 Block 通过变量名引用上游输出——形成数据管道。apply_action 默认 debug=true（dryRun 不落库），需人工审批后才生产写回。

3.3评测与治理 安全护栏

这是 AIP 最独特的部分——Palantir 的核心理念：AI 的写操作不直接落库，先生成提案（Draft），经人工审批后才写回。这确保了 AI 出错不污染生产数据。

Evals 门控 质量门槛

用途：Agent 质量评测与发布门控，决定 Agent 能否升级到 L4 全自动化。

什么时候用：Agent 上线前或升级 L4 前，跑评测集验证质量是否达标。

指标说明
总体通过率当前 87%，L4 门槛 ≥92% → 未达标，不能 L4
派单准确性94% ✅
工具调用合规91% ✅
幻觉率78% ❌ 未达标
延迟 p953.2s ⚠️ 警告
L4 门控条件：Evals ≥92% 且 Draft 审批通过 → 两项都满足才能发布为无人值守 Agent。
Draft 审批台 人在回路

用途：Human-in-the-Loop 审批工作台，处理 Agent 产生的写操作提案。

核心理念：物理隔离。Agent 的写操作不直接写入生产本体，而是先生成 Draft 进入物理隔离的 Draft Dataset，经人工审批后才落库。Agent 即使出错也不会污染生产数据。

三栏布局：

栏目内容
左栏 · 任务列表待审批 Draft 任务（如"纯度异常 ↔ 设备振动 · 知识回填"，置信度 0.93）
中栏 · 任务详情提案类型（InsightBackfill / Action / 工具调用）+ 变更表格（新建/关联/更新 × 对象 × 字段）+ 影响面卡片
右栏 · 审批历史时间线：提案创建 → 请求审查 → Comment → Awaiting approval

审批操作：

  • 查看决策链：跳转 Decision Lineage，查看 Agent 为什么做出此提案
  • 驳回：附理由退回，Agent 可学习修正
  • 批准并写入：将 Draft 变更正式写入生产本体
决策谱系 可追溯

用途：单次 Agent 决策的完整因果链追踪——从输入到输出的每一步都可审计。

什么时候用：排查 Agent 为什么做出某个决策、回溯错误原因、审计合规性时。

6 段链路（按 Trace ID 查询）：

① 输入 用户消息 + Selection 上下文 ↓ ② 检索 Wiki Tool 调用，命中 SOP v2.3 ↓ ③ 推理 模型 gpt-4o-mini 生成方案 ↓ ④ 熔断事件 L4 自动化熔断触发，降级为 L2 ↓ ⑤ 输出 建议派单方案 → 进入 Draft ↓ ⑥ 回填 Insight Backfill（知识回填）
可观测性 运行监控

用途：Agent 运行时的全链路监控。

什么时候用：运维人员监控 Agent 健康状态、排查性能瓶颈、定位失败节点时。

两个视图：

  • Workflow Canvas：工作流画布，节点执行状态可视化（成功绿/失败红/进行中蓝）
  • Trace Timeline：追踪时间线，每步耗时可视化条，点击查看详细输入输出和错误日志
成熟度楼梯 L1→L4

用途：展示 Agent 从临时分析到全自动化的 4 个成熟度等级，以及升级需要什么条件。

L1
临时分析 无自主
AIP Threads，拖文档即问即答，只读不写。沙箱环境，无门控要求。
L2
任务 Agent 人机协作
Chatbot Studio + Prompt + 工具 + Ontology/Wiki。写操作须 HITL 确认。配置完整即可。
L3
Agentic 应用 自主执行
工作台/OSDK 嵌入，Agent 组件化，变量绑定，可自主完成多步任务。门控：L2 验证通过。
L4
自动化 Agent 全自动
发布为 Function/Automate，无人值守写回。门控：Eval ≥92% + Draft 审批通过。失败率 >5% 自动熔断降级回 L3。

L2 模型路由 策略层

用途：根据任务类型、数据敏感度、成本预算，将请求路由到最合适的模型。

什么时候用：优化成本（便宜任务用小模型）、保障合规（PII 不出域）、配置高可用回退时。

路由规则示例策略
摘要/分类本地 vLLM 小模 70% + Azure gpt-4o-mini 30%，禁公网
业务问答 + WikiAzure gpt-4o 100%
含 PII 字段本地 vLLM 100%，强制不出域
Provider 不可用熔断降级 → gpt-4o-mini（回退链）
熔断器状态机：Closed（正常）→ 错误率 >10% 或 p99 >3000ms → Open（熔断） → 等待 30s → Half-Open（半开探测） → 3 次探测成功 → Closed。
L3 模型目录 目录层

用途：模型发现与注册入口。

目录 vs 已注册的区别：「目录」是平台支持的所有模型清单（可发现，但未授权使用）；「已注册」是配置了配额、已暴露给 AIP 智能体可选的模型。

工作流：供应商配置（L1）→ 路由策略（L2）→ 目录浏览 → 注册模型（L3）→ AIP 可选。
