### 2.2 7 大模块分层定位

| 层级 | 模块 | 定位 | 一句话描述 |
| --- | --- | --- | --- |
| 用户界面层 | AIP Analyst | 面向业务用户的分析工具 | 自然语言查数据、生成图表 |
| 用户界面层 | AIP Assist / Chatbot Studio | 对话式 AI 应用 | 配置和运行聊天机器人 |
| 编排构建层 | AIP Logic | 核心构建引擎 | 无代码构建 LLM 函数 |
| 质量保障层 | AIP Evals | 质量安检门 | 评测集 + 门控上线 |
| 可观测性层 | AIP Observability | 全程监控 | 链路追踪 / 指标 / 告警 |
| 模型基础设施层 | Model Catalog + Capacity | 模型供应 | 模型登记 / 容量 / 生命周期 |
| 数据处理层 | Document Intelligence | 文档加工 | 非结构化文档→结构化数据 |

### 2.3 各模块详细关系

#### 2.3.1 Model Catalog（模型目录）—— 基础设施层

**位置**：最底层，是所有 AIP 功能的模型供应方。

**与其他模块的关系**：
- 为 **AIP Logic** 的 Use LLM Block 提供可选模型
- 为 **Chatbot Studio** 提供可选的底层 LLM
- 为 **AIP Evals** 提供跨模型对比的数据源
- **容量管理**（Capacity Management）是 Model Catalog 的配套，控制模型的使用配额和速率限制

**一句话**：没有 Model Catalog，其他所有用到 LLM 的模块都无法工作。

#### 2.3.2 AIP Logic（逻辑编排）—— 核心构建层

**位置**：中间层，是 AIP 的"发动机"。

**与其他模块的关系**：
- **向上**：被 **Chatbot Studio**、**AIP Analyst** 调用 —— 这些上层应用把 Logic 当"函数"来用
- **向下**：调用 **Model Catalog** 里的模型，调用 **Document Intelligence** 处理文档
- **质量**：发布前必须过 **AIP Evals** 门控
- **运维**：运行时被 **AIP Observability** 监控和追踪

**一句话**：Logic 是 AIP 的"函数工厂"，所有复杂的 LLM 编排逻辑都在这里构建，然后被上层应用复用。

#### 2.3.3 Chatbot Studio（聊天机器人工作室）—— 应用封装层

**位置**：用户层，面向业务人员配置对话机器人。

**与其他模块的关系**：
- **依赖 Logic**：Chatbot 的工具调用、RAG 检索背后，很多是用 Logic 函数实现的
- **依赖 Model Catalog**：选择底层 LLM
- **依赖 Evals**：L4 级别的 Agent 必须通过 Evals 门禁才能上线
- **被 Assist 调用**：AIP Assist 平台助手里可以选择不同的 Chatbot 模式

**一句话**：Chatbot Studio 把 Logic + 模型 + RAG 打包成一个"对话应用"，让非技术人员也能配置。

#### 2.3.4 AIP Evals（评测门控）—— 质量保障层

**位置**：横向贯穿，是"安检站"。

**与其他模块的关系**：
- **评测 Logic**：每个 Logic 函数发布前，跑评测集，测通过率
- **评测 Chatbot**：Chatbot 上线前，跑对话评测
- **门控作用**：未达标 → 禁止发布为生产 Function / 禁止挂 Automate / 禁止升级 L4
- **用 Model Catalog**：跨模型对比评测（比如 GPT-4 vs Claude vs 自研模型）

**一句话**：Evals 是 AIP 的"质量安检门"，所有逻辑和机器人上线前都要从这里过一遍。

#### 2.3.5 AIP Observability（可观测性）—— 运维监控层

**位置**：横向贯穿，是"监控摄像头"。

**与其他模块的关系**：
- **监控 Logic 执行**：每个 Logic 运行的耗时、token 用量、成功率都被记录
- **监控 Chatbot**：对话的每一轮都有 trace
- **监控 Model Catalog**：模型的使用率、配额消耗
- **链路追踪**：从用户提问 → Logic 执行 → 工具调用 → 模型调用 → 结果返回，全链路可追踪
- **告警**：失败率高、延迟高、成本超预算时告警

**一句话**：Observability 是 AIP 的"眼睛"，所有模块运行时发生了什么，它都能看到。

#### 2.3.6 AIP Analyst（分析助手）—— 用户应用层

**位置**：最上层，直接面向终端用户。

**与其他模块的关系**：
- **依赖 Logic**：复杂的数据分析逻辑（比如聚类、趋势预测）背后调用 Logic 函数
- **依赖 Ontology**：直接在本体对象上做自然语言查询
- **依赖 Model Catalog**：选择分析用的 LLM
- **被 Observability 监控**：用户的每一次分析查询都被追踪

**一句话**：Analyst 是给业务分析师用的"自然语言数据分析工具"，把 AIP 的能力直接暴露给最终用户。

#### 2.3.7 Document Intelligence（文档智能）—— 数据处理层

**位置**：数据输入层，是"文档加工厂"。

**与其他模块的关系**：
- **为 Logic 提供输入**：Logic 可以调用 Document Intelligence 来解析 PDF、提取表格
- **为 Chatbot RAG 提供源**：Chatbot 的知识库来源，可以是经过 Document Intelligence 处理后的文档
- **为 Analyst 提供数据**：Analyst 可以查询文档中提取的结构化数据
- **在 Pipeline 里运行**：Document Intelligence 通常作为 Pipeline Builder 的一个节点，批量处理文档

**一句话**：Document Intelligence 把非结构化文档（PDF/Word/图片）变成结构化数据，喂给其他 AIP 模块用。

#### 2.3.8 Agent 工具配置链路 —— 实际落地架构

**位置**：横跨用户界面层与编排构建层，是 AIP 决策引擎中连接 LLM 推理层和平台执行层的关键配置枢纽。

**背景**：在 Foundry 原始架构中，Agent（智能体）不是独立模块，而是 **Chatbot Studio + AIP Logic + AIP Assist** 三者交叉产生的运行实体。一个 Agent = Prompt（提示词）+ Tools（工具箱）+ Context（Ontology/Wiki 上下文）+ Model（模型路由）+ Safety（Evals 门控/HITL 策略）。

**7 种工具类型的调用方向与安全约束**：

| 工具类型 | 说明 | 调用目标 | 安全策略 |
|---------|------|---------|---------|
| **Action（动作）** | 写回动作（如派单维修） | → 本体 Action 引擎 | 3 种执行策略：① 自动提交 ② 弹表单 HITL 确认 ③ 仅生成 Draft 到提案台 |
| **Object Query（对象查询）** | 查询本体对象属性（如 Device.status），含 Wiki 结构化字段（wiki.risk_level 等） | → 本体对象存储（只读） | 可限定属性子集；Wiki 字段作为属性子集的一部分读取，无需独立工具 |
| **Function（函数）** | 调用函数或已发布的 AIP Logic | → Function 引擎 / Logic 画布 | 类型安全核；可挂已发布 Logic |
| **Update App Var（应用变量）** | 更新 Workshop 应用状态 | → Workshop 应用状态 | 默认 Draft 可提案 |
| **Command（命令）** | 命令类工具 | → 系统命令执行器 | L4 级别需 Evals 绿灯 |
| **Request Clarification（澄清）** | 信息不足时向用户提问 | → 对话 UI 暂停 + chips | 不涉及写操作，安全等级最高 |
| **Capability（智能体接入）** | 如短视频 Job，平台代调 Facade | → Capability Adapter → MediaSet | 产物状态写回须经 Action（CAP-03）；禁沙箱扛 GPU |

**核心安全设计原则**：

> **LLM 只「请求」工具；平台以调用用户权限代调（A-08）。写路径默认可提案。**

这意味着：
1. LLM 本身**不直接执行**任何写操作，只发出"我想用这个工具"的请求
2. 真正执行的是**平台层**，携带用户权限、经过安全策略检查后代为调用
3. 写路径默认 **Draft（提案台）**，不一定立即生效
4. L4 级别 Agent 必须通过 **Evals 门控** 才能上线（见 2.3.4）
5. Capability 产物状态写回必须经过 **Action**（CAP-03 约束），不能绕过
6. **Wiki 字段不是独立工具**——它是本体对象的"注释层"，Agent 通过 Object Query 的属性子集（如 `wiki.risk_level`、`wiki.specification`）直接读取，不需要独立的 Wiki Field Tool

**谁使用这套配置链路**：

| 角色 | 用途 |
|------|------|
| **平台管理员** | 为每个 Agent 配置可用工具集、执行策略、HITL 规则 |
| **AIP 开发者** | 调试 Agent 能力边界，验证工具组合是否覆盖业务场景 |
| **安全治理人员** | 审查写路径权限、哪些操作需要人工确认（HITL 策略） |
| **Agent 运行时的 LLM** | 配置完成后，LLM 在对话中根据用户意图从已启用工具中选择发起调用请求 |

**与 Foundry 官方架构的对应关系**：

| AOS 实现 | Foundry 原始概念 | 说明 |
|----------|-----------------|------|
| agents.html | Chatbot Studio | 每个 Agent = 一个 Chatbot 实例 |
| aip-assist.html | AIP Assist | Assist 实例也可视为特殊 Agent |
| aip-analyst.html | AIP Analyst | Analyst 实例也可视为分析型 Agent |
| aip-tools.html | （Chatbot Studio 内嵌的工具配置） | Foundry 把工具配置嵌在 Studio 内，AOS 独立为页面 |
| 7 种工具类型 | Chatbot 工具绑定 + Action + Function | AOS 将 Foundry 分散的工具类型统一为 7 种分类；Wiki 字段不独立为工具，通过 Object Query 属性子集读取 |

**一句话**：Agent 工具配置链路是 AIP 决策引擎的"武器库管理员"——定义每个 Agent 能用什么工具、怎么用、安全策略是什么，是连接 LLM 推理层（只读+请求）和平台执行层（代调+写回）的关键配置枢纽。

### 2.4 数据流动路径

```
Document Intelligence → Logic（编排） → Evals（质检） → Chatbot / Analyst（应用）
                            ↑                    ↑
                    Model Catalog      Observability
                    （提供模型）        （全程监控）
```

**核心逻辑**：
1. **Model Catalog** 提供模型弹药
2. **Document Intelligence** 处理文档数据

## 三、核心能力差距对照

### 2.1 AIP Logic（无代码 LLM 函数构建器）

**官方能力**（`AIP/aip-logic/`）：
- 8 种 Block 类型：Input / Create Variable / Get Object Property / Use LLM / Transform / Apply Action / Conditionals / Execute
- 三栏 UI：左（块链）· 中（调试器）· 右（运行面板）
- 调试器：展 CoT · 工具调用 · 提议编辑预览（不真写）
- ProposeEdits：逻辑提议编辑，支持字段级合并
- Logic 状态管理：草稿 / 已发布 / 已废弃
- 版本管理：逻辑版本历史 / 回滚
- Automate 集成：从 Logic 创建自动化

| 项 | 官方 | 当前状态 | 差距说明 |
| --- | --- | --- | --- |
| 三栏 UI | ✅ | ✅ | 已有 LogicCanvasPage |
| 8 Block 类型 | ✅ | ✅ | 已有完整实现(#199) |
| 调试器 | ✅ | ✅ | 已有 DebugSession |
| **ProposeEdits** | ✅ | ✅ | 无提议编辑预览 |
| **Logic 状态管理** | ✅ | ✅ | 无草稿/发布/废弃状态 |

**差距结论**：核心 UI 和 Block 类型已完成；ProposeEdits、状态管理、Wiki 字段、LangGraph 运行时为关键缺口。

## 五、结论

当前 AOS AIP 决策引擎的核心骨架（Logic 编排、Evals 门控、Agent 基础）已具备，但与 Foundry AIP 官方能力相比，仍有以下核心差距：

1. **生产安全缺口**：Evals 门控、L4 熔断、权限感知
2. **核心功能缺口**：ProposeEdits、LangGraph 运行时、Wiki 字段
3. **可观测性缺口**：链路追踪、告警、仪表盘
4. **新模块缺口**：AIP Analyst、Document Intelligence

建议按优先级分阶段推进，优先保障生产安全和核心功能。
