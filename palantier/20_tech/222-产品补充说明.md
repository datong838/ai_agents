## 2. 12 种 Widget 组件类型

Foundry Workshop 的 Widget 是**插件化的**——新的 Widget 类型通过组件市场（Marketplace）注册到平台，画布编辑器自动发现并列出。以下是平台内置的 12 种核心组件类型：

### 2.1 组件清单

| # | 组件类型 | 中文名 | 用途 | 典型配置 |
|---|---------|--------|------|---------|
| 1 | **Table** | 表格 | 展示对象列表/数据集，支持排序、筛选、分页、行选中 | 绑定 ObjectSet，配置列、行操作(Action) |
| 2 | **Chart** | 图表 | 可视化图表（折线/柱状/饼图/散点等） | 绑定数据集或聚合查询 |
| 3 | **Form** | 表单 | 用户输入表单（创建/编辑对象） | 绑定 Action 入参，字段映射 |
| 4 | **Object Set View** | 对象集视图 | 浏览和筛选本体对象集合 | 绑定 ObjectType，筛选条件 |
| 5 | **Navigation Bar** | 导航栏 | 顶部/侧边导航菜单 | 链接配置（页面跳转/外部链接） |
| 6 | **Hero / Markdown** | 图文区块 | 富文本/Markdown 展示区域 | 静态内容或绑定变量 |
| 7 | **Container** | 容器 | 布局容器（水平/垂直/卡片） | 子 Widget 嵌套 |
| 8 | **Map** | 地图 | 地理可视化（标记/热力图/边界） | 绑定地理坐标字段 |
| 9 | **Timeline** | 时间轴 | 事件时间线展示 | 绑定时序数据 |
| 10 | **Button / Action** | 按钮组 | 触发动作/事件的按钮 | 绑定 Event → Action/Function |
| 11 | **IFrame** | 内嵌框架 | 嵌入外部页面 | URL 配置 |
| 12 | **Custom Widget** | 自定义组件 | 用户通过代码自定义的 React 组件 | 代码仓库中的 .tsx 组件 |

### 2.2 组件的插件化扩展

```
                    ┌─────────────────────┐
                    │   Widget Registry   │  ← 组件注册表
                    │   (组件注册表)       │
                    └─────────┬───────────┘
                              │
           ┌──────────────────┼──────────────────┐
           │                  │                  │
    ┌──────▼──────┐   ┌──────▼──────┐   ┌──────▼──────┐
    │ 内置组件     │   │ 市场组件     │   │ 自定义组件   │
    │ (12 种内置)  │   │ (Marketplace │   │ (代码仓库    │
    │              │   │  下载安装)   │   │  .tsx 文件)  │
    └─────────────┘   └─────────────┘   └─────────────┘
```

**新增组件的途径**：
1. **市场安装**：从 Foundry Marketplace 浏览并安装社区/官方组件包
2. **代码开发**：在代码仓库中编写 React/TypeScript 组件，通过 Widget SDK 注册
3. **平台内置**：AOS 平台版本升级时新增的内置组件

## 3. Workflow 模式（事件流编排）

### 3.1 Widget 模式 vs Workflow 模式

| 维度 | Widget 模式 | Workflow 模式 |
|------|-----------|--------------|
| **编辑对象** | UI 组件（视觉元素） | 事件流（交互逻辑） |
| **产出** | 页面布局 | 事件 → 动作绑定链 |
| **类比** | 前端页面编辑器 | 低代码工作流编辑器 |

### 3.2 Workflow 编排的内容

Workflow 模式下，开发者编排的是 Widget 之间的**联动关系**：

```
用户操作 (Event)          条件判断          执行动作 (Action)
─────────────────────────────────────────────────────────
表格行 onSelect     ──→  if 严重级=高  ──→  弹出确认表单
按钮 onClick        ──→  (无条件)      ──→  调用 Action 派单
筛选器 onChange     ──→  debounce 300ms ──→ 刷新数据集
页面 onLoad         ──→  (无条件)      ──→  初始化默认筛选
```

这些事件绑定在当前页面通过 **Events Tab**（第 159 行）和 **workshop-events.html**（事件配置面板）进行管理。

### 3.3 workshop-events.html 的角色

事件配置面板独立展示当前页面/Module 的所有事件绑定：

| 字段 | 说明 |
|------|------|
| 触发器 | Widget 上的事件（onSelect / onClick / onChange） |
| 动作 | 写入变量 / 调用 Action / 刷新数据集 |
| 目标变量 | 事件写入的目标变量名 |
| 幂等 | 是否启用 idempotencyKey 防重复提交 |

## 4. Module 接口与嵌套 Loop（workshop-module-interface.html）

### 4.1 Module 的概念

Module 是**可复用的页面片段**——一组 Widget 组合在一起，定义输入/输出接口，可以在多个页面中嵌入。

### 4.2 接口契约

```
┌─────────────────────────────────┐
│  Module：维修 Inbox             │
│  ┌─────────────────────────┐    │
│  │ input.selection         │ ← 调用方传入选中的工单列表
│  │ input.filterStatus      │ ← 调用方传入筛选状态
│  │ output.selectedId       │ → 向调用方输出选中的工单ID
│  └─────────────────────────┘    │
│                                 │
│  内部 Widget 组合：              │
│  [表格] [筛选器] [详情侧栏]      │
└─────────────────────────────────┘
```

### 4.3 嵌套 Loop

Module 可以通过 Loop 嵌套渲染——父 Module 遍历数据集，每行渲染一个子 Module：

```
父 Module：风险告警管理
  └── Loop 遍历 alertList
       ├── 子 Loop · 工单列表行   ← 每行绑定 row 变量
       │   └── 子 Module · 详情侧栏  ← row.workOrder 绑定到 input
       └── 子 Loop · 工单列表行
```

## 7. Agent 创建向导（agents.html）

### 7.1 背景：Agent 生命周期断裂

在之前的分析中，我们发现 `agents.html` 只有 Agent **编辑器**（提示词 / 工具箱 / 试运行 / 发布），没有 Agent **创建入口**。左侧列表的「+」按钮之前无实际行为，用户无法通过向导创建新的智能体。

**断裂点**：

```
❌ 之前：  创建（无入口）→ 编辑器 → 发布
✅ 现在：  + 新建 → 向导(4步) → Draft Agent → 编辑器 → 试运行 → Evals → 发布
```

### 7.2 创建向导设计（4 步）

点击左侧列表头部的「+」按钮，弹出全屏模态向导弹窗：

```
┌─────────────────────────────────────────────────────────────────────┐
│  新建智能体                                              [×]          │
├─────────────────────────────────────────────────────────────────────┤
│  ● 基础信息  ──  ○ 能力配置  ──  ○ 安全等级  ──  ○ 确认创建      │
│  (已完成)        (未到达)        (未到达)        (未到达)            │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  [当前步骤的表单内容]                                               │
│                                                                     │
├─────────────────────────────────────────────────────────────────────┤
│  第 N / 4 步          [取消] [上一步] [下一步] / [创建智能体]      │
└─────────────────────────────────────────────────────────────────────┘
```

### 7.3 四步配置详情

| 步骤 | 名称 | 必填项 | 说明 |
|------|------|--------|------|
| **Step 1** | 基础信息 | 智能体名称、图标(6选1)、业务域(6选1) | 业务域：设备运维 / 电商客服 / 风控分析 / 内容创作 / 知识检索 / 财务报销 |
| **Step 2** | 能力配置 | LLM 模型(3选1+目录)、系统提示词 | 本体上下文(多选 ObjectType)、初始工具集(多选工具类型) |
| **Step 3** | 安全等级 | 成熟度等级(L0-L4 单选) | 护栏配置：禁止臆造字段 / Token 上限 / 速率限制 / 自动入 Draft |
| **Step 4** | 确认创建 | — | 汇总预览 + 创建后待办清单 |

### 7.4 安全等级与成熟度楼梯的衔接

创建向导的 Step 3 安全等级直接对应 `aip-maturity.html` 成熟度楼梯：

| 等级 | 名称 | 写回权限 | 使用场景 |
|------|------|---------|---------|
| L0 | 只读问答 | 无 | 知识检索型（如文档问答 Agent） |
| L1 | Draft 暂存 | 写入 Draft 审批台 | 低风险数据录入 |
| **L2** | **HITL 人机协同** | **弹窗确认后执行** | **推荐默认，适合大多数业务** |
| L3 | Capability 委托 | 委托其他 Agent 执行 | 复杂编排 |
| L4 | 无人值守写回 | 全自动 | **高风险，须 Evals 全绿** |

### 7.5 创建后流程

```
向导完成
  ↓
新 Agent 出现在左侧列表（Draft 状态）
  ↓
进入编辑器（提示词 / 工具箱 / 试运行 / 发布）
  ↓
试运行验证 → Evals 门控测试 → 成熟度升级 → 发布到 Workshop
```

## 8. 外部智能体插件接入方案

### 8.1 背景：问题定义

当前 `aip-capabilities.html` 视觉稿展示了 4 种已接入的 Capability（短视频生成、直播稿引擎、电商数字人、教育数字人）和 4 种可接入类型（Media Job / Script Engine / Avatar Session / HTTP Adapter），但**缺少具体如何接入一个外部 Agent 的配置流程和字段样例**。

实际场景中，用户拥有大量外部 Agent 资源（如 awesome-llm-apps 中的 140+ 开源 Agent），需要把它们接入 AOS 平台作为 Capability（智能体插件），供内部 Agent 通过 Capability 工具调用。

### 8.2 外部 Agent 生态分析（awesome-llm-apps 为例）

`awesome-llm-apps` 仓库（125k+ Star）包含 140+ 开源 Agent，覆盖 10 大类别：

|---|------|------|-----------|---------|

| 2 | Starter AI Agents | 16 | ai_travel_agent, ai_data_analysis_agent | 单文件 Streamlit，API Key 即跑 |
| 3 | Advanced AI Agents | 52 | ai_fraud_investigation, ai_deep_research | 生产级，含工具/记忆/多步推理 |
| 4 | Always-on Agents | 2 | release_radar, hn_briefing | 后台常驻，定时推送 |
| 5 | Voice AI Agents | 4 | insurance_claim_live, voice_rag | 语音进语音出 |
| 6 | MCP AI Agents | 6 | browser_mcp, github_mcp | 基于 Model Context Protocol |

### 8.3 五种 Adapter 接入路径

根据外部 Agent 的运行时特征，设计 5 种 Adapter 接入路径：

```
                              ┌──────────────────────────────────────────┐
                              │        AOS Capability Gateway            │
                              │     (Facade + Vault + Action 盖章)        │
                              └──────────────┬───────────────────────────┘
                                               │
            ┌──────────────┬──────────────┬────┴─────────┬──────────────┬──────────────┐
            │              │              │              │              │              │
     ┌──────▼──────┐ ┌─────▼──────┐ ┌─────▼──────┐ ┌─────▼──────┐ ┌─────▼──────┐
     │ A-Type      │ │ B-Type     │ │ C-Type     │ │ D-Type     │ │ E-Type     │
     │ HTTP API    │ │ Process    │ │ MCP        │ │ Docker     │ │ Session    │
     │ Adapter     │ │ Wrapper    │ │ Bridge     │ │ Container  │ │ Gateway    │
     └─────────────┘ └────────────┘ └────────────┘ └────────────┘ └────────────┘
     已有 HTTP      Streamlit/     MCP Server     Docker 镜像     语音/数字人/
     端点的 Agent   Flask 单文件    注册的 Agent   打包的 Agent    实时会话 Agent
```

| Adapter 类型 | 适用 Agent 形态 | 部署方式 | 典型来源 |
|-------------|---------------|---------|---------|
| **A-Type · HTTP API** | 已有 REST/GQL 端点 | 外部服务 URL | SaaS API、自建服务 |
| **B-Type · Process Wrapper** | Streamlit/Flask 单文件 | AOS 沙箱内 fork 子进程 | awesome-llm-apps 大多数 Starter Agent |
| **C-Type · MCP Bridge** | MCP Server 注册的 Agent | MCP 协议桥接 | awesome-llm-apps MCP AI Agents |
| **D-Type · Docker Container** | Docker 镜像打包 | AOS K8s 编排拉起 | 需独立运行环境的 Agent |
| **E-Type · Session Gateway** | 语音/数字人实时会话 | WebSocket 长连接 | Voice AI Agents、Avatar Session |

#### 8.3.1 Adapter 选用决策矩阵（详细）

> **核心原则**：先看 Agent 的运行形态，再选 Adapter。仓库扫描会自动推荐，但用户必须理解差异才能正确判断。

| 判断维度 | HTTP API | Process Wrapper | MCP Bridge | Docker Container | Session Gateway |
|---------|----------|----------------|------------|-----------------|----------------|
| **Agent 代码形态** | 已部署的 Web 服务 | Python/Node 单脚本 | 实现 MCP 协议的 Server | 有 Dockerfile 的完整应用 | 音视频流式应用 |
| **平台怎么调用** | 发 HTTP 请求 → 收 JSON | fork 子进程 → stdin/stdout JSON-RPC | MCP JSON-RPC（stdio/SSE） | K8s Pod 拉起 → HTTP/Grpc | WebSocket 长连接 |
| **启动延迟** | **毫秒级**（远程服务已就绪） | **秒级**（进程 fork <2s） | **秒级**（MCP 握手 <1s） | **慢**（冷启动 10-30s） | **长连接**（首次连接数秒） |
| **资源开销** | 极低（只消耗网络） | 低（一个子进程 ~100MB） | 低（同 Process） | **高**（独立 Pod + 镜像） | **高**（TURN 服务器 + 流媒体编解码） |
| **隔离级别** | 天然隔离（远程） | AOS 沙箱（cgroups+seccomp） | AOS 沙箱 | **最强**（K8s Pod 完全隔离） | 会话级隔离 |
| **Capability Level** | C0/C1/C2 均可 | C0 sync 为主 | C0/C1 | C1 Job 为主 | C2 Session（必须） |
| **选错了的后果** | ✗ 选了 Process → 在沙箱内跑不起来（没有代码可 fork） | ✗ 选了 HTTP API → Agent 没有暴露端口 | ✗ 选了 Process → 无法发现工具列表（非 MCP 协议） | ✗ 选了 Process → 缺少系统依赖崩溃 | ✗ 选了其他 → 无法处理流式音视频 |

**快速决策路径**：

```
Agent 已有 HTTP 接口？
├─ 是 → HTTP API（最轻量，无需部署代码）
└─ 否 → 是 Python/Node 脚本？
   ├─ 是 → Process Wrapper（默认推荐，沙箱内执行）
   └─ 否 → 实现了 MCP 协议？
      ├─ 是 → MCP Bridge（标准化工具发现）
      └─ 否 → 需要 Docker 特殊环境？
         ├─ 是 → Docker Container（K8s Pod 拉起）
         └─ 否 → 有音视频流？
            ├─ 是 → Session Gateway（WebSocket 长连接）
            └─ 否 → 检查 Agent 是否可改造为 Process Wrapper
```

**自动推荐规则**（仓库扫描引擎实现）：

| 扫描信号 | 推荐 Adapter | 置信度 |
|---------|-------------|--------|
| 检测到 `requirements.txt` + `*.py` 入口 | Process Wrapper | 高 |
| 检测到 `FastAPI` / `Flask` / `Streamlit` | Process Wrapper | 高 |
| 检测到 `Dockerfile` / `docker-compose.yml` | Docker Container | 中（也可能用 Process） |
| 检测到 `mcp` / `@modelcontextprotocol` 依赖 | MCP Bridge | 高 |
| 检测到 `aiohttp` / `websocket` + 音频处理库 | Session Gateway | 中 |
| 仓库 URL 是已知 SaaS API 的文档页 | HTTP API | 低（需用户确认） |

### 8.4 Capability Manifest 标准契约

每个外部 Agent 接入时，必须填写（或由平台自动生成）一份 Manifest，作为 Capability 的元数据契约：

```yaml

apiVersion: aos/v1
kind: Capability
metadata:
  name: "ai-fraud-investigation"          # 唯一标识
  displayName: "欺诈调查 Agent"            # 展示名
  description: "交叉比对公开记录，标记可疑设施"
  version: "1.0.0"
  category: "风控分析"                     # 业务域分类
  source:                                  # 来源信息
    type: "github"                         # github / local / market / custom
    repo: "awesome-llm-apps"
    path: "advanced_ai_agents/single_agent_apps/ai_fraud_investigation_agent"
    license: "Apache-2.0"

spec:
  adapterType: "B-Process"                 # A-HTTP / B-Process / C-MCP / D-Docker / E-Session

  # ── 运行时配置 ──
  runtime:
    framework: "Agno"                      # Agno / ADK / OpenAI-SDK / LangGraph / raw
    entryPoint: "agent.py"                 # 入口文件（B/D-Type）
    healthCheck: "/health"                 # 健康检查端点（A/E-Type）
    timeout: 60                            # 超时秒数（sync 模式）
    memory: "512Mi"                        # 内存限制
    cpu: "0.5"                             # CPU 限制

  # ── 模型配置 ──
  model:
    provider: "openai"                     # openai / gemini / claude / local-ollama

  # ── 工具/能力暴露 ──

      description: "执行欺诈调查"
      inputSchema:                         # JSON Schema 入参
        type: "object"

          facility_name: { type: "string" }

      outputSchema:                        # JSON Schema 出参

          risk_score: { type: "number" }
          red_flags: { type: "array" }

  # ── 安全护栏 ──
  security:
    capabilityLevel: "C1"                  # C0 sync / C1 job / C2 session
    writeBack: false                       # 是否写回本体

  writeBack:
    enabled: true
    objectType: "FraudReport"              # 写入的本体对象
```

### 8.5 外部 Agent 导入向导设计（5 步）

在 `aip-capabilities.html` 页面的「可接入类型」区域，新增「**从外部导入**」入口，弹出 5 步导入向导：

```
┌─────────────────────────────────────────────────────────────────────┐
│  导入外部智能体                                          [×]          │
├─────────────────────────────────────────────────────────────────────┤
│  ● 选择来源  ──  ○ 分析适配  ──  ○ 配置 Manifest  ──  ○ 安全 ── ○ 确认 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  [当前步骤内容]                                                     │
│                                                                     │
├─────────────────────────────────────────────────────────────────────┤
│  第 N / 5 步             [取消] [上一步] [下一步] / [完成导入]      │
└─────────────────────────────────────────────────────────────────────┘
```

#### Step 1：选择来源

| 来源类型 | 说明 | 字段 |
|---------|------|------|
| **GitHub 仓库** | 从 awesome-llm-apps 或任意 GitHub 仓库导入 | repo URL + 子目录路径 + 分支 |
| **本地代码** | 从 AOS 代码库中已有的 Agent 代码导入 | 代码库路径选择器 |
| **市场安装** | 从 AOS Capability Marketplace 安装 | 搜索 + 一键安装 |
| **HTTP 端点** | 直接填写已部署的 Agent 服务 URL | Base URL + Auth 配置 |
| **MCP Server** | 注册已有的 MCP Server | MCP Endpoint + Server Name |

**样例（GitHub 导入）**：

```
来源类型： ◉ GitHub 仓库   ○ 本地代码   ○ 市场安装   ○ HTTP   ○ MCP

Agent路径：advanced_ai_agents/single_agent_apps/ai_fraud_investigation_agent
分支：     main

[自动扫描] → 检测到：Python · Agno 框架 · requirements.txt · agent.py 入口
                     推荐 Adapter：B-Type (Process Wrapper)
```

#### Step 2：分析适配

平台自动扫描 Agent 代码/仓库结构，识别并匹配 Adapter 类型：

| 扫描项 | 检测内容 | 影响 |
|--------|---------|------|
| **框架识别** | Agno / ADK / OpenAI SDK / LangGraph / raw | 决定运行时 wrapper |
| **入口检测** | `agent.py` / `app.py` / `main.py` / Streamlit | 决定启动命令 |
| **依赖分析** | `requirements.txt` / `pyproject.toml` / `package.json` | 决定沙箱构建 |
| **模型依赖** | OpenAI / Gemini / Claude / Ollama | 决定密钥配置项 |
| **工具依赖** | Firecrawl / SerpAPI / DuckDuckGo / Qdrant | 决定外部服务密钥 |
| **运行模式** | sync / job / session | 决定 Adapter 子类型 |

**用户可在此步骤调整**：修改推荐 Adapter 类型、修正入口文件、添加环境变量。

#### Step 3：配置 Manifest

平台基于 Step 2 的扫描结果，**预填** Manifest 模板，用户校验修改：

| 配置区 | 字段 | 说明 |
|--------|------|------|
| **基础信息** | 名称 / 显示名 / 描述 / 版本 / 业务域分类 | 必填 |
| **运行时** | 框架 / 入口 / 超时 / 内存 / CPU | 自动填充可调 |
| **模型** | Provider / Model / API Key(Vault ref) | 从环境变量自动检测 |
| **能力声明** | capability name / kind(sync·job·session) / input-output Schema | 核心配置 |
| **外部密钥** | SerpAPI Key / Firecrawl Key 等第三方密钥 | 全部走 Vault ref |
| **产物路由** | 写入哪个 Object Type / MediaSet | 对接本体 |

#### Step 4：安全等级与网络白名单

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| **Capability Level** | C0 sync / C1 job / C2 session | C0 |
| **网络白名单** | 允许 Agent 访问的外部域名列表 | 仅 LLM API 域名 |
| **速率限制** | 次/分钟上限 | 30 |
| **Token 预算** | tokens/会话上限 | 10,000 |
| **写回权限** | 是否允许写本体对象 | false |
| **HITL 审批** | 写回是否强制人工审批 | true |
| **沙箱隔离** | 是否在独立容器/进程中运行 | true |

#### Step 5：确认导入

汇总预览 + 连通性测试 + 导入执行：

```
✅ 代码已克隆到 AOS 沙箱
✅ 依赖已安装（requirements.txt · 23 个包）

✅ 连通性测试通过（investigate() → risk_score: 0.72）

```

### 8.9 Adapter 实现技术参考

## 9. 模型接入的三层栈式架构（已注册模型 / 模型路由 / 模型供应商）

> **背景**：控制面板「AIP 设置」页面有 3 个 Tab（AIP 设置 / 模型启用 / **已注册模型**），侧边栏「模型管理」下又有 3 个独立菜单（**模型目录 / 模型供应商 / 模型路由**）。需要澄清这 5 处的关系。

### 9.1 三层栈式架构图

### 9.2 三个菜单/页面的关系定位

| 位置 | 层级 | 关注对象 | 关键问题 | 谁来用 |
|------|------|---------|---------|--------|
| **AIP 设置 > 已注册模型** | 顶层 (L3) | 逻辑模型 + 用户配额 | "AIP 智能体能用什么？给每个用户限多少？" | 平台管理员 / 模型管理员 |

### 9.2.1 三层职责（用截图中的 GPT 5.2 举例）

> 截图来自「AIP 设置 → 已注册模型」页面，模型名称 GPT 5.2（`gpt-5.2`），以下字段逐项映射到三层职责：

| 层级 | 关注问题 | 截图中 GPT 5.2 的字段体现 | 典型值 |
|------|---------|--------------------------|--------|

| 截图字段 | 归属层 | 说明 |

| TPM 限速 `10,000` | **L3** | 按用户/按租户的 Tokens Per Minute 配额 |
| RPM 限速 `5,000` | **L3** | 按用户/按租户的 Requests Per Minute 配额 |
| 注册实例限制 | **L3** | 并发实例上限（防滥用） |
| 支持的端点 `Responses / Chat` | **L3** | 声明此模型支持哪些 API 调用模式 |

**核心洞察**：截图里 GPT 5.2 的「提供商=OpenAI」「后端类型=Direct OpenAI」看起来像是在这个页面配置的，但实际上它只是 **L2 路由信息的只读映射**。真正的 API Key 和连接配置在 L1 模型供应商页面，这个页面看不到也不会编辑。

### 9.3 三者是否冲突？是否独立？

**结论：三者不是冲突，也不是完全独立，而是「栈式分层 + 下层为上层服务」的关系。**

1. **不是冲突**：截图里 GPT 5.2 的「提供商=OpenAI」「后端类型=Direct OpenAI」是 L3 在引用 L2 路由时**预填的展示信息**——L3 选中哪个路由，自然能看到这个路由最终落到哪个供应商。它是一个**只读透出**，而非重复配置。

2. **不是完全独立**：L3 必须依赖 L2 才能工作；L2 必须依赖 L1 才能工作。下层不存在，上层无意义。

3. **下层为上层服务**：
   - 删 L1 供应商 → L2 引用此供应商的路由失效 → L3 中挂载这些路由的模型标记为「不可用」
   - 改 L2 路由权重 → L3 不需改动，但实际调用效果立即变化（流量重新分布）
   - 改 L3 用户限速 → 不影响 L2/L1，仅约束前端智能体的调用配额

## 10. 活知识 Wiki 的 Slate 编辑器架构

> **背景**：大同打开 `ontology-wiki.html` 后对「中间这块深色 Slate 编辑器是不是 Wiki？为什么是这个样子？」产生疑问。需要区分「数据层 Wiki」与「页面层 Wiki」两个不同概念。

### 10.1 两个完全不同的 "Wiki"

之前我们讨论的「Wiki 是数据层」指的是 **本体对象的注解字段**（specification / risk_level / remark），通过 Object Query 工具读取，是「数据」。

而 `ontology-wiki.html` 描述的是 **页面层 Wiki**——一个**可拖拽组装的活文档页**，类似 Foundry 的 Documentation Workshop + Slate 编辑器。两者的关系：

| 维度 | 数据层 Wiki | 页面层 Wiki |
|------|-------------|------------|
| **位置** | Ontology Object 的字段（specification 等） | 独立的 Wiki 页面资源 |
| **形态** | 字符串字段 + Wiki 标记语法 | 树状结构（Widget 嵌套） |
| **创建者** | 本体管理员在对象编辑器填入 | 业务人员/分析师用 Slate 编辑器组装 |
| **渲染** | 由 Object Query 工具读取，文本展示 | 整页呈现，带布局、图表、Object Set |
| **版本** | 跟随 Object 版本 | 独立版本（Page 1 v9 这种） |
| **关联** | 通过属性名引用其他字段 | 通过 Widget 引用 Object Set / Function / Event |

| Tab | 含义 | 可插入什么 Widget |

### 10.4 为什么 Wiki 设计成这样？（设计哲学）

1. **数据驱动文档**：Wiki 不是静态文本，而是**活文档**——Widget 实时从 Ontology 拉取最新数据。新增一个对象实例，Wiki 页自动反映。

2. **零代码可视化**：分析师不需要写 SQL 就能拼装页面，对象集筛选条件直接用表单构建（截图中的 `Recovered is true` 就是 WHERE 子句）。

3. **资源可发现性**：通过 9 个 Tab 把所有 Ontology 资源暴露给业务人员，每个资源都可一键插入页面。

4. **分层嵌套**：Widget 可嵌套（`w_nav_bar > w_widget36 > w_widget...`），支持复杂布局。

5. **版本化与分支**：`Page 1 v9` + 顶部的 `Save to branch` 按钮（与 Git 分支同源），支持 Wiki 内容的版本回滚和分支实验。

### 10.7 与 AIP 决策引擎的关系

Wiki 页面**不是** AIP 智能体直接调用的工具。但 Wiki 页面中的 Widget 引用了：
- **Object Set Widget** → 关联到 Object Query 工具
- **Function Widget** → 关联到 Function 工具
- **Event Widget** → 关联到事件触发

AIP 智能体在工具箱里看到的 "Object Query" 工具，其底层数据源可以来自 Wiki 页中预先定义好的 Object Set 配置。这就是为什么之前我们把 Wiki 字段工具从 Agent 工具箱移除（它是数据注解），但 Object Set 工具保留（它是 Object Query 工具的实例）。

## 13. 新建应用创建入口（Workshop Module 创建向导）

> **背景**：用户问"如果我要做第 5 个应用，怎么起一个？是新建 Module 吗？"——当前 `workshop.html` 应用列表页只有「最近使用」和「全部应用」的卡片，**没有「+ 新建应用」入口**，与 Agent 生命周期断裂（有编辑器无创建向导）属于同一类产品缺陷。

### 13.1 核心概念澄清

| 概念 | 说明 | Foundry 对应 |
|------|------|-------------|
| **Module（模块）** | = 一个完整的 Workshop 应用，有独立的 layout、variables、events、functions | Workshop Module |
| **Layout（布局）** | Module 内的「页面」，一个 Module 可以有多个 Layout（首页/详情/设置等） | Workshop Layout |
| **Widget（微件）** | 每个 Layout 里的 UI 组件（表格/图表/表单等） | Workshop Widget |

**新建第 5 个应用 = 新建一个 Module。** 创建后自动进入画布编辑器。

### 13.2 与 4 个构建工具的关系

4 个构建工具不是创建入口，而是 Module 创建后编辑过程中使用的 4 类编辑能力：

| 构建工具 | 在 Module 生命周期中的角色 |
|---------|-------------------------|
| **画布编辑** | 创建后**默认进入**的页面，拖拽 Widget 组装界面 |
| **模块接口** | Module 创建后**逐步配置**，定义 Parameters / Functions / Events 接口 |
| **事件配置** | Module 创建后**逐步配置**，绑定 Widget 交互事件 |
| **发布入口** | Module 编辑完成后**最后一步**，版本化 + 发布到 Apollo |

### 13.3 创建流程设计：独立页面（非弹窗）

> **设计决策**：Module 创建使用**独立页面**（`workshop-create.html`），而非 Agent 那样的弹窗向导。
> 原因：Step 2 数据绑定需要 ObjectType 浏览器（对象类型树+属性列表+过滤条件），Step 3 模板选择需要布局预览区——弹窗塞不下这些复杂组件。

**页面结构**：左侧步骤导航（随时跳转任意步骤）+ 右侧配置区 + 底部操作栏

```
应用列表（workshop.html）
  └─ 点击「+ 新建 Module」按钮（应用列表右上角）
      └─ 跳转到独立创建页面 workshop-create.html
          ┌──────────┬─────────────────────────────────┐
          │ 步骤导航  │ 配置区                           │
          │          │                                  │
          │ ● 1 基本信息 │ [表单 / 对象树 / 模板预览 / 汇总] │
          │ ○ 2 数据绑定 │                                  │
          │ ○ 3 模板选择 │                                  │
          │ ○ 4 确认创建 │                                  │
          ├──────────┴─────────────────────────────────┤
```

### 17.3 插件引入向导（4 步）

| **Step 4** | 连通测试 | 5 项测试（DNS/TLS/鉴权/健康检查/Schema冒烟）逐项通过状态 + 注册汇总 + 完成后引导挂载 |

### 17.4 外部 Agent 导入向导（5 步）

| 步骤 | 名称 | 要素 |
|------|------|------|
| **Step 1** | 选择来源 | GitHub 仓库 / 本地代码库 / 市场安装（卡片选择），含 repo URL + 子目录 + 分支输入 |

| **Step 3** | 配置 Manifest | 基于扫描预填的 Manifest（能力名称/角色描述/能力标签/Capability Level/超时/内存），右侧 YAML 预览 |
| **Step 4** | 安全与网络 | 沙箱隔离级别（严格/标准/无）、CPU上限、速率限制、护栏、网络白名单、环境变量注入、安全提示 |
| **Step 5** | 确认导入 | 5 项测试（代码拉取/依赖安装/沙箱启动/LLM路由/冒烟测试）+ 导入汇总 + 完成后引导挂载 |

### 17.5 两个向导的差异对比

| 维度 | 插件引入 | 外部 Agent 导入 |
|------|---------|---------------|
| **前提** | 已有 HTTP 端点 | 有代码/仓库 |
| **Adapter** | A-Type HTTP（内置） | B/C/D/E-Type（需选择） |
| **代码扫描** | 无（端点即契约） | 有（自动识别框架/入口/依赖） |
| **沙箱** | 不需要（外部服务） | 必须（cgroups+seccomp） |
| **密钥管理** | Vault ref（KMS） | 环境变量注入 |
| **产物** | Capability 注册 | Capability + Agent 源码缓存 |

#### 路径 3：编排协议引入（Agent Handoff）

**关联页面**：`aip-logic.html`（AIP 逻辑画布）

claudeskills 的 `ORCHESTRATION.md` 定义了 4 种多 Agent 协调模式：

| 模式 | 描述 | AOS 对应场景 |
|------|------|-------------|
| **Solo Sprint** | 单 Agent 按阶段切换技能 | AIP Logic 单分支流，Agent 在不同节点加载不同 Tool |
| **Domain Deep-Dive** | 单 Agent 叠加多个 Skill | Agent 挂载多个 Tool，在运行时动态选择 |
| **Multi-Agent Handoff** | Agent 互相审查输出 | AIP Logic 多分支汇聚 → 审查节点 |
| **Skill Chain** | 顺序技能流水线 | Pipeline Builder 的 DAG 链式执行 |

**最有价值的是 Handoff 模式**——定义了 Agent 间上下文传递的标准格式：

```
Handoff Context = {
  decision_summary: "已完成的决策摘要",
  artifacts: ["产出文件列表"],
  open_questions: ["遗留问题"],
  next_agent: "下一个 Agent 的角色"
}
```

目前 AOS 的 AIP 逻辑画布支持多分支汇聚，但没有定义汇聚节点上 Agent 之间的「上下文交接」格式。引入此 Handoff 协议后：
- 汇聚节点自动生成上下文摘要
- 下游 Agent 接收上游的决策摘要、产物列表和遗留问题
- 在画布上可视化「交接点」（类似 Foundry Pipeline 的数据传递节点）

#### 路径 4：安全审计器引入

**关联页面**：`aip-agent-import.html` Step5 确认导入

`engineering/skill-security-auditor/scripts/skill_security_auditor.py` 是一个零依赖安全扫描器，覆盖 6 类风险：

| 风险类别 | 扫描内容 | AOS 对应 |
|---------|---------|---------|
| 命令注入 | `os.system()` / `subprocess()` 无沙箱调用 | 外部 Agent 代码安全门控 |
| 代码执行 | `exec()` / `eval()` / `__import__()` | 动态代码执行审计 |
| 数据泄露 | 硬编码密钥、明文 Token、日志输出敏感信息 | 密钥泄露检测 |
| Prompt 注入 | 用户输入拼入系统提示词 | Agent 对话安全 |
| 依赖供应链 | `requirements.txt` 中的已知恶意包 | 依赖审计 |
| 权限提升 | 文件系统越权、网络端口越权 | 沙箱配置验证 |

**落地建议**：在 `aip-agent-import.html` 的 Step5（确认导入）中，在现有「代码拉取 → 依赖安装 → 沙箱启动 → LLM 路由 → 冒烟测试」流程后，**新增第 6 步「安全扫描」**：
- 运行 `skill_security_auditor.py` 对导入的 Agent 代码进行全量扫描

## 20. AIP Logic 逻辑画布功能架构详解

> **背景**：大同审阅 `aip-logic.html` 视觉稿后发现，画布上大量按钮和区域缺少交互响应，更关键的是没有文档系统说明每个功能点的参数模型、数据流向和后端实现。本章作为「前后端打通、后端实现补齐」的作战指南。

### 20.1 页面整体布局

```
┌─────────────────────────────────────────────────────────┐
│ Header: 面包屑 | 搜索 | [取消] [保存到分支]               │
├─────────────────────────────────────────────────────────┤
│ Tab 栏: [编辑] [自动化] [运行历史]                        │
├─────────────────────────────────────────────────────────┤
│ Block 工具栏: [+创建变量] [+获取属性] [+使用LLM]          │
│   [+数据变换] [+应用动作] [+写回] [+执行] [+分支]         │
├──────────────┬──────────────┬───────────────────────────┤
│  ① 编排区     │  ② 配置区     │  ③ 预览区                 │
│  (col-5)     │  (col-4)     │  (col-3)                  │
│              │              │                           │
│  块链 DAG    │ 选中块的属性  │ 单次运行结果               │
│  纵向排列     │ 参数表单     │ 输入/输出/Token/延迟        │
│  ↓ 箭头连接   │              │                           │
│              │              │ [重新运行]                 │
└──────────────┴──────────────┴───────────────────────────┘
```

**三栏职责分工**：

| 栏 | 作用 | 数据来源 | 交互行为 |
|----|------|---------|---------|
| ① 编排区 | 展示 Block 块链的 DAG 结构（纵向从上到下） | `LogicGraph.nodes` + `edges` | 点击块→选中并联动配置区；拖拽调整顺序 |
| ② 配置区 | 编辑选中 Block 的参数（动态表单） | 选中 Block 的 `config` 字段 | 表单输入实时同步到 Block config JSON |
| ③ 预览区 | 单次试运行的结果回显 | `POST /v1/logic/run` 返回值 | 点击「重新运行」触发 dry-run |

### 20.2 三大顶部 Tab

#### Tab 1: 编辑（默认）

画布编辑模式。用户在此拖拽 Block、配置参数、构建块链。

- **后端对应**：`LogicGraph` 模型（`nodes: List[Block]` + `edges: List[GraphEdge]`）
- **保存动作**：顶部「保存到分支」→ `PUT /api/aip/logic-state`（状态管理）+ `POST /api/aip/logic-version`（版本快照）
- **状态流转**：草稿(draft) → 发布(published) → 废弃(deprecated)

#### Tab 2: 自动化

将当前 Logic 绑定到调度或事件触发器，实现无人值守运行。

- **后端对应**：`AutomateEngine`（`aip_extras.py`），通过 `logic_id` 关联当前 Logic
- **触发器类型**（5 种）：

| 触发器 | `event_type` | 说明 | 典型场景 |
|--------|-------------|------|---------|
| 对象变更 | `object_changed` | 本体对象 CRUD 事件 | 新订单创建 → 自动风险分诊 |
| 定时调度 | `schedule` | Cron 表达式 | 每 15 分钟扫描 pending 订单 |
| 人工触发 | `manual` | 用户手动点击 | 运维批量操作 |
| Webhook | `webhook` | 外部 HTTP 回调 | 支付回调 → 自动发货 |
| 阈值告警 | `threshold` | 指标超限触发 | 退款率 > 20% → 风控升级 |

- **条件评估器**：`_eval_condition()` 支持 `eq/ne/gt/lt/ge/le` 操作符
- **冷却机制**：`cooldown_seconds` 防止短时间内重复触发
- **API 端点**：`POST /v1/aip/automate/triggers`（创建触发器）→ `POST /v1/aip/automate/triggers/{id}/fire`（手动触发）

#### Tab 3: 运行历史

查看历史执行记录，包括状态、耗时、输入和输出。

- **后端对应**：`AutomateRun` 记录表（`aip_extras.py`）+ `TraceLogicEngine`（链路追踪）
- **API 端点**：`GET /v1/aip/automate/runs` + `GET /api/aip/trace-logic`
- **展示字段**：运行编号、状态（成功/失败/超时）、耗时、输入摘要、风险结果
- **可下钻**：点击单条记录 → 查看完整 trace（每步 Block 的输入/输出/Token/延迟）

### 20.3 八种 Block 类型详解

> **命名对齐**：后端 `logic_engine.py` 的 `BlockKind` 枚举是权威定义（8 种）。前端工具栏的「+写回」和「+分支」在实际引擎中分别由 `apply_action` 和 `LogicGraph.edges.condition` 实现。

#### Block 1: 创建变量 (`create_variable`)

| 维度 | 说明 |
|------|------|
| **工具栏按钮** | `+ 创建变量` |
| **功能** | 在执行上下文中定义新变量，支持 DSL 表达式 |
| **参数 (config)** | `name: str`（变量名）、`expr: str`（DSL 表达式）、`type: str`（类型标注） |
| **输入** | 无（从 `ExecutionContext.variables` 读取已有变量） |
| **输出** | 写入 `ctx.variables[name]` |
| **后端实现** | `_blk_create_variable()` → 调用 `FunctionEngine.evaluate(expr, ctx.variables)` |
| **DSL 示例** | `total = order.amount * order.tax_rate`、`is_vip = customer.tier == "gold"` |
| **引擎依赖** | `function_engine.py`（`evaluate()` + `parse()`） |

#### Block 2: 获取属性 (`get_property`)

| 维度 | 说明 |
|------|------|
| **工具栏按钮** | `+ 获取属性` |
| **功能** | 从本体对象（Object/Action Set）中读取字段值，注入上下文 |
| **参数 (config)** | `object_ref: str`（对象引用，如 `order`）、`properties: List[str]`（字段名列表）、`wiki_ref: str`（可选，关联 Wiki 文档） |
| **输入** | `ctx.variables[object_ref]`（必须是 Object 引用） |
| **输出** | 逐个写入 `ctx.variables[property_name]` |
| **后端实现** | `_blk_get_property()` → 调用 `Ontology API` 获取对象属性 |
| **Wiki 字段支持** | 221plan M1-3 已实现：属性可以是普通字段(text/number/bool)或 Wiki 字段(rich text) |
| **安全提示** | 读取操作，无写回风险 |

#### Block 3: 使用 LLM (`use_llm`)

| 维度 | 说明 |
|------|------|
| **工具栏按钮** | `+ 使用 LLM`（黄色高亮，核心 AI Block） |
| **功能** | 调用大语言模型，按 System Prompt + 变量上下文生成结构化输出 |
| **参数 (config)** | `prompt: str`（系统提示词）、`model: str`（模型选择，如「私有-中」）、`temperature: float`（默认 0.3）、`max_tokens: int`（默认 512）、`output_schema: dict`（JSON Schema，约束输出格式）、`input_vars: List[str]`（注入 Prompt 的变量名） |
| **输入** | `ctx.variables` 中指定的 `input_vars` |
| **输出** | `BlockResult.output`（结构化 JSON）+ `BlockResult.cot`（Chain-of-Thought 链路） |
| **后端实现** | `_blk_use_llm()` → 调用 `LLMGateway.chat(messages, model, temperature, max_tokens)` |
| **模型路由** | `model` 参数经过 L2 路由层 → 映射到 L1 供应商的实际 API（参见第 9 章三层架构） |
| **Token 追踪** | 每次调用记录 input_tokens / output_tokens / latency → 写入 trace |
| **调试模式** | `POST /v1/logic/debug` 时，CoT 链路完整保留，可在配置区查看推理过程 |
| **引擎依赖** | `llm_gateway.py`（`chat()` 方法） |

#### Block 4: 数据变换 (`transform`)

| 维度 | 说明 |
|------|------|
| **工具栏按钮** | `+ 数据变换` |
| **功能** | 对变量进行过滤、映射、聚合等数据变换操作（Pipeline Builder 风格） |
| **参数 (config)** | `expr: str`（变换 DSL）、`input_var: str`（输入变量名）、`output_var: str`（输出变量名） |
| **输入** | `ctx.variables[input_var]`（通常是 Object Set 或 List） |
| **输出** | 写入 `ctx.variables[output_var]` |
| **后端实现** | `_blk_transform()` → 调用 `FunctionEngine.evaluate()`（与 create_variable 共用引擎，但处理的是集合操作） |
| **DSL 示例** | `filter(order_list, lambda o: o.amount > 500)`、`map(items, lambda x: x.price * 0.9)`、`sort(orders, key="created_at", desc=True)` |
| **与 Pipeline Builder 的关系** | Pipeline Builder 是数据工程师的 DAG 编排工具；AIP Logic 的 transform Block 是面向 AI 决策的轻量变换 |

#### Block 5: 应用动作 (`apply_action`)

| 维度 | 说明 |
|------|------|
| **工具栏按钮** | `+ 应用动作` |
| **功能** | 对本体对象执行 Action（如修改状态、创建工单、发送通知） |
| **参数 (config)** | `action_type: str`（Action 类型名）、`target_object: str`（目标对象引用）、`params: dict`（Action 参数）、`write_back: bool`（是否直接写回本体，默认 false） |
| **输入** | `ctx.variables[target_object]` |
| **输出** | `BlockResult.proposed_edits`（提议编辑列表） |
| **后端实现** | `_blk_apply_action()` → `writeback.py` 执行四步写回链路 |
| **写回四步链路** | ① 收集 ProposedEdits → ② 合并策略（last_write_wins / field_level / manual_review）→ ③ 审批门控（L4 须 Evals 全绿）→ ④ Ontology API 写回 |
| **安全等级衔接** | 参见第 7.5 节 Agent 安全等级表：L1(只读) / L2(草稿) / L3(审阅后写回) / L4(无人值守写回) |
| **Debug 模式行为** | `write_back=false` 时，ProposedEdits 只收集不落库 → 用户在配置区预览差异 → 确认后才合并写回 |
| **引擎依赖** | `writeback.py`（WriteBack 类） |

#### Block 6: 写回 (`write_back`)

> **重要说明**：前端工具栏的「+写回」按钮，在引擎层**不是一个独立的 BlockKind**。它实际是 `apply_action` Block 在 `write_back=true` 时的行为。

| 维度 | 说明 |
|------|------|
| **工具栏按钮** | `+ 写回`（绿色高亮，表示写操作） |
| **实际语义** | 创建一个 `apply_action` Block，预配置 `write_back=true` + 默认合并策略 |
| **与「应用动作」的区别** | 「应用动作」侧重描述要做什么（如 `escalate_to_supervisor`）；「写回」侧重确认结果要落库（如 `update_status → shipped`） |
| **视觉区分** | 绿色边框 = 已确认会写回本体；灰色边框 = 仅提议，需人工审批 |
| **后端实现** | 同 `apply_action`，`writeback.py` 处理 |
| **MergeStrategy** | `last_write_wins`（后写覆盖）/ `field_level`（字段级合并）/ `manual_review`（人工合并） |

#### Block 7: 执行 (`execute`)

| 维度 | 说明 |
|------|------|
| **工具栏按钮** | `+ 执行` |
| **功能** | 调用子流程、执行语义搜索、或运行注册的外部工具 |
| **参数 (config)** | `exec_type: str`（`sub_logic` / `semantic_search` / `tool`）、`target: str`（目标 ID）、`params: dict` |
| **输入** | `ctx.variables` 中的参数 |
| **输出** | 写入 `ctx.variables["execute_result"]` |
| **后端实现** | `_blk_execute()` |
| **子流程** | `exec_type="sub_logic"` → 加载另一个 LogicGraph 递归执行 |
| **语义搜索** | `exec_type="semantic_search"` → 向量库查询（Pinecone/Milvus），返回 Top-K 结果 |
| **工具调用** | `exec_type="tool"` → `ToolRegistry.get_tool(target).invoke(params)` |
| **引擎依赖** | `tool_registry.py`（`ToolDef` + `invoke()`）+ 向量数据库 |

#### Block 8: 分支 (`branch`)

> **重要说明**：前端工具栏的「+分支」按钮，在引擎层**不是一个独立的 BlockKind**。分支通过 `LogicGraph` 的 `GraphEdge.condition` 实现。

| 维度 | 说明 |
|------|------|
| **工具栏按钮** | `+ 分支` |
| **实际语义** | 在当前块链中插入一个条件路由点，生成 2+ 条 outgoing edges，每条 edge 有一个 condition DSL |
| **实现方式** | `LogicGraph.edges` 中增加多条 edge，`condition` 字段为 DSL 表达式 |
| **条件 DSL 示例** | `risk_level IN [high, critical]`、`order.amount > 500 AND order.is_cross_border` |
| **引擎执行** | `run_graph()` 方法（第 113-153 行）：遍历 edges → 评估 condition → 只执行匹配的分支 |
| **汇聚** | 多条分支执行完后汇聚到同一个下游 Block → 需要汇聚节点（见 20.4） |
| **防死循环** | `max_steps` 参数限制图遍历最大步数（默认 100） |

### 20.4 汇聚节点 / Handoff 上下文

> **视觉稿位置**：编排区底部的「块 #5 · 汇聚 · Handoff 上下文」节点（靛蓝色边框 + 三格信息卡）

**汇聚节点的存在意义**：当分支执行完毕后，多个执行路径的结果需要合并到一个统一的上下文，传递给下游 Agent 或人工审批台。

**三段式上下文结构**（来源：第 18.3 节 claudeskills Handoff 协议）：

| 段 | 字段名 | 内容 | 示例 |
|----|--------|------|------|
| 决策摘要 | `decision_summary` | LLM 或规则引擎给出的最终判定结论 | "订单 ORD-0721-002 风险等级判定为**高**，触发升级审批" |
| 产物列表 | `artifacts` | 本轮执行产生的所有输出文件/数据 | `risk_assessment.json` / `order_snapshot.diff` / `escalation_ticket.log` |
| 开放问题 | `open_questions` | 遗留的待确认项，需要人工或下游 Agent 处理 | "客户历史退款率 22% 是否需要人工复核？" |

**传递目标 (`handoff_to`)**：

| 目标类型 | 说明 | 目标对象 |
|---------|------|---------|
| 风控审批 Agent | 传递给另一个 AIP Logic 进行二次决策 | `risk-approver` Agent |
| 人工审批台 | 推送到 Draft Inbox，等待人工确认 | `aip-draft-inbox.html` |
| 外部 Webhook | 推送到外部系统的 HTTP 回调 | 业务方 API |

**附加选项**：
- `include_trace`：是否包含完整运行 trace（Token 用量/延迟/中间结果）
- `auto_summarize`：是否自动用 LLM 生成交接摘要

**后端实现**：汇聚节点不是引擎的独立 BlockKind，而是 `LogicGraph` 中多条 edge 指向同一节点时的隐含行为。`run_graph()` 在汇聚点等待所有入边执行完毕后合并 `ExecutionContext`。

### 20.5 编排区块链语义

视觉稿中的编排区展示的是一个**纵向块链**（不是自由画布 DAG）。每个 Block 用箭头 `↓` 连接，表示数据流向。

**当前样例（风险分诊编排）的块链结构**：

```
块 #1: Input (order : Object · Order)
  ↓
块 #2: Get Property (order.status / amount / currency / region)
  ↓
块 #3: Use LLM · 风险评估 (model=私有-中, temp=0.3, max=512)
  ↓ ↓ (双路分支)
  ├─ 块 #4A: Branch · 高风险 → Apply Action: escalate_to_supervisor
  └─ 块 #4B: Branch · 低风险 → Write Back: update_status → shipped
  ↓ ↓ 汇聚
块 #5: Merge · Handoff 上下文 (decision + artifacts + open_questions)
```

**数据流模型**：每个 Block 从 `ExecutionContext` 读取输入变量，执行后将输出写回同一 Context。下游 Block 通过变量名引用上游的输出。

### 20.6 配置区动态表单

配置区（② 栏）根据**选中 Block 的 kind** 动态渲染不同的表单：

| Block Kind | 配置区内容 | 表单控件 |
|------------|-----------|---------|
| `create_variable` | 变量名、DSL 表达式、类型标注 | Input + CodeEditor + Select |
| `get_property` | 对象引用、属性列表、Wiki 引用 | ObjectPicker + MultiSelect |
| `use_llm` | 模型选择、Temperature、Max Tokens、Prompt 编辑器、输出 Schema | Select + Slider + CodeEditor + SchemaEditor |
| `transform` | 输入变量、输出变量、变换 DSL | Select + Select + CodeEditor |
| `apply_action` | Action 类型、目标对象、参数、write_back 开关 | Select + ObjectPicker + JSON + Toggle |
| `execute` | 执行类型、目标 ID、参数 | Select + Select + JSON |
| 分支 (edge) | 条件 DSL | CodeEditor |
| 汇聚节点 | Handoff 三段式表单（如视觉稿所示） | DecisionSummary + Artifacts + OpenQuestions + TargetSelect |

### 20.7 预览区与试运行

预览区（③ 栏）展示单次试运行的结果：

- **触发**：用户点击「重新运行」→ `POST /v1/logic/run`（传入当前 LogicGraph + 输入数据）
- **展示**：
  - 运行编号和时间（如 `#1047 · 16:42`）
  - 输入摘要（如 `ORD-0721-001`）
  - 输出结果（如 `风险: 低`、`原因: 金额适中，稳定客户`）
  - 性能指标（如 `延迟: 1,240ms`、`Token: 入 284 · 出 47`）
- **调试模式**：点击 `POST /v1/logic/debug` → 返回每步 Block 的 CoT 链路和 ProposedEdits → 在配置区展开推理过程

> 本节为「上战场」提供逐文件对照：每个前端功能点对应的引擎文件、路由文件、测试文件。

### 21.3 四个 Tab 详解

#### Tab 1: 函数代码

**用途**：查看和编辑当前函数的源代码。

| 前端元素 | 后端 API | 数据模型 |
|---------|---------|---------|
| 代码编辑器（Monaco/CodeMirror） | `GET /v1/functions-runtime/functions/{fn_id}` | `RuntimeFunction.source`（Python/TS/SQL 源码） |
| 语言标识（Python/TS/SQL） | `RuntimeFunction.language` | `Literal["python", "typescript", "sql"]` |
| 保存 | `POST /v1/functions-runtime/functions` | `RegisterFunctionRequest` |
| TypeScript 类型签名预览 | `GET /v1/functions-runtime/functions/{fn_id}/ts-signature` | `typescript_signature(fn_id) -> str` |
| 代码校验（AST 检查） | `POST /v1/python-functions/validate` | `PythonBuilder.validate_code(code) -> list[str]` |

**后端引擎**：
- Python 函数：`PythonBuilder`（`functions_python_builder.py`）— 沙箱执行，黑名单 import/builtins/dunder
- 统一运行时：`FunctionsRuntime`（`functions_runtime.py`）— 多语言注册表
- 表达式函数：`FunctionComposer`（`function_sandbox.py`）— DSL 表达式组合

**安全约束**：
- 代码大小限制：`MAX_CODE_SIZE = 5000` 字符
- AST 节点限制：`MAX_AST_NODES = 1000`
- 执行超时：`TIMEOUT_SEC = 5.0`（沙箱）/ 可配置（Python Builder）
- 禁止：`import os` / `import subprocess` / `__import__` / `eval` / `exec`

#### Tab 2: 测试运行函数

**用途**：编写测试用例，手动触发函数执行，查看输入/输出/断言结果。

| 前端元素 | 后端 API | 数据模型 |
|---------|---------|---------|
| 测试用例列表 | `GET /functions-dev-tools/tests?function_id={fn_id}` | `FunctionTestCase[]` |

| 运行测试 | `POST /functions-dev-tools/tests/{case_id}/run` | `FunctionsTestDebugEngine.run_test(case_id)` |

| 调试会话（断点） | `POST /functions-dev-tools/debug-sessions` | `FunctionDebugSession`（breakpoints, current_line, variables） |
| 单步执行 | `POST /functions-dev-tools/debug-sessions/{session_id}/step` | `step(session_id) -> FunctionDebugSession` |

**后端引擎**：`FunctionsTestDebugEngine`（`functions_dev_tools.py`，W2-AO #143）

#### Tab 3: 运行历史（当前激活）

**用途**：查看函数的历史执行记录，包括每次运行的耗时、状态、调用链路追踪。

| 前端元素 | 后端 API | 数据模型 |
|---------|---------|---------|
| 运行记录列表 | `GET /tracing-perf-geo-map/tracing/traces?status=completed` | `TraceContext[]` |
| 单次运行详情 | `GET /tracing-perf-geo-map/tracing/traces/{trace_id}` | `TraceContext` |
| 完整 Span 树（火焰图） | `GET /tracing-perf-geo-map/tracing/traces/{trace_id}/tree` | `{spans: TraceSpan[], total_duration_ms, by_service}` |
| 性能 Profile | `GET /functions-dev-tools/profiles?function_id={fn_id}` | `ProfileResult[]`（duration_ms, memory_bytes, cpu_percent, hotspots） |
| Logic 链路追踪 | `GET /api/aip/trace-logic` | `TraceLogicItem[]` |

**后端引擎**：
- 分布式追踪：`DistributedTracingEngine`（`tracing_perf_geo_map.py`，W2-BO #26）— **核心引擎**
- Logic 追踪：`TraceLogicEngine`（`aip_trace_logic.py`）— Logic 执行链路
- 性能分析：`FunctionsTestDebugEngine.profile()` — CPU/内存/热点分析

**Trace 数据模型**：
```python
class TraceContext(BaseModel):
    id: str                     # trace_id
    trace_id: str
    root_span_id: str
    span_count: int             # Span 总数
    service_count: int          # 涉及的服务数
    status: Literal["active", "completed", "error"]
    started_at: datetime
    completed_at: datetime | None

class TraceSpan(BaseModel):
    id: str                     # span_id
    trace_id: str
    parent_span_id: str | None  # 父 Span（构成树）
    operation_name: str         # 如 "sendEmailWithTaskPriority"
    service_name: str           # 如 "function-runtime" / "claude-3.5-haiku"
    start_time: datetime
    end_time: datetime | None
    duration_ms: float
    status: Literal["active", "completed", "error"]
    attributes: dict[str, Any]  # 自定义属性
    events: list[dict]          # 事件列表
```

**火焰图渲染逻辑**：
- 每个 Span 渲染为一条水平条（`.p-trace-bar`）
- 宽度 = `duration_ms / total_duration_ms × 100%`
- 左偏移 = `(span.start_time - trace.start_time) / total_duration × 100%`
- 嵌套层级 = parent_span_id 链深度（缩进 `ml-4` / `ml-6`）
- 颜色编码：
  - 灰色（`p-trace-bar-parent`）= 顶层请求 Span
  - 浅灰（`p-trace-bar-nested`）= 用户代码 / 子操作
  - 蓝色（`p-trace-bar-nested` + `#93c5fd`）= 关联对象查询
  - 青色渐变（`p-trace-bar-ai`）= LLM 调用（Claude/GPT 等）
- AI Span 特殊标记：显示模型名 + Token 数 + 耗时

#### Tab 4: 删除代码函数

**用途**：安全删除函数，含依赖检查和级联清理。

| 前端元素 | 后端 API | 数据模型 |
|---------|---------|---------|
| 依赖检查提示 | `GET /v1/oma/function-types/{name}/usage` | `UsageRecord[]`（被哪些 Logic/Agent/Pipeline 引用） |
| 确认删除 | `DELETE /v1/functions-runtime/functions/{fn_id}` | `FunctionsRuntime.delete(fn_id) -> bool` |
| Python 函数删除 | `DELETE /v1/python-functions/{name}` | `PythonBuilder.delete(name) -> None` |
| 关联清理 | 自动调用 `DELETE /v1/oma/function-types/{name}/code-location` | 移除代码位置记录 |

**删除安全流程**：
1. **依赖检查**：先查询 `get_usage(name)` → 如果有活跃引用，阻止删除并提示引用列表
2. **用户确认**：显示影响范围（N 个 Logic / M 个 Agent 引用此函数）
3. **级联清理**：删除函数本体 + 代码位置记录 + 测试用例 + 性能 Profile
4. **审计记录**：写入 `DecisionRecord`（`decision_audit.py`）记录删除操作

## 22. Pipeline Builder — 管道构建双页面功能架构

> **问题来源**：用户反馈 pipeline-list.html 和 pipeline.html 都展示了链路图，无法区分两者关系——是「加工中 vs 成品」？还是「列表 vs 编辑器」？

### 22.1 两个页面的定位

**不是「加工中 vs 成成品」。两个页面都是成品，关系是「列表导航 → 单条编辑」**：

```
pipeline-list.html (管道构建列表)
│
│  角色：项目总览 / 文件树浏览器
│  类比：IDE 的文件树面板（如 VS Code 左侧文件列表）
│
│  用户在这里做什么：
│    - 浏览当前分支下所有管道和步骤
│    - 按颜色分组筛选（Teal/Green/Pink/New color）
│    - 快速预览某管道的拓扑结构（缩略 SVG）
│    - 点击文件树条目 → 跳转到 pipeline.html 编辑
│
├── 左栏：颜色图例（4 色分类 + 添加颜色）
├── 中栏：缩略画布（SVG 矩形 + 连线，只读不可拖拽）
└── 右栏：Pipeline file tree（当前分支全部步骤列表）
         │
         │  点击任意条目
         ▼
pipeline.html (单管道编辑器)
│
│  角色：单个管道的 DAG 编辑器
│  类比：IDE 的代码编辑器（如 VS Code 中间编辑区）
│
│  用户在这里做什么：
│    - 拖拽变换工具（Filter/Join/Aggregate...）到画布
│    - 配置变换节点参数（关联字段、表达式、输出列）
│    - 预览中间结果（底部数据表格）
│    - 配置输出目标（数据集 / Object Type / 链接类型）
│    - 提议 / 部署管道
│
├── 顶部工具栏：撤销/重做 + 分支 + 已保存/提议/部署 + 编辑/提案/历史三 Tab
├── 左栏（变换工具栏）：10+ 个变换算子 + 添加数据集 + 参数
├── 中栏（DAG 画布）：可拖拽节点 + SVG 连线 + 缩放控制 + 底部预览表
└── 右栏（输出侧栏）：数据集输出 / Object 类型输出 / 链接类型输出 + 详细信息
```

### 22.2 为什么两个页面都有链路图？

| | pipeline-list.html 中栏 | pipeline.html 中栏 |
|---|---|---|
| **用途** | 概览地图（看全貌） | 工作台（编辑细节） |
| **可交互** | ❌ 只读 SVG | ✅ 拖拽节点 / 配置参数 |
| **数据来源** | 当前分支全部管道的拓扑 | 单个管道的 DAG |
| **节点颜色** | 按颜色分组（图例分类） | 按节点类型（数据集=黄 / 变换=蓝 / 输出=绿） |
| **缩放/预览** | ❌ 无 | ✅ 缩放控制 + 底部数据预览表 |

**设计意图**：list 页面是 Foundry Pipeline Builder 的「File Tree 视图」——用户先在文件树中找到要编辑的管道，再进入编辑器。这和 GitHub 的仓库列表 → 单个仓库页面是同一模式。

### 22.3 pipeline-list.html 三栏详解

#### 左栏：颜色图例

| 元素 | 后端对应 | 用途 |
|------|---------|------|
| Teal (3) | `PipelineConfig.color_groups` 中 color=teal 的组 | 标记某类管道步骤 |
| Green (4) | color_groups 中 color=green | 标记另一类步骤 |
| Pink (2) | color_groups 中 color=pink | 标记另一类步骤 |
| New color (5) | color_groups 中自定义颜色 | 用户新增的分类 |
| Add color 按钮 | `update_config(color_groups)` | 新增颜色分组 |

**后端模型**：`PipelineManagementEngine.update_config(config_id, color_groups=...)`

#### 中栏：缩略画布

| 元素 | 后端对应 | 用途 |
|------|---------|------|
| SVG 矩形 + 连线 | `Pipeline.nodes` + `Pipeline.edges` 的拓扑渲染 | 全局预览 |
| 节点文字（如 Join/classification） | `PipelineNode.label` | 步骤名称 |
| 节点颜色 | `PipelineConfig.color_groups` 映射 | 分类标记 |
| 点击节点 | 跳转到 `pipeline.html` | 进入编辑 |

#### 右栏：Pipeline file tree

| 元素 | 后端对应 | 用途 |
|------|---------|------|
| 文件树条目列表 | `PipelineStore.list_all()` 下所有管道的步骤 | 导航 |
| 管道图标（蓝色拓扑/绿色+/紫色棱形） | `PipelineNode.kind`（dataset/transform/llm） | 类型标识 |
| 点击条目 | 跳转 `pipeline.html` | 进入单条编辑 |

**API 调用**：`GET /v1/pipeline-builder` 返回全部管道列表

### 22.4 pipeline.html 详解

#### 顶部工具栏

| 元素 | 后端对应 | 用途 |
|------|---------|------|
| 撤销/重做 | `PipelineEditor.undo()` / `redo()` | 命令式 DAG 编辑（MAX_UNDO=50） |
| 分支切换器 | `PipelineBranchEngine.list_branches()` | 在不同分支上编辑 |
| 已保存 | `PipelineEditor.apply(command)` 成功 | 持久化状态 |
| 提议 | `PipelineLayoutEngine.create_proposal()` | 提交变更提议供审查 |
| 部署 | `PipelineOutputEngine.execute()` | 执行输出写入 |
| 编辑/提案/历史 Tab | `PipelineLayoutEngine.list_proposals()` / `list_history()` | 视图切换 |
| 搭建 ✓ / 检查 5/5 | `Pipeline.validate()` + `DataExpectation.run_all()` | 校验状态 |

#### 左栏：变换工具栏

**10 个核心变换算子**（对应 `TRANSFORM_REGISTRY` 中的 15 个内置算子，HTML 展示前 10 个高频算子）：

| 按钮 | 后端算子 | config 参数 |
|------|---------|-----------|
| Filter | `filter` | `expression`: 筛选表达式 |
| Join | `join` | `right_key`, `left_key`, `how`: inner/left/right |
| Aggregate | `aggregate` | `group_by`, `agg`: count/sum/avg/min/max |
| Explode | `explode` | `column`: 要展开的列表字段 |
| Cast | `cast` | `column`, `to`: string/number/integer/boolean |
| Union | `union` | `right_rows`: 拼接的数据 |
| Sort | `sort` | `by`, `descending`: bool |
| Distinct | `distinct` | `columns`: 去重列 |
| Expression | `expression` | `name`, `formula`: DSL 表达式 |
| Window | `window` | `func`: row_number/rank/lag/lead/running_sum/moving_avg |

**额外 5 个算子**（后端已实现，前端工具栏未展示，可通过"+ 添加"或代码模式使用）：

| 算子 | 功能 |
|------|------|
| Pivot | 行转列（透视表） |
| Unpivot | 列转行（逆透视） |
| Fillna | 空值填充（constant/ffill/bfill/mean/median） |
| Normalize | 归一化（minmax/zscore） |
| String Ops | 字符串操作（upper/lower/trim/replace/substring/extract） |

**其他工具栏元素**：

| 按钮 | 后端对应 | 用途 |
|------|---------|------|
| + 添加数据集 | `PipelineNode(kind="dataset")` | 添加数据源节点 |
| 参数 | `PipelineConfig.parameters` | 定义管道参数 |

#### 中栏：DAG 画布

| 元素 | 后端对应 | 用途 |
|------|---------|------|
| 数据源节点（黄色） | `PipelineNode(kind="dataset")` | 输入数据 |
| 变换节点（蓝色） | `PipelineNode(kind="transform")` | 数据变换 |
| LLM 节点（紫色） | `PipelineNode(kind="llm")` | AI 增强 |
| 输出节点（绿色） | `PipelineNode(kind="output")` | 写入目标 |
| 连线（实线=活跃/虚线=分支） | `PipelineEdge` | 数据流 |
| 缩放控制 | 前端 canvas | 视图缩放 |
| 底部预览表 | `PipelineEditor.preview(inputs)` | 实时预览结果 |

#### 右栏：输出配置侧栏

| 区域 | 后端对应 | 用途 |
|------|---------|------|
| 数据集输出 | `OutputConfig(target_dataset_rid, write_mode, primary_key)` | 输出到数据集 |
| Object 类型输出 | `OutputConfig` → Ontology Object Type | 输出到本体 |
| 链接类型输出 | `OutputConfig` → Ontology Link Type | 创建实体关系 |
| Write Mode | `Literal["append", "snapshot", "upsert", "replace", "update", "delete"]` | 6 种写入模式 |
| 详细信息 | `PipelineConfig` + 协作者 | 元数据 |

### 22.5 三种管道类型

后端 `PipelineTypeEngine` 支持 3 种管道类型（前端 list 页面未区分，但 pipeline 编辑器根据类型展示不同配置）：

| 类型 | 触发方式 | 容错策略 | 适用场景 |
|------|---------|---------|---------|
| **batch** | scheduled | restart/skip/checkpoint_replay | 定时全量处理 |
| **incremental** | on_change | checkpoint_replay | 增量同步（Watermark + Checkpoint） |
| **streaming** | continuous | exactly_once | 实时流处理（Tumbling/Sliding/Session 窗口） |

### 22.10 使用流程（用户视角）

```
1. 用户进入「管道构建」→ 看到 pipeline-list.html
   ├── 左栏按颜色分组查看步骤
   ├── 中栏缩略图了解整体拓扑
   └── 右栏文件树找到要编辑的管道步骤

2. 点击文件树条目 → 跳转到 pipeline.html
   ├── 左栏拖拽变换工具到画布（如 Filter → Join → Expression）
   ├── 选中节点 → 底部预览表查看中间结果
   ├── 配置节点参数（表达式、关联键、聚合维度）
   └── 右栏配置输出目标（数据集 / Object Type / 链接类型）

3. 验证 → 点击「搭建」→ validate() + run_expectations()
   ├── 校验 DAG 无环
   ├── 校验数据期望（主键唯一/行数/空值）
   └── 全部通过 → 显示「搭建 ✓ 检查 5/5」

4. 部署
   ├── 直接部署 → PipelineOutputEngine.execute() 执行输出写入
   └── 或提交提议 → create_proposal() 供团队审查

5. 切换分支
   ├── 在 feat/xxx 分支上编辑
   ├── 完成后 merge_branch() 合并到 main
   └── 或 revert_branch() 回滚
```

### 24.3 左栏：Fallback 链可视化

Fallback 链是**有序列表**，每个节点代表一个模型选项：

| 节点属性 | 说明 |
|---------|------|
| **序号** | 1st / 2nd / 3rd...（Primary → Fallback 1 → Fallback 2） |
| **模型** | 从已注册模型列表中选择 |
| **权重** | 0-100%，同级节点的权重之和无需等于 100%（按比例分配） |
| **角色** | `Primary`（首选）/ `Fallback`（降级备选） |
| **条件** | 可选：`当错误率 > X%` / `当延迟 > Yms` / `当余额不足` 时触发 fallback |

**交互**：
- 拖拽节点可调整顺序（改变 Fallback 优先级）
- 点击节点 → 右栏切换到该节点的详细配置
- 「+ 添加 Fallback 节点」按钮 → 从已注册模型列表选一个

### 24.4 右栏：配置面板（4 个折叠区）

#### 24.4.1 权重分配
- 每个模型一个滑块（0-100%），实时显示百分比
- 权重之和不强制为 100%，按比例分配（如 60+30+10 = 100%，但 6+3+1 也按 6:3:1 分配）
- 权重变更时左栏 Fallback 链节点实时更新百分比显示

#### 24.4.2 熔断阈值
| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| 错误率阈值 | number (0-100%) | 5 | 连续错误率超过此值时熔断该节点 |
| 熔断恢复时间 | number (秒) | 60 | 熔断后等待多少秒再尝试恢复 |
| 最小请求样本 | number | 20 | 至少多少个请求后才计算错误率（避免小样本误判） |
| 熔断动作 | select | `跳到下一 Fallback` | `跳到下一 Fallback` / `返回错误` / `使用缓存` |

#### 24.4.3 超时设置
| 参数 | 默认值 | 说明 |
|------|--------|------|
| 请求超时 | 30s | 单次请求最大等待时间 |
| 重试次数 | 2 | 超时后重试次数（同模型重试） |
| 重试退避 | `exponential` | `fixed`（固定间隔）/ `exponential`（指数退避） |

#### 24.4.4 路由策略
- **加权随机**（默认）：按权重概率分配请求
- **最低延迟优先**：优先调用最近 5 分钟 P99 延迟最低的模型
- **最低成本优先**：优先调用单价最低的模型（可能质量较低）

### 24.5 底部：路由测试面板

用户可输入一个测试 prompt，点击「测试路由」后：
1. 引擎模拟路由决策（不真正调用 LLM）
2. 显示：命中哪个模型（基于当前权重+策略）、预计延迟、预计费用
3. 如果用户想真正调用，点击「实际调用」按钮（消耗 API 额度）

## 26. Workshop 画布三模式：组件 / 工作流 / 预览

### 26.1 设计意图

`workshop-canvas.html` 顶部工具栏左侧有 3 个模式切换按钮，代表 Module 编辑器的**三种工作视角**：

| 模式 | 按钮 | 图标 | 视角定位 |
|------|------|------|---------|

| **工作流** (Workflow) | `data-mode="workflow"` | 十字准星 | 可视化编排 Module 内的事件→条件→动作链 |
| **预览** (Preview) | `data-mode="preview"` | 眼睛 | 隐藏编辑面板，以终端用户视角查看运行态 |

三种模式共享同一个 `p-slate-body` 容器，通过切换左栏 / 画布 / 右栏的内容实现视角转换。

### 27.3 触发器类型（6 种）

| 图标 | 名称 | `trigger_type` 枚举值 | 绑定 Widget | 说明 |
|------|------|----------------------|-------------|------|
| 🕐 | 页面加载 | `on_page_load` | 全局（无需绑定） | 页面首次渲染完成后触发 |
| 🖱 | 行点击 | `on_row_click` | Table / List | 用户点击表格行触发 |
| 📊 | 组件点击 | `on_widget_click` | 任意 Widget | 用户点击组件触发 |
| 🔍 | 筛选变化 | `on_filter_change` | Filter / Search | 筛选条件变化时触发 |
| ⏰ | 定时器 | `on_timer` | 全局（需配置间隔） | 定时触发（cron 或 interval） |
| ⚙ | 自定义 | `custom` | 任意 | 用户自定义事件名 |

### 27.4 动作类型（6 种）

| 图标 | 名称 | `ActionType` 枚举值 | 参数输入框 placeholder | 说明 |
|------|------|-------------------|----------------------|------|
| 📝 | 写入变量 | `update_variable` | `例: selectedOrder = ${row.id}` | 向页面变量写入值 |
| ⚡ | 调用 Action | `call_function` | `例: refreshOrders(force=true)` | 调用后端 Action 函数 |
| 🔄 | 刷新数据集 | `refresh_dataset` | `例: ordersDataset` | 重新拉取数据集 |
| 🔀 | 导航 | `navigate` | `例: /orders/${row.id}/detail` | 跳转到指定页面 |
| 🔲 | 打开模态框 | `open_modal` | `例: orderDetailModal` | 打开指定模态框 |
| 📡 | 发送事件 | `emit_event` | `例: orderSelected { id: ${row.id} }` | 向事件总线发送事件 |

### 27.5 第 3 步预览链结构

```

[动作图标] [动作名称]: [参数]
    ↓
[动作图标] [动作名称]: [参数]  (如果有多个动作)
    ↓
幂等键: [✓ 已启用 / ✗ 未启用]
```

### 27.6 确认后的行为

1. **模态关闭**：点击「✓ 确认添加」后，模态淡出关闭
2. **表格追加**：新事件行以蓝色高亮（`bg-blue-50`）追加到事件表格底部
3. **新增标签**：行首显示「新增」绿色徽章（2 秒后淡出）
4. **Toast 提示**：显示「✅ 事件已添加：onPageLoad → refreshOrders」
5. **字段自动填充**：根据用户在向导中的选择，自动填充表格行的「触发器」「Widget」「动作」「状态」列

#### 按类型变化的字段

| 类型 | 初始值区显示 |

| **Number** | 数字输入 + 最小/最大约束 |
| **Boolean** | true/false 切换 |
| **DateRange** | 开始时间（now-7d 语法）+ 结束时间 |
| **Array** | 数组项类型 + JSON 编辑器 |

- 保存时：关闭弹窗 → 更新对应行的名称/类型/初始值单元格 → 高亮闪烁该行 2 秒 → toast 确认
