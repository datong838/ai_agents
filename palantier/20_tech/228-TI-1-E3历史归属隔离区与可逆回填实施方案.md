## 1. 评审结论先行

TI-1 E3 只解决 TI-1 公共底座中的历史归属和历史断链，不重新设计 TenantScope，不改变 E2 双写语义，不进入 E4～E7。目标是把“未知或断链的历史记录”转换成可审计的三类决策：

1. `ASSIGN`：只有唯一、双向一致的证据才允许归属并回填。
2. `QUARANTINE`：证据缺失、冲突、多租户候选或父子断链的记录只进隔离决策账本，默认不从原表搬走。
3. `NO_ACTION`：已正确归属、系统全局记录或不在本波范围的记录不修改。

**本文评审通过只能解锁 E3-0 只读重基线与 E3-1 账本 DDL 实现；E3-2 dry-run、E3-3 隔离库演练、E3-4 共享非生产回填、E3-5 任何客户/生产操作仍需逐门单独授权。**

## 3. E3 范围与非目标

### 3.1 本波范围

| 资源 | E3 处理 | 不允许的捷径 |
|---|---|---|
| `authz_tuple` | 对租户列为 NULL 的历史 tuple 生成归属决策；只回填唯一双向可证明的记录 | 不按用户当前登录组织、对象前缀、创建时间或“默认组织”单证据猜测 |
| `meta_membership` | 复核组织、工作区和成员审计闭包；输出 ASSIGN/QUARANTINE/NO_ACTION | 不为了过 FK 而伪造 `meta_workspace` 父记录 |
| `twa_ws_member` | 以权威组织/工作区目录与邀请/加入审计闭包取证 | 不将 `project_id` 相同视为同一组织 |
| `twa_audit` | 只根据可验证的 workspace 事件链处理断链 | 不更改审计正文、actor、action 或时间 |
| E1 的 7 个 NOT VALID FK | 输出可否进入 E4 Validate 的精确阻断清单 | E3 不执行 `VALIDATE CONSTRAINT` |

`meta_workspace`、`twa_workspace`、`twa_invite`、`twa_join_request` 只作归属证据源或父级完整性检查；除非后续决策清单逐项证明，不在 E3 默认修改它们。

### 3.2 明确非目标

- 不处理 TI-2～TI-5 的 Module、Object/Graph、Data OS、Connector、AIP 和非 PostgreSQL 资源。
- 不修改 E2 `OFF/SHADOW/ENFORCE` 语义，不把 `shadow/enforce` 设为共享环境默认值。
- 不切换 authz check/list/delete 读路径；这是 E5。
- 不执行 FK Validate/NOT NULL/主键改造；这是 E4/E7。
- 不创建或强制 RLS；这是 E6。
- 不将未知数据默认归给测试组织、栖月汇或当前登录用户。
- 不通过删除历史行、清空表或制造假父记录来让约束变绿。

## 4. 数据分类与归属证据规则

### 4.1 统一决策状态机

```text
DISCOVERED
    ↓ 生成脱敏快照
EVIDENCE_PENDING
    ├─ 唯一双向证据 → ASSIGN_APPROVED
    ├─ 证据不足/多候选 → QUARANTINED
    └─ 无需处理 → NO_ACTION
ASSIGN_APPROVED
    ↓ 独立库演练 + 人工批准
BACKFILLED
    ├─ 对账通过 → VERIFIED
    └─ 对账失败 → ROLLED_BACK
```

禁止跳过 `ASSIGN_APPROVED` 直接进入 `BACKFILLED`。状态只可追加事件，不覆盖历史决策。

### 4.2 `authz_tuple` 双向证据

一条历史 tuple 只在以下条件全部满足时才能 `ASSIGN`：

1. `object_key` 可映射到权威对象/资源目录，且该对象只属于一个 `org_id/project_id`。
2. `user_key` 可映射到权威主体，并能通过成员关系、邀请/加入事件或同期审计证明其在同一 TenantScope 具有合法关系。
3. 对象侧和主体侧结论完全一致，候选 TenantScope 数量等于 1。
4. 证据时间窗覆盖 tuple 可观察的有效期；只有“现在是成员”不足以证明历史归属。
5. 没有标记冲突、撤销、账号合并或跨组织迁移事件。

任一条不满足即 `QUARANTINE`。不允许使用 relation 名、对象 ID 格式或统计多数做单证据归属。

### 4.3 工作区父子断链证据

对 `meta_membership/twa_ws_member/twa_audit` 的断链记录，证据强度从高到低为：

1. 签名且可验证的工作区创建/删除事件、不可变审计或恢复备份。
2. 权威组织目录 + 工作区目录 + 成员/邀请/加入事件的闭包一致性。
3. 其他子表的复合 FK 闭包，且不存在第二 TenantScope 候选。

单独的 `org_id/project_id` 文本、名称相似、主体当前成员身份、时间接近或测试 fixture 都不构成恢复父记录的足够证据。

### 4.4 证据等级

| 等级 | 定义 | 可导致的决策 |
|---|---|---|
| A | 两个以上独立权威源双向一致，无冲突 | 可提交 `ASSIGN_APPROVED` |
| B | 单一权威源或只能一向闭包 | 只能 `QUARANTINE` |
| C | 启发式、名称/ID/时间猜测 | 禁止归属，记录为 `INSUFFICIENT_EVIDENCE` |
| X | 多候选、证据相互冲突或来源不可验证 | `CONFLICT`，失败关闭 |

## 5. 账本与隔离区模型

### 5.1 必须新增的三类不可变记录

| 概念名 | 作用 | 最小字段 |
|---|---|---|
| `tenant_backfill_batch` | 一次 dry-run/演练/执行的封套 | batch id、环境指纹、source snapshot hash、code commit、mode、status、created/approved/completed time |
| `tenant_ownership_decision` | 每条记录的归属决策与证据摘要 | batch id、resource、key fingerprint、decision、evidence grade/hash、candidate count、target scope、before/after hash、reason code |
| `tenant_quarantine_record` | 证据不足/冲突/断链记录的隔离决策 | batch id、resource、key fingerprint、reason code、candidate scope hashes、source snapshot hash、review status |

物理表名在 E3-1 评审时最终冻结；无论实现名称如何，都必须满足强 TenantScope 主键、append-only、无业务修改/删除 Router、状态事件不覆盖的约束。

### 5.2 数据最小化

- 账本不保存 `authz_tuple` 的 user/object/relation 原文，使用与 E2 一致的稳定 key fingerprint。
- 不保存 Token、Secret、成员个人资料、审计正文或业务 payload。
- 证据只保存来源类型、版本/事件 ID 的指纹、查询口径、结果 hash 和候选数。
- 原始证据如果必须保留，只能进入受控并加密的离线审计包，不进应用日志、Git 或普通证据 JSON。

### 5.3 “隔离”的两层语义

1. **逻辑隔离（E3 默认）**：原行不动，记录 `QUARANTINE`，阻断其进入回填、E4 Validate 和新读路径。
2. **物理隔离（高风险子门）**：先完整备份，再将原行逐列复制到受控 quarantine schema/离线存储，校验行数与 hash 后才允许从活跃表移除。

本文评审不授权物理隔离。如断链行最终必须移出才能进入 E4，必须生成逐资源决策清单，由业务负责人与数据负责人双批准。

## 6. 可逆回填算法

### 6.1 Dry-run 先行

Dry-run 只读取一致性快照，产生脱敏决策账本和三类汇总：

```text
totalDiscovered
= assignApproved
+ quarantined
+ noAction
+ blockedByDrift
```

汇总守恒不成立、任一 key fingerprint 重复、任一决策有多个目标 Scope，都必须失败关闭。

### 6.2 真实回填前置条件

- 只处理已批准 batch 中 `ASSIGN_APPROVED` 的精确指纹集合。
- 每行必须仍与 dry-run 的 before hash 一致；发生任何并发变更即停止该 batch。
- `authz_tuple` 只允许 `org_id IS NULL AND project_id IS NULL` 的行进入回填。
- 必须用完整复合键与 before hash 定位，禁止宽范围 `UPDATE ... WHERE org_id IS NULL`。
- 单 batch 小批量事务执行；事务内同时写决策事件和 after hash，不允许“数据已改、ledger 未写”。
- 使用稳定 advisory lock/batch lock，限制 lock timeout 和 statement timeout，不与在线写长时间争锁。
- 运行开关保持 E2 既有值；E3 不通过修改开关规避冲突。

### 6.3 回滚算法

回滚只对某一个已完成 batch 的行执行：

1. 依据 resource + key fingerprint 重新计算定位候选行。
2. 要求当前 after hash 与 ledger 一致，且租户列仍等于本 batch 写入的 Scope。
3. 只把本 batch 从 NULL 写入的租户列恢复为 NULL；禁止覆盖后续合法修改。
4. 任一 after hash 不一致则该行不自动回滚，batch 进入 `ROLLBACK_CONFLICT`，由人工处理。
5. 回滚后重算全量行数、租户聚合、NULL 数、孤儿数和 hash，追加 `ROLLED_BACK/ROLLBACK_CONFLICT` 事件。

不得通过 Alembic downgrade 丢弃 E2/E3 账本来实现数据回滚。

## 7. 备份、恢复与环境硬门

### 7.1 工具硬门

当前本机缺少 `pg_dump/psql`。在安装与 PostgreSQL 服务端主版本匹配的客户端工具并完成恢复演练前：

- 可编写 E3-0/E3-1 的只读工具、DDL 和测试。
- 不得执行 E3-4 共享非生产历史 DML。
- 不得连接客户库或生产库执行 E3。

### 7.2 备份套件

每个待执行环境必须生成：

1. 全库 custom-format 逻辑备份，加密存储并记录 SHA-256。
2. TI-1 受影响表、Alembic 版本、约束和索引的 schema-only 快照。
3. 受影响表的逐表行数、租户聚合、NULL/孤儿数和顺序无关内容 hash。
4. E3 source snapshot、dry-run decision ledger 和待批准 batch manifest。
5. 恢复操作手册、工具版本、操作人/复核人与保留期。

备份不进 Git，证据文档只保存备份 ID、hash、时间、工具版本和恢复结论。

### 7.3 恢复演练退出门

- 备份恢复到新的隔离数据库，不覆盖源库。
- 恢复库 Alembic revision、schema hash、行数、租户聚合、NULL/孤儿数和内容 hash 与源快照一致。
- 在恢复库完整执行 dry-run → 回填 → 对账 → 回滚 → 再对账。
- 回滚后恢复到 source snapshot，差异为 0；隔离决策事件保留且可审计。

## 10. 迁移和执行安全契约

### 10.1 Migration 原则

- E3 migration 必须是 `228ti1e2dual` 之后的唯一新 head。
- Migration `upgrade()` 只创建账本表、索引和约束，禁止包含 `UPDATE/DELETE/INSERT ... SELECT` 历史 DML。
- 账本如果已产生记录，禁止直接 downgrade 丢表；必须先完成审计归档和批准。
- E3 不修改 E1 的 7 个 FK validated 状态，不修改 RLS 状态。

### 10.2 执行身份与职责分离

- `planner`：只读生成 dry-run 和决策候选，无 UPDATE/DELETE 权限。
- `approver`：审批 batch manifest，不能修改 classifier 输出。
- `executor`：只能执行已批准 batch，不能自批。
- `verifier`：独立重算对账与 hash，不能写业务表。

同一主体不得同时充当 approver 和 executor。客户/生产环境需要业务负责人 + 数据负责人双批准。

### 10.3 幂等和并发

- batch id + source snapshot hash + code commit 形成唯一执行身份。
- 同 batch 重放只返回已有结果，不重复更新。
- source snapshot 变化必须创建新 batch，禁止继续使用旧批准。
- 并发 E2 新写不进入已冻结 E3 batch，由新一轮快照处理。

## 11. 测试矩阵

| 测试类 | 必测场景 | 退出标准 |
|---|---|---|
| Schema | 单 head/current、账本强租户键、append-only、E1 FK 仍 NOT VALID、RLS 仍 0 | 全部 GREEN |
| Baseline conservation | E1 冻结快照、当前快照、审计增减三方对账 | 未解释差异为 0 |
| Classifier positive | 对象/主体双向唯一证据 | 只生成一个 ASSIGN |
| Classifier negative | 单证据、多候选、时间不一致、账号迁移、断链 | 全部 QUARANTINE/失败关闭 |
| Cross-tenant | 相同 ID 双租户、主体与对象异租户、跨组织同 project id | 不得产生 ASSIGN |
| Data minimization | tuple 原文、Token、payload、个人资料扫描 | ledger/log/evidence 零泄漏 |
| Apply | 精确指纹、NULL-only、before hash、中途失败 | 原子性且无部分 batch |
| Idempotency | 同 batch 重放、已改行、新 snapshot | 重放零写，漂移失败关闭 |
| Rollback | 正常回滚、after hash 冲突、后续合法变更 | 只撤销本 batch，冲突不覆盖 |
| Restore drill | 全库备份恢复、apply/rollback、五类对账 | 回滚后与 source snapshot 差异 0 |
| Existing behavior | E2 OFF/SHADOW/ENFORCE、authz API、TWA 组织/工作区 | 无 E3 引入回归 |

共享数据库的固定 ID 测试不能用于 E3 回填验证。E3 真库测试必须使用独立数据库/schema、唯一随机租户和可验证清理。

## 12. 对账、证据与可观测性

### 12.1 每个 batch 必须对账

| 维度 | 执行前 | 执行后 | 要求 |
|---|---|---|---|
| 资源总行数 | snapshot | snapshot | 回填时必须不变 |
| NULL 租户行 | N | N - assigned | 变化量等于已批准且成功行 |
| 租户聚合 | before | after | 只增加批准 Scope 的精确数量 |
| 孤儿行 | before | after | 逻辑隔离不伪造下降；物理隔离另行对账 |
| decision 守恒 | discovered | assigned + quarantined + noAction + blocked | 必须相等 |
| 内容 hash | before | after | 只允许批准列发生变化 |

### 12.2 证据产物

- `e3-source-snapshot.json`：环境指纹、revision、表/行/租户/NULL/孤儿聚合和 hash。
- `e3-baseline-reconciliation.json`：E1 冻结值到 E3 source snapshot 的增减解释。
- `e3-decision-summary.json`：每资源 ASSIGN/QUARANTINE/NO_ACTION/BLOCKED 数量，不含原文。
- `e3-restore-drill.json`：备份/恢复 ID 和 hash、工具版本、apply/rollback 对账。
- `e3-execution-evidence.md`：授权边界、commit、batch、验证、风险和下一门。

所有 JSON 必须通过 schema 验证和敏感信息扫描后才可提交。

| 风险 | 严重度 | 缓解/阻断 |

5. 执行 batch 前后总行数守恒；只有批准的租户列变化；ledger 无原文/敏感数据。
6. 不能安全归属的行全部在 quarantine ledger 中；如仍在活跃表，必须明确阻断 E4 而不伪称已清理。
7. E2 开关语义、authz API 和组织/工作区既有功能无回归。

9. 栖月汇 BUSINESS_DATA 仍为 0；未知非 PostgreSQL 资源仍如实保持阻断，不因 E3 误判为全资源空。
10. 证据文档列出未处理风险、实际回滚点和下一门授权；不将 E3 GREEN 写成 E4/E5/E6 GREEN。

如逻辑隔离的历史断链仍保留在活跃表，E3 可以标记“决策与可逆回填 GREEN / E4 BLOCKED”，但不能标记“TI-1 数据完整性 GREEN”。
