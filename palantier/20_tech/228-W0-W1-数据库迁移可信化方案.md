# 228-W0-W1 数据库迁移可信化方案

> 日期：2026-07-31
> Worker：W1 / `aos-platform-w1` / `feature/223-worker-1`
> 基线：`14e6bb2`
> 状态：已合并并通过 Wave 0 最终回归

## 1. 目标

修复 Alembic 骨架导致的导入失败、错误 stamp、异常吞没和生产仍依赖运行时 DDL 等问题，先建立可信的迁移控制面，不借机改业务表语义。

## 2. 现状证据

- `services/aos-api/pyproject.toml` 缺 `alembic`、`sqlalchemy`。
- `aos_api/migrations.py` 未按环境变量分支，版本表检测错误。
- baseline 的 upgrade/downgrade 为空。
- `main.py` 无条件 `run_migrations()` 后再 `init_schema()`。
- 全仓仍有大量运行时 DDL，本波不能无审计地一次性删除。

## 3. 设计

### 3.1 三种显式模式

| 模式 | 用途 | 行为 |
|---|---|---|
| `legacy-bootstrap` | dev/test 兼容 | 允许既有初始化逻辑；记录明确日志 |
| `managed` | 生产/验收 | 全量 schema snapshot 完成前统一 fail-closed；不得 stamp、upgrade 或启动 |
| `disabled` | 特殊只读诊断 | 不迁移；仅在显式配置下允许 |

禁止未配置时静默猜测生产模式。

### 3.2 数据库分类

1. 空库：识别为空库；全量 schema snapshot 完成前不得执行不完整 baseline。
2. 已有兼容库：执行 schema preflight；全量 snapshot 完成前不得 stamp baseline。
3. 不兼容库：明确失败，不继续启动。
4. 已受 Alembic 管理：检查 revision；全量 snapshot 完成前仍不得声称可安全 upgrade。

本波审计确认：现有 baseline 只能覆盖 10 张核心业务表和 1 个索引，不能代表全量生产 schema。因此本波采用：

- 明确记录核心 baseline 的覆盖范围与非生产属性；
- `managed` 对所有数据库分类统一 fail-closed；
- 不执行 stamp，不执行不完整 baseline upgrade；
- `legacy-bootstrap` 保持现有开发/测试兼容路径；
- 建立运行时 DDL 清单；
- 后续独立 Wave 建立全量 snapshot 后，才允许逐类开放 managed；
- 不得伪称已完成生产 migration、autogenerate 或 `alembic check`。

### 3.3 错误策略

- managed 模式 fail-fast。
- dev/test 可选择降级，但日志必须包含模式、revision 和失败类型，不能包含凭据。
- 使用 SQLAlchemy inspector 或 Alembic API 正确检测版本表，禁止执行布尔值。
