## 零、复核结论

### 0.1 是否可以开发

**可以开发，但第一步只能是 Wave 0“可信基线修复”。**

当前不能把 v1.0 实施记录中的 P0-1、P0-2 当作真实完成，原因是：

1. Alembic 依赖缺失，干净环境导入 `aos_api.main` 即失败。
2. Alembic baseline 是空迁移，生产启动仍无条件执行 `init_schema()`。
3. 路由聚合生成器已不能从当前 `main.py` 再生 505 个路由映射。
4. 缺少路由集合等价、重复路由、OpenAPI 可生成等专项测试。
5. `scripts/ci.sh` 根目录计算错误，实际会跳过前端门禁并以错误路径调用后端测试。
6. 电商资料中发现密钥材料及疑似业务/个人数据转储，必须先建立隔离与扫描门。

## 一、风险台账（v2.0）

### R0：敏感转储、凭据和 PII 暴露

**级别：P0 / Critical，阻断真实电商开发和客户交付。**

审计发现：

- `docs/palantier/20_tech/电商平台接入/微商城电商接入方案/niushop_b2c_v5.sql`
  含完整私钥材料。
- 同一文件还含疑似业务记录、个人信息和支付相关数据。
- 本计划和任何日志中不得复制、展示或派生该密钥内容。

处置顺序：

1. 由凭据所有者确认密钥是否真实有效；有效则立即轮换/吊销。
2. 原始转储隔离，不进入仓库、CI、镜像、安装包或客户材料。
3. 用脱敏/合成数据重建测试夹具；测试不得依赖真实个人数据。
4. 增加 secret scan、PII scan 和构建产物扫描。
5. 若文件曾进入版本历史或外部分发，单独制定历史清理与影响通报方案。

验收：

- [x] 不在任何输出中泄露密钥正文。
- [x] 扫描器能以非零退出码拦截私钥、常见 Token、明文凭据。
- [x] 合成夹具覆盖现有测试需要。
- [x] 客户包、镜像和 CI artifact 不包含原始转储。
- [ ] 凭据轮换/吊销由责任人留存外部确认记录。

### R1：数据库迁移体系是假闭环

**级别：P0 / Critical。旧实施记录仅代表“骨架提交”，不代表完成。**

当前事实：

- `services/aos-api/pyproject.toml` 未声明 `alembic`、`sqlalchemy`。
- `main.py` 无条件导入迁移模块，干净 Python 环境报 `ModuleNotFoundError`。
- `6cd2ca0eff8f_baseline.py` 的 `upgrade()` / `downgrade()` 均为空。
- `target_metadata=None`，因此 v1.0 所写的 autogenerate / `alembic check` 不成立。
- `migrations.py` 文档声称由 `AOS_DB_MIGRATE` 控制，但实现没有按变量分支。
- 版本表检测把 `has_table()` 的布尔结果再次交给 `execute()`，异常后会误判为无版本表。
- 启动阶段迁移失败被吞掉，并继续无条件执行 `init_schema()`；生产不能保证 schema 正确。
- 全仓仍有大量 `CREATE/ALTER/ensure_schema` 运行时 DDL，需要分批盘点，不能一次性强拆。

目标：

1. 干净环境安装后可导入 API。
2. 明确三种模式：`test/dev/bootstrap`、`managed migration`、`migration disabled`。
3. 在全量 schema snapshot 完成前，所有 managed 状态统一 fail-closed，不得 stamp 或执行不完整 baseline。
4. managed production 中迁移失败必须 fail-fast，不得回退到运行时 DDL 后带错 schema 启动。
5. 运行时 DDL 建立登记表，逐波迁入版本化 migration。

验收：

- [x] 依赖声明完整，干净安装可导入 `aos_api.main`。
- [x] 当前核心 baseline 的覆盖范围被明确限定为 10 张核心表与 1 个索引。
- [x] 全量 snapshot 完成前，空库、已有库、已管理库和不兼容库均阻止 managed production 启动。
- [x] 不再无条件 stamp，也不执行不完整 baseline upgrade。
- [x] dev/test `legacy-bootstrap` 兼容路径有明确测试。
- [x] 当前 baseline 明确不可逆，恢复依赖备份；完整迁移仍列为后续前置任务。

**级别：P0 / High。旧提交为“部分完成”。**

验收：

## 二、电商产品与契约前置

### 2.1 六层边界

结构修复必须保护以下依赖方向：

1. L1 数据→本体：Connector / Sync / Pipeline / OKF / Ontology。
2. L2 工作台：固定布局的任务、Artifact、审批与业务操作。
3. L3 FDE：对话理解→认证→API 探索→字段映射→同步配置→测试验证。
4. L4 AIP：Plan Mode + TAOR + 权限门 + Diff + Checkpoint + Verification。
5. L5 Wiki：Semantic / Episodic / Working 三层记忆与治理。
6. L6 数字同事：基于上五层执行，不绕过权限和本体。

结构重构不得把 AIP 退化为 Conversation+Message；核心模型是
**Task + Artifact + Action**。

### 2.2 编码前必须冻结的公共契约

| 契约 | 必须明确的唯一口径 |
|---|---|
| 能力 ID | 先解决 G9/G10 在总览、总方案、Connector、排期中的歧义 |
| 平台数量 | 区分“真实接入平台”“指向目录”“规划平台”，解决 7/8/9 口径混用 |
| TaskStatus | canonical 状态、允许转换、终态、暂停、审批、回滚和旧值映射 |
| TAOR | 明确逐 step 执行与 until-complete 循环的关系 |
| 外部身份 | `(workspace_id, platform, shop_or_marketplace_id, external_id)` |
| Money | 存储单位、Decimal 精度、舍入、币种、JPY、MoneyBag 和汇率来源 |
| Time | UTC+带时区 ISO8601；保留源时区；稳定游标使用 `(updated_time, external_id)` |
| Enum | canonical value + `raw_status` + `unknown` 前向兼容 |
| Error | 统一错误信封；不得包含 Token、Secret、明文 PII |
| 租户隔离 | Token、缓存、Checkpoint、Memory、Trace、Eval、对象和 Link 全部按 workspace 隔离 |

这些契约另行写入 `228-EC-公共契约冻结方案.md`，未冻结前不得开展真实平台写回。

### 2.3 Pipeline 诚实能力门

当前微商城方案已明确：

- Pipeline DAG、Join、自定义 SQL 不能按 live 能力宣称。
- jdbc-mysql 当前主要是单表路径。
- 首波真实接入只能选：
  1. 分表同步 + Ontology Link；或
  2. DBA 提供只读 VIEW。

禁止：

- 创建任务后立即伪造 `SUCCEEDED`。
- 无执行引擎却在页面、文档或验收中宣称 Join 已完成。
- 用前端 Mock 结果代替数据落盘、血缘和质量证据。

### 2.4 向后兼容与安全

- 现有 API 方法签名和主返回结构优先保持兼容。
- 内存/mock 只能作为显式的 dev/test 降级路径，生产不得静默回退。
- Evals 关闭时旧流程保持可用；开启后通过注入加门，不重写 8 个核心引擎。
- 外部写回、资金、删除、认证配置必须人工确认并展示 Diff。
- OAuth Token 必须加密、自动刷新、workspace 隔离并具备审计。
- REST / GraphQL / Webhook 必须处理分页、限流、超时、重试分类、幂等、去重、失败重入队。
- 抖音明文敏感数据不得落 AOS Dataset、缓存、日志或导出。
- Wiki 的 Semantic / Episodic / Working 生命周期分离；低可信知识必须经 Draft 审核。

### 2.5 电商开发 P0 Gate

在进入淘宝/拼多多/京东/抖音/Shopify/Amazon 真实接入前，必须完成：

## 四、测试与回归军规

### 4.1 Worker 级

1. 方案自检：范围、依赖、兼容、数据、回滚。

4. 静态检查。
5. 提交前 diff 审查，确认未越过文件所有权。

### 4.2 合并级

每合入一个 worker：

1. 检查 commit 只包含授权文件。
2. 运行该 worker 的专项测试。
3. 检查与已合入 worker 的交互。
4. 记录实际测试数、失败数、跳过数。

### 4.3 Wave 级

每个 Wave 退出前必须执行：

- 后端全量 pytest。
- Web Vitest + TypeScript + build。
- Desktop Vitest + TypeScript + build。
- Ontology SDK test。
- OpenAPI / migration / Router inventory。
- secret / PII / 禁止依赖 / 交付许可门。
- Helm 或等价部署模板检查。

如果环境缺少必需工具，状态是“阻塞”，不是“通过”。

### 4.4 电商专项矩阵

| 类别 | 必测场景 |
|---|---|
| 向后兼容 | 旧 API、旧状态、额外字段、`None`、空数组、unknown enum |
| 租户隔离 | 两 workspace / 两店铺相同 external_id 不串数据 |
| 金额时间 | CNY/USD/JPY、舍入、DST、跨时区、同毫秒稳定游标 |
| 同步可靠性 | 分页边界、401 刷新、429、5xx、超时、幂等、断点续跑、重复/乱序/删除 |
| Ontology | 缺失 Customer、嵌入 Payment、平台特有字段、悬挂 Link、坏映射回滚 |
| 安全 | Secret/PII、SQL/Prompt 注入、日志脱敏、高风险未审批绝不执行 |
| 产品回归 | mock/dev 显式降级仍可用、Evals 关闭旧流程不变、OrderManagement/Canvas 不回归 |

Evals 发布门继续沿用：

- ≥95%：通过。
- 85%～95%：人工审批。
- <85%：阻断。
- 相对基线下降 ≥5%：报警。

## 五、回滚与数据保护

| 风险 | 回滚/保护 |
|---|---|

| 外部写回误操作 | 默认关闭；人工确认；Diff；幂等键；审计；可回滚时先建 checkpoint |
