## 2. A1 交付范围

- 单个 `REPEATABLE READ READ ONLY` 事务内读取全部 published rows，并用一次冻结 trust-root view 构造确定性 `RegistrySnapshot`。
- 共用 M1 ReleasePolicy；区分 candidate 生命周期失效与全局 descriptor/content/signature/config 完整性故障。
- 确定性 SemVer 解析、stable-first、optional 顶层显式启用、真实 attempt/backtrack 预算、cycle/conflict/capability/contribution 检测及可解释最短路径。
- permission、migration、contribution 精确三集合 diff 与纯 `CompositionLockPayload` 生成。
- Composition/Lock 与 Installation 基础 PostgreSQL Store：原子写入、等价幂等、回读重算、CAS 基础原语、租户隔离和异常脱敏。
- A1 未新增 HTTP Router、未开放安装状态机、未执行 Bundle 代码、SQL、外部调用或具体电商业务。

## 3. 集成终审与 P1 闭环

| P1 | 红证据 | 关闭方式 |
|---|---|---|
| 一次 snapshot 混用动态可信根；单个失效根扩大为全局拒绝服务 | 首轮 W4 对抗组在修复前 `8 failed, 15 passed` | ReleasePolicy 先冻结 provider；候选级 root/evidence 生命周期失效只排除对应 candidate，配置/完整性故障仍整体失败 |
| prerelease 抢占 stable | 独立终审构造 stable 与显式 prerelease 同时可行场景 | stable 集合优先；仅无可行 stable 且约束显式允许时选择 prerelease |
| Resolver 只计 attempt、不计 branch backtrack | 真实搜索越过 10,000 step 预算 | attempt 与失败 branch backtrack 分别计步；`observed=10001` 稳定失败 |
| 三类资源冲突路径为空 | explicit/capability/contribution 对抗断言失败 | 从全部顶层请求到 owner 选择最短路径，等长按完整 tuple 字典序稳定裁决 |
| SQL 先过滤 stale/missing/revoked evidence，掩盖同一 candidate 的 manifest/content/crypto 损坏 | 第二轮真实 PostgreSQL 3×3 组合组修复前 `10 failed, 1 passed` | SQL 只筛 published；每行先在 Python policy 做完整性验证，再判 candidate 生命周期资格，完整性故障优先全局失败 |
| raw SQL row 在 policy 前占用 snapshot candidate 预算 | 多个失效候选 + 一个有效候选、limit=1 时旧实现错误超限 | 预算只统计合格 candidate；第 `max+1` 个合格候选立即以 `observed=max+1` 失败 |
| 脱敏测试夹具自身命中 credential URL critical | 源码扫描 `critical=2` | 先冻结测试规则，再改为 scanner 认可的 placeholder；未增加 allowlist，最终恢复 `critical=0` |

第二轮 W4 独立闭环：新增 11 项由 `10 failed, 1 passed` 转为 `11 passed`；W4 两文件最终 `34 passed`。三路只读终审中，一路先确认 Store/可信根边界无 P0/P1，另两路分别发现并复现 SQL 错误优先级与 eligible-only budget 缺口；问题全部先更新方案后修复。
