## 1. 方案目标

将 8 个电商平台（微商城、淘宝/天猫、拼多多、京东、抖音、Shopify、Amazon）的业务数据接入 AOS 平台，经过**数据接入 → 数据同步 → 管道清洗 → OKF 映射 → 本体实例化 → 上层消费**六阶段完整链路，使原始数据库记录转变为**有语义、有关系、可操作、可推理**的数字孪生对象。

> 以下各章节均对照平台实际界面逐一说明，以**微商城订单**为例穿插贯穿全链路。

### 1.1 模块化交付边界

本文的六阶段数据链路不以“一个电商单体模块”交付，而是被下列资产组合实现：

| 层 | 交付物 | 边界 |
|---|---|---|
| AOS 平台内核 | Registry、Resolver、Installation、Evidence、Connector/Pipeline/Logic/Action 运行时 | 禁止包含电商术语和某平台分支 |
| `domain.ecommerce.core` | 统一电商本体、Link、指标接口、数据质量和隐私契约 | 不包含 Niushop 表名或智能体策略 |
| `solution.ecommerce.*` | 基础运营、增长参谋长、六数字同事、Logic/Workshop/Evals | 不包含店铺 Secret 和具体平台协议 |
| `platform.ecommerce.*` | Niushop/淘宝/京东/抖音等平台协议、字段映射、Pipeline 模板 | 不定义通用增长策略 |
| `vertical.ecommerce.*` | 美妆、服饰、生鲜等品类扩展 | 不改写核心 Order/Product 语义 |
| `InstanceOverlay` | 组织/项目、店铺、SecretRef、真实资产引用和开关 | 只属于客户实例，不发布为公共包 |

FDE 资产包页展示可安装和可复用的包；接入案例页展示某客户实例的组合锁、运行证据和阶段。两者不得混用。

## 3. 各阶段详解（对照界面）

### Stage 1 · 数据接入（Data Connection）

> **对应界面**：`data-connection.html`（数据链接器） → `source-new.html`（新建源向导） → `source-detail.html`（源详情 · 探索源）

#### 3.1.1 数据链接器页（Data Connection）

进入 **数据链接器** 页面后，界面是**双栏布局**：

- **左侧分类导航**（260px）：分两个分组
  - **Sources**（15 个 Palantir 官方连接器）：PostgreSQL / MySQL / SQL Server / Oracle / Salesforce / SAP / Shopify / Amazon / Kafka / S3 / Snowflake / Workday / ServiceNow / NetSuite / Stripe（每个连接器含能力标签：Batch / Streaming / Media / Virtual / Webhooks）
  - **Protocol sources**（5 个协议源）：FTP / JDBC / LDAP / REST / GraphQL
- **右侧主区**：
  - 页面标题"数据链接器"+ 描述
  - 连接器卡片网格（每个卡片含连接器图标、名称、类型标签、能力标签、支持的操作）

> **注意**：数据链接器页面严格对照 Palantir 官方连接器门户，仅展示 Palantir 支持的 ~190 种官方连接器。电商平台（抖音/淘宝/京东/拼多多等）的接入方案不在本页展示，而是在运维区"接入案例"页面统一承载。

#### 3.1.2 新建源向导（source-new.html）

点击"+ 新建源"后进入**4 步向导**，界面顶部有步骤指示器：

```
✓ 选择类型 ──── ② 连接方式 ──── ③ 命名与项目 ──── ④ 配置连接
```

**Step 1 · 选择类型**：从连接器目录选择（PostgreSQL / MySQL / Salesforce / Shopify / Amazon SP-API 等），界面顶部以绿色卡片显示已选类型（如"PostgreSQL · 已选择数据源类型"）。

**Step 2 · 连接方式**：两个卡片选择
- **通过代理**（推荐）：使用数据链接器代理作为中间层，从您的网络到 Foundry 的单一验证入口。选中后下方列出可用代理（`prod-agent-01` v2.14.3 · us-east-1 · ●在线）
- **直接连接**：Foundry 直连数据源，需要 VPC 网络打通

**Step 3 · 命名与项目**：
- 数据源名称（如 `prod-mysql-orders`）
- 选择所属项目（建议每源一个新项目）

**Step 4 · 配置连接**：填写连接参数（Host / Port / Database / 用户名 / 密码），测试连接。

#### 3.1.3 源详情页（source-detail.html）

连接创建后，进入源详情页，界面包含 **5 个 Tab**：

| Tab | 功能 |
|-----|------|
| 概览 | 连接基本信息、健康状态、关联同步任务 |
| **探索源** | 核心功能：以图谱方式展示源端所有表结构，点击表名 → 右侧预览数据 |
| **功能** | 功能路由：列出此源支持的能力（批量同步✓ / 流式同步✗ / 虚拟表✗ / 媒体集同步✗） |

| 设置 | 连接参数、凭证、代理、权限 |

**探索源 Tab 的布局**（三栏）：
- **左侧**（240px）：表/视图树形列表，含搜索框，点击可选中表

> **以微商城为例**：连接建立后识别出 302 张 MySQL 表。在探索源界面，操作员选中 `order` 表，看到它的列（`order_id` / `order_sn` / `order_money` / `user_id` / `create_time` / `pay_time` / `ship_status` 等 20+ 字段），以及它与 `user`（外键 `user_id`）、`order_goods`（外键 `order_id`）、`order_logistic`（外键 `order_id`）的关联关系。

### Stage 2 · 数据同步（Sync）

> **对应界面**：`sync-routing.html`（功能路由） → `sync.html`（同步配置详情）

#### 3.2.1 功能路由页（sync-routing.html）

从源详情的"功能"Tab 点击进入，界面展示：
- 面包屑：数据链接器 / `prod-mysql-orders` / 功能 / 批量同步
- 功能能力卡片列表：
  - **批量同步**（✓ 可用）：SNAPSHOT 和 APPEND 事务类型，标签"SQL 查询 / 增量 / SNAPSHOT/APPEND"
  - **流式同步**（✗ 不可用）："此源类型不支持"灰色禁用
  - **虚拟表**（✗ 不可用）："仅 REST API 源"灰色禁用
  - **媒体集同步**（✗ 不可用）

点击"创建"进入同步配置页。

#### 3.2.2 同步配置页（sync.html）

界面为 **4 Tab** 布局：配置 / 计划 / 运行历史 / 高级

**配置 Tab 包含 3 个卡片**：

**卡片 1 · 输出位置**：
- 输出数据集路径（只读，如 `/Foundry/Ecom/orders_sync`）
- 所属项目（只读，如 `Ecom Data Pipeline`）

**卡片 2 · 同步配置**：
- **SQL 查询**：代码编辑器（深色背景 monospace），如：
  ```sql
  -- 从 orders 表增量同步新订单
  SELECT order_id, customer_id, order_date, total_amount, status, updated_at
  FROM orders
  WHERE updated_at > ?
  ORDER BY updated_at ASC
  ```
  提示："通配符 ? 将在首次运行时替换为初始值，后续运行替换为上次同步的最大增量列值"
- **事务类型**（单选）：`SNAPSHOT — 全量快照` / `APPEND — 增量追加`（增量推荐高亮蓝框选中）
- **增量同步配置**（蓝底信息块）：
  - 增量列下拉（`updated_at` / `order_id` / `created_at`），提示"必须严格递增的列"
  - 初始值输入（`2026-07-01 00:00:00`），提示"大于之前所有运行的最大值"
- **调度计划**下拉：每 15 分钟 / 每 1 小时（默认选中）/ 每日 02:00 UTC / 手动触发

**卡片 3 · 预览**：
- 数据预览表格（前 20 行），含"刷新预览"按钮

**计划 Tab**：Cron 表达式编辑器 + 下次运行时间预测 + 调度日历
**运行历史 Tab**：历史运行记录表（运行时间 / 状态 / 耗时 / 拉取行数 / 写入字节数）
**高级 Tab**：重试策略 / 超时设置 / 资源配额

#### 3.2.3 同步落盘

同步执行后，数据以 **Parquet + Iceberg** 格式落盘为 Dataset。原始数据"原汁原味"——字段名、数据类型、脏数据都原封不动保留。

> **以微商城订单为例**：配置 `orders_sync` 同步任务，选择 APPEND 增量模式，增量列 `updated_at`，每 1 小时调度。首次全量拉取后，`/Foundry/Ecom/orders_sync` Dataset 中产生 12,847 行订单记录。

#### 3.2.4 同步能力约束

| 事务类型 | 行为 | 适用场景 |
|----------|------|----------|
| SNAPSHOT | 每次全量拉取并覆盖目标 Dataset | 商品目录、店铺信息（数据量小，变更频繁） |
| APPEND | 仅追加新增行，按增量列水位线 | 订单、退款记录（单调递增，量级大） |
| UPDATE | 按主键 upsert（覆盖更新） | 库存、用户画像（同 ID 多次更新） |

> **关键约束**：所有平台的同步能力统一阻塞于 G1（REST API Connector）和 G2（OAuth Token Manager）两项 W2+ 基础设施。

### Stage 3 · 管道清洗（Pipeline Builder）

> **对应界面**：`pipeline.html`（管道画布） → `dataset.html`（输出 Dataset 预览） → `lineage.html`（数据血缘）

管道清洗是六阶段链路中**最核心的一层**——上游同步过来的原始数据（Raw Dataset）虽然已落盘，但存在三类问题：① 数据类型混乱（金额存成字符串、时间戳存成整数）；② 信息孤岛（订单表只有 `user_id` 没有客户名称、只有 `goods_id` 没有商品信息）；③ 数据质量问题（已删除订单未清理、重复拉取、枚举值不统一）。Pipeline Builder 通过**可视化算子编排**（9 种核心算子：Filter / Join / Aggregate / Explode / Cast / Union / Sort / Distinct / Expression）解决这三类问题，输出结构化的干净 Dataset（Curated Dataset），为下游 OKF 语义映射铺平道路。

#### 3.3.1 管道画布界面（pipeline.html）

进入 Pipeline Builder 后，界面为**顶部工具栏 + 画布 + 右侧输出面板**三段式布局：

**① 顶部工具栏**：
- 左侧：撤销/重做 · Git 分支指示器（`feat/order-enrichment`）· "已保存"状态 · "提议"·"部署"按钮

- 右侧：构建状态徽章（`搭建 ✓` · `检查 5/5`）· 搭建设置 · 分享 · 详细信息

**② 画布工具栏**（画布上方横向）：
- 变换算子按钮组：`Filter` / `Join` / `Aggregate` / `Explode` / `Cast` / `Union` / `Sort` / `Distinct` / `Expression`
- `+ 添加数据集` · `参数`

**③ 画布区**（SVG 有向无环图 DAG）：
- 三种节点类型，颜色区分：

  - 🔵 **变换节点**（蓝色）— 如 `JOIN`、`EXPRESSION`，展示变换名称 + 输入输出行数

**④ 底部预览面板**（可折叠）：

**⑤ 右侧输出面板**：

- **Object 类型输出**：`Order`（Write Mode: Update by PK · 已部署）
- **链接类型输出**：`Order → Customer`（1:N · placed_by · 已部署）
- **详细信息**：描述、查看次数(142/30d)、协作者(张/李/王/+2)

#### 3.3.2 变换算子组件库（9 种核心算子）

Pipeline Builder 的画布工具栏提供 **9 种可视化变换算子**，每种对应一类数据处理操作。以下逐一详解：

**Filter 组件 — 条件过滤**
- 功能：按布尔条件表达式保留/剔除行
- 配置面板：条件表达式编辑器（支持 `AND` / `OR` / `IN` / `IS NULL` / `LIKE` 等）
- 订单场景示例：
  ```
  Filter: status != 'deleted' AND order_type IN ('normal','presale')
  Filter: amount > 0 AND created_at >= '2026-01-01'
  Filter: is_test_order IS NULL OR is_test_order = false
  ```
  剔除已删除订单、测试订单、金额为 0 的无效订单

**Join 组件 — 关联补全**
- 功能：按等值条件关联两个数据集，输出合并后的宽表
- 配置面板：Join 类型（Inner / Left / Right / Outer）+ Join 键选择 + 输出列选择
- 核心场景——**订单关系网构建**（详见 §3.3.3）
- 订单场景示例：
  ```
  Join (Inner): order.user_id = customer.id
  Join (Left):  order.goods_id = product.sku_id
  Join (Left):  order.order_id = shipment.order_id
  ```

**Cast 组件 — 类型转换**
- 功能：强制转换列的数据类型（STRING → DECIMAL / STRING → DATETIME / INTEGER → STRING 等）
- 配置面板：列选择 + 目标类型 + 格式模板（如日期格式 `yyyy-MM-dd HH:mm:ss`）+ 空值处理策略（NULL / 默认值 / 报错）
- 订单场景示例：
  ```
  Cast: order_money  STRING → DECIMAL(12,2)     '199.00' → 199.00
  Cast: create_time  STRING → DATETIME          '2026-07-22 14:30:00' → timestamp
  Cast: is_paid      STRING → BOOLEAN           'true'/'false' → true/false
  Cast: goods_count  STRING → INTEGER           '3' → 3
  ```
  解决源系统类型混乱问题——微商城 MySQL 中金额/时间/数量大量以 VARCHAR 存储

**Expression 组件 — 表达式/派生列**
- 功能：基于现有列创建新的计算列，支持 50+ 标量函数（数学运算 / 字符串处理 / 日期提取 / 条件映射 / 枚举转换）
- 配置面板：表达式编辑器（语法高亮 + 自动补全）+ 新列名 + 类型推断
- 订单场景示例：
  ```
  Expression: ship_status_code → enum映射
    CASE ship_status_code
      WHEN 1 THEN 'pending'
      WHEN 2 THEN 'shipped'
      WHEN 3 THEN 'in_transit'
      WHEN 4 THEN 'delivered'
      WHEN 5 THEN 'returned'
      ELSE 'unknown'
    END AS status_enum

  Expression: is_cross_border → 派生列
    CASE WHEN region IN ('HK','TW','SG','US') THEN true ELSE false END

  Expression: order_age_hours → 日期运算
    (NOW() - created_at) / 3600 AS order_age_hours

  Expression: risk_tag → 多因子标签
    CASE
      WHEN amount > 5000 AND is_new_customer = true THEN 'high_value_new'
      WHEN amount > 5000 AND is_new_customer = false THEN 'high_value'
      WHEN refund_count_30d > 3 THEN 'frequent_refund'
      ELSE 'normal'
    END AS risk_tag
  ```

**Aggregate 组件 — 聚合统计**
- 功能：按分组维度聚合，输出统计指标（COUNT / SUM / AVG / MIN / MAX / COLLECT_LIST）
- 配置面板：分组列选择 + 聚合函数选择 + 输出列命名
- 订单场景示例：
  ```
  Aggregate GROUP BY customer_id:
    COUNT(*)            → order_count
    SUM(amount)         → total_spent
    AVG(amount)         → avg_order_value
    MAX(created_at)     → last_order_date
    MIN(created_at)     → first_order_date
    COLLECT_LIST(status)→ order_status_history
  ```
  输出 Customer LTV（客户生命周期价值）宽表，反哺到 Customer OT

**Explode 组件 — 数组展开**
- 功能：将包含数组/JSON 列的行展开为多行（每行一个数组元素），用于处理嵌套数据
- 配置面板：数组列选择 + 保留原始行 Toggle + 空数组策略（保留/丢弃）
- 订单场景示例：
  ```
  Explode: order_items ARRAY<STRUCT>
    一行订单（含 N 个商品项）展开为 N 行，每行一个商品项
    便于后续按商品维度统计
  Explode: tags STRING (JSON)
    '["新人","跨境","高风险"]' 展开为 3 行
  ```

**Sort 组件 — 排序**
- 功能：按指定列对数据集排序，支持多列复合排序
- 配置面板：排序列选择 + 升序/降序 Toggle + NULL 值排序策略（FIRST / LAST）
- 订单场景示例：
  ```
  Sort: created_at DESC NULLS LAST, amount DESC
    按创建时间倒序排列，时间相同的按金额倒序
    用于生成"最新大额订单"看板
  ```

**Window 组件 — 窗口函数**
- 功能：在数据窗口内计算排名、偏移、累计值
- 配置面板：分区列（PARTITION BY）+ 排序列（ORDER BY）+ 窗口范围 + 函数选择
- 订单场景示例：
  ```
  Window PARTITION BY customer_id ORDER BY created_at DESC:
    ROW_NUMBER()       → customer_order_seq     （客户第 N 笔订单）
    LAG(amount, 1)     → prev_order_amount      （上一笔订单金额）
    SUM(amount) OVER ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
                       → cumulative_spent       （累计消费金额）
  ```

**Union 组件 — 纵向合并**
- 功能：将多个相同 Schema 的数据集纵向堆叠（UNION ALL / UNION DISTINCT）
- 配置面板：输入数据集选择 + 列对齐映射 + 去重 Toggle
- 订单场景示例：
  ```
  Union: 微商城订单 + 天猫订单 + 拼多多订单
    三平台订单统一列名后合并为一个 unified_orders 数据集
  ```

**Distinct 组件 — 去重**
- 功能：按全部列或指定列去重，保留首次出现行
- 配置面板：去重列选择 + 保留策略（FIRST / LAST / 随机）
- 订单场景示例：
  ```
  Distinct ON order_id: 去除增量同步重复拉取的订单行
  ```

> Pipeline 还支持 **代码级编写模式**（Code Pipeline）：使用 `@transform` 装饰器以 Python/SQL 编写自定义变换逻辑，适用于可视化算子无法覆盖的复杂场景。

#### 3.3.3 订单关系网构建（Join 组件核心场景）

这是管道清洗阶段**最关键的工作**——原始订单表（`orders_raw`）只是一个"孤岛"，只有订单自身的字段。通过 **Join 组件串联多张表**，将孤立订单扩展为一张拥有完整业务上下文的**宽表**，形成**订单关系网**。

**订单需要关联的全部业务关系：**

| 关联方向 | Join 目标表 | Join 键 | Join 类型 | 补全的信息 | 关系语义 |
|----------|------------|---------|-----------|-----------|----------|
| 订单 → 消费者 | `customers_sync` | `order.user_id = customer.id` | **Inner** | 客户名称、手机号、会员等级、LTV、标签、注册时间 | **谁买了** |
| 订单 → 商品 | `order_goods_sync` | `order.order_id = og.order_id` | **Left** | SKU 列表、商品名称、单价、数量、规格属性、类目 | **买了什么** |
| 订单 → 商品详情 | `products_sync` | `og.goods_id = product.sku_id` | **Left** | 品牌、SPU/CPU、产地、成本价、商品图片 | 商品全维度 |
| 订单 → 物流 | `logistics_sync` | `order.order_id = logistics.order_id` | **Left** | 物流公司、运单号、发货时间、揽收时间、签收时间、签收状态 | **怎么发的** |
| 订单 → 售后 | `aftersales_sync` | `order.order_id = as.order_id` | **Left** | 退款状态、退款金额、退款类型、退款原因、处理人 | **退了没** |
| 订单 → 异常风控 | `risk_events_sync` | `order.order_id = risk.order_id` | **Left** | 风险等级、风险类型（刷单/套利/薅羊毛）、风控决策、处置时间 | **有无风险** |
| 订单 → 优惠券 | `coupons_sync` | `order.coupon_id = coupon.id` | **Left** | 优惠券类型（满减/折扣/无门槛）、优惠金额、活动 ID、领取渠道 | **享受了什么优惠** |
| 订单 → 店铺 | `shops_sync` | `order.shop_id = shop.id` | **Inner** | 店铺名称、平台、经营类目、店铺评分 | 来源店铺 |
| 订单 → 库存（扣减） | `inventory_sync` | `og.goods_id = inv.sku_id` | **Left** | 扣减前库存、扣减后库存、库存预警标记 | 库存联动 |
| 订单 → 评价 | `reviews_sync` | `order.order_id = rv.order_id` | **Left** | 评分、评价内容、评价时间、是否追评 | 履约反馈 |

**订单关系网拓扑图：**

```
                    ┌──────────────┐
                    │  customers   │  ← 消费者（谁买了）
                    │  name/level  │
                    │  phone/LTV   │

                           │ placed_by (N:1)
                           │
    ┌──────────────┐       │       ┌──────────────┐
    │  coupons     │       │       │ order_goods  │  ← 订单商品（买了什么）
    │  type/amount │       │       │ sku/qty/price│
    │  activity_id │       │       └──────┬───────┘
    └──────┬───────┘       │              │ contains (N:M)
           │ used_coupon   │              │
           │               │       ┌──────┴───────┐
    ┌──────┴───────────────┴──┐    │  products    │  ← 商品详情

    │  status / created_at    │    └──────────────┘
    │  user_id / shop_id      │
    └──┬──────────┬───────────┘
       │          │          │          │
       │ 1:N      │ 1:N      │ 1:N      │ 1:N
       ▼          ▼          ▼          ▼

经过这一系列 Join，一张原本 14 列的孤立订单表（`orders_raw`），扩展为一张拥有 **40+ 列**的宽表——不仅知道"这笔订单花了多少钱"，还知道"**谁**买了、买了**什么**、**怎么**发的、**退了**没有、**有没有**风险、用了**什么**优惠券"。这张宽表就是下游 OKF 语义映射和本体关系构建的数据基础。

> 关系网中的每一条边（如 `placed_by` / `contains` / `shipped_via`）都会在 Stage 5 本体实例化阶段转化为 **Link Type**，形成可图谱探索的对象关系图。

#### 3.3.4 数据质量校验管道

除了结构化清洗和关系补全，管道清洗阶段还负责**数据质量保证**（Data Quality），主要通过 Filter 组件 + Expression 组件的组合实现：

**质量校验规则矩阵：**

| 质量维度 | 校验规则 | 用到的组件 | 处置动作 |
|----------|---------|-----------|----------|
| **唯一性** | `order_id` 全局唯一，重复行标记 | Filter + Distinct | Distinct 去重 |
| **非空** | `order_id` / `user_id` / `amount` 不可为空 | Filter | Filter `IS NOT NULL` |
| **有效性** | `amount > 0` / `status IN (valid_enums)` | Filter + Expression | 异常行打标 `quality_flag = 'invalid'` |
| **一致性** | `paid_at >= created_at` / `shipped_at >= paid_at` | Expression | 违反时打标 `time_anomaly = true` |
| **枚举映射** | `ship_status` 原始码 → 统一枚举 | Expression | 映射到 `pending/shipped/delivered/returned` |
| **跨表一致性** | `order.amount = SUM(order_goods.subtotal)` | Expression + Aggregate | 不等时打标 `amount_mismatch = true` |
| **格式规范** | 手机号正则 / 邮箱格式 / 运单号前缀 | Expression | 不符时清空或打标 `format_invalid` |

> 质量校验不直接丢弃异常行，而是打上 `quality_flag` 标记列（`valid` / `warning` / `invalid`），让下游 OKF 和 Ontology 能按标记分流处理。

## 4. 数据流转升维模型

数据在链路中逐步"升维"，以**微商城订单**为例：

```

Stage 4 · 语义对齐数据
  Order.totalAmount = 199.00 — 有业务语义："这是订单总金额"

  Order.region: "cross-border" — 有分类标记

       ↓ Stage 5 · 本体实例化

Stage 5 · 数字孪生对象
  Order #20250723001
    ├── ←placed by→ Customer "张三" (LTV: ¥8,200 · VIP)
