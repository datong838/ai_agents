## 一、为什么需要编排总览

### 1.1 问题

6 个数字同事各自有 5-6 个技能，合计 35 个技能。但电商运营不是"一个数字同事干完所有事"，而是**多个数字同事协作完成一个业务目标**。

例如：
- 客服收到"面霜过敏"投诉 → 需要导购顾问确认成分 → 需要私域管家标记客户过敏史 → 需要内容官修改产品文案
- 数据参谋发现转化率下降 → 需要活动策划师做促销 → 需要内容官生成促销素材 → 需要客服专员准备售后话术

**如果没有编排层，6 个数字同事就是 6 个孤岛。**

### 1.2 目标

本文档定义：
1. **数字同事之间的协作关系图** — 谁跟谁协作、什么时候协作、怎么传递上下文
2. **典型电商场景的编排流程** — 6 个核心业务场景的跨数字同事流程
3. **协作机制设计** — 上下文传递、权限传递、状态同步、异常处理
4. **LLM 函数链全景** — 35 个技能如何通过编排层串联

### 2.2 协作关系矩阵

| 发起方 → 接收方 | 触发条件 | 传递内容 | 协作模式 |
|---------------|---------|---------|---------|
| 数据参谋 → 活动策划师 | GMV 下降/转化率异常 | 异常报告 + 归因分析 + 建议做活动 | 建议驱动 |
| 数据参谋 → 内容官 | 内容表现下降 | 内容效果数据 + 优化建议 | 建议驱动 |
| 数据参谋 → 私域管家 | 客户流失预警 | 流失客户列表 + 原因分析 | 建议驱动 |
| 活动策划师 → 内容官 | 活动方案锁定 | 活动主题 + 选品 + 需要的素材 | 任务派发 |
| 活动策划师 → 导购顾问 | 新品上架/选品确认 | 产品信息 + 定价 + 目标人群 | 任务派发 |
| 私域管家 → 导购顾问 | 客户咨询/复购推荐 | 客户画像 + 购买历史 + 偏好 | 上下文传递 |
| 私域管家 → 内容官 | 客户分层完成 | 人群标签 + 需要的内容类型 | 任务派发 |
| 导购顾问 → 客服专员 | 客户下单后 | 订单信息 + 产品使用注意 | 上下文传递 |
| 导购顾问 → 私域管家 | 客户过敏/肤质信息 | 肤质画像 + 过敏原 | 数据回写 |
| 客服专员 → 导购顾问 | 产品使用咨询 | 客户问题 + 产品信息 | 转接 |
| 客服专员 → 活动策划师 | 售后异常聚集 | 异常工单 + 产品问题 | 告警驱动 |
| 客服专员 → 私域管家 | 客户投诉记录 | 投诉内容 + 客户情绪 | 数据回写 |

### 2.3 协作模式定义

| 模式 | 说明 | 示例 |
|-----|------|------|
| **建议驱动** | 数据参谋发现问题 → 建议其他数字同事行动 | GMV 下降 → 建议活动策划师做促销 |
| **任务派发** | 一个数字同事完成任务后派发子任务 | 活动方案锁定 → 派内容官准备素材 |
| **上下文传递** | 客户从一个数字同事流转到另一个 | 私域管家触达 → 客户咨询 → 转导购顾问 |
| **数据回写** | 一个数字同事产出数据写回给另一个 | 导购顾问发现过敏 → 回写私域管家标记 |
| **告警驱动** | 异常事件触发其他数字同事响应 | 客服收到批量投诉 → 告警活动策划师 |

## 三、协作机制设计

### 3.1 上下文传递

数字同事之间传递上下文，采用**结构化交接文档**：

```typescript
interface HandoffContext {
  id: string;
  fromAgent: AgentType;
  toAgent: AgentType;
  reason: string;                    // 交接原因

  // 客户上下文（如有）
  customerId?: string;
  customerProfile?: {
    skinType?: string;
    allergies?: string[];
    purchaseHistory?: string[];
    segment?: string;
  };

  // 任务上下文
  taskId?: string;
  taskType?: string;
  taskStatus?: string;

  // 已完成的工作
  completedSteps: {
    agent: string;
    step: string;
    result: string;
    timestamp: string;
  }[];

  // 需要接收方做的事
  requestedAction: {
    type: string;
    description: string;
    priority: 'low' | 'normal' | 'high' | 'urgent';
    deadline?: string;
  };

  // 相关数据
  relevantData?: Record<string, any>;

  // 权限传递
  permissions: {
    canModifyCustomer: boolean;
    canCreateOrder: boolean;
    canApproveRefund: boolean;
  };

  createdAt: string;
}
```

### 3.2 状态同步

```
数字同事A 执行任务
    │
    ├─ 任务状态变更 → 写入 Task OT → 通知编排层
    │                                    │
    │                              编排层检查：
    │                              · 是否需要触发其他数字同事？
    │                              · 是否有依赖的任务？
    │                              · 是否有阻塞的任务？
    │                                    │
    │                              ├─ 不需要 → A 继续执行
    │                              │
    │                              ├─ 需要触发 → 创建 HandoffContext → 通知 B
    │                              │
    │                              └─ 有依赖阻塞 → A 暂停，等待 B 完成
    │
    └─ 任务完成 → 通知编排层 → 编排层决定下一步
```

### 3.3 权限传递规则

| 场景 | 发起方 | 接收方 | 权限传递 |
|-----|--------|--------|---------|
| 客户咨询转导购 | 私域管家 | 导购顾问 | 读取客户画像 + 购买历史 |
| 导购发现过敏 | 导购顾问 | 私域管家 | 写入客户标签（过敏原） |
| 活动方案派素材 | 活动策划师 | 内容官 | 读取活动方案 + 产品信息 |
| 客服转人工 | 客服专员 | 人工客服 | 读取对话记录 + 已处理内容 |
| 数据参谋给建议 | 数据参谋 | 运营 | 仅建议，无直接执行权 |

**核心原则：权限最小化传递，只传必要的。**

### 3.4 异常处理

| 异常类型 | 处理方式 |
|---------|---------|
| 接收方数字同事不可用 | 降级为人工处理，记录异常 |
| 上下文不完整 | 接收方主动询问补充信息 |
| 权限不足 | 阻止执行，通知运营 |
| 超时未响应 | 编排层介入，决定等待/转人工/取消 |
| 循环依赖检测 | A 等 B、B 等 A → 编排层打破死循环 |

### 4.1 场景一：新客首购全流程


**编排要点：**
- 私域管家先识别新客，打上"新客"标签
- 导购顾问接管，基于客户画像做需求诊断和产品推荐
- 客户犹豫时，导购顾问向内容官请求种草文案
- 下单后，客服专员接手做使用指导和售后关注
- 数据参谋在后台追踪首购转化率和 LTV 起点

## 六、编排层架构设计

### 6.1 Orchestrator 核心接口

```typescript
interface Orchestrator {
  // 场景识别
  identifyScene(context: UserContext): SceneType;

  // 数字同事路由
  routeToAgent(scene: SceneType, context: UserContext): AgentType;

  // 上下文传递
  createHandoff(from: AgentType, to: AgentType, context: HandoffContext): void;

  // 结果聚合
  aggregateResults(taskResults: TaskResult[]): AggregatedResult;

  // 验证
  verifyChain(chain: TaskStep[]): VerificationResult;
}
```

```python
ORCHESTRATION_RULES = {
    # 场景→数字同事映射
    "scene_routing": {
        "new_customer": ["private_manager", "shopping_advisor"],
        "repurchase": ["private_manager", "shopping_advisor", "data_analyst"],
        "big_sale": ["activity_planner", "content_officer", "private_manager", "data_analyst", "customer_service"],

        "customer_service → activity_planner": "批量售后异常时",
    },

    # 上下文传递规则
    "context_transfer": {
        "always_transfer": ["customer_id", "customer_profile"],

        },
```

### 6.3 编排层数据模型

```typescript
interface OrchestrationFlow {
  id: string;
  scene: SceneType;                // 场景类型
  trigger: string;                  // 触发原因

  // 参与的数字同事
  agents: {
    agent: AgentType;
    role: 'primary' | 'secondary' | 'support';
    skills: string[];                // 需要的技能
  }[];

  // 执行顺序
  sequence: {
    step: number;
    agent: AgentType;
    skill: string;
    dependsOn?: number[];           // 依赖的前置步骤
    handoffTo?: {                   // 完成后交接给
      agent: AgentType;
      context: HandoffContext;
    };
  }[];

  // 状态
  status: 'pending' | 'running' | 'completed' | 'failed' | 'cancelled';
  currentStep: number;

  // 结果
  results?: {
    step: number;
    agent: string;
    skill: string;
    result: any;
    artifacts?: string[];           // 产出物ID
  }[];

  createdAt: string;
  completedAt?: string;
}

type SceneType = 'new_customer' | 'repurchase' | 'big_sale' | 'complaint'
                | 'new_product' | 'daily_patrol' | 'custom';
type AgentType = 'private_manager' | 'shopping_advisor' | 'content_officer'
               | 'customer_service' | 'activity_planner' | 'data_analyst';
```
