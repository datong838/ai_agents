## 1. 目标与边界

在不把电商逻辑写入 L0 的前提下，以 Bundle/Installation 注册八个 Workshop Module；复用 AIP Task、Action、Evidence、Memory 等唯一权威能力；通过 L2 Adapter capability 与 L3 Overlay 装配具体平台和组织。

当前唯一代码开发主线是 `aos-platform/m1`，同一开发者可按授权维护四层代码；对象 Authority、租户、安全、迁移、真实副作用和发布门仍逐项生效。不新建第二套 Task/Agent/Action/Memory/Analyst 状态机，也不读取或覆盖历史 worker 工作树的未提交内容。

### 1.1 本轮状态解释

旧 `APPROVED_TECHNICAL_BASELINE_V2`、T-R1～T-R4 与历史 Delivery Receipt 只保留为内部整理、自检和方案收敛记录，不能作为本轮正式审查或封板证据。本轮输入冻结、首轮发现、两轮整改、复审证据与最终结论统一记录在 [21-技术方案审查记录与封板结论](21-技术方案审查记录与封板结论.md)。本轮已按用户“审查—优化—再审查—再优化，最终审核通过”的明确指令达到正式技术封板；即使封板，也仍需逐波取得开发授权。

## 5. 技术决策

1. 前端只通过领域 BFF/read-model 与唯一 AIP SDK 消费权威能力，不直接拼散乱通用 API。
2. Module manifest 声明 route、permissions、objects、capabilities、widgets、Evals 和 dependencies；导航由 active installation projection 生成。
3. L1 领域服务可以引用 L0 contracts，L0 禁止 import 电商包；Adapter 只实现 capability，不承载经营策略。
4. 所有读模型可重建，canonical authority 不存在前端或 Redis/localStorage。
5. 每个技术波都先做 capability/readiness 和失败态，再开放正向动作。
6. 专业职责、Stage、assignee 和 Module entry 分离；10 类共享 capability 是稳定语义目录，不等于固定十个 Agent；旧 Agent 显示名只作 alias/crosswalk 输入，不冻结运行编制。
7. prepare/freeze/start 分离；收费、批量或不可逆动作还必须经过 exact ImpactPreview/Approval/Lease。
8. TaskBrief/EvidenceBundle/Eval/ResponsibilityPlan 等通用 authority 若 L0 尚未提供，先回到 L0/AIP 评审，不在 L1 BFF 建临时真源。

9. 当前 Workshop 注册协议先复用并扩展既有 Bundle authority；旧 W01/W02/W03 通过迁移和 redirect 收敛，不允许删除后另起一套 Module 真源。
10. 计划态、代码 GREEN、运营就绪必须分栏表达；任何文档状态不能代替 Store/API/浏览器/Provider 证据。

## 6. 正式技术审查退出门

本技术方案通过不等于实施授权。正式通过条件：

1. 输入清单及 hash 已冻结，旧 `APPROVED_*` 仅作为历史记录；
2. 架构、authority、安全、TenantScope 和第二真源审查 P0=0；
3. API、对象、真实文件边界、Bundle 兼容、测试、迁移、回滚、波次与产品追踪审查 P1=0；
4. 产品需求 → 技术合同 → D-waves Task → 测试/证据，以及反向链路均可追踪；
5. AIP-6 A6A～A6F、AIP W0/W2、AIP-5 E7、AIP-8/9 等依赖按 `planned/code_green/operational_ready` 分开，不把方案写成能力已就绪；

7. 正式审查记录显示本轮 P0=0、P1=0，且用户明确批准封板。
