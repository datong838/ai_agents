## 1. 方案要解决的问题

经营参谋已有指标、态势、方案、任务、执行和复盘能力，但对一家刚接入的新店，首先需要回答的不是“今天执行得怎样”，而是：

1. 这家生意由哪些渠道、实体、商品、客户、推广者、内容、订单和组织能力组成；
2. 当前经营停滞或增长的真正原因是什么，哪些只是表象；
3. 哪些机会值得优先验证，证据是否充分；
4. 应选择哪一种方案组合，成本、风险、停止条件和效果窗是什么；
5. 经人工批准后，应把哪些任务交给增长方案、内容、达人、客户、价格等专业工作台。

本方案把前面对栖月汇私域微商城、栖月汇/裕威参行微信小店、裕威参行抖店的研究经验，蒸馏为可持续运行的 `BusinessInvestigationCase`。具体平台的方法进入 AdapterPack，具体店铺的账号、计划和策略进入 InstanceOverlay，不能写入 AIP 或 Workshop 通用内核。

## 3. 总体架构与分治

```text
经营负责人 / 经营参谋工作区
  └─ 选择渠道 → 经营实体 → 分析记录
      └─ 创建/继续 BusinessInvestigationCase
          ↓ command + exact refs
Workshop L1 投影与交互
  └─ Case 信封 / 三波次 / 数据门 / 成果 / Handoff
          ↓ canonical command
AIP L0 编排与决策控制
  ├─ Task + PlanRevision + TaskRun + Checkpoint
  ├─ ResearchJob / EvidenceBundle / EvalContract
  ├─ ProductionContext / HandoffDecision
  └─ EffectReview / MemoryCandidate
          ↓ DataRequirementRevision
Data OS / Data FDE / Adapter Authority
  ├─ API / Browser Observation / DB Discovery / File
  ├─ Dataset / Data Product / Quality / Cutoff / Lineage
  └─ SourceReadiness + FulfillmentReceipt
          ↓ governed facts
Ontology / Digital Twin
  ├─ BusinessEntity / Store / Product / Customer / Creator
  ├─ Order / Content / Campaign / Relationship / Commission
  └─ snapshot / object set / graph / semantic metric refs
          ↑ exact refs + evidence
AIP 恢复 Checkpoint → 画像 → 问题机会 → 方案候选
          ↓ approved handoff only
GrowthPlan / TaskGraph / 八专业工作台 / Action 治理链
```

### 3.1 不得跨越的边界

- Workshop 不连接 MySQL、SSH 隧道、平台 API、浏览器会话、源表或原始客户明细；
- AIP 不保存源平台 Cookie、Token、密码、数据库凭据或浏览器会话；
- 本体层不复制源系统成为第二数据仓库，只持有治理后的对象、关系、修订和快照；
- Data/Adapter 不决定经营结论，只履行数据需求、质量、语义映射和证据；
- Adapter 不直接获得客户触达、商品发布、改价、签约或结算权限；
- Case、TaskRun、ResearchJob、Action、Evidence、Memory 各自只有一个权威，不得在 BFF、前端或 L1 再造状态机。

## 4. 领域聚合与唯一所有权

| 对象 | 唯一权威 | 用途 |
|---|---|---|
| `BusinessInvestigationCase` | 电商 L1 SolutionPack / PostgreSQL | 绑定组织、工作区、渠道、经营实体、分析类型与当前修订 |
| `BusinessInvestigationRun` | 电商 L1 对 Case 的一次运行，绑定 AIP TaskRun | 一次首次分析、周期复盘或专题分析，不替代 TaskRun |
| `Task/PlanRevision/TaskRun/Checkpoint` | AIP L0 | 长任务、计划、暂停恢复和执行时间线 |
| `ResearchJob` | AIP L0 | 浏览器观察、Schema 推理、外部研究等受治理异步任务 |
| `DataRequirementRevision` | Data/Adapter Authority，AIP 为 requester | 描述需要的事实、关系、指标、质量、时间窗和用途 |
| `DataRequirementFulfillment` | Data/Adapter Authority | 接受、拒绝、部分履行、完成与不可满足的不可变回执 |
| `BusinessDossierRevision` | 电商 L1 | Wave 1 领域制品；只作为既有 `InsightRevision` 的输入证据，不替代 Insight Authority |
| `ProblemMapRevision` | 电商 L1 | 问题树、直接原因、结构根因、反证和假设；采纳后的结论发布为既有 `InsightRevision` |
| `OpportunityMapRevision` | 电商 L1 | 机会、资产、窗口、约束、价值和验证成本；采纳后的决策摘要引用既有 `DecisionSummaryRevision` |
| `SolutionPortfolioRevision` | 电商 L1 | 多方案比较的领域制品；被选方案只能编译为既有 `GrowthPlanRevision` 的新修订 |
| `GrowthPlanRevision(DRAFT)` | 既有电商 Analyst Authority | 唯一方案草案权威；“GrowthPlanCandidate”只作界面/事件语义别名，不新增表、Store、resourceType 或生命周期 |
| `EvidenceBundle/EvalContract` | AIP L0 | 事实覆盖、新鲜度、反证、不确定性和评价合同 |
| `SourceReadiness` | Data/Adapter | 数据源与数据产品是否足以支持当前目的 |
| `HandoffDecision/EffectReview/MemoryCandidate` | AIP L0 | 交接决定、效果评价和经验治理 |
| Workshop 页面 View | Workshop 可重建投影 | 展示和命令入口，不是业务权威 |

`BusinessInvestigationCase` 是电商领域聚合，不进入通用 AIP L0；AIP 只负责通用执行、证据和决策控制。未来非电商领域可以复用 AIP 原语，但拥有自己的领域 Case。

### 4.1 既有 Analyst Authority 复用矩阵

当前 m1 已存在 `InsightRevision → DecisionSummaryRevision → GrowthPlanRevision → TaskGraphRevision → EcommerceEffectReviewRevision` 的 PostgreSQL Authority、Store、迁移与 `/v1/ecommerce-workshop/views/analyst` 只读投影。生意探究只能扩展输入制品与 Case/Run 档案，不能平行复制这条主链：

| 生意探究产物/动作 | 必须复用的既有对象 | 实施约束 |
|---|---|---|
| 画像、问题、机会被采纳 | `InsightRevision` | 新领域制品保留 exact ref；采纳结论经既有 Insight Store 发布 |
| 问题/机会评审结论 | `DecisionSummaryRevision` | 证据链、归因路径、假设、反证和不确定性仍由既有 Authority 保存 |
| 方案候选与人工批准 | `GrowthPlanRevision` 的 `DRAFT → APPROVED` 新修订 | 禁止创建 `GrowthPlanCandidate` canonical resource、表或第二 Store |
| 计划物化 | `TaskGraphRevision` | 只消费 approved exact GrowthPlanRevision，保持 mapping/count 守恒 |
| 效果复盘 | `EcommerceEffectReviewRevision` | 不以 BusinessInvestigationRun 结论替代效果 Authority |
| 工作台展示 | 现有 Analyst v2 聚合 View 的兼容扩展 | 首版新增 Tab/子投影，不另建可争用的 Analyst 页面状态源 |

`BusinessInvestigationCase/Run` 可以作为新的领域聚合，但它只保存业务档案、阶段制品 exact refs 和跨层 Receipt；不得复制上述五类对象的 payload 或状态机。

## 5. 统一身份模型

### 5.1 渠道、经营实体和分析记录

```text
ChannelRef
  └─ BusinessEntityRef (一家具体店铺/机构)
       └─ BusinessInvestigationCase (分析主题与长期档案)
            └─ BusinessInvestigationRun (一次首次分析/复盘/专题)
                 └─ Artifact revisions + TaskRun refs
```

- `ChannelRef`：`private-mall`、`wechat-store`、`douyin-store`、`taobao` 等稳定渠道类型；
- `BusinessEntityRef`：渠道作用域的具体经营实体；同名店铺跨渠道仍是两个实体；
- `Case`：一个可长期维护的分析主题；
- `BusinessInvestigationRun`：一次有独立 cutoff、范围、证据和结果的领域运行；周期任务必须创建新 Run，不能覆盖历史结果；它通过 exact ref 绑定 AIP `TaskRun`，但不复制 AIP 执行状态机。

所有 ID 必须绑定 `org_id + project_id`，服务端从 Principal 推导，客户端不得提交或覆盖租户。

## 6. Case、Run 与三波次状态机

### 6.1 Case 生命周期

长期 Case 只表达业务档案是否仍可继续产生分析记录：

```text
DRAFT → ACTIVE → ARCHIVED → CLOSED
```

- `DRAFT`：主题、经营实体或分析模板尚未冻结；
- `ACTIVE`：允许创建新的首次、周期或专题 Run；
- `ARCHIVED`：保留历史但不再自动创建 Run，可经授权恢复；
- `CLOSED`：业务主题终止，只读封存。

经营画像、问题机会和方案设计的运行状态属于 `BusinessInvestigationRun`，不能直接挂在长期 Case 上，否则周期复盘与专题分析会争用同一个状态。

### 6.2 BusinessInvestigationRun 生命周期

```text
DRAFT
  → SCOPED
  → WAITING_DATA
  → PORTRAIT_RUNNING
  → PORTRAIT_REVIEW
  → DIAGNOSIS_RUNNING
  → DIAGNOSIS_REVIEW
  → SOLUTION_RUNNING
  → SOLUTION_REVIEW
  → READY_FOR_DECISION
  → HANDED_OFF
  → CLOSED
```

横向状态：`PAUSED / BLOCKED / STALE / UNKNOWN / RECONCILING / CANCELLED`。

状态推进必须满足：

1. exact expected version/CAS；
2. 前一阶段产物修订和 hash 精确绑定；
3. EvidenceBundle coverage、freshness、marking 与 Eval 门通过；
4. 当前 TaskRun、Checkpoint 与租户一致；
5. 需要人工决定的门有不可变 Decision；
6. unknown 不得自动转成功，必须 reconcile。

### 6.3 Wave 1：经营画像

输入：冻结的 Case scope、经营实体、平台方法、时间窗、已有本体快照与 DataRequirement。  
输出：`BusinessDossierRevision`，至少覆盖基本盘、商品供应、流量获客、内容达人、交易履约、客户关系、价格利润、组织能力、外部环境，并标出 coverage、quality、freshness、unknown。  
退出门：画像并非“信息很多”即可，必须满足本 Case 的 `PortraitEvalContract`；不满足则回到补数或缩小结论范围。

### 6.4 Wave 2：问题与机会

输入：同版 BusinessDossier、EvidenceBundle、经营问题与假设集合。  
输出：`ProblemMapRevision + OpportunityMapRevision`。每个节点包含 evidence refs、反证、置信度、影响、可逆性、验证成本和仍需补证项。  
退出门：相关性不得包装成因果；根因结论必须记录替代解释和反证。

### 6.5 Wave 3：方案设计

输入：批准进入方案设计的问题/机会 revision。  
输出：`SolutionPortfolioRevision`，包含多个方案候选、组合、目标人群、机制、单位经济、依赖、预算、风险、停止条件、效果观察窗和 Handoff 目标。  
退出门：只发布既有 `GrowthPlanRevision` 的 `DRAFT` 修订；“GrowthPlanCandidate”仅作为产品展示称谓。必须经人工审批产生 `APPROVED` successor revision，并通过 ImpactPreview，才能进入 TaskGraph materialize 与专业工作台。

### 6.6 周期、并发与幂等

- 定时策略属于 Case 的版本化 `SchedulePolicyRef`，每次触发创建新的 Run；
- 触发幂等键固定为 `caseId + scheduleRevision + scheduledAt + analysisType`；
- 同一 Case、同一 analysisType 默认只允许一个非终态 Run，避免周报重叠；
- 专题 Run 可以与周期 Run 并行，但必须有独立 TaskRun、cutoff、budget、Checkpoint 和 artifacts；
- 若上一次周期 Run 尚未完成，新触发进入 `SKIPPED_OVERLAP` 或待人工合并，不能覆盖旧 Run；
- 计划补跑生成新 Run 并记录 `supersedes/triggeredBy`，不修改原计划时间；
- Case 聚合只投影 `latestRunRef/activeRunRefs`，不复制各 Run 的执行详情。

### 6.7 跨层创建与发布的一致性

Case 服务、AIP、Data/Adapter 和本体是独立权威，禁止依赖跨库事务或前端串联。统一采用本地事务 + Outbox + immutable Receipt + CAS：

```text
L1 create BusinessInvestigationRun(PREPARING)
  └─ same transaction append InvestigationRunRequested outbox
       → AIP idempotent compile Task/Plan/TaskRun
       → AIP CompilationReceipt(exact refs + hashes)
       → L1 CAS bind TaskRun and move to scoped/waiting/running
```

- AIP 编译失败时 Run 保持 `PREPARING/BLOCKED`，不伪造 TaskRun；
- AIP 已成功但 L1 回写超时时，通过同 idempotency key 查询 Receipt 并 reconcile，不重复创建；
- Stage candidate 由 AIP 产生后，L1 领域服务验证 schema、scope、evidence、Eval 和 hash，再发布正式领域 revision 与 `ArtifactPublicationReceipt`；
- DataRequirement fulfillment 与 Ontology hydration 都以 Receipt 通知 AIP，AIP 不根据 HTTP 超时猜测成功；
- 所有消费者保存最后 event sequence/watermark，重复事件幂等，乱序事件等待缺口或 reconcile；
- compensation 只撤销可撤销投影/租约，不删除不可变 Task、Run、Evidence、Decision 或 Receipt。

## 7. DataRequirement 逐层履行协议

### 7.1 需求内容

`DataRequirementRevision` 至少包含：

- `purposeCode`：回答哪个经营问题；
- `businessEntityRef`、`channelRef`；
- `requiredFacts`：对象、关系、指标和语义；
- `timeWindow/grain/cutoff/freshnessSla`；
- `qualityThresholds`：完整性、一致性、唯一性、有效性；
- `marking/piiPolicy/minimumPopulation`；
- `acceptableDegradation`：允许缩小到什么范围；
- `requestedOutputs`：Dataset、DataProduct、OntologySnapshot、Evidence refs；
- `requesterTaskRunRef/checkpointRef`；
- `expectedVersion/idempotencyKey`。

### 7.2 履行状态

```text
REQUESTED → ACCEPTED → DISCOVERING → MAPPING → PROFILING
          → PARTIALLY_FULFILLED → FULFILLED
          ↘ REJECTED / UNSATISFIABLE / BLOCKED / STALE
```

Data/Adapter 返回 `FulfillmentReceipt`，而不是把源数据直接回传给 Workshop。Receipt 必须指向：

- source snapshot/cutoff；
- Dataset/DataProduct revision；
- mapping/quality report；
- Ontology projection/snapshot；
- Evidence/lineage；
- unmet facts 与降级原因。

AIP 收到 Receipt 后重建 EvidenceBundle 和 SourceReadiness；门通过后才从原 Checkpoint 恢复。

### 7.3 回执消费与恢复

`FulfillmentReceipt`、`HydrationReceipt` 和 `SourceReadinessRevision` 必须携带同一 requirement exact ref、cutoff、lineage 和 event sequence。AIP 只在三者满足所需输出且同版时 CAS 解除 pending requirement；部分履行只更新 coverage，不自动推进阶段。Receipt 迟到、重复或顺序不明进入 reconcile，历史 Checkpoint 保持可达。

## 8. 平台观察与自省

浏览器看遍前后台、数据库全域探索是高水平自省手段，但正式系统必须包装为治理任务：

```text
ObservationPlanRevision
→ HumanAssistedLogin / SessionLease
→ PlatformCapability + allowlist
→ read-only steps
→ screenshot/DOM/export/schema facts
→ ObservationReceipt
→ Data Product / Ontology / Evidence
```

- 人工可预先登录；AOS 不记录密码、Cookie、Token 或会话 payload；
- 默认只读，允许菜单导航、筛选、滚动、详情查看和受控导出；
- 发布、改价、上下架、触达、签约、结算等进入 ActionProposal→Approval→Lease→Receipt；
- 页面变化、权限不足、验证码、超时必须产生 blocker，不可假成功；
- 微商城 MySQL SSH、微信小店、抖店的路径和语义分别由 L2 AdapterPack 定义；
- 观察结果仍需质量、语义和证据门，截图不是全部经营事实。

共同要求：

- 复合租户身份和 FORCE RLS；
- revision/event append-only；
- current revision 采用 expected version CAS；
- payload hash、source hash 和 exact ref 小写 SHA-256；
- 大证据只保存受控引用，不把截图、PII 或模型响应原文塞入领域表；
- `Case → Run → AIP TaskRun → ArtifactRevision` 有显式 FK/合同检查；
- Case 维护 `latest_run_ref` 与活动 Run 投影，但 Run 状态唯一由 Run 事件推进；
- `(tenant, case_id, analysis_type, trigger_key)` 唯一，周期触发和人工重试均幂等；
- 状态事件与业务产物分离，便于审计和投影重建。

`DataRequirement` 表组由 Data/Adapter 方案决定，本方案不在 Workshop 数据库复制第二份。

## 11. Readiness、失败与恢复

Readiness 至少分轴：

1. `SourceReadiness`：需要的数据产品是否就绪；
2. `SemanticReadiness`：对象、关系、指标和版本是否可解释；
3. `EvidenceReadiness`：required facts coverage/freshness 是否满足；
4. `AnalysisReadiness`：模型、Route、Policy、Eval、Binding 是否在启动截点可用；
5. `HandoffReadiness`：目标工作台、Capability、预算、审批是否可接受；
6. `ActionReadiness`：外部副作用链是否授权。

任一轴失败只阻断依赖步骤，不把未知显示为 0，也不清除已有不可变产物。恢复必须绑定 blocker resolution Receipt，并从最近合法 Checkpoint 继续。

## 12. 安全、隐私与治理

- Principal 从会话确定 `org_id/project_id`；跨租户查询返回不可见而非存在性泄漏；
- PII、客户关系、佣金、医疗/健康相关信息按 marking 和 purpose 最小披露；
- 不保存模型私有推理链，只保存决策摘要、证据链、归因路径、关键假设和不确定性；
- Browser/DB/API 采集均有 scope、cutoff、license/terms、operator 和 Receipt；
- ResearchJob 与 AgentRun 必须使用启动时新鲜 Health/Binding/SourceReadiness；
- 当前 `AOS-000283` 只记录 Workshop 96/96 工程链、W8-12 浏览器合同和 BI-W0 计划整改事实；发布仍为 NO_GO，且不自动授权本新增能力；任何运行 blocker 都不得被本方案覆盖；
- `org-org/dev-project` 是真实正向范围，`dev-org/dev-project` 只能验证隔离失败关闭。

## 15. 验收门

1. 工作台无法提交 SQL、源表、Cookie、Token 或租户；
2. 渠道切换后只返回对应经营实体，跨店铺数据不残留；
3. 周期复盘创建新 Run，不覆盖历史 cutoff 和产物；
4. 三波必须串行，补证和回退创建新 revision；
5. required facts 缺失时进入 WAITING_DATA，不能生成确定性结论；
6. 画像、问题、机会、方案均能回链 exact Evidence 与 lineage；
7. SourceReadiness/Health/Binding 过期立即阻断依赖步骤；
8. `GrowthPlanRevision(DRAFT)` 未产生 approved successor 时不能 materialize TaskGraph；
9. 外部 Action 未经 Proposal/Approval/Lease/Receipt 不发生副作用；
10. `org-org/dev-project` 正向和 `dev-org/dev-project` 负向隔离通过；
11. restart 后 Case、Run、Checkpoint 和历史修订可恢复；
12. unknown/reconcile、late data、撤销和 successor revision 均可审计。
