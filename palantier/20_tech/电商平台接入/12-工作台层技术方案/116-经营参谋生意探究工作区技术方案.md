## 1. 页面定位

“生意探究”是 `经营参谋 · 增长指挥中心` 的默认首 Tab，不是第九个一级工作台。它负责把一次长期经营分析的范围、步骤、数据门、证据、阶段成果和交接状态呈现给经营负责人。

Workshop 只做两类事情：

1. 消费严格、可审计、Principal-scoped 的聚合投影；
2. 把用户的范围选择、暂停恢复、补数请求、阶段评审和 Handoff 决定提交给 canonical API。

页面不得连接平台后台、数据库、浏览器控制器、模型 Provider 或任意 SQL。

### 2.1 视觉稿与技术合同映射

视觉稿已经验证页面层级、信息密度和主要交互，本方案不得在实现时另造一套导航。视觉元素与 canonical 合同的映射如下：

| 视觉稿元素 | 技术合同 | 运行边界 |
|---|---|---|
| “生意探究”默认首 Tab | Module contribution + feature flag | Tab 可见不等于 Case runtime ready |
| 顶部渠道下拉 | `ChannelView[]` | 只返回当前 Principal 可见渠道 |
| 经营实体平铺单选 | `BusinessEntitySummary[]` | 切换后原实体状态必须原子清空 |
| “分析记录”分组下拉 | Case + `BusinessInvestigationRun` summaries | 历史记录只读，不复用其他 Run 产物 |
| Case 信封 | Case/Run exact refs + cutoff + schedule | “演示 Case”不能冒充真实运行 |
| 经营画像→问题机会→方案设计 | canonical PlanRevision + Stage projection | 不能通过点击跳过阶段门 |
| x/y 步与 Checkpoint | AIP TaskRun/PlanRevision/Checkpoint | 不由前端常量或计时器推进 |
| 数据与运行门 | 六轴 Readiness + blockers | unknown 不显示为 0/成功 |
| 当前分析工作区 | Stage artifact/evidence projection | 不展示私有推理链 |
| 计划与定时 | versioned SchedulePolicy + Run trigger | 定时触发新 Run，不覆盖历史 |
| 暂停/继续/补证/评审 | allowed commands + CAS/idempotency | 命令后必须回读同版结果 |
| Handoff 目标 | HandoffEnvelope/Decision | 未批准不进入专业工作台执行 |

视觉稿中的数字、步骤、店铺状态和按钮反馈是产品演示；实施验收必须替换为真实 API 投影，并保留页面已有“演示边界”诚实披露。技术实现可在不改变信息架构的前提下改善无障碍、错误态和响应式布局，但不得删除渠道→经营实体→分析记录三级选择、三波串行和数据门。

## 3. 三级选择模型

### 3.1 渠道视角

顶部渠道下拉来自组织已安装且用户可见的 `ChannelView`：

- 全部渠道；
- 私域商城；
- 微信小店；
- 抖音；
- 淘宝；
- 拼多多；
- 后续由安装贡献的其他渠道。

“全部渠道”首版只用于浏览和筛选实体，不建立跨渠道混合 Case。v1 对 `cross-channel-comparison` analysisType 必须由服务端以稳定 `CROSS_CHANNEL_COMPARISON_NOT_SUPPORTED` 失败关闭；跨渠道比较留待后续独立评审指标口径、币种、时间窗和归因一致性后再开放。

### 3.2 经营实体

经营实体平铺单选，来自 `BusinessEntitySummary`：

```ts
type BusinessEntitySummary = {
  entityRef: ExactRef
  channelRef: ExactRef
  displayName: string
  entityKind: 'store' | 'private_mall' | 'organization_unit'
  readiness: 'case_ready' | 'portrait_missing' | 'integration_pending' | 'data_blocked'
  activeCaseCount: number
  latestCutoff?: string
  blockerSummary?: string
}
```

同名实体在“全部渠道”下追加渠道名；切换实体后必须清空前一个实体的 Case、数字、结论和操作状态，先显示 skeleton/empty，再加载新投影，防止跨店污染。

### 3.3 分析记录

“分析记录”分组下拉：

- 当前与周期：首次全店经营分析、每周经营复盘；
- 专题分析：体验增长、达人销售、商品结构等；
- 已关闭历史：按完成时间倒序，可检索和分页。

每条记录显示名称、Case/Run ID、类型、状态、时间窗、当前阶段/步骤和摘要。已关闭记录只读；重新分析必须创建新 Run 或 successor Case。

## 4. 聚合 View 合同

首版页面只消费一个聚合 `InvestigationWorkbenchView`，避免多个组件自行拼权威：

```ts
type InvestigationWorkbenchView = {
  tenantScope: { orgId: string; projectId: string }
  generatedAt: string
  viewRevision: number
  viewHash: string
  etag: string
  dataCutoff?: string
  authority: { id: string; fixedGit?: string; deliveryStatus: string }
  selection: {
    selectionRevision: number
    channels: ChannelView[]
    selectedChannelRef?: ExactRef
    entities: BusinessEntitySummary[]
    selectedEntityRef?: ExactRef
    records: InvestigationRecordSummary[]
    selectedCaseRef?: ExactRef
    selectedRunRef?: ExactRef
  }
  envelope?: CaseEnvelopeView
  stageRail?: StageRailView
  currentWorkspace?: CurrentStageWorkspaceView
  gates?: ReadinessGateView[]
  artifacts?: StageArtifactSummary[]
  evidence?: EvidenceSummaryView
  timeline?: TimelineEventView[]
  handoff?: HandoffView
  allowedCommands: AllowedCommand[]
  blockers: BlockerView[]
  nonClaims: string[]
}
```

服务端必须返回 Principal 对应租户；前端 strict parser 遇到 tenant、revision、enum、hash 或 required field 不匹配时失败关闭，不用 fallback 示例填充。

渠道、实体、Case、Run 和内容必须来自同一个 `selectionRevision/viewRevision`。切换任一选择时，前端先使旧内容失效，再以完整选择键请求新 View；服务端不得把“新选择器 + 旧内容”拼成混合响应。响应的 ETag 用于只读缓存和命令后精确回读，`dataCutoff` 与 `generatedAt` 分开，避免把页面生成时间误当数据时间。

## 5. Case 信封

信封首屏显示：

- 分析名称、Case ID、Run ID、revision/hash；
- 渠道、经营实体、分析类型；
- scope、time window、cutoff、负责人；
- 当前状态、阶段、x/y 步、Checkpoint；
- 计划与定时、下一次复跑；
- 真实/演示/历史标识；
- Authority 与数据新鲜度摘要。

演示 Case 必须显式 `DEMO`，不能与真实租户运行混合。页面上的计划日期和进度来自服务端投影，不由前端计时器推进。

信封同时显示长期 Case 状态与当前 `BusinessInvestigationRun` 状态：Case 只表达 active/archived/closed，三波阶段、waiting/paused/blocked 属于当前 Run。多个周期或专题 Run 不得共同覆盖一个“当前状态”。

## 6. 三波次进度条

固定三个业务阶段，不固定阶段内部步骤数：

```text
1 经营画像 → 2 问题与机会 → 3 方案设计
```

阶段状态：`not_started / running / waiting_data / waiting_human / blocked / review / accepted / returned / completed`。

- 点击阶段只查看已有产物，不允许绕过顺序启动；
- 未来阶段可预览定义，但不可显示伪造结论；
- 返回上一阶段会显示 revision 差异和 ReturnDecision；
- 阶段完成仅表示产物通过阶段门，不表示经营方案已执行。

## 7. 当前分析工作区

当前工作区回答：

1. 本步要回答什么经营问题；
2. 正在使用哪些数据产品、本体快照和 Evidence；
3. 当前动作由谁承担；
4. 已知事实、分析、假设、建议分别是什么；
5. 哪些冲突、未知和反证影响结论；
6. 缺什么数据、由谁履行、何时可恢复；
7. 本步输出什么 Artifact，进入下一步的 Eval 是什么。

不展示私有推理链；对外只展示决策摘要、证据链、归因路径、关键假设和不确定性。

## 8. 数据与运行门

右侧门控区按轴显示：

- `SourceReadiness`
- `SemanticReadiness`
- `EvidenceReadiness`
- `AnalysisReadiness`
- `HandoffReadiness`
- `ActionReadiness`

状态颜色：绿色完成、蓝色进行、黄色等待、红色阻断、灰色未开始。数字 `0` 只用于有权威计量的业务数量；未知状态必须显示“未知/缺证据”，不能显示 0。

每个 blocker 包含：code、影响步骤、owner、证据、创建时间、恢复条件、resolution receipt。页面不能提供“忽略阻断继续”按钮。

## 9. DataRequirement 交互

用户点击“请求补数”打开经营语义表单，只允许选择：

- 要回答的经营问题；
- 对象/关系/指标；
- 时间窗、粒度和新鲜度；
- 允许的降级范围；
- purpose、marking 和人工说明。

禁止输入 SQL、表名、数据库地址、后台 URL、Cookie、Token、SSH 或任意 Connector 配置。提交后显示 DataRequirement ID、状态、owner、预计输出和 Checkpoint；真正履行在 Data/Adapter 层。

## 11. 允许命令

页面不根据按钮可见性推断权限，服务端返回 `allowedCommands`：

| 命令 | 作用 | 关键门 |
|---|---|---|
| `CREATE_CASE` | 建立 Case | entity readiness、purpose |
| `CREATE_RUN` | 首次/周期/专题运行 | profile、cutoff、idempotency |
| `PAUSE_RUN` | 人工暂停 | current version |
| `RESUME_RUN` | 从合法 Checkpoint 恢复 | blocker resolved、fresh readiness |
| `REQUEST_DATA` | 提交数据需求 | purpose/marking |
| `CONFIRM_SCOPE` | 冻结范围 | maker/checker 视风险 |
| `REVIEW_STAGE` | accept/return/request_more | exact artifact/Eval |
| `PREPARE_HANDOFF` | 准备交接 | approved SolutionPortfolio |
| `DECIDE_HANDOFF` | 接受/拒绝/补充 | receiver reauthorization |
| `CLOSE_RUN` | 封存 Run | terminal state、summary |

任何外部平台操作都不在这组命令中。

所有页面命令只调用经营参谋 L1 Application Service。前端/BFF 不得先调用 Case API、再调用 AIP API、最后自行拼接成功状态；跨层编译、数据履行、领域产物发布和 Handoff 由服务端 Outbox/Receipt/CAS/Reconcile 协调。HTTP 超时后页面显示 `UNKNOWN/正在对账`，先按 idempotency key 查询命令结果，不能再次点击制造重复 Run。

## 12. Strict Web SDK

建议唯一 SDK：

```text
apps/web/src/api/ecommerceInvestigation/
  contracts.ts
  parser.ts
  client.ts
  index.ts
```

具体目录只作为未来开发范围建议，不表示当前创建代码。SDK 要求：

- base URL 固定 `/v1/ecommerce/investigations`；
- GET/POST 清单显式，禁止 generic request；
- POST 自动带 `Idempotency-Key`；
- CAS 命令带 `If-Match`/expectedVersion；
- tenantScope、enum、ISO time、SHA-256、ExactRef 严格解析；
- AbortSignal、timeout、错误 code、retry policy 显式；
- state-changing POST 默认不自动重试；
- AUTH/403/404/409/412/422/429/503 分别呈现诚实状态。

## 15. 路由、安装与 Feature Flag

- 路由仍属于经营参谋模块，不新增一级菜单；
- Tab 由安装的 `workshop-module/v1` 贡献和 feature flag 控制；
- 未安装时不显示；安装但依赖未满足时显示 blocker，不隐藏为成功；
- 唯一 flag namespace：`ecommerce.investigation.read`、`ecommerce.investigation.commands`、`ecommerce.investigation.schedule`、`ecommerce.investigation.handoff`；不得再引入 `workshop.analyst.business-investigation.*` 别名；
- 默认先开 read-only/demo，再按独立波次打开 commands；
- 回滚关闭 command flag，不删除 Case 权威数据。

### 15.1 现有 Analyst v2 兼容路线

当前 m1 已有 `GET /v1/ecommerce-workshop/views/analyst`（operationId `ecommerceWorkshopAnalystViewGet`）、唯一 `api/ecommerceWorkshop` 客户端和 `AnalystPage` 七个只读 view。生意探究必须 additive 接入：

1. 保留现有 operationId、七 view ID、响应字段和 `/workshop/analyst` 路由；
2. 新增 `GET /v1/ecommerce-workshop/views/analyst/investigations`（最终 operationId 在 BI-W0B 冻结）作为嵌套只读聚合，不把多个后端请求散落到组件；
3. 前端 client/parser 继续位于 `api/ecommerceWorkshop` 的领域 SDK 内；可按子目录拆文件，但不得创建第二个 tenant、error、ETag 或 selection 状态机；
4. `BusinessInvestigationTab` 作为现有 `AnalystPage` 的默认首 Tab contribution，Feature Flag 关闭时七 view 行为与合同完全不变；
5. schema 采用 additive minor revision；旧客户端忽略新增可选 contribution，新客户端遇到已声明字段漂移仍失败关闭；
6. BI-W7 必须先跑现有 Analyst v2 parser、client、页面和浏览器累计回归，再验收新 Tab。

### 15.2 计划、重叠与历史运行

- “计划与定时”编辑的是 versioned SchedulePolicy，不直接修改浏览器定时器；
- 周期触发创建新 `BusinessInvestigationRun`，幂等键由 case/schedule/scheduledAt/type 组成；
- 同 Case、同类型存在非终态 Run 时显示“上次尚未完成”，按策略跳过或请求人工合并；
- 专题 Run 可并行，但各自持有独立 TaskRun、cutoff、Evidence 和 artifacts；
- “继续分析”对 paused/waiting 状态执行 resume，对没有 Run 的记录执行 create，不得用同一前端动作模糊两种命令；
- 历史 Run 只读，补跑创建 successor，并显式显示 `supersedes/triggeredBy`。

## 16. 安全与隐私

- UI 不显示 Secret、Cookie、Token、数据库地址和源表；
- PII 默认聚合/脱敏，详情需 purpose + marking + authorization；
- 下载/导出必须独立授权、加 watermark 和审计；
- URL 不携带敏感查询条件；
- 错误信息不泄漏跨租户实体是否存在；
- 所有 command 由服务端 Principal 绑定租户；
- `dev-org/dev-project` 只作负向隔离验证。

## 17. 可观测性

页面和 API 记录：

- request/trace；
- server exact lineageId（不得用 trace_id 替代）；
- Case/Run/Stage/Checkpoint refs；
- command idempotency outcome；
- blocker age、waiting-data age、unknown backlog；
- View 生成 cutoff 和 source revision；
- 用户操作事件仅含安全元数据。

Telemetry Span 为 0 表示缺失证据，不表示业务数量为 0。

## 18. 浏览器验收矩阵

1. 1280/1440/1920 三视口无裁切、重叠和横向隐藏；
2. 键盘可切 Tab、选择渠道/实体/记录、打开证据和关闭抽屉；
3. 渠道切换不残留前一实体数据；
4. 同名店铺在全部渠道视角可辨；
5. 历史记录只读，不出现写按钮；
6. waiting-data 能查看需求与恢复条件；
7. unknown 不显示成功或自动重试；
8. Demo 标识不可隐藏；
9. 403/409/412/422/503 有明确恢复建议；
10. `org-org` 正向和 `dev-org` 负向隔离；
11. 刷新后恢复同 Case/Run/Checkpoint；
12. Handoff 未批准不显示“已执行”。

## 19. 实施波次

| 波次 | 范围 | 退出条件 |
|---|---|---|
| WK-BI-0 | View/Command/OpenAPI/strict SDK 方案冻结 | 无第二 authority、P0/P1 关闭 |
| WK-BI-1 | 只读渠道/实体/记录/Case 信封 | 真实 API、无 fallback、隔离通过 |
| WK-BI-2 | 三波次/门控/时间线/证据只读 | exact refs、unknown 诚实态 |
| WK-BI-3 | pause/resume/request-data/review commands | CAS、幂等、回读、失败关闭 |
| WK-BI-4 | Handoff 与历史封存 | receiver reauthorization、只读历史 |
| WK-BI-5 | 视觉、无障碍、浏览器、故障注入 | 三视口/键盘/错误矩阵 GREEN |

开发前重新核对当前 Authority、m1 工作树和 AIP/Data 依赖；当前唯一开发主线为 m1，但单人串行授权仍不能替代 BI 计划实现授权、迁移门或真实运行门。
