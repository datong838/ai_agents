## 1. 边界与领域真源

达人工作台是 L1 电商领域应用模板，只编排 AIP/O1/Adapter 的 canonical authority，不复制公共 Task、Evidence、Eval、Action 或平台账号真源。领域资产包括：

- `CreatorCandidateRevision`：租户内候选摘要、受控身份别名、来源与 freshness refs；联系方式只保存受控 PII ref；
- `CreatorMatchObservation`：同一特征/模型/策略/证据版本下的评分事实，默认 `PRELIMINARY`；
- `CreatorMatchDecisionRevision`：人工或政策确认、排除、需补证决定，不改写 Observation；
- `OutreachBatchRevision` / `OutreachBatchItemRevision`：批次及候选快照、排除原因、频控/容量/预算预检结果；
- `ContractRef`、`DeliveryRef`、`RelationshipRevision`：只保存受控外部引用、条款 Diff、履约和长期关系事实。

上述 authority 必须 tenant-scoped、append-only revision、CAS/幂等、RLS/FORCE RLS；读取投影可重建，不能成为第二业务真源。

## 2. 五段服务与公共契约

1. **Discovery**：由 frozen CreatorDiscoveryBrief 通过 canonical ResearchJob/Adapter 获得 Artifact；provider、capability、output schema、budget、deadline、lineage 固定为 exact refs。
2. **Evidence Build**：按签名的 creator required-facts profile 计算来源许可、身份、匹配、频控、合同/履约标准的 `complete/partial/blocked/unknown`，生成 EvidenceBundle 与 Build Receipt；调用方不能自报 coverage 或 license 结论。
3. **Matching**：读取同 cutoff 的候选与 Evidence，输出特征、置信度、解释和 evidence refs；低于政策阈值、冲突或缺失信息一律 `PRELIMINARY`，只能人工确认/补证，不能自动淘汰。
4. **Batch prepare/freeze**：收集候选、稳定去重，复核历史联系、渠道频控、账号容量、预算、purpose/marking 和 capability readiness；freeze 固定 candidate/evidence/match/policy/brief/eval exact refs。
5. **start 与后续合作**：不属于 W6-03。W6-04 显式 start 后才创建私信、寄样、合同或佣金 Action；合同、履约和 Relationship 沿同一合作 lineage 追加事实。

## 3. Discovery 与来源治理

`CreatorDiscoveryProfileRevision` 至少冻结允许的 provider/source kinds、使用许可、地理/平台范围、字段最小化、去重键策略、输出 Schema、freshness TTL 和 retention。Research Artifact 必须先通过许可、hash、Schema、恶意内容与 PII gate，再由受控 Normalizer 映射成候选；任意前端 URL、Cookie、Token 或裸联系方式不得进入 ResearchJob manifest、日志、Receipt 或模型上下文。

Provider disabled、许可 unknown/denied、回调验签失败、事件 gap、Artifact hash 漂移或 output Schema 漂移时，Discovery 进入 blocked/unknown/reconcile；不得用历史快照静默替代当前结果。

## 4. 身份、去重与 Match 契约

去重顺序为稳定平台身份 → 已确认 alias → 经政策允许的受控指纹；不同来源的同名/相似账号不能自动合并。冲突形成 `CreatorIdentityConflict` 并保留 originals refs。每次合并、拆分或确认都写 revision/actor/reason/evidence，旧批次因 identity revision 漂移而 stale。

Match 必须固定：candidate revision、Campaign/Brief、EvidenceBundle、feature schema、model/Logic publication、policy revision、cutoff 与 content hash。Observation 与 Decision 分离；评分不是事实真源，解释只展示特征摘要、证据链、关键假设和不确定性，不展示模型推理链。

## 5. OutreachBatch prepare 零副作用契约

`prepare` 只创建/修订草稿批次，不调用 provider、不发私信、不建物流单、不锁佣金、不占用外部配额。每个 item 明确 `eligible / excluded / needs_review / unknown` 及 reason refs；批次统计必须满足输入数量守恒：

`input = eligible + excluded + needs_review + unknown + deduplicated`

`freeze` 使用 expected version/If-Match 和 Idempotency-Key，固化 Brief、Evidence、Eval、ResponsibilityPlan、MatchDecision、FrequencyPolicy、CapacitySnapshot 与 candidate item hashes。任一 exact ref、许可、频控、容量、预算或 capability 漂移即 stale，要求重新 prepare；不得在 start 时静默换版。

## 6. 动作与权限分门

`outreach.send`、`sample.ship`、`contract.accept`、`commission.change` 是四个独立 capability、ImpactPreview、Proposal、Approval、ExecutionLease 与 Receipt 门。一个批准不得跨 capability；`prepare/freeze` 不产生任何 Action/Lease。联系方式、合同和佣金按 purpose/marking 最小披露，Secret 只用 account/secret ref；批量 Action 必须去重、频控并支持 partial/unknown/reconcile。

显式 `start` 必须携带 frozen OutreachBatch expected revision/hash 和独立 Idempotency-Key，服务端在一个 authority 事务中重新验证批次状态、候选 items、Brief/Evidence/Eval/Responsibility/Match/Frequency/Capacity、账号和 capability。验证通过只物化 item-level Action Proposal refs 与 `BatchStartReceipt`；不得在一个 Proposal 中混合四类动作，也不得由 BFF 循环直调 provider。

批次 reducer 只从 item Receipt 聚合，满足：

`started = accepted + applied + failed + unknown + skipped_before_action`

`accepted` 不是完成；`unknown` 禁止自动重放，只允许 provider reread、Webhook 对账或人工 Case。每个 item 独立保留 ActionType/account/Impact/Approval/Lease/Receipt exact refs；批次 `partial` 不覆盖单项事实，也不把未启动项计为失败。

## 7. 合同、履约与长期关系链

`ContractRef` 只指向受控合同 authority，不保存未脱敏全文；`ContractTermDiffRevision` 记录条款版本、差异、金额/佣金、有效期、Evidence 和 maker-checker 决定。`contract.accept` 只能消费已批准的精确 Diff，合同或佣金漂移后旧批准失效。

`DeliveryRef` 连接寄样、内容交付、验收、结算等外部/内部 Receipt；乱序、缺失或结果未知进入 Observation/Case，不猜测已履约。`RelationshipRevision` 只从成熟窗口后的履约、效果和人工观察追加；不得让短期曝光或未对账结果直接覆盖长期关系评级。三者与 Batch、Action、Receipt、EffectReview 保持同一合作 lineage，撤销/纠错以新 revision/compensation 追加，禁止改写历史。

## 8. Module API 与前端读取模型

统一 Module API 的 W2 只读 operation 为 `ecommerceWorkshopCreatorGrowthViewGet` / `GET /v1/ecommerce-workshop/views/creator-growth`，返回 case/timeline 和最小摘要：Brief/Evidence/Eval/Responsibility/Match/Batch exact refs、readiness、blockers、data cutoff 和当前 PRELIMINARY/partial/unknown 状态。W3/W6 commands 才创建领域 Draft、Batch、Handoff 或后续 Action refs；BFF 不直接调用私信、物流、合同 provider。

“五阶段”必须拆成两条正交轴：

- `workflowPhase`：`discovery / evidence / matching / batch_prepare / start`，描述生产与批次准备流程；
- `businessStage`：`candidate / outreach / contract / delivery / relationship`，描述达人合作生命周期。

同一个 creator/item 可以在两轴上同时有状态，服务端不得把两者压进一个 `stage` enum。所有候选、去重、批次、合同、履约、关系数字使用同一 cutoff 与声明分母；`partial/unknown/stale/blocked` 不并入完成，批次聚合不覆盖 item Receipt。

页面保持五 Tab 和既有视觉风格，但正式实现必须展示：

- 来源、许可、freshness、冲突和缺失证据；
- Match 特征摘要、置信度、政策阈值、人工 Decision 与 PRELIMINARY 警示；
- prepare 数量守恒、去重/频控/容量/预算结果和被排除原因；
- `prepare 0 触达`、start 独立门、partial/unknown/reconcile 及可干预入口；
- 稳定 H1、语义 Tab、键盘焦点和受控 PII 披露。

未安装领域 authority 或依赖未就绪时，只显示 loading/empty/blocked/stale/unknown 和明确恢复动作，不注入视觉稿示例数据。

Readiness 分 discovery、evidence-build、match、batch-prepare、outreach、sample、contract、commission、assignee，不使用单一“达人可用”状态。W6-03 只允许前四项达到 code-green；外部动作仍由 W6-04/W5 对应 capability 单独裁决。当前 AOS-000041 已交付 CapabilityBinding/SkillBinding Canonical API/OpenAPI，但真实 binding 与 runnable Agent 仍为 0，BIND1-5 strict SDK/UI/browser 尚未关闭；因此 assignee 继续 blocked，不能因为 6/37/10 定义或 Binding API 存在而点亮。
