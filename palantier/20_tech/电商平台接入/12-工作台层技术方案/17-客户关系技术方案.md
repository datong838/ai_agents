# 客户关系技术方案

> Module：`ecommerce.customer`｜Route：`/workshop/customer`｜Bundle：growth  
> 当前状态：`W6-07 IMPLEMENTATION_IN_PROGRESS / ZERO_CONTACT_RESOLUTION / ZERO_SEND / NO_RELEASE`；当前 P08/JDBC/客户只读专项已 GREEN，唯一开发者正按 [55-W6-07-客户SegmentJourneyDialogue与BatchPrepare预检ADR.md](55-W6-07-客户SegmentJourneyDialogue与BatchPrepare预检ADR.md) 第 7 节收敛 PII 资产并施工 Consent、Segment、Journey、Dialogue 与零副作用 Batch。ProtectedContact、start、发送、Provider、Effect 与 release 属于 W6-08 独立门。

## 1. 身份、隐私边界与真源

`CustomerLite` 由 canonical Customer 的隐私最小化投影产生，复用同一稳定 identity，但不成为联系方式、Consent 或 Preference 真源。客户工作台只能通过受控 exact ref 消费：

- `CustomerLite`：最小业务属性、状态与派生指标；禁止复制 mobile、OpenID、昵称、头像、地址等 PII；
- `ConsentRevision` / `PreferenceRevision`：purpose、channel、scope、granted/withdrawn、effectiveAt、retention、marking 与来源 Receipt；
- `ProtectedContactRef`：仅在获批执行边界由受控 contact resolver 解析，不进入 Segment、Batch item、URL、日志、Evidence 摘要或分享视图；
- `SegmentRevision` / `JourneyRevision`：只存定义、策略和成员查询 revision，不复制成员 PII 列表；
- `TouchpointObservation`：记录已发生触点及 external Receipt refs，不覆盖渠道真源。

P08 映射、全局 PII 分类、source adapter drop 集与 CustomerLite Schema 必须收敛为一个可审计契约。当前 `p08-customer-lite.yaml` 仍声明若干 PII 映射，与运行时八字段 drop 和 CustomerLite 最小化约束漂移；W6-07 编码前必须修复资产、测试和当前 JDBC runtime 的一致性，不能通过恢复 sample-input 回退来让旧测试变绿。

## 2. Segment 权威契约

`SegmentRevision` 固定 definition AST、query/schema hash、source object revisions、cutoff、consent/purpose/marking/retention policy refs、k-anonymity policy、actor 与 content hash。成员集合由查询 revision 在受控服务端计算，结果以稳定 Customer refs、eligible/excluded/unknown 计数和 exclusion reason refs 表达；不落地可导出的 PII 清单。

任一源 revision、Consent/Preference、policy、cutoff 或查询编译器变化使旧 membership snapshot stale。小群体默认只返回聚合；需要逐项准备时必须通过 purpose-scoped 资格判断，未授权、撤回、retention 到期和 unknown 均不得进入 eligible。

旧版 `decision_tag` 与 Widget filter 只能作为迁移输入或解释线索，不能冒充 `SegmentRevision` authority；迁移必须保留来源、规则版本、cutoff 和差异 Receipt。

## 3. Journey 与 Dialogue 契约

`JourneyRevision` 固定阶段图、进入/退出条件、允许触点、间隔/频控、时间窗、预算/容量、渠道候选、停止条件、Eval/Policy refs 和版本。状态跃迁由 Observation/Receipt 驱动；规则变化创建新 revision，不覆写历史客户旅程。

`DialogueBrief` / `JourneyBrief` 是 typed TaskBrief spec；`DialogueEvidenceSelection` 固定客户目的范围内允许使用的 Evidence refs，`DialogueEvalPack` 与独立评估 publication/gate 精确绑定，`DialogueStrategyRevision` 固定策略、模板和失败返回点。文案生成可以动态编排撰写—评估—修改—复评责任，但责任不可消失，且最终 Artifact 必须回到同版 Brief/Evidence/Eval/Responsibility。

连续消息聚合使用场景化 `AggregationPolicyRevision`，保留每条 original message ref、occurredAt、channel sequence、Consent/purpose 变化和 build receipt。摘要只是可重建投影，不能成为第二份客户记录，也不能替代原文授权。

## 4. Customer Dialogue Batch prepare 零副作用

`prepare` 输入 Segment/Journey/DialogueBrief exact refs 与受控 cutoff，稳定去重后逐项计算 identity、Consent、purpose、marking、retention、k-anonymity、Preference、频控、Journey eligibility、strategy/Eval、渠道 capability、账号容量、预算和预计发送量。它只创建 `CustomerDialogueBatchRevision` 与 items：

- `eligible`：当前具备进入 freeze 的全部证据；
- `excluded`：有稳定、可解释的排除原因；
- `needs_review`：需要人工决策或补证；
- `unknown`：关键权威不可确认，失败关闭；
- `deduplicated`：重复目标合并但保留来源 refs。

必须满足 `input = eligible + excluded + needs_review + unknown + deduplicated`。Batch item 只保存 Customer stable ref 与 eligibility evidence，不保存 mobile/OpenID/地址或可直接发送 payload。

`freeze` 通过 expected version/If-Match 和 Idempotency-Key 固化 Segment/Journey/Brief/Evidence/Eval/Responsibility/Consent policy/frequency policy/channel capability/target set/item hashes，并生成 prepare Receipt。prepare/freeze 都不得解析真实联系方式、创建 channel Action、调用 provider 或发送消息；任何 exact ref、Consent、频控、容量、预算或渠道 readiness 漂移都令 Batch stale，必须重新 prepare。

## 5. 显式 start 与触达边界

W6-08 的显式 `start` 才可为 frozen eligible items 创建 channel Action。执行前重新验证 Consent 撤回、Preference、purpose、retention、频控、渠道账号、capability、容量、预算、内容 hash 和审批；由受控 contact resolver 在最小生命周期内解析目标并直接交给 Adapter，Workshop 不回写联系方式。

每项执行必须具备 Proposal/Impact/Approval/Lease/Attempt/Receipt 的独立绑定和幂等键。撤回与 start 并发时以执行前最新 Consent authority 失败关闭；外部结果 unknown 只进入 reread/Webhook/人工 Case/reconcile，禁止重复发送。partial 以 item 状态守恒表达，不能把“批次部分成功”压成整体成功。

### 5.1 Start 线性化与撤回竞态

批次 start 只接受 frozen Batch exact revision、expected version 与 Idempotency-Key，按稳定 item key 排序。每项在 Consent authority 的同一串行化边界内完成：锁定当前 Consent/Preference revision → 复验 purpose/retention/频控/账号/capability → 创建绑定 exact hashes 的 `DispatchAttempt` 与短期 `ContactExecutionPermit` → 记录线性化 sequence。撤回若先取得 sequence，item 变为 `skipped_withdrawn` 且不得解析 contact；DispatchAttempt 若先取得 sequence，本次已获授权，随后撤回立即失效所有未线性化/未获 permit 的 item 并阻断未来触达。UI 和 Receipt 必须展示这个先后关系，不能声称绝对同时。

Permit 为一次性、短 TTL、绑定 customer/channel/purpose/content/account/adapter/attempt hash。Adapter 在实际 dispatch 前向受控 resolver 兑换 opaque dispatch handle；resolver 再验证 permit 未过期/未撤销，直接向受信 Adapter 交付目的地址。Workshop、Proposal payload、任务日志和普通 Receipt 永远拿不到 raw contact。仅在数据库里把 Lease 标记 consumed 后再调用 provider 的现有做法不满足该门，必须先有 durable Attempt/outbox 与可恢复状态。

### 5.2 频控 reservation 与结算

`FrequencyPolicyRevision` 固定 customer、channel、purpose、Journey/campaign、quiet hours、rolling windows、上限、例外、timezone 和 policy hash。start 以 CAS 在这些维度创建 reservation；并发 Batch 共享同一 authority，不能各自计算本地计数。

- provider `accepted/applied`：reservation 结算为已占用触点；
- `failed_before_dispatch`：按政策释放，并保留失败 Receipt；
- `unknown/accepted_pending`：保持占用，直到 signed webhook/reread/reconcile 或 TTL 后进入人工 Case，禁止因超时自动重发；
- withdrawn/skipped：不消费发送额度，但记录排除 Observation；
- compensation/new message：是新的获批 Action，重新走 Consent 与频控，不能复用原 Permit。

通用按 ActionType 的 minute/day guardrail 仍保留为平台保护，但不能替代客户级频控。

### 5.3 Item 状态守恒

每个 frozen item 只有一个当前聚合状态，历史 Attempt/Receipt append-only：`prepared → start_requested → reserved → permitted → dispatching → accepted/applied/failed/unknown/reconciled`，以及 `excluded/skipped_withdrawn/cancelled` 分支。批次视图必须满足 frozen total 等于各终态/进行态与去重项之和；partial 是可查询事实，不是错误字符串。取消只阻止尚未取得 Permit 的 item，已经 dispatching 的 item 必须通过 provider reread/Webhook 确认，不能伪造回滚。

## 6. Handoff 与跨 Module 协作

客服、内容、达人、价格和统一运营之间只交 Customer/Segment/Journey/Case/Artifact scoped refs、purpose、requestedOutcome 与截止时间；接收方记录 accept/reject/request-more Receipt。补充信息由来源重新授权，不复制 Evidence 原文、成员列表或联系方式。关系结果以 Observation/EffectReview 回传，不写来源 Module 表。

## 7. Module API 与前端

Module view 返回受 purpose 限制的 CustomerLite/Segment/Journey/Brief/Evidence/Eval/Responsibility/Batch/Impact refs、readiness、blockers、cutoff、freshness、Consent/retention 决策摘要、数量守恒和 originals reachability。commands 只创建 revision、RecommendationDraft、Batch 或 Handoff；BFF 不计算第二套分群、不解析 contact、不直调渠道。

正式页面需展示 Segment 定义与 revision Diff、Journey 阶段和停止条件、Dialogue 的 Brief/Evidence/Eval/责任生命周期、Batch eligible/excluded/review/unknown/deduplicated 数量、`prepare 0 发送`、Consent/频控/撤回状态、partial/unknown/reconcile 与人工干预入口。小群体只显示聚合；依赖未就绪时诚实呈现七态，不注入静态视觉稿示例数据。

### 7.1 W2-08 只读聚合合同

W2-08 只注册 `GET /v1/ecommerce-workshop/views/customer`（operationId：`ecommerceWorkshopCustomerViewGet`），并以 `customer/segment/journey/dialogue` 四个 view 复用统一 Envelope。Envelope 必须携带 schema/resource revision、evaluatedAt、dataCutoff、stable cursor、source freshness/quality、exact scoped refs、服务端 disclosure decision、typed blockers 与 originals reachability；CustomerLite、Consent、Segment、Journey、Dialogue、Batch 和 outreach readiness 分轴展示，不得压成一个 ready。

`customer` 只返回 purpose-scoped CustomerLite 最小字段与 Consent/Preference/marking/retention 摘要，不返回任何 protected contact；`segment` 固定 definition/query/schema hash、source/policy refs、cutoff、k-anonymity 与 eligible/excluded/unknown/deduplicated 守恒；`journey` 固定定义、阶段、进入/退出、跃迁、停止、容量与失效；`dialogue` 固定 Brief/Evidence/Eval/Responsibility/strategy/original refs，并可读取零副作用 Batch 计数。小群体只给聚合，unknown 不得映射 eligible，Consent 撤回或 retention 到期只使依赖投影 stale，不改写历史。

该端点不得承载 segment build、Journey transition、Batch prepare/freeze、ProtectedContact resolve、start、send 或 provider 调用；不得把“准备完成”显示为“已触达”。完整预检、两轮审查结论和当前阻断见 [89-W2-08-客户CustomerLiteConsentSegmentJourney只读模型预检ADR.md](89-W2-08-客户CustomerLiteConsentSegmentJourney只读模型预检ADR.md)。
