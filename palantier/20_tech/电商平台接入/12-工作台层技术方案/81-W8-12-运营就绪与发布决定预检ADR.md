# W8-12 运营就绪与发布决定预检 ADR

> 日期：2026-08-15  
> 状态：`ENGINEERING_OPERATIONAL_DECISION_CONTRACT_BROWSER_GREEN / RELEASE_DECISION_NO_GO / BACKEND_AND_SECURITY_BASELINE_RED / NO_REAL_TENANT_MUTATION / NO_EXTERNAL_EFFECT / NO_RELEASE`
> 基线：`AOS-000281`、`m1@5b8ca21d914b893634399350662c659846869b5e`
> 证据：`.evidence/workshop/w8-12/`

## 1. 决策

W8-12 是工作台 96 项 DAG 的最终决策门，不是把 W8-01～11 的状态汇总成一个绿色标签。运营就绪必须按 capability 和风险等级逐项裁决；发布决定只对同一不可变候选版本、明确 rollout 范围和有效批准成立。当前 W8-11 未 GREEN、产品正式评审与封板未完成、候选版本和运营 Receipt 不存在，也没有针对该候选的独立发布批准，因此唯一诚实结论是 `NO_GO`。

用户对 W1～W8 的连续开发授权允许在依赖与安全门内持续施工，但不授权真实租户变更、生产 Feature Flag、Provider 副作用或发布。后续收到的发布批准还必须精确绑定 candidate、capability、租户/受众、窗口、残余风险、stop condition 与 rollback owner；泛化的“继续”“完成清单”不能代替它。

## 2. 逐 capability 运营就绪

每项能力独立记录 `READY / BLOCKED / NOT_APPLICABLE`。记录至少包含风险等级、合同/API/SDK/migration、Bundle/Installation/config、tenant/RLS/PII/policy、服务/队列/Provider/账号/容量、浏览器/无障碍、Action/Approval/Lease/Receipt/unknown/reconcile/Usage、SLO/告警/runbook/DR、owner/approver、证据 cutoff 和下一允许动作。

- `READY`：全部适用门在同一候选版本有不可变正负证据，且无阻断性漂移；
- `BLOCKED`：缺失、过期、mixed-revision、unknown、不可复算或依赖未 GREEN；
- `NOT_APPLICABLE`：必须有范围、原因、owner、approver 和 release-bound 证据，不是跳过测试的别名。

平台级汇总不得掩盖某个高风险 capability 被阻断，也不得因只读能力 READY 就放行发布、调价、退款或触达。任一能力只能沿记录的 canary 阶段晋升，不能继承其他能力的 READY。

## 3. Release decision authority

`ReleaseDecision` 至少绑定：

1. Git/authority/artifact/Bundle/Installation/OpenAPI/Alembic/config 与依赖 revision；
2. capability readiness matrix、证据 cutoff 与 drift check；
3. open incident、漏洞、unknown backlog 和已接受残余风险；
4. maker/checker/approver 的身份、权限、时间、范围和到期；
5. rollout cohort、观察窗口、停止条件、kill/rollback/fail-forward/compensation；
6. on-call、支持沟通、审计保留和发布后客户影响/Usage/Effect/reconcile 验证。

候选漂移、mixed-revision 证据、关键安全/租户/Secret/PII/许可/策略异常、超界 unknown 外部动作、kill/恢复/值守不可用或批准缺失/错配均自动 `NO_GO`。`GO` 只授权记录中的阶段和能力；每阶段开始前仍回读 canonical authority。批准到期、撤销、候选漂移或出现新关键证据后，旧 `GO` 自动失效。

## 4. 两轮审查

第一轮发现“整体运营就绪”可能掩盖高风险外部动作未就绪，整改为 capability × risk 独立状态，并为 `NOT_APPLICABLE` 增加严格证据。第二轮发现连续开发授权可能被误读为发布批准，整改为 candidate-bound maker-checker、到期/撤销、rollout 与 stop/rollback 完整合同。

复审结论：合同层 P0/P1 已关闭；实际发布门因 W8-11、产品封板、exact candidate、运营 Receipt 与具体发布批准均缺失而保持 `NO_GO`。本轮未执行代码、migration、数据库、浏览器、真实租户、Provider、Flag、发布或恢复操作，也没有把文档通过冒充 operational ready。

## 6. 验收与停止条件

- 八 capability 必须逐项出现且身份唯一；READY 只能由同 candidate、同 cutoff、同 authority 的完整适用门正负 Evidence 产生，高风险阻断不得被低风险 READY 汇总掩盖。
- `NOT_APPLICABLE` 必须携带 scope、reason、owner、approver 与 release-bound Evidence；缺一即 blocked，不能作为 skipped/deselected/xfail 的替代标签。
- candidate 必须绑定 Git clean、AOS revision、artifact/Bundle/Installation/OpenAPI/Alembic/config hashes 与 W8-11 exact cumulative Evidence；本次实际输入为空，页面必须显示 candidate unknown、W8-11 blocked。
- ReleaseDecision 必须绑定相同 candidate、完整 capability scope、maker/checker/approver、有效期/撤销、残余风险、rollout cohort/窗口/stop condition、kill/rollback/fail-forward/compensation、on-call/支持沟通、审计保留与发布后客户影响/Usage/Effect/reconcile 验证；缺一自动 `NO_GO`。
- 专项、Task Cockpit 既有测试、Web 累计、双端 TypeScript、生产构建、diff check 与内置浏览器均需 GREEN；本波不重跑或改写真实 Backend/Security 基线，不通过清数据、删密钥、自动豁免或降低门槛制造绿色。
- 浏览器必须确认唯一 H1/main、无横向溢出、八 capability 全部 honest blocked、candidate/approval/rollout/Receipt unknown、`NO_GO` 可见且没有状态改变按钮。
- 本波最多签发 `ENGINEERING_OPERATIONAL_DECISION_CONTRACT_BROWSER_GREEN / RELEASE_DECISION_NO_GO / BACKEND_AND_SECURITY_BASELINE_RED / NO_REAL_TENANT_MUTATION / NO_EXTERNAL_EFFECT / NO_RELEASE`；工程清单 `96/96` 只说明施工合同闭合，不说明产品封板、运营就绪或发布完成。
