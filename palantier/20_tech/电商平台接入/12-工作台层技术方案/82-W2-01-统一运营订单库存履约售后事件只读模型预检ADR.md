# W2-01 统一运营订单、库存、履约、售后与事件只读模型预检 ADR

> 日期：2026-08-15
> 状态：`READ_MODEL_CONTRACT_APPROVED / HARD_GATE_BLOCKED / NO_EXTERNAL_EFFECT`
> 基线：`AOS-000035`、`w2-workshop@b1ca41f98507e11afb445cf3939d675ba3bc7b2b`；W3-12 authority 边界重核：`AOS-000039 / w2-workshop@e74b5fd73e9c4a24ee8bbb873d80d6c896e772ab`
> 证据：`.evidence/workshop/2026-08-15-w2-01-unified-operations-read-model-preflight.json`

## 1. 决策

W2-01 使用唯一 `WorkshopViewEnvelope` 聚合订单、订单行、库存、履约、支付、售后事件与 OperationCase 的可重建只读投影，不复制交易 payload，也不成为领域 authority。当前代码只有 `ecommerceWorkshopModulesList` 与 `ecommerceWorkshopModuleReadinessGet`；通用 Ontology list 虽有 Principal scope 与字段脱敏，但缺少 Workshop 的跨源 cutoff、quality、blocker、timeline、稳定 cursor 和 join 守恒，因此不能直接冒充 W2-01。

W1-10、W2-00 均未 GREEN。AOS-000041 下最新真实运行中 OrderLine/P06 已成功，但 Order/P05、ProductSku/P03、Shipment/P07、Payment/P12 仍失败；OperationCase、AggregationPolicyRevision 与明确售后 authority 也不存在。本轮只冻结合同；不新增 API/Store/SDK/UI，不查询或改写真实租户。

## 2. 读模型合同

目标只读 operation 为 `ecommerceWorkshopOperationsViewGet` / `GET /v1/ecommerce-workshop/views/operations`。根 envelope 固定 module/view/route/schema/resource revision、evaluatedAt/dataCutoff、readiness/permissions、lineageRefs 与 partialReasons；内部七个 source slice 各自给出：

- sourceObservedAt/sourceEventAt/projectedAt/cutoffAt，latest run ref/status/error；
- quality/reconciliation、row/active/deleted/unmatched counts 及明确分母；
- stable cursor、确定性排序与 tie-break；
- scoped subject/Evidence/Task/Action/Case refs；
- field disclosure/masking、blockers、next admissible action。

模块级状态与 slice 状态必须同时可见。只有当前合格查询确实返回 0 才是 empty；failed/stale/forbidden/unknown/blocked 不得映射为 0。Order header、line、payment、shipment 与 case 数量口径独立，不能相加；late/duplicate/deleted/partial/unknown 和 unmatched join 必须保留在对账分母中。

## 3. Authority 与安全边界

Inventory 若复用 ProductSku，必须引用批准的库存语义与 revision；售后必须引用批准的 Event/Object 合同，不能从 refund 字段或页面名称推断。L0/O1 原始事件与交易对象保持唯一业务真源；W3-12 可建立 event-sourced L1 OperationCase 聚合 authority、AggregationPolicyRevision 和分类/SLA/kill 决定，但不得复制 originals payload，且 W2 view 不能成为这些 authority。对应 authority 缺失时保持 blocked。

租户只取 verified Principal，拒绝 client org/project/cutoff/readiness/permission/aggregate 注入。raw provider 主键、地址、支付、客户或 Secret payload 不进入 refs、日志或 Receipt。通用 Ontology reader 只能在服务端最小披露聚合中复用，前端只消费 Workshop 唯一 strict SDK。

## 4. 两轮审查与测试门

第一轮发现原方案把 Order/Inventory/Shipment/事件列为同层来源，却没有 slice cutoff、分母与 unmatched 守恒，现已补齐七 slice 和独立 readiness。第二轮发现 core-12 并无独立 Inventory/售后 OT，且通用对象 API 易被误当成完成，现已增加 authority 解析门和 Workshop envelope/SDK 边界。

合同层复审通过；实现必须等待 W1-10、W2-00 GREEN。W3-12 已进一步关闭“L1 Case 是否允许成为 authority”的歧义：允许 Case 作为引用 originals 的事件化聚合 authority，不允许成为交易/事件真源或可变页面投影。届时测试覆盖 strict DTO/SDK、租户/RLS、cutoff/latest-run、五对象 join/unmatched、售后/Case 缺失态、分页排序刷新、正负租户浏览器和 PII/Secret/provider-id 扫描。当前没有实现可测，运行通用 Ontology 测试不能证明 W2-01，故不生成伪测试数、不勾选 Task。命令与可逆聚合细则见 100 号 ADR。

## 6. 2026-08-24 D0 售后 originals 闭环实施方案

> 实施基线：`AOS-000165 / m1@cf3f949`
> 目标：将 `aftersale.event` 从 `contract_only` 升级为可被 W2-01 消费的唯一原始事件 authority，不从 Order/OrderLine 的 refund 字段、页面名称或 Case 投影反推售后事实。

### 6.1 权威表与安全边界

1. 新增 `ecommerce_aftersale_event` append-only 原始事件表，主键为 `(org_id, project_id, event_id, source_revision)`；同一租户的 `source_hash` 、`event_type`、`status`、`occurred_at` 和 exact Order/OrderLine refs 不允许被原地改写。
2. 表开启 `ENABLE/FORCE ROW LEVEL SECURITY`，运行角色只有 `SELECT/INSERT`，撤销 `UPDATE/DELETE/TRUNCATE`，并复用 append-only trigger。
3. 持久化只保存不含 PII/Secret/provider payload 的最小 originals；不存客户姓名、电话、地址、备注、凭证或付款账号。
4. 迁移本轮只交付代码与静态/专项测试，不对真实数据库执行 `upgrade`；downgrade 在表非空时必须 fail closed。

### 6.2 只读端口与 W2-01 组合

1. `EcommerceAftersaleEventReader` 必须使用 `REPEATABLE READ READ ONLY`、Principal 租户 scope、显式 org/project 谓词、timezone-aware cutoff、`limit <= 50` 和 `(occurred_at, event_id, source_revision)` 确定性倒序。
2. reader 只返回 exact ref/hash 与事件时间，不返回 payload；坏 hash、错租户行、天真时间或数据库异常统一 fail closed。
3. D0 descriptor 的售后 `semantic_revision` 升为 2，`persistence_state` 改为 `existing_original`，并绑定本波 exact Delivery Receipt。
4. W2 `aftersaleEvents` slice 仅在 reader 当次读取成功时为 `ready`；合格空集是 0，读取异常仍为独立 `AFTERSALE_EVENTS_READ_FAILED_CLOSED`，不影响其他六个 slice。
