## 2. 第一轮审查：浏览器矩阵与证据绑定

第一轮发现原清单只有“八页浏览器矩阵和真实数据对账”，缺少矩阵维度、每格证据、正式 HTTP、状态适用性和 authority 绑定。整改后冻结：

- 八 Module × 1280/1440/1920 × loading/empty/forbidden/stale/partial/failed/unknown/blocked/ready 的适用矩阵；不适用项写 `not_applicable + reason + contract evidence`。
- 每格记录 release/bundle/installation/module/API/schema revisions、TenantScope/cutoff、DOM/H1/nav/main/aria-current、键盘路径、visible focus、network、console、authority refs 与 screenshot。
- 正向业务证据只认 `org-org/dev-project`；`dev-org/dev-project` 只作零行/不可见隔离。
- Formal HTTP、刷新、深链、后退/前进、租户切换、晚到响应、三视口、200% zoom、reduced motion 和文本替代均进入门。
- 静态视觉稿、file URL、Mock、sample、API 失败关闭、blocked 页和单独截图只能作为负向或局部基础证据。

第一轮结论：`PASS_AFTER_REMEDIATION`。

## 3. 第二轮审查：数据对账、当前事实与误绿

12 个源必须逐项固定 pipeline/schedule/latest run refs、sourceEventAt/projectedAt/evaluatedAt/cutoff、freshness/quality/reconciliation、source/canonical/query counts、matched/unmatched/ambiguous/excluded/unknown/deduplicated，以及 PII/Secret/marking/purpose/retention 决策。页面 headline 和 filter total 必须声明 denominator/cutoff/timezone，并从 UI ref 追到 API/authority exact row 或 Receipt。

当前实时证据只支持：12/12 历史 source 与 query count 相等、canary=0；AOS-000041 下最新 Schedule 已改善为 `7 succeeded / 5 failed`，OrderLine/P06 成功，ProductSku/P03、Order/P05、Shipment/P07 为 `PIPELINE_EXECUTOR_FAILED`，CustomerLite/P08、Payment/P12 为 `PIPELINE_NOT_FOUND`。因此 `DEP-DATA=RED`，历史行或单条改善不能覆盖其余 latest run failure。

本轮重跑通用壳测试为 `5 files / 22 tests passed`，只证明七态、安装导航、租户切换晚到响应隔离与 legacy replacement。W2-01～W2-08 业务 view、W2-09 shared runtime、八页正向 HTTP 与 authority reconciliation 均不存在；不能运行或生成伪正向 EvidencePack。

第二轮结论：`PASS_AFTER_REMEDIATION`。

## 4. 不变量

1. W2-00～W2-09 Receipt 必须与当前 release/hash 一致，不能跨 commit 累加测试数。
2. historical count equality、HTTP 200、页面可打开或 screenshot 不等于数据/业务 GREEN。
3. unknown/stale/invalid/missing/not-comparable/excluded/deduplicated 不补零、不并入成功。
4. 浏览器数值必须绑定 exact denominator/cutoff/source run/authority refs。
5. positive 只认 `org-org/dev-project`；`dev-org/dev-project` 永不作为真实完成证据。
6. API 与 DOM 不得泄露 PII、Secret、provider id、Evidence 正文或 media payload。
7. failed/blocked 是诚实负向证据，不替代 ready 正向。
8. 无真实数据、无业务 view 或无 formal HTTP 时保持 blocked，不用 Mock 越门。

## 5. 解锁条件

## 7. 2026-08-24 实施方案

当前 `m1@afc8438` 已交付 W2-02～W2-09 的 strict contract、bounded reader、Web read page 与 SharedContext 集成。W2-10 不再以历史“无上游实现”停工，而是实现一个可重复、失败关闭、只读的六轴累计判定器。判定器只消费 EvidencePack，不读写业务表、不重跑 pipeline、不发布或切换 installation。

### 7.1 文件级清单

- `scripts/workshop/w2_cumulative_gate.py`：校验 exact release identity、W2-00～W2-09 Receipt 集合、六轴证据结构、P01～P12 数据守恒、八 Module 三视口矩阵、正负租户边界与 fixture/mock 禁止项，生成确定性 GREEN/RED 决定。
- `scripts/workshop/tests/test_w2_cumulative_gate.py`：先覆盖六轴全 GREEN，再覆盖缺 Receipt、跨 release、非真实正向、P01～P12 不完整、canary 非零、矩阵缺格和额外字段等失败关闭路径。
- `.evidence/workshop/2026-08-24-w2-10-cumulative-gate-input.json`：只保存聚合、无 PII/Secret 的当前 evidence manifest。
- `.evidence/workshop/2026-08-24-w2-10-cumulative-gate-decision.json`：保存判定器输出的六轴状态、理由码与缺口；RED 是有效发布决定，不伪写 GREEN。

### 7.2 判定器不变量

1. 输入 schema 必须 exact-key；未知字段、重复 id、空 ref、不同 release/cutoff/tenant 直接 RED。
2. `source_data_green`、`eight_view_runtime_green` 和 `browser_positive_green` 的 GREEN 证据禁止 `fixture/mock/sample/static/file_url/blocked_shell`。
3. 源数据必须恰好 P01～P12，每项 latest run 成功、freshness/quality/reconciliation GREEN，且 source/canonical/query 与 matched/unmatched/ambiguous/excluded/unknown/deduplicated 可对账。
4. 浏览器正向必须覆盖八 Module × `1280/1440/1920` 的 ready 格，其他状态每格要么有验收证据，要么有 `not_applicable + reason + contractRef`。
5. 正向只认 `org-org/dev-project`；`dev-org/dev-project` 必须是零可见的负向 canary。
6. 任一轴 RED 都输出 `NO_RELEASE`，不触发发布、迁移、Provider、pipeline 或业务数据操作。

### 7.3 验证与退出

先跑判定器专项测试，再跑 Workshop API/Web 累计回归、TypeScript/OpenAPI 一致性。浏览器以正式 HTTP 重验八菜单、三视口、唯一 H1/main/nav/aria-current、键盘/focus、刷新、SharedContext 与无写入口；若本地 fixture 被用于视觉回归，只记为负向/视觉证据，不进入三个运营 GREEN 轴。最终交付的是“可重复的累计决定”；只有六轴全 GREEN 才能勾选 W2-10 运营退出门。
