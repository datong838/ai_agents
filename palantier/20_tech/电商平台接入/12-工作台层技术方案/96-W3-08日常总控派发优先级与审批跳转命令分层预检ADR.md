# W3-08 日常总控派发、优先级与审批跳转命令分层预检 ADR

> 日期：2026-08-25  
> 状态：`W3-08_CODE_CONTROL_BROWSER_GREEN / NO_RELEASE / MIGRATION_NOT_APPLIED / NO_EXTERNAL_EFFECT`  
> 范围：基于当前 m1 的 W3-06、W3-07、Task authority 与 Task Cockpit exact approval navigation 实现缺口；只新增 canonical authority、严格投影与测试，不执行真实派发、审批、AgentRun、Action、迁移或发布。

## 1. 结论

日常总控必须是“可解释的意图编排入口”，不能成为第二个任务调度器或审批系统。W3-08 冻结三类独立合同：

1. `DispatchIntentRevision` 保存派发建议、Diff、影响与 exact refs；确认后才调用 W3-06/W3-07 canonical authority；
2. `TaskPriorityDecisionRevision` 保存业务优先级变更，和前端 ViewPreference 排序严格分离；
3. `ApprovalNavigationTarget` 只解析 canonical 审批目的地与 readiness，打开页面不产生 ApprovalDecision。

2026-08-25 独立回读确认：W3-06 canonical module handoff、W3-07 responsibility successor/takeover 与 Task Cockpit approval navigation 已进入 m1；审批投影已经提供 exact target、server `commandReadiness`、required permission、blockers 与 return-focus token。当前真实缺口收敛为：Task authority 只有创建时 priority 字段，没有可审计 reprioritize command；总控没有 immutable DispatchIntent 确认层；工作台尚未把派发/优先级与既有审批跳转组合成严格贡献视图。

本波不复制第二套 Handoff、Responsibility、Takeover 或 Approval authority。DispatchIntent 只冻结建议、Diff、exact refs 与 canonical command descriptor；确认时重新校验 Task/Run/Step/Responsibility/Lease/fence 状态，输出 canonical invocation receipt。由于本波浏览器验收禁止触发真实命令，验收仅覆盖建议、阻断、确认按钮资格与回读模型，不产生任何外部副作用。

## 2. Authority 边界

| 能力 | 唯一 owner | 总控允许做什么 | 禁止做什么 |
|---|---|---|---|
| 派发 | Task/Handoff/Responsibility/Takeover canonical services | 创建 Intent、展示 Diff/影响、确认调用、回读 Receipt | 直接改 owner、复制 Handoff/Responsibility 状态 |
| 业务优先级 | TaskPriorityDecision authority + canonical Task CAS | 提议旧/新值、reason 与 policy | 用拖拽/排序直接写 Task priority |
| 审批跳转 | canonical ActionProposal/Approval authority | 解析 exact target，导航并返回焦点 | 猜 route、在总控本地批准、把打开页面显示成 approved |
| 页面状态 | CockpitReadModel | 从 canonical Receipt 重建 | optimistic owner/priority/approval success |

## 3. 派发合同

`DispatchIntentRevision` 固定 TaskGraph/TaskRun、PlanStep/Attempt、source/target Module installation、ResponsibilityPlan/slot、current/requested assignee、Capability/AgentInstance、Handoff/SLA/Risk policy、Evidence/Context requirement、actor/policy decision、cutoff、expected versions 与 `dispatchBindingHash`。

`ecommerceWorkshopDispatchIntentCreate` 只产生建议、Diff、readiness blockers 和 Receipt，不改变 owner。`ecommerceWorkshopDispatchConfirm` 重新校验 tenant、权限、版本、readiness、职责分离、Handoff allowlist/marking、active Lease/fence 与 Provider unknown；再调用 canonical command。任何 drift 都使旧 Intent stale，禁止静默升级 latest。

## 4. 优先级合同

Task priority 是业务事实，ViewPreference sort/filter 是个人视图，两者不可混用。`ecommerceWorkshopTaskPriorityDecide` 输入至少包含 Task exact ref、old/new priority、reason code、policy ref、expected Task version、cutoff 与 idempotency key；输出 immutable Decision/Receipt 与新 Task exact ref。

服务端校验范围、角色、SLA/risk policy、已终结任务、并发版本和 reason；同 key 同 hash 重放，不同 hash 冲突。批量优先级必须逐 Task 产生 outcome，partial/unknown 不冒充整批成功。当前 canonical Task 无该命令时总控保持 blocked，不用通用对象 PATCH 或前端缓存绕行。

## 5. 审批跳转合同

`ecommerceWorkshopApprovalNavigationResolve` 根据 exact TaskRun/Proposal/Approval ref 返回 `ApprovalNavigationTarget`：route identity、target exact ref、当前 commandReadiness、required permission、blockers 与 return-focus token。它不接受客户端拼接任意 URL。

点击后 canonical 审批页重新校验 TenantScope、maker-checker、slot/顺序/资格、expiry、proposal hash、evidence/preview drift。返回总控时按 token 恢复焦点并刷新 read model；`forbidden/stale/expired/unknown` 显示稳定 reasonCode。导航成功不等于决定成功，Approval accepted 也不等于 Action applied。

## 9. 两轮审查

第一轮发现：旧命令列表把 prioritize、handoff/reassign 和 open-approval 并列成页面动作，未冻结各自 authority，容易形成 BFF 第二状态机。整改后增加 DispatchIntent、TaskPriorityDecision 与 ApprovalNavigationTarget 三合同，并明确总控只组合 exact refs。结论：`PASS_AFTER_REMEDIATION`。

第二轮发现：即使调用 canonical API，页面仍可能通过 optimistic update 把“已受理/已打开”误报为“owner 已变/优先级已生效/审批通过”。整改后所有成功只显示 Receipt，并强制从 CockpitReadModel 回读；导航目的页重新鉴权，打开不等于批准。结论：`PASS_AFTER_REMEDIATION`。

## 10. 2026-08-25 实施与验收闭合
