## 一、设计哲学：任务驱动，不是聊天驱动

### 1.1 为什么不是聊天框？

> 来源：Claude Code 产品哲学深度解析

**核心判断**：国内产品 vs Claude Code 的核心差距 —— 我们做的是"聊天框 + 工具调用"（对话产品），Claude Code 做的是"任务执行框架"（工作流产品）。

| 对话产品（错误） | 工作流产品（正确） |
|---------------|-----------------|
| 聊天框是唯一入口 | 任务列表是入口，聊天只是辅助 |
| 进度条转圈不说话 | Plan Mode 展示方案，用户可编辑 |
| 全文件覆盖式修改 | Diff 视图精确呈现变更 |
| 演示永远是 happy path | 失败处理是第一优先级 |
| 假设模型完美 | 生产环境的 Agent 由最坏情况定义 |

### 1.2 核心数据模型

```
Conversation + Message  ❌  对话产品
Task + Artifact + Action  ✅  工作流产品
```

**客情维护平台的数据流**：

```
用户意图
   │
   ▼
┌─────────────────┐
│ Task（任务）     │ ← 左侧任务列表展示
│ 类型：客户沉淀   │
│ 状态：执行中     │
└────────┬────────┘
         │
    ┌────┴────┐
    ▼         ▼
┌─────────┐ ┌─────────┐
│ Plan    │ │ Artifact │ ← 中间 Plan Mode + 右侧产出面板
│ 执行计划 │ │ 产出物   │
└─────────┘ └─────────┘
    │
    ▼
┌─────────┐
│ Action  │ ← 权限门控确认后执行
│ 执行动作 │
└─────────┘
```

### 1.3 客情维护平台要做的事

| 展示什么 | 为什么重要 | Claude Code 对应机制 |
|---------|-----------|---------------------|
| 私域管家当前在做什么 | 过程透明 = 产品灵魂 | Plan Mode |
| 产出了什么（话术/分层） | 可预测性 > 创造性 | Artifact 机制 |
| 需要什么确认 | 可靠性 > 灵活性 | Permission Gate |
| 历史执行记录 | 信任是被建构的 | Checkpoint |
| 失败如何处理 | 由最坏情况定义 | Verification Loop |

## 一点五、技术决策：不走画布编辑，采用固定布局 + 组件复用

### 1.5.1 决策结论

客情维护平台**不使用 CanvasPage 画布编辑器**，采用独立的固定三栏布局页面，但**复用画布的视觉和组件基础设施**。

### 1.5.2 为什么不走画布编辑？

画布编辑器的核心定位是**配置态**（用户搭页面、摆组件、配属性），而客情维护平台的核心定位是**运行态**（任务驱动、实时进度、Artifact 产出）。两者在数据模型上有本质差异：

| 维度 | 画布编辑（CanvasPage） | 客情维护平台 |
|------|----------------------|-------------|
| **数据模型** | `CanvasNode[]` 静态配置，持久化到 `Module` | `Task[]` 动态运行时对象，由 TAOR 循环驱动 |
| **布局方式** | 自由拖拽，用户可调整组件位置和大小 | 固定三栏（25%/45%/30%），不支持拖拽 |
| **组件类型** | 13 种 `CanvasKind`（table/filter/graph/metric...） | 业务专属组件（task-list/artifact-panel/permission-gate） |
| **模式切换** | 三种模式（widget/workflow/preview） | 单一模式：任务执行态 |
| **持久化** | JSON 结构保存到 `Module` | 运行时状态，通过 TAOR 循环管理 |
| **底部区域** | 9 Tab 内容展示区 | 固定快捷看板（单行指标） |

如果硬套画布，会出现：
1. 每个任务都要变成一个 `CanvasNode`，但任务有执行状态、日志、权限门控等画布没有的概念
2. 拖拽自由布局对任务流没有价值，反而增加认知负担
3. 底部 9 Tab 在客情维护场景下几乎全部空置

### 1.5.3 复用哪些基础设施？

虽然不走画布编辑，但复用以下视觉和组件基础设施，避免重复造轮子：

| 复用项 | 来源 | 客情维护平台用途 |
|-------|------|-----------------|
| `BpCard` 基础组件 | 全局 Bp 组件 | 任务卡片、产出卡片（圆角 2px） |
| `BpTabs` 组件 | 全局 Bp 组件 | Artifact 面板的 Tab 切换 |
| `.bp-hover-card` 类 | 全局 CSS | 任务列表悬停反馈 |
| 顶栏布局 | `BpShell` 已有顶栏 | 标题 + 新建任务按钮 + 刷新 |
| 侧边栏导航 | `nav.ts` 注册机制 | 工作台目录下新增菜单项 |
| 路由机制 | `routes.tsx` | 新增 `/workshop/customer-relations` |
| Widget 注册思路 | `WidgetPreview` 渲染器参考 | 客情维护专用 Widget 的 props 接口设计参考 |

### 1.5.4 新增组件清单

客情维护平台的新增组件均为**业务专属组件**，不复用 `CanvasKind` 体系：

| 组件 | 职责 | 对应画布能力 | 差异 |
|------|------|-------------|------|
| `TaskListPanel` | 任务列表 | 无对应 | 画布无任务概念 |
| `TaskDetailPanel` | 任务详情（Plan/进度/日志） | 无对应 | 画布无执行计划概念 |
| `PermissionGatePanel` | 权限门控（Diff 视图） | 无对应 | 画布无权限概念 |
| `ArtifactPanelWidget` | 产出面板 | 最接近 `metric` 但语义不同 | 画布 metric 是静态指标，这里是动态产出 |
| `TaskLogTimeline` | 日志时间线 | 无对应 | 画布无日志概念 |
| `Customer360CardWidget` | 客户画像卡片 | 最接近 `detail-drawer` | 画布是抽屉式，这里是嵌入式 |
| `AIInsightPanelWidget` | AI 洞察面板 | 无对应 | 画布无 AI 洞察概念 |

## 三、三个核心区域详细设计

### 3.1 区域一：任务列表（左侧）

**功能**：展示所有数字同事的任务状态，是客情维护平台的入口。

**组件**：`TaskListPanel`

**数据结构**：
```typescript
interface TaskCard {
  id: string;
  agent: string;           // "private_manager" | "shopping_advisor" | ...
  agentName: string;       // "私域管家" | "导购顾问" | ...
  title: string;           // "客户沉淀（30人）"
  status: TaskStatus;      // "running" | "awaiting_approval" | "completed" | "failed"
  currentStep: number;     // 2
  totalSteps: number;      // 4
  updatedAt: string;       // ISO 时间
  priority: "low" | "medium" | "high" | "critical";
}
```

**视觉设计**：
- 每个任务一张卡片，高度 72px
- 状态图标：🔵 进行中 / 🟡 待确认 / ⚪ 待启动 / ✅ 已完成 / ❌ 失败
- 选中态：左侧 3px 蓝色边框 + 背景色 `#f0f4ff`
- 悬停态：背景色 `#f5f5f5`（bp-hover-card）
- 卡片圆角：2px（Foundry 规范）
- 字体：13px 标题 / 12px 副标题 / 11px 时间

**交互**：
- 点击卡片 → 中间区域切换为对应任务的详情
- 右键菜单：暂停 / 取消 / 查看日志
- 拖拽排序：长按拖拽调整任务优先级

**筛选**：
- 全部 / 进行中 / 待确认 / 已完成
- 按数字同事筛选（私域管家 / 导购顾问 / 内容官...）

**功能**：展示当前选中任务的执行计划、进度、日志、权限门控。

**组件**：`TaskDetailPanel`（内部含多个子面板）

**日志级别**：
- `info`：灰色，常规执行信息
- `success`：绿色，步骤完成
- `warning`：黄色，验证失败但已自动修复
- `error`：红色，需要人工干预
- `checkpoint`：蓝色，检查点标记

**交互设计**：
- **批准并导入**：执行 Step 3，发送企微好友申请
- **编辑话术**：展开编辑器，可逐条修改话术（Diff 视图高亮变更）
- **跳过**：跳过此 Step，进入 Step 4
- **推迟**：保留任务状态为"待确认"，稍后处理

**Diff 视图**：
- 变更精确呈现，不是全量覆盖
- 绿色 = 新增/修改的内容
- 红色 = 删除的内容（如截断的超长部分）
- 灰色 = 未变更的内容

## 五、与 Claude Code 理念的映射

| Claude Code 机制 | 客情维护平台实现 | 所在区域 |
|-----------------|---------------|---------|
| **Plan Mode** | 中间区域的可编辑执行计划 | 区域二 |
| **Diff 视图** | 权限门控面板的话术预览（精确呈现变更） | 区域二（权限门控态） |
| **Permission Gate** | 步骤级别的 [批准]/[编辑]/[跳过] | 区域二（权限门控态） |
| **Task + Artifact** | 左侧任务列表 + 右侧产出面板 | 区域一 + 区域三 |
| **Checkpoint** | 日志流中的检查点标记 | 区域二（日志面板） |
| **Verification Loop** | 产出面板中的"合规 30/30"检查 | 区域三 |
| **TAOR 循环** | 任务状态的流转（planning → executing → completed） | 区域一（状态图标） |
| **Trust Trajectory** | 新用户高频确认 → 老用户基本自动化 | 权限门控的渐进式放松 |
