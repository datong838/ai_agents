### 3.1 目标

1. 建立不可变 Bundle Registry 和 canonical manifest 验证。
2. 建立确定性依赖解析、Composition Request 和精确 Lock。
3. 建立租户安装计划、批准、dry apply、verify 和 rollback 状态机。
4. 建立通用 Evidence 证据引用与接入实例阶段计算。
5. 把 FDE 资产页和接入案例页从静态/Mock 改为真实 API 页面。
6. 用最小电商包骨架验证通用平台的装箱边界，不实施 Niushop 业务数据。

### 3.2 非目标

- 不开发电商 G0～G6 业务逻辑。
- 不连接、读取或写入栖月汇生产数据库。
- 不实现任意外部 URL/用户上传压缩包的远程发布；M0 只从服务端 allowlist `bundles/` 和测试 fixture 加载受控内容索引。
- 不执行 Bundle 中的任意 Python/SQL/脚本。
- 不实现真实领域 migration apply；M2 只产生并批准 migration plan/hash。
- 不启用生产 Action、Automation、对外发布或业务写回。

### 3.3 M0 真实完成

## 5. Canonical Manifest 契约

### 5.1 允许的 `kind`

```text
DomainPack
SolutionPack
VerticalPack
PlatformAdapterPack
PluginPack
```

`PlatformRelease` 仍归 Apollo Release；`BundleComposition` 是解析结果；`InstanceOverlay` 是租户实例修订，三者都不作为普通 FDE Bundle 发布。

### 5.2 必填字段

```yaml
apiVersion: aos.dev/v1alpha1
kind: SolutionPack
metadata:
  id: solution.example
  version: 1.0.0
  displayName: Example
  publisher: aos
  license: internal
spec:
  platformApi: ">=1.7.0 <2.0.0"
  dependencies: []
  optionalDependencies: []
  conflicts: []
  exports: {}
  capabilities:
    provides: []
    requires: []
  permissions:
    roles: []
    markings: []
    dataScopes: []
    actionTypes: []
  migrations:
    plan: null
    downgradePolicy: retain-canonical
  preflight: null
  regression: null
  rollback: null
```

`content_hash` 由服务端对受控内容清单和 canonical manifest 计算，不信任客户端自报值。`signature` 是发布包的独立签名封装，不参与被签名内容的 hash 计算。

M0 的内容来源只支持服务端受控 `bundle://` 引用，指向仓库 allowlist `bundles/` 或测试 fixture。`manifest_loader` 自行枚举文件、计算 path/digest/size/media_type 内容索引并验证签名；API 不接受本地绝对路径、任意 URL 或客户端自报文件 hash。远程上传/对象存储发布需后续独立供应链方案。

### 5.3 M1 包内验证证据约定

M1 为避免 Loader、RegistryService 和 M5 夹具各自猜测文件名，冻结以下最小包内约定：

```text
bundle.yaml
bundle.signature.json
evidence/
  sbom.json
  bundle-evals.json
```

- `bundle.signature.json` 是 Ed25519 签名封装，包含 `algorithm/keyId/signature/signedAt`；它不进入被签名的 `content_hash`，避免签名自引用。
- `bundle.yaml` 的 canonical JSON 与除签名封装外的全部受控文件索引共同生成 `content_hash`；`evidence/sbom.json` 和 `evidence/bundle-evals.json` 因此都被内容签名覆盖。
- `evidence/sbom.json` 必须是对象，至少声明 `format` 和 `components[]`；Loader 只保存摘要和状态，不把大 SBOM 写入业务表。
- `evidence/bundle-evals.json` 必须是对象，只有 `status=passed` 且 `failed=0` 才生成 `bundle_evals=valid`；缺失、格式错误或失败结果不得伪绿。
- SBOM/Evals 文件自身不能单独证明可信；只有同一版本的 `content_hash`、publisher trust root 和 `signature_verification` 同时有效，Service 才允许 `validated/published`。
- 后续可扩展远程证据签发器和 DSSE/SLSA，但不得改变 M0 的失败关闭语义。

### 5.4 安全验证

- Bundle ID 只允许小写字母、数字、`.` 和 `-`；禁止路径分隔符。
- export/migration/eval/rollback 路径必须在 Bundle root 内，解析真实路径后再次检查。
- Manifest 禁止出现密码、Token、私钥、数据库 URL 和真实 `secretRef` 值。
- `permissions` 只是声明，不代表已授权；安装时生成 diff 并单独批准。
- `published` 要求 content hash、Ed25519 签名、publisher trust root、SBOM/Evals 证据全部有效。
- 未签名开发包可保存为 `draft`，但不得进入 approve/apply。

### 5.5 M1 生产可信根与安全读取补充契约

- 生产可信根只允许来自服务端部署挂载的只读 JSON，例如 `AOS_BUNDLE_TRUST_ROOTS_FILE`；API、Header、Query、Body 均不得上传或覆盖可信根。
- 每条可信根严格绑定 `publisher + keyId + Ed25519 publicKey + notBefore + notAfter + revokedAt + revision`；配置缺失、不可读、重复键、未知字段、无效时间或公钥全部失败关闭。
- `signature_verification` evidence 必须记录 `trustRootRevision`，`expiresAt` 取可信根 `notAfter`；validate/publish 均使用当前可信根重新验签，不能只相信历史 `valid` 状态。
- `signature_verification.artifactHash` 固定为服务端对持久化 signature envelope canonical JSON 的 SHA-256；validate/publish 必须重新计算并与 evidence 绑定，禁止替换 envelope 后沿用旧证据。
- 可信根缺失/未知/过期/撤销表示包不可发布，返回稳定签名错误；可信根配置损坏、文件临时不可读等服务端故障返回稳定 `TRUST_ROOT_UNAVAILABLE`/503。只读 Registry 目录不因可信根故障失效。
- validate/publish 必须先探测当前可信根 Provider 可用性，再判定历史 evidence，并在放行前完成当前可信根复验，避免服务端故障被旧 `invalid` evidence 遮蔽成客户端 400；版本创建期间若 Provider 明确故障，也返回 503 且不得写入半成品版本。
- 旧实现按 signature 文件原始字节计算的 evidence hash 不具备 canonical envelope 语义，升级后不得兼容放行；迁移只对仍可变的 `draft/validated` 版本依据数据库内持久化 envelope 重算 canonical hash 并标记 `canonical-envelope-v1`，畸形 envelope 继续失败关闭；终态版本不改写，只保留为历史目录记录。
- 私钥不进入平台配置、数据库、Bundle 或测试提交；测试私钥只在测试运行时生成。
- Bundle 读取必须从 allowlist root 的目录 fd 开始逐级使用 fd-relative open 与 `O_DIRECTORY/O_NOFOLLOW`；枚举和读取基于已打开 inode，禁止“先 realpath 检查、再按完整路径打开”造成中间目录换链竞态。

## 6. PostgreSQL 真源模型

### 6.1 M1 Registry 表

| 表 | 主要字段 | 不可变/约束 |
|---|---|---|
| `asset_bundle` | publisher、bundle_id、kind、display_name | `publisher + bundle_id` 唯一 |
| `asset_bundle_version` | version、manifest_json、content_hash、signature、status、created_by | `bundle + version` 唯一；published 禁止 update/delete |
| `asset_bundle_dependency` | version_id、dependency_id、version_range、optional | 由 manifest 投影，不允许手工编辑 |
| `asset_bundle_artifact` | version_id、relative_path、artifact_ref、digest、size、media_type | 只保存受控内容索引；禁止未校验 URL/绝对路径 |
| `asset_bundle_evidence` | version_id、type、artifact_ref、artifact_hash、status、expires_at | 证据元数据不放大文件/秘密 |
| `asset_bundle_version_event` | version_id、from_status、to_status、actor、reason、evidence_revision、evidence_snapshot、created_at | append-only；状态迁移、操作人、原因与当时 evidence canonical 快照同事务 |

M1 的 validate/publish 门禁必须在单个数据库事务内锁定 bundle、version 及该版本全部 evidence，基于锁定快照重新执行 content hash、当前可信根、签名、SBOM/Evals 和职责分离检查，再更新状态并追加 lifecycle event。禁止 Service 事务外先检查、Store 另开事务迁移状态的 TOCTOU 结构。

`evidence_snapshot` 的增量迁移采用诚实兼容语义：升级前已存在的 lifecycle event 以 `NULL` 明确表示“历史快照未捕获”，不得用空数组伪装已重建；迁移完成后数据库触发器禁止任何新事件写入 `NULL`，并核对事件快照等于同事务锁定的当前 evidence。Store/Service 回读非历史事件时必须复验 evidence 结构、稳定排序、唯一键和 `canonical_sha256(snapshot) == evidence_revision`。任何迁移后事件存在时均阻断降级，避免静默丢失审计快照。

新事件的 `evidence_revision` 还必须在 PostgreSQL 触发器内由 `evidence_snapshot` 重新计算并逐字相等，禁止仅校验“合法 SHA-256 格式”。数据库 canonical JSON 采用应用专属的递归 JSONB 序列化函数：对象键按 `C` 排序、数组保持顺序、标量使用 JSON 表示；摘要使用 `pgcrypto.digest(..., 'sha256')`。升级迁移执行 `CREATE EXTENSION IF NOT EXISTS pgcrypto`，扩展不可用或迁移角色无安装权限时失败关闭；升级后必须用代表性 Unicode、嵌套对象、数组、布尔、空值和数值样本验证数据库结果与 Python `canonical_json` 一致。降级只删除 AOS 自有 canonical 函数，不删除可能被其他模块共享的 `pgcrypto` 扩展。

Registry 目录和包元数据允许全局读，但普通 GET 默认不得暴露 evidence 内部 metadata、生命周期 actor、事故 reason 或完整 evidence snapshot；这些字段只供服务端门禁和后续独立审计权限接口使用。

### 6.2 M2 Resolver/Installation 表

| 表 | 主要字段 | 约束 |
|---|---|---|
| `bundle_composition` | tenant、composition_id、request/snapshot/current-ref 正文与 hash、resolver_version | tenant+id；等价输入去重；identity immutable |

## 7. 状态机与并发契约

### 7.1 Bundle Version

```text
draft → validated → published → deprecated
                         └→ revoked
draft|validated → rejected
```

- `validated` 由 schema/hash/signature fixture/SBOM/Evals 证据计算，不接受 body 中的 `validated=true`。
- `published` 之后 manifest/content hash 不可修改；只能发布新版本。
- `revoked` 禁止新安装，并计算受影响 installation。

### 7.2 Installation Revision

```text
draft → submitted → approved → applied → active → rolled_back
                  └→ rejected
```

每个 mutation 要求：

- `Idempotency-Key`。
- create 以外使用标准强 `If-Match` ETag；成功动作插入 N+1 immutable revision 并增长 `etag_version`。
- Principal 的 org/project/subject/roles/markings。
- 状态迁移 allowlist。
- submit/approve/apply/verify 事务内重验 lock 所选精确版本仍 published、证据/current trust root 仍有效。
- 事务内写 immutable revision、当前/active/previous 指针、approval/evidence、append-only event 和幂等 receipt。

并发竞争中只有一个请求成功；其他返回 `409 REVISION_CONFLICT`，不自动覆盖。

### 7.3 职责分离

- Registry 全局可读；所有写操作必须同时满足角色与目标 publisher scope。scope 只取已经验签的身份 claim `asset_publishers`，请求中的 publisher 仅是目标标识，不能赋权。
- 普通 `admin` 不自动获得全部 publisher；只有显式 `asset-registry-admin` 且 scope 含 `*` 才拥有平台级发布者写权限。生产身份缺 publisher scope 时失败关闭。
- Bundle 创建者可执行 validate；publish actor 必须同时不同于 `created_by` 与 `validated_by`，形成最小两人 maker-checker。deprecate/revoke 要求目标 publisher 权限、非空 reason，并与状态变更同事务审计。
- publisher 可注册/提交 Bundle version；installation submit 仍必须满足 M2 独立角色、marking 和 Principal 门，发布者身份本身不赋予安装审批权。
- installation requester 不能批准自己的同一 revision。
- approver 批准的是精确 lock + permission diff + migration plan hash，且 Principal markings 必须覆盖目标 marking；`admin` 不绕过 maker-checker 或 marking。
- apply/verify 只消费已批准 revision，body 不允许覆盖 lock 或 diff。

## 8. 依赖解析与 Lock 算法

### 8.0 M2 公共契约前置冻结

M2 并行编码前先冻结以下公共契约，Worker 不得各自猜测：

完整字段、hash payload、解析预算、immutable installation revision、CAS/幂等、DDL trigger、角色/marking 和测试边界以专项规范 [228-M2 Resolver、Lock 与 Installation 公共契约冻结方案](228-M2-Resolver-Lock-Installation公共契约冻结方案.md) 为唯一实施真源；本节只保留摘要。两者冲突时先修正文档，不允许代码自行选择。

1. `RegistrySnapshotReader` 必须在单个数据库只读快照中读取全部仍为 `published` 且证据当前有效的候选，并由服务端计算 `registrySnapshotHash`；禁止 `list + N 次 get` 拼接快照。
2. `CompositionRequest/RegistrySnapshot/ResolvedBundle/CompositionLockPayload/StoredCompositionLock` 使用 strict DTO、camelCase alias 和 `extra=forbid`；公共导出由总控统一修改。
3. `signatureFingerprint` 固定为当前有效 `signature_verification` evidence 的服务端 `artifactHash`，不得使用客户端字段或仅用 `keyId`。
4. `currentInstallationRef` 解析时固定为 `installationId + revision + lockHash + overlayRevision` 的不可变快照并进入 lock hash，禁止把可变引用直接写入 lock。
5. Manifest 的 navigation/API/UI contribution 必须从已签名内容派生结构化索引后才能做真实冲突检测；无数据来源时不得伪称检测通过。

完整 Registry snapshot 落在 composition 真源，snapshot hash、规范化请求、最终 selected candidates、依赖边、capability provider、diff、resolver version 和当前 installation 固定 revision 进入 canonical lock payload。`compositionId`、revision、时间戳及 `lockHash` 自身不得进入 hash。解析采用固定排序、最高稳定版、全图确定性回溯和资源上限；optional dependency 仅在顶层显式请求其目标时启用。

### 8.1 输入

```json
{
  "requested": [
    {"publisher": "aos", "id": "solution.ecommerce.growth", "version": "1.0.0"},
    {"publisher": "aos", "id": "platform.ecommerce.niushop", "version": "1.0.0"}
  ],
  "platformApiVersion": "1.7.0",
  "platformRelease": "aos-platform/1.7.0",
  "environment": "dev",
  "currentInstallationRef": null,
  "registrySnapshotHash": "sha256:..."
}
```

org/project 从 Principal 注入，不信任 body 中的租户值。

### 8.2 确定性规则

1. 候选版本只来自指定 registry snapshot 的 `published` 且未 revoked 版本。
2. 先约束 platform API，再解析必选依赖，最后处理显式请求的 optional dependency。
3. 同一依赖的多个范围取交集；交集为空返回冲突路径。
4. 多个可行版本选择最高稳定版；相同 SemVer precedence 按 version/publisher/id/content_hash 升序并选第一项。
5. 检测依赖循环、显式 conflicts、capability 唯一提供者冲突和路由/导航占位冲突。
6. resolved 列表使用固定排序、canonical JSON 和 SHA-256 生成 lock hash。

### 8.3 输出

Lock 必须包含：

- 请求包与精确 resolved 包的 `publisher/id/version/content_hash/signature_fingerprint/release_evidence_revision`。
- platform release/API 版本。
- registry snapshot hash。
- capability providers。
- permission diff 与 hash。
- migration plan 与 hash。
- contribution diff 与 hash。
- UI/API/navigation contribution diff。
- lock hash 与 resolver version。

## 14. M1～M5 分波实施与退出门

### M1：Registry 真源与 Manifest 安全（已完成）

**实施：**

- 契约、schema、canonical JSON/hash、SemVer、Ed25519 verifier、路径/敏感信息扫描。

- publish/deprecate/revoke 状态和不可变保护。
- 旧 Apollo Asset 保持原状，不做双写。

**退出门：**

- schema/hash/签名/SemVer/路径穿越/敏感字段单测通过。
- 已发布版本 UPDATE/DELETE/覆盖全被拒绝。
- 跨 publisher create/validate/publish/deprecate/revoke 全部失败关闭，Body/Query 伪造 publisher 不能扩大身份 scope。

- 同一主体创建并发布被拒，不同发布主体成功；规则和审计事件重启回读后仍成立。

- 中间目录换链不能读取 allowlist 外文件。
- 直接 SQL 写入“正确 evidence snapshot + 任意 revision”必须被数据库触发器拒绝，且拒绝后版本仍可正常回读；数据库与 Python canonical hash 交叉样本必须完全一致。
- OpenAPI 确定性、无重复 operationId、迁移 upgrade/downgrade 门通过。
- 累计 Web/Desktop 门必须同时通过；共享 Web 源码不得使用 Desktop `ES2020` 类型库不支持的 `ErrorOptions` 构造签名。兼容补丁仅保留相同错误消息并显式挂载 `cause`，不得改变 dry-run 成功/失败语义。

### M2：Resolver、Lock 与 Installation 控制面（M2-A0 GREEN，M2-A1 已授权）

**实施：**

- M2-A0 已完成：signed contribution claims、严格 composition/lock/installation DTO、稳定错误与 Schema、七张 PostgreSQL 真源表、immutable/hash/指针历史不变量。
- M2-A1 Core：单事务 Registry snapshot、共用 release policy、依赖图、版本交集、capability/conflict 检测、确定性 lock、permission/migration/UI/API diff 与真实 PostgreSQL Store。
- M2-A 专项与 M1 累计回归全部通过后，才进入 M2-B。
- M2-B Control Plane：全量 immutable installation revision/event/approval、持久化幂等、职责分离、marking、ETag/CAS 和状态机。
- dry apply/verify/rollback，不执行 Bundle 代码、migration 或外部调用；关键动作重验 exact selected bundles 的发布、证据与 trust-root 状态。

**退出门：**

- 随机输入顺序不改变 lock hash。
- 缺依赖、循环、版本/capability/路由冲突都返回可解释错误路径。
- 自批、旧批准重放、CAS 冲突、幂等冲突、跨租户全部失败关闭。
- 同 key 同请求并发只提交一份数据；lock/revision/approval/event/receipt 直接 SQL 篡改全部失败。
- active → rollback 恢复前 revision，事件链可追溯。

### M3：FDE 资产页真实化

**实施：**

- 页面切换 canonical API，移除隐式 Mock fallback。
- kind/status/publisher 列表、详情、依赖图、diff、composition resolver、installation history。
- 真实加载/空/错误/禁用/无权限状态。

**退出门：**

- 组件、API mock 契约、前端类型和构建通过。
- 浏览器验证空 Registry、API 500、依赖冲突、未签名包禁用、resolve 成功、刷新回读。
- 页面不出现无证据的“已发布/已验证”。

### M4：Evidence 与接入案例

**实施：**

- Evidence store、expiry/revoke、case/instance、snapshot、stage projection 和统计聚合。
- 接入案例列表/详情/时间线/阻塞项全部切 API。
- 当前实例与参考案例分区。

**退出门：**

- body 伪造 stage 无效；缺证据不能跳级。
- 证据过期/撤销触发阶段降级和事件。
- 双租户、统计真实性、空态、错误态和刷新回读通过。
- 前端常量“7 已上线”、“1.2M 行”和 `live=生产` 不再参与运行。

### M5：最小电商包组合验证

**实施：**

- 建立 `domain.ecommerce.core`、`solution.ecommerce.operations-base`、`solution.ecommerce.growth`、`platform.ecommerce.niushop` 最小 manifest 骨架。
- 使用测试专用 Ed25519 密钥夹具发布不可变测试版本。
- 创建栖月汇脱敏 InstanceOverlay fixture，不包含真实 org/source/secret。
- resolve → diff → submit → 职责分离 approve → dry apply → verify → active → rollback。

**退出门：**

- 电商包卸载/回滚后 AOS 通用功能与其他领域无回归。
- 内核源码静态扫描不 import 电商 Bundle。
- 包内不含真实密钥、客户引用、Niushop 业务数据或未授权生产能力。
- M1～M5 全量专项和平台累计回归通过，证据完整。
