## 0. 使用的 Rules

## 1. A1 目标与非目标

### 1.1 目标

- 从同一个 PostgreSQL `REPEATABLE READ` 只读事务构造 `RegistrySnapshot`，并复用 M1 发布证据策略。
- 对 snapshot 执行确定性版本解析、依赖图、能力、显式冲突和签名 contribution 冲突检查。
- 生成精确 `permissionDiff`、`migrationPlan`、`contributionDiff` 和不可变 composition lock。
- 实现 composition/lock 与 installation 基础持久化、完整性回读、租户隔离和等价输入幂等。
- 用属性测试、真实 PostgreSQL 测试和对抗测试关闭资源上限、并发快照、篡改与歧义风险。

### 1.2 非目标

- 不新增公开 HTTP API，不修改 Router manifest、生成聚合文件或 `main.py`。
- 不实现 submit/approve/apply/verify/rollback 业务状态机；该部分属于 M2-B。
- 不执行 Bundle SQL、Python、migration、外部调用或生产平台写入。
- 不改 FDE 页面、接入案例页面和具体电商资产包。

## 3. 模块边界与 Protocol

### 3.1 ReleasePolicy

`release_policy.py` 提供无存储副作用的公共判定：给定版本记录、当前时间和可信根状态，验证 published/not-revoked、五类 current release evidence、evidence revision、content hash、签名指纹和 trust root。M1 `RegistryService` 与 M2 snapshot reader 必须复用该判定，禁止跨模块调用下划线私有函数。

### 3.2 RegistrySnapshotReader

`registry_snapshot.py` 只接受服务端注入的连接工厂、clock 和 release policy。它在单个 `REPEATABLE READ READ ONLY` 事务中读取候选、manifest、签名与 evidence，构造 DTO 后由 `RegistrySnapshot.build()` 排序并计算 hash。任一版本在同一快照内信息缺失、重复或不一致时整体失败，不返回部分 snapshot。

### 3.3 Resolver

`resolver.py` 是纯算法入口：

```text
resolve(
  request: CompositionRequest,
  snapshot: RegistrySnapshot,
  baseline: CompositionLockPayload | null
) -> CompositionLockPayload
```

解析器不得访问数据库、网络、环境变量或当前时间，也不得伪造 composition UUID、revision 或 `createdAt`。`checkedAt` 不进入 hash。候选、顶层请求和所有集合先 canonical 排序；选择规则、错误路径和 step budget 固定。baseline 只接受已经完成完整性验证的旧 `CompositionLockPayload`；由上层 Store/Service 从 active installation 绑定的 `StoredCompositionLock` 提取，Resolver 不承担持久化回读验证。

### 3.4 Store

- `composition_store.py`：接收 Resolver 生成的 `CompositionLockPayload`，由持久化边界分配 composition UUID、revision、`createdAt` 并包装为 `StoredCompositionLock`；原子写入 composition + revision 1 lock；等价输入命中同一结果；回读重算全部 JSON/hash 并验证跨列一致性。
- `installation_store.py`：A1 只实现创建 draft 基线、按租户读取/list 和幂等 command 基础原语；不开放 M2-B 状态迁移。
- 所有写操作使用单事务；数据库错误映射为稳定领域错误；不得返回 psycopg 原始文本、SQL 或连接信息。

## 4. 确定性解析规则

1. 候选只来自请求指定的 `RegistrySnapshot`；禁止解析中回查当前 Registry。
2. 顶层坐标必须显式 publisher；依赖缺省 publisher 只继承声明者。
3. 合并同一坐标的全部 version range，交集为空返回稳定版本冲突路径。
4. 优先最高 stable；只有约束显式包含 prerelease 时才允许 prerelease。
5. optional dependency 只有其目标 coordinate 同时出现在顶层 `requested` 时才进入图；不得因其他 required/optional dependency 间接出现而自动启用。
6. 每次候选尝试和回溯递增 step；节点、边、深度、候选、claim、payload 和 step 任一达到 `max+1` 立即失败。
7. 图完成后依次检查：cycle、显式 conflict、缺 capability/provider 歧义、API/navigation/UI contribution 冲突。
8. resolved bundles、edges、providers 与 conflict path 均按冻结 sort key 输出。
9. baseline 只从已验证 current active installation 绑定的旧 lock payload 重建；禁止用当前 Registry 反查旧版本。
10. 三类 diff 使用精确集合差：`added=target-baseline`、`removed=baseline-target`、`unchanged=intersection`，migration/contribution 保留 owner coordinate。

### 4.1 集成终审 P1 封口决定

M2-A1 首轮集成终审发现的边界按以下规则冻结，完成修复与对抗回归前不得判 GREEN：

1. **可信根视图不可混合**：一次 `RegistrySnapshotReader.read()` 必须在读取候选前取得一份不可变 trust-root snapshot，所有 candidate 只使用该视图。`FileTrustRootProvider` 必须单次安全读取并返回内存冻结视图；不支持冻结视图的动态 provider 在 Registry snapshot 路径失败关闭，禁止逐 candidate 重读动态配置。
2. **候选失效不扩大为全局拒绝服务，且不得掩盖完整性损坏**：证据过期/撤销/缺失、当前可信根不存在、尚未生效、已过期/撤销或 evidence 所绑定 trust-root revision 已被轮换时，只排除对应 candidate。trust-root 配置读取/解析故障、manifest/artifact/content hash 损坏、重复 signature evidence、同一 current root revision 下密码学签名不成立等完整性故障仍整体失败关闭。SQL 只能筛选发布状态、租户边界和单行载荷硬约束，不得先按 evidence 当前性、可信根可用性或最终候选预算过滤 published candidate；每个 published candidate 必须先在 Python policy 中完成 descriptor/content/signature 完整性验证，再判定其是否因 evidence/trust-root 生命周期失效而被排除。若同一 candidate 同时存在完整性损坏与证据/可信根失效，完整性损坏优先并导致整个 snapshot 失败关闭。
3. **stable-first**：只要全部约束同时匹配至少一个 stable candidate，就必须在 stable 集合中选最高版本；只有不存在可行 stable 且约束显式包含 prerelease 时，才在 prerelease 集合中选最高版本。不得用 SemVer precedence 较高的 prerelease 抢占可行 stable。
4. **预算精确计数**：每次 candidate attempt 计一步；该 branch 因 dependency/cycle/resource conflict 失败并返回上层继续搜索时再计一步 backtrack。`observed=10001` 必须返回 `RESOLUTION_LIMIT_EXCEEDED`，不得因只计 attempt 穿越 10,000 step 门。
5. **资源冲突路径可解释**：explicit conflict、capability missing/multiple、contribution collision 的 `details.path` 不能固定为空。必须从所有顶层 requested 出发，依据已解析有向 edges，选择到任一 conflict owner 的最短路径；长度相同时按完整 coordinate/via tuple 字典序选择。顶层 owner 的路径至少包含该 requested 节点。resource owners 继续 canonical 排序。
6. **cycle 维持既有 DTO 自校正**：`DependencyCycleDetails` 负责旋转到字典序最小节点并保持真实方向；新增复杂图对抗测试证明，不另设平行 cycle 格式。
7. **snapshot candidate 预算只统计最终合格候选**：`MAX_SNAPSHOT_CANDIDATES` 在 published row 完成完整性验证及 evidence/trust-root 资格判定后计数；因证据或可信根生命周期失效而被排除的 candidate 不得占用该预算，也不得让其他有效 candidate 的 snapshot 全局失败。Reader 必须逐行评估并在第 `max+1` 个合格 candidate 立即返回稳定 `RESOLUTION_LIMIT_EXCEEDED`，`observed=max+1`；不得在 policy 执行前对原始 SQL 行计数或 `LIMIT max+1`。数据库事务、发布状态过滤、单行 schema/payload 上限继续作为独立安全边界。
8. **证据时间文本必须跨 Python/PostgreSQL 唯一规范化**：Registry API、current evidence 与 persisted lifecycle `evidenceSnapshot` 中的 RFC3339 时间必须使用同一 UTC offset 和小数秒规则；微秒小数末尾 `0` 必须裁掉，小数全为 `0` 时省略小数点。不得让 Python `datetime.isoformat()` 的固定六位尾零与 PostgreSQL `jsonb_build_object(timestamptz)` 的裁零表示形成同一时刻两种正文。`created.evidence`、事件 snapshot 和回读 snapshot 必须逐字一致，且返回 snapshot 必须继续以 `canonical_sha256(snapshot) == evidenceRevision` 重算通过；不得只把测试改成 datetime 语义相等而掩盖正文漂移。

W4 必须补充上述封口项的独立复现与关闭测试；仅直接调用阈值 helper 不能替代真实搜索预算测试。

## 7. 集成顺序与失败处理

1. M2-A0 最终全量回归 GREEN，证据文档提交，五分支对齐同一 `m1` SHA。
2. 四 Worker 从该 SHA 开始，仅修改各自文件域；每个提交先专项再提交。
3. 总控逐个审查：契约一致性 → 安全失败关闭 → 数据库原子性 → 测试真实性。
4. 每合并一个 Worker 先跑其专项和既有 M1 Registry 回归；四个全部合并后跑完整累计门。
5. 任一累计门失败，停在 A1 修复，不进入 M2-B；修复先更新本方案或风险说明，再做最小代码改动。

不得用跳过测试、降低断言、Mock PostgreSQL、接受随机 hash、泄漏底层异常或扩大公共导出来换取 GREEN。

## 8. A1 退出门

同时满足才可标记 M2-A1 GREEN：

- 上位 M2-A 全部解析、预算、snapshot、lock、store 与 migration 退出门通过；
- A0 五个公共 DTO 与错误/schema 契约无漂移；
- M1 Registry 专项与后端全量无回归；
- Web、Desktop、SDK、OpenAPI、typecheck、build 和安全扫描累计门通过；
- 任务代码全部提交；用户既有 `AppShell.tsx` 及执行期间新增的用户文档改动保持原样且不进入 M2 提交；
- 证据文档记录精确提交、测试数、迁移 head、已知非阻断 warning 与风险；
- `m1` 与四个 worker 再次对齐同一提交。

M2-A1 在 `aos-platform m1@eedf3ae` 的全量候选后，由失败样例复核发现 Python/PostgreSQL timestamptz 小数尾零文本不一致的确定性 P1；方案先升级到 v1.9 并暂停 M2-B。最终 `m1@a6e4d31` 以 evidence 专用最小规范化关闭该问题，固定微秒 `123450/123456/0` 的真实 PostgreSQL 回归、36 组多时区对照、独立复核及全部累计门通过。过程与最终证据见 [M2-A1 核心解析与持久化回归证据](../evidence/m0/m2-control/2026-08-03-M2-A1核心解析与持久化回归证据.md)。

M2-A1 最终 GREEN 只允许进入 M2-B 方案复核和编码，不代表 M2、M0 或电商领域能力已经完成；M2-B 未通过不得进入 M3。
