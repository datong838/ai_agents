# 228-M5 最小电商包组合验证实施方案

> 状态：**v1.0 · 实施冻结；M4-5 已最终 GREEN，允许进入 M5-0**
> 代码预备基线：`aos-platform m1@8964c4b`
> 目标：用无业务实现、无客户数据的四个最小电商 Bundle，证明 M1～M4 通用内核可以完成真实发布、确定性组合、受控安装、验证、激活与回滚
> 停止门：M5 最终 GREEN 后只允许对账并冻结 G0；开始 Niushop、微信小店、抖音、快手等具体平台代码前必须暂停汇报

## 1. 使用的 Rules

1. 先方案后编码；本文件已实施冻结，任何范围变化必须先回写方案，再创建或修改 `bundles/` 与 M5 测试。
2. M5 不重新设计 Registry、Resolver、Composition、Installation、Evidence 或 Case；只组合验证现有能力。
3. 通用内核不得 import、按 ID 特判或内置电商/Niushop Bundle；电商内容只能进入 `bundles/` 和测试。
4. 只允许 manifest、空内容目录声明、最小 SBOM/Evals、synthetic Overlay fixture 与测试支撑；不实现 SQL、Connector、Pipeline、业务 Logic、Action 或页面。
5. 私钥只在测试运行时生成并停留在内存；仓库不提交私钥、固定签名、真实 trust root、Secret 或连接串。
6. 每个小波先专项、再前序累计；本波真实缺陷只做最小修复，不借机重构既有架构。
7. 每个小波完成后先收口 `m1`，再同步四个 Worker 到同一 HEAD/tree，推送五个远端并验证 ahead/behind `0/0`、工作树 clean。
8. 每波更新 M0、两份 `00` 总计划、228 路线、AOS 开发上下文和证据；状态必须区分“骨架存在”“测试发布”和“真实平台已接入”。

## 2. 业务目标与真实完成定义

M5 不是电商功能开发，而是对 AOS 模块化架构的第一组领域组合验收。完成时必须真实证明：

- 四个最小 Bundle 通过当前 strict Manifest、Loader、内容 hash、SBOM、Evals、Ed25519 和发布职责分离门。
- 解析三个叶子包时，Resolver 自动补齐领域核心包，产生固定四包 lock、依赖边和三类 diff。
- 安装走完 `draft → submitted → approved → applied → active → rolled_back`，maker/checker、幂等、ETag/CAS、Evidence 和 active pointer 都由现有控制面执行。
- 回滚后没有电商贡献残留，其他通用能力、已有 Bundle 和 M1～M4 回归不受影响。
- 任何文档或页面不得把该结果描述为“Niushop 已接入”或“电商业务已上线”。

## 3. 非目标与停止边界

- 不访问真实 Niushop、微商城、微信小店、抖音或快手。
- 不读取或写入真实客户 org/project/source/secret/dataset/order。
- 不实现 Niushop 表映射、schema fingerprint、API、JDBC、Pipeline 或 Connector。
- 不实现电商 Ontology、Growth Logic、数字同事、达人邀约、控价或生产 Action。
- 不新增 Bundle uninstall API。M5 只验证现有 rollback；不得把 `rolled_back` 宣称为 `uninstalled`。
- 不新增 InstanceOverlay Store/API。M5 只冻结并验证脱敏文件契约，把其 canonical hash 作为现有 opaque `overlayRevision`；不得宣称完成生产实例管理。
- 不虚构独立 diff API。diff 是 Composition lock 内的 `permissionDiff`、`migrationPlan`、`contributionDiff`。

## 4. 当前代码能力与缺口

| 目标 | 现有能力 | M5 使用方式 | 缺口/裁决 |
|---|---|---|---|
| Manifest 与内容 | strict `BundleManifest`、allowlist Loader、路径/敏感项扫描、canonical hash | 直接加载四个仓库骨架 | 不改生产 DTO |
| 发布可信度 | 当前 trust root、Ed25519、SBOM/Evals、五类 release evidence、maker/checker | 临时副本 + 运行时密钥 + 真实 PostgreSQL 发布 | 固定签名和私钥不得入库 |
| Resolver | snapshot、SemVer、依赖闭包、稳定排序、capability/conflict、lock hash | 三叶请求自动补 core | 不把平台包耦合到业务 SolutionPack |
| Diff | permission/migration/contribution diff 已进入 immutable lock | resolve 后从 lock/GET 读取 | 无独立 `/diff` |
| Installation | receipt-first、ETag/CAS、职责分离、revalidation、apply/verify/rollback Evidence | 复用现有 API/Service/Store | 首装只证明 null baseline rollback |
| InstanceOverlay | 控制面仅接受 `overlayRevision` 规范化字符串 | 新增 JSON Schema + synthetic fixture + canonical hash | 不新增 Store/API，不验证真实 binding |
| 安全边界 | Loader 与仓库敏感扫描 | 新增 M5 scoped 负向门 | 通用 Web 旧客户映射不被 M5 复制或依赖 |

## 5. 四包冻结模型

### 5.1 公共字段

四个 `bundle.yaml` 均固定：

```yaml
apiVersion: aos.dev/v1alpha1
metadata:
  version: 1.0.0
  publisher: aos
  license: internal
spec:
  platformApi: ">=1.7.0 <2.0.0"
  optionalDependencies: []
  conflicts: []
  capabilities: { provides: [], requires: [] }
  permissions: { roles: [], markings: [], dataScopes: [], actionTypes: [] }
  migrations: { plan: null, downgradePolicy: retain-canonical }
  preflight: null
  regression: null
  rollback: null
```

不得加入 `contentHash`、`signatureRef`、`validated`、`secretRef` 或任何自行宣称完成度的字段。`contributions` 省略，表示无运行时贡献。

### 5.2 坐标、类型、依赖与空导出

| 坐标 | kind | required dependencies | 只声明的空 exports |
|---|---|---|---|
| `domain.ecommerce.core@1.0.0` | `DomainPack` | 无 | `ontology/schemas/policies` |
| `solution.ecommerce.operations-base@1.0.0` | `SolutionPack` | `domain.ecommerce.core >=1.0.0 <2.0.0` | `logic/workshops/evals` |
| `solution.ecommerce.growth@1.0.0` | `SolutionPack` | `domain.ecommerce.core >=1.0.0 <2.0.0` | `agents/logic/workshops/evals/policies` |
| `platform.ecommerce.niushop@1.0.0` | `PlatformAdapterPack` | `domain.ecommerce.core >=1.0.0 <2.0.0` | `connectors/schemas/mappings` |

依赖方向固定为三个叶子只依赖 core。平台适配包不得依赖某个业务 SolutionPack；组合请求显式请求三个叶子，Resolver 自动补入 core，并产生三条 required edge。

`platform.ecommerce.niushop` 在 M5 只是架构坐标和空目录，不代表 Niushop 能力存在。

## 7. InstanceOverlay synthetic 契约

M0 中“栖月汇脱敏 fixture”在本方案中收紧为完全中性的 `instance-overlay.synthetic.json`：不在 Git 文件名、ID、displayName、namespace 或值中保留客户名。

Schema 必须 `additionalProperties: false`，至少冻结：

- `apiVersion/kind/metadata.id/revision`；
- synthetic `orgRef/projectRef`；
- `compositionLockRef`；
- `sourceRefs/secretRefs` 只能是规范化不透明引用，不能包含凭据；
- `datasetNamespace/selectedDomains/schedules/featureFlags`；
- `approvals.overlayRevisionRef`。

M5 只证明 schema、拒绝未知字段/明文秘密/权限扩大字段，并由测试在 fixture 外部对 canonical JSON 计算稳定 hash 作为现有 `overlayRevision`；fixture 不得自报自身 hash、“已批准”或“已投产”。Overlay 对 Bundle 能力和权限只能收缩，不能扩大；具体约束执行器留给后续独立方案。

## 8. 运行时签名与发布证据

- 仓库四包只提交 unsigned source；测试复制到临时 allowlist root。
- 测试运行时调用 `Ed25519PrivateKey.generate()`，私钥只在局部变量内存在。
- 以内存 trust root 绑定 `publisher=aos`、测试 `keyId`、相对数据库时钟有效期和 revision。
- 按生产 canonical manifest + artifact index 生成签名 payload；临时写入 `bundle.signature.json` 后重新加载。
- 断言签名文件不进入 artifacts/content hash；篡改任一受控文件后发布失败关闭。
- 每个 published 版本必须具有 current valid 的 `manifest_validation/content_hash/signature_verification/sbom/bundle_evals`。
- 最小 SBOM：`{"format":"CycloneDX","components":[]}`；最小 Evals：`{"status":"passed","failed":0}`。它们仅证明 M5 空骨架通过当前门，不代表业务质量。

## 9. 组合与安装闭环

准确流程：

```text
四包真实 PG 发布
  → Registry snapshot
  → resolve(operations-base, growth, niushop)
  → immutable lock + embedded diff
  → GET lock 对拍
  → create installation draft
  → submit
  → checker approve exact lock/diff hashes
  → dry apply
  → verify / active
  → rollback
```

必须断言：

- lock 恰好四包、core 只出现一次、三条 edge、输入乱序仍保持相同选择与 hash。
- resolve 相同幂等键/同 envelope 回放不新增记录；同键异 envelope 冲突。
- create/action 的 ETag、`etagVersion`、current revision 同步从 1 增到 6。
- maker 自批 403 且零写；checker 与 maker 不同，批准绑定 exact lock 与三类 diff hash。
- apply/verify/rollback 分别产生 `dry_apply/verification/rollback` 服务端 Evidence，hash 可复算且绑定目标 revision。
- active 时 `activeRevision=5`；首次安装 rollback 后 active/previous 均为 null，事件链完整。
- active 后即使选中 release 被 revoke，rollback 仍允许安全退出。
- non-null previous 的升级回滚仍由既有 migration/Store 门证明；M5 不夸大为公共升级 E2E。

## 10. 安全与反偷渡门

以下任一命中即 M5 RED：

- `aos_api`、共享 packages 或通用 Web import `bundles`/ecommerce 资产，或按四个 bundle ID 特判。
- Bundle/fixture 中出现真实客户名、真实 org/project/source/dataset、手机号、邮箱、OpenID、订单、`ns_*` 表、数据库 URL、Token、私钥或凭据值。
- Niushop 包出现 SQL、真实字段映射、schema fingerprint、网络地址、可执行 Connector/Action/Pipeline。
- 缺 SBOM/Evals、Evals `failed>0`、证据未被签名覆盖或篡改后仍能发布。
- rollback 后仍保留本次 installation active pointer 或电商运行贡献。
- 用 rollback 冒充 uninstall，或把测试发布/active 冒充真实平台上线。

仓库全量 scanner 的既有 warning 单独记录；M5 新增文件作用域必须 critical=0、warning=0。

## 11. 分波与四 Worker 所有权

### M5-0：契约与无业务骨架

- W1：四个 `bundle.yaml`、SBOM/Evals、空 export 目录与 strict 契约测试。
- W2：InstanceOverlay JSON Schema、synthetic fixture、canonical hash/负向测试。
- W3：内核反向依赖、客户/秘密/平台业务偷渡和 scoped scanner 测试。
- W4/总控：依赖图、文件边界、文档与跨组一致性收口。

退出门：所有静态文件可由真实 Loader/Schema 读取；无签名骨架只能作为 source，不得宣称 published；新增作用域扫描 GREEN。

### M5-1：运行时签名与 Registry 发布

- W1：薄测试 helper，完成临时 copy、runtime key、canonical sign/trust root。
- W2：真实 PostgreSQL 四包 create/validate/maker-checker publish/restart snapshot。
- W3：签名/SBOM/Evals/篡改/过期或撤销 trust root 负向门。
- W4/总控：M1 累计门、静态审查和五分支收口。

退出门：四包均由生产 Service/Store 发布为 immutable test version；五类 evidence valid；不存在固定私钥或固定签名。

### M5-2：Composition 与 Installation 闭环

- W1：三叶请求、core 自动闭包、稳定边/选择原因/lock hash/输入乱序。
- W2：真实 PostgreSQL resolve、embedded diff、安装 1～6 revision 生命周期、职责分离、幂等/CAS/Evidence。
- W3：release revoke 后 rollback、active pointer、无关安装/通用能力不受影响和反残留测试。
- W4/总控：跨层对拍、前序累计与五分支收口。

退出门：完整闭环 GREEN，所有事实来自现有生产 Service/Store；无新端点、表或 DTO。

### M5-3：M0 最终累计门与证据收口

- M1～M5 资产域、真实 PostgreSQL、Router/OpenAPI、Web/Desktop/Ontology SDK 全量回归。
- Alembic single head/current、OpenAPI 两次干净进程确定性、security gate。
- 四包和 synthetic fixture 静态边界复验。
- 五分支/五远端同 HEAD/tree、ahead/behind `0/0`、clean。
- 更新两份 `00`、M0、228 路线、AOS 上下文和最终证据。

## 12. 验收矩阵

| 面 | 必验结果 |
|---|---|
| Manifest | 四包 strict、路径存在、依赖无歧义、无未知/安全自证字段 |
| Loader | artifact 稳定排序、content hash 稳定、签名文件排除、篡改失败关闭 |
| Registry | 五类证据、职责分离、不可变发布、重启回读、快照仅含 eligible release |
| Overlay | strict schema、synthetic、无秘密/客户值、hash 确定性、opaque revision 传递 |
| Resolver | 三叶 + 单 core、三 edge、乱序确定性、lock/diff/hash 稳定 |
| Installation | 六态、maker/checker、幂等、ETag/CAS、revalidation、三类 Evidence、rollback |
| 边界 | 内核零 import/特判、无平台实现、无真实数据、无 uninstall 伪声明 |
| 累计 | M1～M5、Web/Desktop/SDK/OpenAPI/security 全部满足门禁 |

## 13. 风险与裁决

- **平台坐标被误认作已接入**：所有 UI/文档显示“fixture/test-only”；M5 不创建 Integration Case 生产样例。
- **平台包耦合业务包**：adapter 与两个 SolutionPack 只共同依赖 core，组合由请求表达。
- **Overlay 能力被夸大**：只交付 schema/fixture/hash，不交付 Store/API/批准执行器。
- **空 Evals 伪绿**：明确只证明骨架契约；业务 Evals 在 G0+ 和具体平台阶段另行提供。
- **回滚等同卸载**：状态和证据始终写 `rolled_back`；uninstall 保持未实现。
- **测试密钥泄漏**：运行时生成、临时目录精确清理、仓库扫描无私钥/credential URL。

## 14. 当前裁决

M4-5 已在 `m1@8964c4b` 完成最终累计回归、OpenAPI/security 门和五分支同步，本方案现已实施冻结并允许开始 M5-0。M5 全程不得进入具体平台实现；若下一步需要读取 Niushop/微商城真实 schema 或写 Connector，必须先暂停并向用户汇报。
