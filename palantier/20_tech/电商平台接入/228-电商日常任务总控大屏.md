## 1. 为什么需要这个大屏

### 1.1 现有工作台定位矩阵（避免重叠）

| 工作台                                       | 视角             | 入口对象              | 覆盖同事        | 覆盖任务范围               |
| ----------------------------------------- | -------------- | ----------------- | ----------- | -------------------- |
| [数据参谋驾驶舱](./12-工作台层方案/04-数据参谋驾驶舱（通用版）.md) | **看数**         | 指标卡 / 趋势图 / 异常告警  | 仅数据参谋       | 数据视角（无任务执行）          |
| [客情维护平台](./12-工作台层方案/05-客情维护平台设计方案.md)    | **看单一同事的任务**   | 私域管家任务列表          | 仅私域管家       | 私域沉淀/分层/触达           |
| [内容日历工作台](./12-工作台层方案/02-内容日历工作台（通用版）.md) | **看内容排期**      | 内容素材 / 发布计划       | 仅内容官        | 内容生产与发布              |
| [活动策划工作台](./12-工作台层方案/03-活动策划工作台（通用版）.md) | **看活动 ROI**    | 活动方案 / 复盘         | 仅活动策划师      | 选品/定价/优惠/复盘          |
| **本文档：日常任务总控大屏**                          | **看全量日常任务的消化** | **6 同事任务 Kanban** | **6 同事全协同** | **售前+售中+售后+复盘 全量日常** |

**结论**：现有 4 个工作台都是"单同事单视角"，缺一个"6 同事协同总视角"。日常运营不是"一个同事干完所有事"，而是数据参谋派活 → 5 个同事分头执行 → 共同复盘 → 经验沉淀。这个总视角必须有一个专门的大屏承载，不能私下悄悄执行。

### 1.2 大屏的 3 个不可替代价值

1. **不让日常任务黑洞化**：每天的种草、直播、售后跟进若是 6 同事各自默默执行，店主看不到全貌；大屏强制把"今天要干什么、谁在干、干到哪、效果如何"完整呈现。
2. **强制复盘与经验沉淀**：每条任务结束必须产出 EffectReview（有效/无效/有害/无结论/未执行 5 分类），经验进入 14-Wiki Episodic 层，反哺下次派发——这是 [电商领域应用规划 §8.2 护城河](./电商领域应用规划.md) 的运营落地。
3. **数据参谋作为"生意参谋"的总调度身份显性化**：现有体系里数据参谋是"为什么"（建议驱动），但缺一个地方让它真正"派活"；大屏让数据参谋的 D01-D06 技能产出真正变成可执行的 AgentTask DAG。

## 2. 核心设计：任务驱动的六同事总控

### 2.1 设计哲学（延续客情维护平台 §11.4.1）

> **Agent 是同事，不是工具/自动售货机。**
> 入口是任务列表，不是聊天框。
> 核心数据模型是 `AgentTask + Artifact + ReviewRecord`，不是 `Conversation + Message`。

### 2.2 数据参谋作为总调度（"生意参谋"角色声明）

数据参谋在大屏中扮演**总调度**（俗称"生意参谋"），其 6 技能（D01 检测/D02 归因/D03 预测/D04 画像/D05 建议/D06 报告，见 [08-数据参谋技能编排](./11-AIP决策引擎升级方案/08-数据参谋技能编排.md)）的产出直接 materialize 为 AgentTask DAG，派发给其他 5 个同事：

```text
数据参谋（生意参谋 / 总调度）
   │
   ├─ D01 检测 → 发现异常/机会 → 生成"调查类"任务派给对应同事
   ├─ D02 归因 → 定位原因     → 生成"处置类"任务
   ├─ D03 预测 → 预判趋势     → 生成"预防类"任务
   ├─ D04 画像 → 客户/商品分层 → 生成"触达类"任务派给私域管家
   ├─ D05 建议 → 经营建议     → 生成"内容/活动类"任务派给内容官/活动策划师
   └─ D06 报告 → 晨报/日报     → 汇总当日全同事产出，进入复盘区
```

### 2.3 六同事角色分工矩阵（在大屏中的职责）

| 同事             | 在大屏中的角色        | 主要承接任务类型            | 典型产出 Artifact                      |
| -------------- | -------------- | ------------------- | ---------------------------------- |
| **数据参谋**（生意参谋） | **总调度 + 复盘主持** | 派发任务、汇总复盘、产出晨报/日报   | GrowthPlan、DailyBrief、EffectReview |
| 私域管家           | 客户侧执行          | 客户沉淀、分层、触达、跟进       | 客户分层表、触达话术、跟进排期                    |
| 内容官            | 内容侧执行          | 种草文章、短视频脚本、封面、文案    | ContentBrief、文章/视频草稿、封面图           |
| 导购顾问           | 推荐侧执行          | 商品推荐、成分分析、搭配方案、直播脚本 | RecommendList、成分报告、直播话术            |
| 活动策划师          | 活动侧执行          | 选品、定价、优惠、ROI 预估     | ActivityPlan、选品表、ROI 模型            |
| 客服专员           | 服务侧执行          | 售前咨询、售中跟进、售后处理、投诉   | ServiceCase、售后工单、满意度报告             |

### 2.4 任务生命周期（6 段式）

```text
派发（数据参谋 D05 / 人工下达）
  → 领取（对应同事 Logic Graph 接收）
  → 执行（TAOR 循环 + Plan Mode + 权限门控）
  → 交付（产出 Artifact，进入待确认）
  → 复盘（EffectReview 5 分类：有效/无效/有害/无结论/未执行）
  → 记忆（经验入 14-Wiki Episodic 层，反哺下次派发）
```

**关键规则**：
- 每条任务必须走完 6 段才算"消化完成"，不能跳过复盘和记忆。
- 复盘为"有害"的任务必须触发根因分析，并标记到对应同事的技能 Evals。
- 记忆入库必须区分"可复用经验"与"一次性上下文"，前者进 Semantic 层，后者仅留 Episodic 层 90 天。

### 3.6 任务模板表字段契约

每条任务模板必须包含以下字段（最小契约）：

```yaml
task_template_id: PRE-01
name: 4大社交平台种草文章
owner_colleague: content_officer
collaborators: [shopping_advisor, private_domain_manager]
frequency: daily
cron: "0 9 * * *"          # 每日早 9 点派发
inputs:                     # 派发时的输入契约
  product_scope: required
  audience_segment: required
outputs:                    # 期望产出 Artifact
  - article_draft
  - cover_image
approval_gate:              # 权限门控
  risk_level: medium
  require_human_review: true
review_criteria:            # 复盘判据
  effectiveness_metric: content_read_count
  threshold: { valid: ">=100", invalid: "10-99", harmful: "<10 AND negative_comments>5" }
memory_policy:              # 记忆策略
  reusable: true            # 进 Semantic 层
  ttl_days: 90              # Episodic 层保留
```

### 4.2 顶栏：今日战况

- **6 段进度条**：派发数 / 执行中 / 待确认 / 已完成 / 已复盘 / 阻塞数（任一阻塞红色高亮）
- **六同事状态条**：每个同事一个状态灯（🟢进行中 / 🟡待确认 / ⚪待启动 / 🔴阻塞 / ✅已完成），点击可筛选左栏
- 数据参谋永远置顶，标记"调度"角色，显示其当日派发完成度

### 4.3 左栏：六同事任务 Kanban

- 每个同事一个泳道，泳道内按任务状态分列（待启动 / 进行中 / 待确认 / 已完成 / 已复盘）
- 任务卡片最小化展示：任务 ID、名称、主责、状态、进度（Step X/Y）、风险等级色块
- 点击卡片 → 中栏切换为该任务详情
- 支持拖拽改派（仅店主权限，触发权限门控）

### 4.4 中栏：当前任务详情

完全复用 [客情维护平台 §11.4.3 区域二](./电商领域应用规划.md) 的三件套：
- **Plan Mode 面板**（可编辑执行计划）
- **执行进度 + 日志流**（结构化日志，非聊天）
- **权限门控面板**（Diff 视图 + 批准/编辑/跳过）

### 4.5 右栏：今日复盘 + 经验沉淀

- **今日已完成复盘列表**：每条任务带 5 分类标签（✅有效 / ⚠无结论 / ❌有害 / 🟡无效 / ⚪未执行）
- **经验入库统计**：今日入库条数（可复用 N 条 / Episodic N 条）
- 点击复盘条目展开 EffectReview 详情 + 关联的 Episodic Memory 条目

### 4.6 底栏：明日预告 + 待确认事项

- 明日已排期任务数（来自固定任务模板的 cron 预测）
- 待确认事项计数（点击跳转中栏第一条待确认任务）
- 阻塞计数（红色高亮，点击展开阻塞原因）

G5 未就绪时，相关任务在大屏显示为"能力未就绪"占位卡片，不进入执行。

## 7. 复盘与记忆机制

### 7.1 日复盘 5 分类（来自 G1 §0 Rules）

| 分类     | 判据                                       | 处置                                     |
| ------ | ---------------------------------------- | -------------------------------------- |
| ✅ 有效   | 达到任务模板 `review_criteria.threshold.valid` | 经验入 Semantic 层（可复用）                    |
| 🟡 无效  | 落在 `invalid` 区间                          | 不入库，仅 Episodic 留痕                      |
| ❌ 有害   | 触发 `harmful` 条件                          | 根因分析 + 标记技能 Evals + 入 Semantic 层（负面警示） |
| ⚪ 未执行  | 任务未实际执行                                  | 记录阻塞原因，次日重排                            |
| 🟠 无结论 | 证据不足无法判定                                 | 人工裁决，补判据后入 Episodic                    |

### 7.2 经验入库（对接 14-Wiki 三层记忆）

```text
EffectReview 完成
  ├─ 可复用经验（文案模板/选品规则/达人合作模式）
  │     → 14-Wiki Semantic 层（永久，经知识治理 L1-L4 分级）
  ├─ 单次上下文（某客户某次互动）
  │     → 14-Wiki Episodic 层（TTL 90 天，重要经验可提升）
  └─ 当前任务上下文
        → 14-Wiki Working 层（任务结束即清理）
```

### 7.3 周复盘 + 月复盘

- **周复盘（REV-02）**：每周日晚，数据参谋主持，统计本周各同事任务有效率，分析技能 Evals 偏差，输出技能调优建议。
- **月复盘（REV-03）**：每月 1 日，数据参谋 + 店主共同，回顾本月 Semantic 层知识增长，提出知识治理提升/降级建议（对接 [14-Wiki 知识治理](./14-行业Wiki基础设施方案/03-知识治理三层过滤.md)）。

### 7.4 记忆反哺下一次任务派发

数据参谋 D05 建议（派活依据）必须读取：
- Semantic 层：历史可复用经验（文案模板、选品规则）
- Episodic 层：近 90 天同类任务的实际效果
- Working 层：当前未完成任务的状态

**禁止凭空派活**——数据参谋派发的每条任务必须能追溯到上述三层之一的历史依据，否则标记"无经验依据"并降级为 Draft。

## 8. 数据契约与 API 对接

### 8.1 任务模型（复用 + 扩展）

```python
AgentTask:  # 复用 G1 GrowthPlan materialize 产物
  task_id: str
  template_id: str | None       # 固定任务有模板，动态任务为 None
  owner_colleague: str           # 6 同事枚举
  collaborators: list[str]
  status: enum                   # dispatched/executing/pending_review/completed/reviewed/blocked
  plan_revision: str             # Plan Mode 不可变 revision
  artifacts: list[Artifact]
  review_record: EffectReview | None

EffectReview:  # 本大屏新增
  task_id: str
  classification: enum           # valid/invalid/harmful/inconclusive/not_executed
  evidence: dict                 # 指标值 + 判据版本
  root_cause: str | None         # harmful 时必填
  evals_marked: list[str]        # harmful 时标记的技能 Evals
  memory_dispatch: dict          # 入库去向（semantic/episodic/working）
```

### 8.2 与 G1 GrowthPlan 的关系

- G1 的 `GrowthPlan → AgentTask DAG` 是本大屏的**任务来源之一**（例行任务主路径）。
- 本大屏的"人工动态下达"是 G1 之外的**补充任务来源**。
- 两者共用 `task_materializer` 和 AgentTask 持久层，不重造。

### 8.3 与 6 同事 Logic Graph 的关系

- 每条 AgentTask 由对应同事的 Logic Graph 执行（Plan Mode + TAOR 循环）。
- 大屏不执行任务，只呈现任务状态和触发权限门控。
- Logic Graph 的 handoff decision 是大屏任务卡片状态变更的事件源。

### 8.4 与 14-Wiki Episodic Memory 的关系

- EffectReview 完成后，按 `memory_dispatch` 写入三层记忆。
- 大屏右栏"经验入库统计"读取 14-Wiki 的入库计数 API。
- 数据参谋派活前的"经验读取"通过 14-Wiki 检索 API。

### 8.5 候选 API 路由（激活实施时再冻结）

```text
GET  /v1/dailyops/dashboard          # 大屏顶栏战况聚合
GET  /v1/dailyops/colleagues/{id}/tasks  # 左栏某同事任务列表
GET  /v1/dailyops/tasks/{id}         # 中栏任务详情（含 Plan/日志/门控）
POST /v1/dailyops/tasks/{id}/review  # 右栏提交复盘
GET  /v1/dailyops/reviews/today      # 右栏今日复盘列表
GET  /v1/dailyops/memory/stats       # 右栏经验入库统计
GET  /v1/dailyops/tomorrow           # 底栏明日预告
```
