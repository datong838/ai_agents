## 1. AIP 在生意探究中的职责

AIP 不拥有电商 `BusinessInvestigationCase`，也不拥有店铺、商品、客户或订单真值。AIP 的职责是把一次生意探究编译为可暂停、可补证、可评估、可交接的长任务：

1. 读取 Case scope 和精确领域修订；
2. 生成 Task、PlanRevision、TaskRun、Step 和 Checkpoint；
3. 发现事实缺口并提出 DataRequirement；
4. 调度 ResearchJob、QueryJob、Ontology 查询或人工确认；
5. 构建 EvidenceBundle，评估 coverage、freshness、冲突和反证；
6. 驱动经营画像、问题机会、方案设计三波串行推进；
7. 通过 Eval、ReviewIssue、ReturnDecision 和 ImpactPreview 控制质量；
8. 只把人工批准的 `GrowthPlanRevision(APPROVED)` exact ref 交给后续系统；`GrowthPlanCandidate` 仅是界面称谓，不是资源；
9. 回收 Receipt、EffectReview 和 MemoryCandidate。

## 2. 复用现有唯一权威

| 现有 AIP 能力 | 生意探究用途 | 禁止做法 |
|---|---|---|
| Task/PlanRevision/TaskRun | Case Run 的通用执行骨架 | 新建第二套分析任务状态机 |
| StepRun/Checkpoint/Timeline | 三波步骤、暂停、恢复、人工接管 | 前端用本地进度冒充 canonical 状态 |
| ResearchJob | 平台观察、Schema 推理、专题研究 | 让外部研究工具持有任务真值 |
| EvidenceBundle BuildJob | required facts coverage/missing/freshness | 客户端计算完整度并写回 |
| EvalContract/ReviewIssue | 阶段质量门和返工 | 单一模型分数自动晋级 |
| ResponsibilityPlan | 六数字同事与人类职责 | 固定拟人 Agent 阵容 |
| LogicRevision/StageTemplateRevision | 将原子 Skill 编译为可复核的阶段方法 | 在页面或领域服务硬编码私有流程 |
| SkillRevision/SkillBindingSet | exact 方法与能力绑定 | 仅凭 displayName 推断可运行 Skill |
| ProductionContextRevision | 冻结 Brief/Evidence/Eval/Responsibility | 手工复制四个 ID 绕过同版门 |
| HandoffEnvelope/Decision | 向专业工作台传递最小精确引用 | 把交接当持久授权 |

## 3. 生意探究编排模板

### 3.1 InvestigationProfile

电商 L1 发布版本化 `InvestigationProfile`，AIP 只解析并编译：

```yaml
profileType: ecommerce.business-investigation
analysisType: full-store-baseline | weekly-review | experience-growth | creator-sales | assortment
stages:
  - portrait
  - diagnosis
  - solution-design
requiredCapabilityRefs: []
requiredFactProfiles: []
stageTemplateRefs: []
evalContractRefs: []
responsibilityTemplateRef: "..."
handoffPolicyRef: "..."
```

Profile 只定义稳定模板，不含具体店铺、凭据、时间窗、预算或页面路径。具体经营实体由 L3 Overlay 与 Case scope 注入。

### 3.2 编译结果

```text
BusinessInvestigationCaseRevision exact ref
→ TaskBriefRevision
→ PlanRevision
   ├─ Stage 1 Portrait
   │   ├─ freeze scope
   │   ├─ assess readiness
   │   ├─ request/collect facts
   │   ├─ build dossier
   │   └─ evaluate/review
   ├─ Stage 2 Diagnosis
   │   ├─ form hypotheses
   │   ├─ gather counter-evidence
   │   ├─ build problem/opportunity maps
   │   └─ evaluate/review
   └─ Stage 3 Solution Design
       ├─ generate alternatives
       ├─ unit economics / impact / risk
       ├─ compare portfolio
       └─ human decision / handoff
→ TaskRun + Checkpoint + Timeline
```

PlanRevision 不固化“28 步”这个展示数字；步骤数由 Profile、平台能力、数据缺口和用户选择编译。页面的 x/y 必须来自 canonical PlanRevision。

### 3.3 原子 Skill → Logic → 职责绑定编译合同

本方案遵循 [163-AIP 通用原子 Skill 分层方案](163-AIP通用原子Skill分层与六数字同事组合方案.md) 与 [164-工作台层 Skill 消费方案](../12-工作台层技术方案/164-工作台层Skill消费与六数字同事产品落位方案.md)，不得把“生意探究”重新实现为一组不可复用的大 Skill。服务端编译顺序固定为：

```text
InvestigationProfile exact ref
 Case/Run/TaskBrief exact refs
 DomainProfile / Evidence / Eval / Policy exact refs
 canonical Skill catalog snapshot
 capability/model/source readiness at cutoff
 method preferences
→ LogicRevisionRef + StageTemplateRevisionRef
→ ordered SkillRevisionRef[]
→ SkillBindingSetRef
→ ResponsibilityPlanRevisionRef
→ PlanRevision + CompilationReceipt
```

约束如下：

1. 经营指标诊断、渠道观察、方案比较等领域方法是 Logic 或领域 Skill 组合，不复制 `build-evidence-pack`、`identify-data-gaps`、`form-hypotheses`、`diagnose-metric-change`、`compare-alternatives`、`estimate-impact`、`rank-recommendations` 等原子能力；
2. `LogicRevisionRef / SkillRevisionRef / SkillBindingSetRef / ResponsibilityPlanRevisionRef` 必须携带 exact id、revision、hash 与 cutoff；displayName、角色名或页面配置不能替代 exact ref；
3. method preference 只是重新编译输入，不允许页面直接创建 SkillBinding、AgentRun 或私有步骤；
4. 任一 exact ref 缺失、漂移、过期、租户不匹配或 readiness 非 GREEN 时，CompilationReceipt 必须失败关闭，领域 Run 保持 `PREPARING/BLOCKED`，不得降级成“已运行”；
5. `CompilationReceipt` 只证明编译结果，不证明 Provider、Binding、AgentRun 或真实数据已可运行。

## 4. AIP 与领域 Case 的绑定

AIP TaskBrief 只保存精确引用：

- `caseRef`：Case id/revision/hash；
- `businessInvestigationRunRef`：领域 `BusinessInvestigationRun` 的 id/revision；
- `businessEntityRef`、`channelRef`；
- `analysisType`、`timeWindow`、`cutoff`；
- `questionSetRevisionRef`；
- `investigationProfileRef`；
- `marking/purpose`；
- `budget/stopCondition`；
- `requestedOutputKinds`。

AIP 不复制 Case/BusinessInvestigationRun 业务 payload，不自行更新 Case current revision。领域服务通过 TaskRun event 与 artifact exact refs 更新 Run 和 Case 投影。AIP `TaskRun` 是执行权威，L1 `BusinessInvestigationRun` 是领域运行档案；二者使用 exact refs 连接，状态必须有显式映射而不能互相覆盖。

## 5. 三波执行合同

### 5.1 Portrait Stage

输入：TaskBrief、已有 OntologySnapshot、MetricProfile、SourceReadiness。  
执行：按照 RequiredFactProfile 构建 EvidenceBundle；缺事实时生成 DataRequirement；必要时创建 ResearchJob。  
产物：Artifact `business-dossier-candidate`，由 L1 服务验证并发布 `BusinessDossierRevision`。  
Eval：覆盖度、口径一致性、新鲜度、未知项披露、跨源冲突和关系完整性。

### 5.2 Diagnosis Stage

输入：批准的 BusinessDossier exact ref。  
执行：建立假设集合，区分异常、问题、根因和机会；为高影响假设主动寻找反证。  
产物：`problem-map-candidate`、`opportunity-map-candidate`，由 L1 发布正式 revision。  
Eval：证据强度、替代解释、因果越界、影响、可逆性、验证成本和不确定性。

### 5.3 Solution Design Stage

输入：批准的问题/机会 revision 与约束。  
执行：生成至少一个维持方案、一个增量方案和一个可比较替代方案；计算单位经济、依赖、预算、风险、停止条件和效果窗。  
产物：`solution-portfolio-candidate`，领域服务发布 revision。  
Eval：目标一致性、证据覆盖、可执行性、合规、预算、Action 风险和 EffectReview 可测量性。

## 6. DataRequirement 请求侧合同

AIP 不决定如何访问源平台，只负责提出经营语义需求：

```json
{
  "requestId": "dr-...",
  "caseRef": {"id": "...", "revision": 1, "hash": "..."},
  "taskRunRef": {"id": "...", "revision": 3},
  "checkpointRef": {"id": "...", "sequence": 8},
  "purposeCode": "PORTRAIT_CUSTOMER_RELATIONSHIP_BASELINE",
  "businessEntityRef": "...",
  "requiredFacts": ["customer_identity", "referrer_relation", "experience_redemption"],
  "timeWindow": {"from": "...", "to": "..."},
  "grain": "customer-day",
  "freshnessSla": "P1D",
  "qualityThresholds": {},
  "acceptableDegradation": {},
  "marking": ["CUSTOMER_RESTRICTED"],

```

## 7. EvidenceBundle 与推断纪律

### 7.1 Evidence 类型

- 结构化事实：Dataset/DataProduct/Ontology snapshot；
- 观察事实：页面、菜单、筛选结果、导出、截图/DOM 的受控引用；
- 经营记录：Metric/Observation/Receipt/Usage/EffectReview；
- 人工事实：经营者确认、范围选择、约束与 Decision；
- 外部研究：公开资料、平台规则、竞品方法，带许可、新鲜度和适用范围。

### 7.2 结论分级

每条分析输出必须标为：

- `FACT`：可回链权威事实；
- `ANALYSIS`：由明确规则或统计计算得到；
- `HYPOTHESIS`：待验证解释；
- `RECOMMENDATION`：基于证据与约束的建议；
- `DECISION`：授权人做出的业务决定；
- `EXECUTION_RESULT`：仅由 Receipt/EffectReview 支持。

不得把假设写成事实，不得把推荐写成决定，不得把页面点击或模型返回写成执行结果。

### 7.3 不保存私有推理链

持久化内容仅包括：决策摘要、证据链、归因路径、关键假设、不确定性、反证、方法版本和限制。不保存模型私有思维过程。

## 8. 假设驱动的自适应研究

生意探究不是一次固定 SQL 报告。AIP 应执行闭环：

```text
Observe → Profile → Hypothesize → Test → Revise → Decide
```

1. Schema Reasoning 读取治理后的结构/语义能力；
2. Adaptive Profiling 根据缺口选择最小新增数据；
3. Hypothesis Registry 保存假设、支持/反证 Evidence 和状态；
4. 高影响、低置信假设优先补证；
5. 若数据成本过高，使用 `acceptableDegradation` 缩小结论，而不是猜测；
6. 新证据到达时生成 successor revision，不修改历史结论。

## 9. ResearchJob 与浏览器观察

AIP 创建 ResearchJob 时必须绑定：

- current TaskRun lineage event；
- ObservationPlan exact revision/hash；
- platform capability revision；
-允许动作、页面范围、预算、超时、停止条件；
- human-assisted login/session lease ref；
- expected artifacts 和 Evidence policy。

ResearchJob 外部状态不直接决定 TaskRun 成功。完成后执行 artifact verify、hash、license/marking、scope 和 lineage 检查；超时或结果不明进入 `UNKNOWN`，等待 Reconcile Receipt，不自动重试。

## 10. 六数字同事与职责

`ResponsibilityPlan` 按能力而非固定 Agent 名称分配：

| ResponsibilitySlot | 典型能力 | 可能承接者 |
|---|---|---|
| InvestigationOwner | 规划、画像、归因、方案比较 | 数据参谋/经营参谋实例 |
| DataSteward | RequiredFact、质量、语义、Readiness | Data FDE/人工数据负责人 |
| ContentResearch | 商品知识、内容差距、信任路径 | 内容官 |
| CustomerResearch | 需求、异议、旅程、同意 | 导购顾问/客服/私域管家 |
| ChannelResearch | 平台流量、达人、活动机制 | 活动策划师/平台技能 |
| BusinessReviewer | 经营判断、范围、风险、批准 | 经营负责人 |

一人或一个 Agent 可承担多个兼容 Slot，但评估、合规、批准和 Receipt 的独立性不能合并。

### 10.1 工作台贡献投影

AIP 为每个已编译步骤输出可验证的贡献引用，Workshop Application Service 再按 164 号方案投影 `SkillContributionView` 与 `RoleCollaborationView`。贡献视图至少包含：

- `taskRunRef / stageRunRef / checkpointRef`；
- `roleRef / assigneeRef / responsibility`；
- `canonicalSkillRef / skillRevisionRef / bindingRef / logicRevisionRef`；
- readiness、freshness、receiptRef 与 blockerRefs；
- input/evidence/output/review/handoff exact refs；
- assumptions、uncertainties、conflicts 与 allowedCommands。

`SkillContributionView` 是可重建只读投影，不是 SkillRun、AgentRun、TaskRun 或领域制品的新 Authority。后端没有 exact 编译与运行证据时，页面必须显示 BLOCKED/UNKNOWN；禁止由 UI 根据角色、进度或产物反推某个 Skill 已执行。

## 11. Eval 体系

### 11.1 Portrait Eval

- required dimensions coverage；
- source freshness/cutoff；
- metric definition compatibility；
- object identity/relationship consistency；
- unknown 和冲突披露；
- PII/marking/minimum population。

### 11.2 Diagnosis Eval

- 事实、分析、假设分离；
- 每个高影响根因有支持与反证；
- 相关性与因果的边界；
- 跨平台口径不被强行合并；
- 问题与机会可回链画像 revision。

### 11.3 Solution Eval

- 多方案可比较；
- 单位经济和预算口径完整；
- 依赖、风险、停止条件和效果窗；
- 是否需要 Action、客户触达或外部写；
- 专业工作台 readiness；
- 不可执行项明确 blocked。

Eval fail 生成 ReviewIssue；返工产生新 Attempt 和 successor artifact，不覆盖历史。

## 12. 人工决策门

人工至少参与：

1. Case 范围和首要经营问题冻结；
2. 高敏感数据目的与最小披露确认；
3. Wave 1 画像是否足以进入归因；
4. Wave 2 哪些问题/机会进入方案比较；
5. Wave 3 方案组合以及 `GrowthPlanRevision(DRAFT)` 是否产生人工批准的 `APPROVED` successor；
6. 所有真实客户触达、商品发布、上下架、改价、签约、预算和结算。

`HandoffDecision=accepted` 只允许目标工作台重新授权所需引用，不赋予 Receiver 持久权限。

## 13. Handoff 到执行系统

HandoffEnvelope 最小内容：

- Case/Run/TaskRun exact refs；
- approved BusinessDossier/ProblemMap/OpportunityMap/SolutionPortfolio refs；
- approved `GrowthPlanRevision` exact ref；
- EvidenceBundle/Eval/ImpactPreview refs；
- budget/stop condition/effect window；
- 目标工作台和 required capability refs；
- marking、expiry、one-time bearer hash。

目标工作台可以 `accept/reject/request_more/return`。接受后仍需自己的 SourceReadiness、Capability、Policy 和 Action 门。

## 14. EffectReview 与持续学习

生意探究不是一次性报告。批准方案执行后：

1. Receipt 和 Task/Action lineage 回流；
2. 到达 maturity window 后生成 EffectReview；
3. 对比 baseline、eligible population 和 attribution method；
4. late data、方法漂移或范围变化生成 successor；
5. 经验只进入 MemoryCandidate；
6. 经许可、来源、freshness、Eval、Approval 后才能晋升共享知识。

每周复盘创建新 `BusinessInvestigationRun` 并编译独立 AIP TaskRun，复用 Case 和 Profile，但冻结新的 cutoff、EvidenceBundle 和 ProductionContext。同一 Case/analysisType 的非终态周期 Run 默认不重叠；调度幂等键、跳过重叠和补跑语义由 L1 Case 服务决定，AIP 只消费确定的 Run exact ref。

## 15. API/事件接缝

目标新增的是编排适配层，不复制现有 AIP authority：

```text
POST /v1/aip/investigations:compile
POST /v1/aip/investigations/{taskRunId}:request-data
POST /v1/aip/investigations/{taskRunId}:review-stage
POST /v1/aip/investigations/{taskRunId}:prepare-handoff
GET  /v1/aip/investigations/{taskRunId}/projection
```

内部优先组合现有 canonical API，而不是直接访问 Store。新增 API 是否必要须在 W0 ADR 中以 OpenAPI 聚合和重复能力审查裁决。

### 15.1 跨权威一致性

AIP 不参与跨数据库事务。所有接缝采用 Receipt-first Saga：

1. L1 Run 服务本地事务写 `PREPARING` Run 与 Outbox；
2. AIP 以 trigger idempotency key 编译 Task/Plan/TaskRun，并写不可变 `CompilationReceipt`；
3. L1 只用 Receipt 的 exact refs/hash CAS 绑定 Run；
4. AIP Stage 产出 candidate artifact，L1 校验并发布正式领域 revision；
5. L1 返回 `ArtifactPublicationReceipt` 后，AIP 才完成对应 Step；
6. Data/Adapter 与 Ontology 同样通过 Fulfillment/Hydration Receipt 恢复 Checkpoint；
7. 超时、重复、乱序、回写失败统一由 ReconcileJob 对账，禁止盲目重试或创建第二份 TaskRun/Artifact。

领域事件和 AIP event 各自由所属权威生成序列；跨层只保存对方 exact ref、sequence 和 hash，不改写对方时间线。

关键事件：

- `InvestigationCompiled`
- `InvestigationCompilationReconciled`
- `DataRequirementRequested`
- `DataRequirementFulfilled/Blocked`
- `StageArtifactSubmitted`
- `StageArtifactPublished/Rejected`
- `StageEvalCompleted`
- `StageReturned/Accepted`
- `GrowthPlanRevisionDraftPrepared`
- `InvestigationHandoffIssued/Decided`
- `InvestigationEffectMatured`

事件只包含 refs、状态、hash 和安全摘要，不含 PII/Secret/模型响应正文。

## 16. Readiness 组合门

启动或恢复任一 Stage 时重新检查：

```text
Case exact revision
+ TaskBrief exact revision
+ LogicRevision / StageTemplateRevision exact refs
+ SkillRevision[] / SkillBindingSet exact refs
+ ResponsibilityPlanRevision exact ref
+ SourceReadiness at cutoff
+ Ontology/Semantic readiness
+ Evidence coverage
+ Provider Health 3/3 at start time
+ Model/Route/Policy/Eval exact refs
+ Capability/Skill Binding readiness
+ Budget/Capacity
+ Responsibility coverage
= eligible stage start
```

当前 `AOS-000283` 只证明既有 Workshop 96/96 工程链、W8-12 浏览器合同和 BI-W0 方案整改事实，发布结论仍为 `NO_GO / BACKEND_SECURITY_RED`；它没有为新增“生意探究”签发同截点 Provider Health、SkillBindingSet、AgentRun 或 SourceReadiness 运行收据，因此本方案不能把六数字同事或自动研究标为 runnable。

## 17. 测试与验收

- 编译同输入同 hash 幂等，异 hash 冲突；
- Logic/Skill/Binding/Responsibility 任一 exact ref 缺失、漂移、跨租户或过期时编译失败关闭；
- 同一输入编译得到确定性 ordered Skill refs 与同 hash CompilationReceipt；
- `SkillContributionView` 只来自服务端 exact refs，不能由角色名、页面进度或产物存在反推；
- Case/Run/TaskRun/Checkpoint 跨租户 fail-closed；
- required facts 缺失生成 DataRequirement 并暂停；
- FulfillmentReceipt exact ref 不匹配不能恢复；
- ResearchJob timeout 保持 unknown，Reconcile 前不成功；
- 三波顺序不可跳跃，Return 生成 successor；
- Evidence/Eval drift 阻断 Stage 与 Handoff；
- 私有推理链、Secret、PII、Cookie、Provider body 不进入持久化；
- `GrowthPlanRevision(DRAFT)` 未产生人工批准的 `APPROVED` successor 时不能 materialize；
- Action 未批准不能触达、发布或修改平台；
- Effect maturity 未到只显示 pending；
- `org-org/dev-project` 正向、`dev-org/dev-project` 隔离负向；
- restart 后 TaskRun/Checkpoint/ResearchJob/Decision 可恢复。
