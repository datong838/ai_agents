## FDE 复合定义声明（消除概念混淆）

**本专项标题"FDE 全链路"是一个复合覆盖术语，不是 [13-FDE 技能编排方案](../13-FDE技能编排方案/00-总览-从静态文档到可编排技能链.md) 定义的"FDE"。** 为消除歧义，明确如下：

| 术语 | 在本专项的含义 | 在 13-FDE 的含义 | 关系 |
|---|---|---|---|
| **FDE 全链路**（本专项标题） | 端到端接入的 4 层复合覆盖：**数据 Pipeline + 本体 OT + AIP Logic + 工作台 Workshop** | — | 本专项自定义术语 |
| **FDE 技能编排**（13-FDE） | — | 6 步数据接入技能编排链（对话理解→认证→API 探索→字段映射→同步配置→测试验证） | 13-FDE 的权威定义 |
| **Pipeline** | §5 的 7 条数据 ETL 管道（Source→TenantFilter→Project→Normalize→...） | FDE 技能 5（同步配置）的下游产物 | 本专项 §5 使用此义 |

**本专项 §4"FDE 组合交付结构"讲的是 Bundle 模块化组合锁（domain+solution+platform+overlay），与 13-FDE 的接入编排技能链是不同概念。** 实施"接入一个新平台"的 AI 化编排见 13-FDE，不在本专项范围。

## 1. 本次结论

微商城数据源真实可达，表结构与核心数据量已完成只读核验；但现有接入脚本和旧方案**不能直接实施**。原因如下：

1. 当前数据库账号对 `niushop_b2c_v5` 拥有全权限，服务端 `read_only=0`，不满足生产只读 Connector 要求。
2. 现有 `qyh_data_access.py`、`qyh_bootstrap_e2e.py` 默认全量读取，并直接调用旧式 ingest 写入遗留 `obj_instance`，绕过可信 Pipeline/Dataset 链路与 C0.2 租户安全闭环。
3. 当前 Pipeline 画布支持节点、连线、拖动和图结构保存，但生产 resolver/executor 尚未注册；JOIN 目前是可视化配置能力，不是可交付的生产执行能力。
4. 旧脚本创建 Pipeline 和 Schedule 的请求体已落后于当前 OpenAPI：Pipeline 缺少必填 `name`，Schedule 使用了旧的驼峰字段与 ingest 结构。
5. 当前可信本体基线是 7 个核心 OT：`Shop`、`Product`、`ProductSku`、`Category`、`Order`、`OrderLine`、`Shipment`。为支撑获客与成交闭环，隐私最小化的 `CustomerLite` 前移到 D1.5 增长扩展；完整 Customer、Payment、Refund 仍在 D2。
6. AIP Logic 已有自由画布、端口拖线、方向箭头、可信 dryRun、运行历史、Evals 与发布治理；外部查询、LLM、Tool、Action 仍需显式注册适配器，未注册必须失败关闭。

因此，本专项按“**先只读发现与配置清单，再补通用执行能力，最后分波次实施**”推进，不能运行旧的一键全量脚本。

## 2. 线上库只读核验快照

### 2.1 核验方式与安全边界

- 日期：2026-08-02（Asia/Shanghai）。
- 链路：本机 `127.0.0.1:13306` 经 SSH 隧道访问远端 MariaDB。
- 事务：`SET SESSION TRANSACTION READ ONLY` + `START TRANSACTION READ ONLY`，结束后 `ROLLBACK`。
- 查询范围：`information_schema`、表计数、字段/索引、状态聚合与时间范围。
- 未读取或输出：姓名、手机号、地址、OpenID、订单号、支付号等业务明细。

### 2.2 数据库事实

| 项 | 只读核验结果 | 实施判定 |
|---|---:|---|
| 数据库引擎 | MariaDB 10.3.39 | Connector 需按 MariaDB 10.3 兼容性验证 |
| 基础表 / 视图 | 302 / 0 | 旧文档“302 表”准确；不能依赖现成 VIEW 完成 JOIN |
| 服务端只读 | `0` | 不可作为安全保证 |
| 当前账号权限 | 业务库全权限 | **P0：实施前必须创建专用只读账号** |

| `ns_goods` / `ns_goods_sku` | 65 / 73 | 商品与 SKU 可进入 D1 |
| `ns_goods_category` | 11 | 分类可进入 D1 |
| `ns_order` / `ns_order_goods` | 177 / 227 | 订单头行可进入 D1 |

### 2.3 已纠正的字段事实

| 错误旧口径 | 真实字段 / 处理 |
|---|---|
| `ns_order.order_sn` | `order_no` |
| `ns_order.user_id` | `member_id` |
| `ns_order.ship_status` | `delivery_status` |
| `ns_order_refund` | 该表不存在；退款状态在 `ns_order` / `ns_order_goods`，另有退款相关日志/支付表需 D2 单独核验 |
| `ns_pay.pay_id` | 主键为 `id` |
| `ns_express_delivery_package.package_id` | 主键为 `id` |
| `order_money` 字符串清洗 | 实际为 `decimal(10,2)`；只需精度/非负校验，不做字符串转数值 |
| `ProductVariant` | 当前平台统一命名为 `ProductSku` |

### 2.4 正式接入前的数据库门禁

必须由数据库管理员创建专用账号，例如 `aos_niushop_ro`，并满足：

```sql
-- 示例权限目标，不在本次执行
GRANT SELECT, SHOW VIEW ON niushop_b2c_v5.* TO 'aos_niushop_ro'@'127.0.0.1';
```

验收要求：

- `SHOW GRANTS` 只能包含最小只读权限；不得有 INSERT/UPDATE/DELETE/DDL/FILE/SUPER。
- Connector secret 由 Secret 管理或运行环境注入，API 请求和配置清单只保存 `secret_ref`。
- 连接级设置 `read_only` 事务；超时、行数、字节数、并发数均有上限。
- SSH 隧道只绑定回环地址，保留心跳和断线重连，不开放公网数据库端口。

## 4. FDE 组合交付结构

专项实施不再使用一个“一键全量 bootstrap”，也不再把栖月汇、Niushop、电商本体和经营逻辑写进同一个 Bundle。栖月汇首期交付是一个不可变组合锁：

```text
domain.ecommerce.core@1.x
+ solution.ecommerce.operations-base@1.x
+ solution.ecommerce.growth@1.x
+ platform.ecommerce.niushop@1.x
+ InstanceOverlay integration.qiyuehui.niushop@revision
= composition.lock@sha256
```

| 资产归属 | 本专项交付物 |
|---|---|
| `domain.ecommerce.core` | 7 个核心 OT、Link、唯一键/租户键、数据质量和隐私契约 |
| `solution.ecommerce.operations-base` | L01～L06、W01～W04 的去 Niushop 化逻辑、Evals 和能力依赖 |

## 5. 数据层与 7 条 Pipeline 规格

### 5.1 通用强制节点

每条管道都使用以下骨架：

```text
Source → TenantFilter → Project → Normalize → Validate → Deduplicate
       → QualityGate ┬→ Dataset / OT sink
                     └→ DLQ（只存键、错误码与脱敏摘要）
```

强制配置：

- `org_id`、`project_id` 由实施上下文注入，不能仅作为普通业务 props。
- `site_id=1` 是源过滤和 Sink 租户键的一部分。
- 唯一键统一加源命名空间：`niushop:{site_id}:{source_pk}`。
- 时间字段从 Unix 秒转换为带时区 UTC 时间；`0` 转 `null`，不得解释成 1970 年业务事件。
- 增量游标采用稳定二元组 `(watermark, primary_key)`，同一时间戳不得漏行。
- 每日低峰做范围重扫并按唯一键幂等覆盖，以捕捉仅状态变化但缺少 `modify_time` 的表。
- 映射、校验、DLQ、Sink 任一节点无真实 executor 时整条运行失败，不得返回 SUCCEEDED。

### 5.2 管道清单

| ID | OT | 源表 / 主键 | 源过滤 | 增量与对账 | 关键映射/校验 |
|---|---|---|---|---|---|
| P01 | Shop | `ns_site.site_id` | `site_id=1` | 每日快照 | `shop_id=niushop:1`；名称非空 |
| P02 | Product | `ns_goods.goods_id` | `site_id=1 AND is_delete=0` | `(modify_time,goods_id)`；`modify_time=0` 回退 `create_time` | `price decimal(10,2)` 非负；状态枚举；`0` 时间转 null |
| P03 | ProductSku | `ns_goods_sku.sku_id` | `site_id=1 AND is_delete=0` | `(modify_time,sku_id)` | `product_id` 指向 P02；价格/库存非负；孤儿进 DLQ |
| P04 | Category | `ns_goods_category.category_id` | `site_id=1` | 每日快照 | `pid=0` 为根；检测分类环和孤儿父级 |
| P05 | Order | `ns_order.order_id` | `site_id=1` | 初装 `(create_time,order_id)`；每小时重扫最近 7 天；每日全状态对账 | `order_no`；`member_id` 仅保留关联键；状态四元组；金额 decimal |
| P06 | OrderLine | `ns_order_goods.order_goods_id` | `site_id=1` | `(create_time,order_goods_id)` + 最近 7 天重扫 | 指向 Order/Product/ProductSku；数量/金额非负；退款/履约状态保留 |
| P07 | Shipment | `ns_express_delivery_package.id` | `site_id=1` | 时间字段可用性核验后确定；未通过前每日快照 | 指向 Order；物流号按敏感级别遮罩；包裹主键是 `id` |
| P08 | CustomerLite | `ns_member.member_id` | `site_id=1` | `(modify_time, member_id)`；D1.5 才落地 | **隐私最小化映射**：只保留 `member_id`/`member_level`/`create_time`/`status` 等脱敏键；**不读** `mobile`/`wx_openid`/`nickname`/`avatar`/`reg_address`；订单聚合由 P05 通过 `placedByLite` 反向 Join 产生 |

> P08 在 D1.5 增长扩展才落地，但前置依赖 `placedByLite` Link（见 §5.4）已在 D1 P05 侧保留 `member_id` 关联键，使 P08 可以无缝追加而不需要回改 P05。P08 的 frozen 规格见 [frozen/02 P08](./frozen/02-pipeline-manifest.yaml)。

### 5.3 为什么 D1 不做多表 JOIN Sink

核心对象先按单表稳定落地，再由 Link 建关系：

- 避免把视觉 JOIN 误当生产执行能力。
- 避免一对多 JOIN 造成 Order/Product 行膨胀和重复覆盖。
- 允许各表独立增量、独立 DLQ、独立回滚。
- 聚合 Dataset 只有在通用 JOIN executor、预览一致性和负向测试完成后才能新增。

### 5.4 核心 Link

| Link | From → To | 来源字段 | 完整性门禁 |
|---|---|---|---|
| `hasSku` | Product → ProductSku | `goods_id` | SKU 不得指向不存在 Product |
| `inCategory` | Product → Category | `category_id` | 多分类字符串需先定义拆分契约 |
| `contains` | Order → OrderLine | `order_id` | 行必须有订单头 |
| `forProduct` | OrderLine → Product | `goods_id` | 缺失进入 DLQ，不自动造对象 |
| `forSku` | OrderLine → ProductSku | `sku_id` | `sku_id=0` 规则需样本核验 |
| `ships` | Shipment → Order | `order_id` | 包裹必须有订单头 |
| `placedByLite` | Order → CustomerLite | `member_id` | 仅使用脱敏客户键，不把 PII 带入 Order 或普通 Logic |

`CustomerLite` 在 D1.5 作为增长扩展落地，只含脱敏键、生命周期、授权、订单聚合和可解释标签；完整 `Customer`、`Payment`、`Refund` 及敏感 Link 延后至 D2，避免模型漂移与隐私越权。

#### 5.4.1 核心 OT 关键属性与派生指标（L01-L03 input 真实来源）

7+1 OT 不仅给出唯一键，还必须显式投影出上层 AIP Logic 需要消费的属性。**派生指标**（标记 Δ）必须由 Pipeline 的 Normalize/QualityGate 节点计算后写入 OT，不能由 Logic 自行计算——保证 Logic 拿到的是可信产物。

| OT | 直接属性（节选） | 派生指标 Δ | 派生口径（基于 [frozen/01 schema fingerprint](./frozen/01-schema-fingerprint.md)） | 下游消费者 |
|---|---|---|---|---|
| `Shop` | `shop_id`/`site_name` | — | — | W01 顶栏站点信息 |
| `Product` | `goods_id`/`price`/`goods_stock`/`goods_state`/`is_delete` | `quality_score Δ` | `evaluate > 0` 时 `quality_score = evaluate_haoping / evaluate`；否则 `null`（无评价数据） | **L01** input、W02 质量告警列 |
| `ProductSku` | `sku_id`/`product_id`/`stock`/`price` | `stock_health Δ` | `stock <= goods_stock_alarm` → `low`；`0 < stock <= alarm` → `watch`；否则 `ok` | L04（库存风险）、W02 低库存队列 |
| `Category` | `category_id`/`pid`/`level` | — | — | W02 分类树 |
| `Order` | `order_id`/`order_no`/`member_id`/`order_status`/`pay_status`/`delivery_status`/`refund_status`/`order_money`/`pay_time`/`create_time`/`is_lock`/`commission_risk_flag` | `risk_score Δ` | `base=0.0`；`commission_risk_flag=1` → +0.40；`refund_status∈{-3,3}` → +0.30；`is_lock=1` → +0.20；`order_status=0 AND pay_status=0 AND now-create_time>24h` → +0.10；截断到 `[0,1]` | **L02** input、W01 异常订单表 |
| `OrderLine` | `order_goods_id`/`order_id`/`goods_id`/`sku_id`/`num`/`refund_status` | — | — | W01 订单详情行 |
| `Shipment` | `id`/`order_id`/`delivery_no`/`delivery_time` | `overdue_hours Δ` | SLA_HOURS=48；`delivery_time=0 AND Order.pay_time>0` 时 `overdue_hours = max(0, (now - Order.pay_time - 48h) / 3600)`；否则 `null`（已发货或未支付不计算） | **L03** input、W01 SLA 队列 |
| `CustomerLite`（D1.5） | `member_id`/`member_level`/`status`/`create_time` | `order_count Δ` / `last_order_days Δ` | 由 P05 通过 `placedByLite` 反向聚合，按 `member_id` 计算 | W03 客户分群、增长 Logic |

> **派生口径的诚实声明**：以上派生指标在 D1 实施 P01-P07 时必须同步落地到 OT schema，否则 L01-L03 的 input 字段就是无源之水。`quality_score`/`risk_score`/`overdue_hours` 的具体阈值（0.98/0.80/24h 等）属于业务规则，在 Evals 用例中固化；派生公式变更等同于 OT schema 变更，需走 OT 增量一致性方案审批。

#### 5.4.2 OT 属性与上层 Logic 的输入端口对齐

```text
P02 quality_score Δ  ─┐
                       ├─→ L01 input.quality_score
P02.evaluate_haoping ──┘     (Logic 只读，不重算)

P05 risk_score Δ  ────→ L02 input.risk_score

P07 overdue_hours Δ ──→ L03 input.overdue_hours
```

如果 L01-L03 在 dryRun 时检测到 input schema 引用了 OT 中不存在的属性，QualityGate 必须失败关闭并报错"上游 OT 缺投影"，不能让 Logic 凭空取到 null。

## 5.5 4 层纵向支撑矩阵（数据→本体→AIP→工作台）

本表是 4 层接入"底层对上层支撑是否足够"的单点证据。**任一空格即代表该波次的端到端支撑链有缺口，必须在该波次启动前补齐**。

| 业务场景 | 第 1 层 Pipeline | 第 2 层 OT（含 §5.4.1 派生指标） | 第 3 层 AIP Logic | 第 4 层 Workshop | 端到端状态 |
|---|---|---|---|---|---|
| 商品质量监控 | P02 / P03 | `Product.quality_score Δ` | **L01** 数据质量门禁 | **W02** 商品与库存运营台 → 质量告警列 | D1 可发布 |
| 订单风险分诊 | P05 / P06 | `Order.risk_score Δ` | **L02** 订单风险分诊 | **W01** 订单与履约运营台 → 异常订单表 | D1 可发布 |
| 履约 SLA 监控 | P05 / P07 | `Shipment.overdue_hours Δ` | **L03** 履约 SLA 分诊 | **W01** 订单与履约运营台 → SLA 队列 | D1 可发布 |
| 库存风险预警 | P02 / P03 | `ProductSku.stock_health Δ` | L04 库存风险（适配器未注册） | **W02** → 低库存队列 | **D2** 受阻：`query_inventory` Tool adapter 未就绪 |
| 分润异常监控 | P05 / P06 + D3 专项 | D3 专项 OT/属性 | L05 分润异常（D3 数据未就绪） | **W04** → 分润面板 | **D3** 受阻：D3 专项表/OT 未落地 |
| 每日运营摘要 | P01-P07 全量 | 全量 OT 聚合 | L06 每日运营摘要（LLM/Metrics 适配器未就绪） | 全部 W0x 顶栏 KPI 区 | **D2** 受阻：Metrics Tool / LLM adapter 未就绪 |
| 客户分群与触达 | P05 + P08（D1.5） | `CustomerLite` + `order_count Δ` / `last_order_days Δ` | G2 增长母方案 Logic（非本专项 L0x） | **W03** 客户与私域运营台 → 客户分群/触达草稿 | **D1.5** 可发布最小版 |

**矩阵阅读规则**：

- 端到端状态 = 该行**最弱一层的就绪状态**（木桶原理）。
- 任一行的 Pipeline/OT/Logic/Workshop 4 格不能为空——空格即 4 层支撑链断点。
- D1 可发布的三条链（质量/风险/SLA）其 OT 派生指标必须在 D1 实施 Pipeline 时同步落地，不能延后。

## 6. AIP Logic：6 条数据与运营基础链路

本节 6 条 Logic 用于数据质量、订单风险、履约、库存和运营摘要，是栖月汇数据底座辅助链路，**不等于**六数字同事的增长 Logic。数据参谋、内容官、导购顾问、客服专员、私域管家和活动策划师的 37 条目标 Logic 由通用母方案统一定义，按 G0～G6 分波实例化。

### 6.1 当前可发布的 3 条确定性链路

下面的配置字段严格使用当前 dryRun 节点契约。发布前必须为表达式引擎建立可验证样例，不能把伪代码直接落库。

#### L01 数据质量门禁

```text
input → get_property(quality_score) → branch(pass/block) → handoff
```

| 节点 | kind | config |
|---|---|---|
| N1（节点 ID `input`） | `input` | `{"schema":{"type":"object","required":["quality_score"],"properties":{"quality_score":{"type":"number"}}}}` |
| N2（节点 ID `quality_score`） | `get_property` | `{"property":"quality_score"}`（唯一上游即 N1） |
| N3 | `branch` | `{"paths":[{"id":"pass","label":"通过","condition":"quality_score >= 0.98"},{"id":"block","label":"阻断","default":true}]}` |
| N4a | `handoff` | `{"decision":"quality_pass","handoff_to":"risk_agent","artifacts":["quality_report"],"open_qs":[]}` |
| N4b | `handoff` | `{"decision":"quality_block","handoff_to":"draft_inbox","artifacts":["dlq_summary"],"open_qs":["确认源数据或映射修复"]}` |

> **input 字段来源声明（B3 断点修复）**：`quality_score` 必须来自 §5.4.1 的 `Product.quality_score Δ`（由 P02 在 Normalize 节点按 `evaluate_haoping / evaluate` 派生）。Logic 不得自行重算，dryRun 时若 OT 中无该投影则失败关闭。下游 Workshop 字段：W02 质量告警列。

#### L02 订单风险分诊

```text
input → get_property(risk_score) → branch(high/normal) → handoff
```

- `input.schema` 使用 JSON Schema 对象，要求 `risk_score:number`；不能写字符串版本号。
- `get_property.property=risk_score`，该节点 ID 固定为 `risk_score`，供分支表达式引用。
- high 条件：`risk_score >= 0.80`；default 为 normal。
- high handoff 到 `risk_agent`，normal handoff 到 `draft_inbox`。
- 本波只生成决策与证据，不调用 `apply_action` 写订单。

> **input 字段来源声明（B4 断点修复）**：`risk_score` 必须来自 §5.4.1 的 `Order.risk_score Δ`（由 P05 在 QualityGate 节点按 `commission_risk_flag`/`refund_status`/`is_lock`/滞留时长加权派生，截断到 `[0,1]`）。Logic 不得自行重算。下游 Workshop 字段：W01 异常订单表的 risk 标签列。

#### L03 履约 SLA 分诊

```text
input → get_property(overdue_hours) → branch(overdue/watch/ok) → handoff
```

- `get_property` 节点 ID 固定为 `overdue_hours`；overdue：`overdue_hours >= 24`；watch：`overdue_hours >= 0`；ok 为 default。
- overdue/watch 进入 `draft_inbox`，附 `shipment_id` 的非敏感引用和 SLA 证据。
- 不直接调用商城发货、催单或改状态 API。

> **input 字段来源声明（B5 断点修复）**：`overdue_hours` 必须来自 §5.4.1 的 `Shipment.overdue_hours Δ`（由 P07 在 QualityGate 节点按 `max(0, (now - Order.pay_time - 48h) / 3600)` 派生；已发货 `delivery_time>0` 或未支付 `Order.pay_time=0` 时取 `null` 不计算）。Logic 不得自行重算。下游 Workshop 字段：W01 SLA 队列的超时小时列。

### 6.2 适配器就绪后才可发布的 3 条链路

| ID | 链路 | 目标节点 | 当前阻断 |
|---|---|---|---|
| L04 | 库存风险 | input → use_tool(query_inventory) → transform → branch → handoff | `query_inventory` Tool adapter 未注册 |
| L05 | 分润异常 | input → use_tool(query_commission) → transform → branch → handoff | D3 专项 OT/数据集和 Tool adapter 未完成 |
| L06 | 每日运营摘要 | input → use_tool(query_metrics) → use_llm → handoff | Metrics Tool、LLM adapter、脱敏输入契约未完成 |

外部节点的严格配置目标：

- `use_tool`：`{"tool":"<registered_name>","arguments":{...}}`
- `use_llm`：`{"prompt":"<versioned_prompt>","model":"<approved_model>"}`
- `apply_action`：只能在 C0.2 后使用 `{"action":"<registered_action>","edits":[...]}`，且必须 Draft → Approve。

### 6.3 Logic 发布门禁

- 每条链至少 10 个确定性 Eval 用例，必须包含缺字段、边界值、非法类型、未知状态和下游不可用。
- L01-L03：`pass_rate=100%`、关键负向样例 `100%` 正确分支、同输入重复运行结果一致。
- L04-L06：适配器未注册时必须失败关闭；不得降级为假数据。
- 发布只能引用通过 Evals 的不可变 revision；修改节点或配置后自动回到 Draft。

D 波（数据底座 + 工作台实施）与 G 波（增长参谋长业务能力分波）是两个正交维度，本表声明两者的并行门禁关系，避免实施时漏掉跨波次依赖。
