## 2. 上下文与动机

### 2.1 为什么要 D4

D1/D1.5 把 7 OT + CustomerLite（共 8 OT）跑通了只读孪生，但从**电商运营业务闭环视角**看还有四个硬缺口：

| 缺口 | 表现 | 后果 |
|---|---|---|
| 横切底座不全 | 只有 Shop（site_id=1），没有 Weapp（三小程序并存）和 Config（业务开关） | 订单的 weapp_id 是裸数字，无法分端分析；业务开关变更无法孪生追踪 |
| 评价缺失 | Product/ProductSku 没有关联评价 | 商品表现宽表缺评分/评价文本，选品和营销没有输入 |
| 支付缺失 | Order.pay_status 是快照，没有独立 Payment OT | 无法回答"这笔钱到底付成功了吗？渠道退款走完了吗？"的核心问题 |
| 302 表衔接未文档化 | 大家都知道"有 302 张表"，但哪些进 OT、哪些 JOIN 用、哪些按需查、哪些完全不管，没有白纸黑字 | 后续工程师接盘会问：302 张表全做 OT 吗？不做的话要查去哪查？ |

### 2.2 D4 做什么（硬范围）

1. **补 4 个 OT**：Weapp（P09）/ SystemConfig（P10）/ ProductReview（P11）/ Payment（P12）
2. **12 OT 闭环确认**：把 8 已有 + 4 新增 = 12 OT 的业务语义、Link 关系、派生指标、在 302 表中的位置，白纸黑字冻结
3. **302 表 4 层衔接架构**：明确每一层消费多少张表、怎么消费、消费者是谁，写死下来
4. **停车场待办冻结**：把"本轮不做但以后可能做"的 ~13 OT 全部列出来，附带激活条件（不能只是"以后做"三个字）
5. **录入计划分阶段**：Phase A/B/C/D 四阶段，每阶段明确产物 + 退出门
6. **SyncTask 真实执行**：把 `run_sync_task` 从 mock（固定 rows=5000, duration=30s）改成真实触发 Pipeline 执行

### 2.3 D4 不做什么（硬边界，放停车场）

以下能力本波不做，激活条件见 §5：

- ❌ 不做 AftersaleTicket（售后工单 OT）—— 停车场 §5.1
- ❌ 不做 Coupon（券 OT）—— 停车场 §5.2
- ❌ 不做 CommissionLog（分润流水 OT）—— 停车场 §5.3
- ❌ 不做 ShareExperience（分享体验码 OT）—— 停车场 §5.3
- ❌ 不做 Dataset 4 个主题宽表 —— 停车场 §5.4（等 OT 稳了再上）
- ❌ 不做同步路由 1→N（一源多目标）—— 停车场 §5.4
- ❌ 不做写回微商城（生产写回）—— 停车场 §5.5（C0.2 未完成）
- ❌ 不修改 phase5_pipeline_engine 的 fail-closed 判定链路

#### 3.5.1 Canonical ID 冻结

所有 OT 均使用 `platform:shop_or_marketplace_id:业务主键`，当前微商城固定为 `niushop:1:*`；不得使用裸数字 ID。各类型规则如下：

| OT | Canonical ID |
|---|---|
| Shop | `niushop:1:{site_id}` |
| Weapp | `niushop:1:{weapp_id}` |
| SystemConfig | `niushop:1:{id}`；业务复合键保留在 properties 供查重 |
| Product | `niushop:1:{goods_id}` |
| ProductSku | `niushop:1:{sku_id}` |
| Category | `niushop:1:{category_id}` |
| ProductReview | `niushop:1:{id}` |
| Order | `niushop:1:{order_id}` |
| OrderLine | `niushop:1:{order_goods_id}` |
| Shipment | `niushop:1:{id}` |
| Payment | `niushop:1:{id}` |
| CustomerLite | `niushop:1:{member_id}` |

Link 两端必须引用以上 Canonical ID；方向和代码键以 `ecom_core_models.CORE_LINK_TYPES` 为准。类型由复合身份中的 `object_type` 隔离，跨店同业务主键因 `shop_or_marketplace_id` 不同而不碰撞。`eval_`、`pkg_`、`pay_`、`m_` 等旧文档前缀不得再作为运行时身份规则。

### 3.6 12 OT 派生指标与 G17 权威验收口径

下表同时冻结计算、eligible denominator、阈值、null 与空集合语义，是 D5 `G17-SPEC` 的唯一上位口径。`eligible_total=0` 一律记 `INCONCLUSIVE/NO_DATA`，不得用 0/0 冒充 GREEN。

| OT / 指标 | 计算与 eligible denominator | 阈值 | null 语义 | 空集合判定 |
|---|---|---:|---|---|
| Product.`quality_score` | `evaluate>0` 的 Product；`evaluate_haoping/evaluate` 截断到 `[0,1]` | 非空率 ≥90% | `evaluate<=0` 或缺失为 null | INCONCLUSIVE |
| ProductSku.`stock_health` | 全量 ProductSku；按 `stock` 与 `goods_stock_alarm` 分为 low/watch/ok | 非空率 ≥85% | `stock` 缺失为 null | INCONCLUSIVE |
| Order.`risk_score` | 全量 Order；base=0 并叠加分润、退款、锁定、停滞风险 | 非空率 ≥90% | 始终有值 | INCONCLUSIVE |
| Shipment.`overdue_hours` | `pay_time>0` 的 Shipment；已发货按 `delivery_time-pay_time`，未发货按 `now-pay_time`，超过 48h 的小时数，最低 0 | 非空率 ≥90% | 未支付或订单支付时间无法关联为 null | INCONCLUSIVE |
| CustomerLite.`order_count` | 至少存在一条 `Order.placedByLite` 的 CustomerLite；关联订单计数 | 非空率 ≥90% | 无关联为 null | Link 或 eligible 为 0 均 INCONCLUSIVE |
| CustomerLite.`last_order_days` | 同上；距最近关联订单 `createdAt` 的自然日数 | 非空率 ≥90% | 无关联或订单时间缺失为 null | Link 或 eligible 为 0 均 INCONCLUSIVE |
| ProductReview.`review_quality_bucket` | 全量 ProductReview；`score>=4.5` high，`score<=3.0` low，其余 mid | 非空率 ≥90% | score 缺失为 null | INCONCLUSIVE |
| Payment.`pay_duration_min` | `pay_time>0` 的 Payment；`(pay_time-_order_create_time)/60`，负值截断 0 | 非空率 100% | 未支付或订单创单时间无法关联为 null | INCONCLUSIVE |

G17 读取 `effective_properties = properties || derived_payload`；Payment 的 `_order_create_time` 只作管道内计算输入，不写入基础属性。派生更新必须使用独立 revision、CAS、Receipt 与同事务 Outbox。

> **W10 语义纠偏**：真实源 `ns_express_delivery_package` 只在包裹已创建后有记录，旧“仅未发货 Shipment eligible”口径会把真实 19 条已支付包裹全部排除，形成不可验收的空集合。W10 将指标冻结为“已支付 Shipment 的 48 小时履约时长”：已发货测实际耗时，未发货测当前等待时长；这不改变 OT、Link 或权威存储架构，只修正指标的业务定义与源表生命周期不自洽问题。

### 4.3 分类判定规则（以后新表/插件进来也按这个分）

1. **进 A 类（OT）**：必须同时满足 3 个条件：(a) 有唯一主键和业务语义 (b) 有下游 Logic Graph 或 Workshop Widget 明确要消费它 © 有 Link 能挂到 12 OT 构成闭环。否则降格。
2. **进 B 类（JOIN 维度）**：只有"name 映射/枚举翻译"语义，没有独立业务实体（如 express_company 只是快递公司名的字典，不能独立存在）。
3. **进 C 类（extra 挂接）**：本身是"某主实体的附属明细/日志/轨迹"，离开主实体无意义（如 order_log 只是订单状态变化记录）。
4. **进 D 类（配置类·按需）**：以"定义/开关/模板/活动"为主，不是业务实体（如 promotion_seckill 只是"秒杀活动定义"，没有活动实例/订单关联就没意义）。
5. **进 E 类（不落孪生）**：纯运维/系统/后台管理用，和 C 端电商业务无直接关系。

## 9. 风险与规避

| 风险 | 影响 | 概率 | 规避措施 |
|---|---|---|---|
| P09 ns_weapp 表只有 3 行（10/11/9），Weapp OT 数据量太少没意义 | 看起来像"为了凑 OT 做 OT" | 高 | 但 Order.weapp_id 关联查询时必须有 Weapp OT 才能转名字；3 行也要做（参考 P01 ns_site 也只有 1 行 Shop，同样必须有）。在文档 §3.1 明确注释："Weapp OT 即使只有几行，作为 Link 关联字典必须存在" |
| P10 ns_config 表 value 是 JSON，字段多样，normalize 复杂 | 做 P10 配置映射工作量大 | 中 | P10 SystemConfig OT 不把每个 config_key 展开成独立字段，只保留通用结构：`properties.config_key` + `properties.app_module` + `properties.weapp_id` + `properties.value_json`（原 JSON 字符串不展开 + 可选 `summary` 字段提取 3 个以内关键字段）。后续 Logic 需要具体某个配置时再单独抽字段。不要为 SystemConfig 做 50 个属性。 |
| P11 ProductReview 图片关联 MediaSet 做不做 | 不做的话评价图片只有 URL，没进平台媒体能力 | 低 | 先不做。挂在 ProductReview.properties.extra.review_images 数组里（只存 URL 列表，不写 MediaFile 表）。MediaSet 关联能力放停车场，需要"评价图片 AI 鉴黄/去重/标签"时再激活 |
| P12 Payment 关联 Order 有两条路径（out_trade_no vs relate_id=order_id），Link 关联二选一会不会错 | Link 漏关联或重复关联 | 中 | 优先用 `relate_id=order_id` 做 Order↔Payment Link（强关联）；`out_trade_no` 作为次要校验字段写入 `Payment.properties.external_order_no` 作为对账用，不做双 Link。避免同一关系两条 Link 重复 |
| SyncTask 真实执行后 Pipeline 失败 → SyncRun 标 failed → 运营看到告警吓一跳 | 误报影响信任度 | 中 | Phase B G8 先专门测 DLQ 入队 + 失败分类，SyncRun.error 用人类可读的错误码（如 `E_SSH_BROKEN=SSH断了，等下次重连自动恢复`，不要把几十行 traceback 扔到前端） |
| 302 表 §4.2 的 A/B/C/D/E 分类会不会以后表多了要重新分 | 分类工作重复 | 低 | §4.3 写了"分类判定规则"，以后新表/插件进来按 5 条规则自动分，不需要再开会。D 类最多（配置类），不会频繁变动 |
| 停车场 11 条会不会永远"停在停车场"没人管 | 重要能力永久搁置 | 低 | §5 每条都写了**激活触发器**（不是模糊的"以后做"），如"退款率连续 2 个月 > 5% → 激活 PA-1 售后 OT"，这些触发器是可量化的，每月开项目状态会时扫一遍停车场条目看有没有命中激活条件。由项目负责人执行，不能让我忘了 |
