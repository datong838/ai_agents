## 一、实验设定

### 1.1 为什么选择栖月汇作为实验载体

前面三个品牌推演主要回答“大型平台电商如何用 Palantir 模式重构运营”。栖月汇是一个不同且更尖锐的样本：

| 维度 | 淘系品牌旗舰店 | 栖月汇微商城 |
|---|---|---|
| 流量来源 | 平台搜索、推荐、广告、直播 | 地推、熟人关系、分享、社群和待建设的公域内容 |
| 交易基础设施 | 平台成熟 | 微信小程序自有商城 |
| 数据主权 | 平台侧数据残缺 | 订单、会员、商品、分润数据相对完整 |
| 核心难题 | 跨平台决策和大规模协同 | 缺少稳定获客引擎，经营动作依赖少数个人 |
| 组织能力 | 专业运营团队 | 小团队、兼职推广者、少量渠道伙伴 |
| 成败判据 | 提升大盘效率 | 能否获得并留住“非店主的新消费者” |

栖月汇的数据量很小，但决策密度并不低：选什么商品、在哪个渠道获客、由谁承接咨询、如何结算分佣、何时复购、何时停止一个无效动作，都需要跨订单、会员、商品、内容、渠道和分润信息判断。

因此本实验可以压测一个更根本的问题：

> **当商家缺少成熟流量和专业团队时，Palantir 模式能否先帮助它发现“经营模型为什么不成立”，再把一个新的获客假设变成可观测、可推演、可行动、可归因和可证伪的闭环？**

### 1.2 当前线上事实快照

| 信号 | 已验证结果 | 证据类型 | 解释限制 |
|---|---:|---|---|

| 当前合格店主 | 34 人 | 线上只读库 | 当前状态不能证明资格在购买前已存在 |

### 1.3 经营侧补充事实

| 经营侧输入 | 对实验的影响 |
|---|---|
| 订单主要依赖地推 | 数据库没有地推活动字段，需补充归因后才能量化 |
| 佣金第一名是公司合伙人，也是唯一拥有美容店的人 | 第一名是特殊渠道节点，不能代表普通店主可复制性 |
| 美容店渠道竞争强，竞品多且有实力 | “复制更多美容店合伙人”不应作为默认增长路线 |
| 普通店主多数沉默，送店铺无法形成持续推广 | “人人开店”假设需要被否证或重构 |

这里得到一个重要修正：

> **当前跑通的不是“普通人开店并持续经营”，而是“少数具备线下客户资产的人能够产生交易”。但美容店渠道本身又很难低成本扩张。**

### 1.4 本次实验命题

本次不再推演“如何把店主招得更多”，而推演以下命题：

> 如果把获客策略、内容资产、咨询成交和实验设计收回公司集中运营，把微信小程序定位为交易真源、会员沉淀和复购承接工具，再把达人/KOC/店主/美容店改造成可归因的获客或服务角色，Palantir/AOS 能否帮助栖月汇形成一套可学习、可审计、可复制的私域电商经营闭环？

### 1.5 待验证假设

| ID | 假设 | 可证伪条件 |
|---|---|---|
| H1 | 公司集中获客比“人人开店”更能稳定产生非店主新客 | 两轮实验后，新模式仍不能产生稳定非店主有效订单 |
| H2 | 小程序的核心价值是成交、身份、履约和复购，不是独立获客 | 有证据证明小程序自然流量可稳定贡献大部分新客 |
| H3 | 佣金应按可归因贡献结算，而非按店主身份自动叠加 | 身份型分佣在控制成本后仍显著优于贡献型分佣 |
| H4 | 先建薄本体与实验闭环，比一次接入全部营销表更快产生价值 | 最小对象集无法回答首批经营决策 |
| H5 | Scenario 是私域电商的一等能力 | 运营决策不需要事前方案比较即可稳定达到目标 |
| H6 | AOS 的主要价值是缩短“发现问题→决策→行动→复盘”周期 | 仅有报表即可达到同等行动采用率与经营改进 |
| H7 | 栖月汇案例可以抽象成中国私域电商通用解决方案 | 第二个不同类型商家无法复用核心对象、Logic、Action 和应用 |
| H8 | consent、归因和 Decision Lineage 是自动化的前提 | 缺少这些治理仍能安全、可解释地规模化运营 |

### 1.6 实验方法

```text
步骤1：从线上事实识别旧经营模型的失败结构
  ↓
步骤2：把“公司集中获客”定义为待验证的反事实方案
  ↓
步骤3：建立私域经营薄本体（Customer/Touch/Lead/Consultation/Order/Incentive/Experiment）
  ↓
步骤4：封装获客、咨询、分佣、复购和停止判断 Logic
  ↓
步骤5：只用 Draft/人工登记跑通 Action 与 Decision Lineage
  ↓
步骤6：模拟内容获客、咨询成交、复购和结算信任四个场景
  ↓
步骤7：实施 14/30/60/90 天分阶段实验
  ↓
步骤8：用可证伪 KPI 判定继续、调整或停止
  ↓
步骤9：从栖月汇实例抽象私域电商 L-Core、L-Pack、Adapter 和 Overlay
```

### 1.7 实验边界

- 本文不承诺公司集中获客一定成功，只定义如何验证。
- 不把用户经营判断伪装成数据库事实。
- 不自动发布内容、不自动加企微、不自动群发、不自动改价、不自动打款。
- 不假定微信视频号、朋友圈、企微或其他平台当前存在特定开放 API。
- 不把手机号、地址、openid 等 PII 放入实验分析数据集。
- 不用小样本结果直接外推中国全部私域商家。
- 不以本文改变 AOS 当前 M3-2 → M4 → M5 的实施顺序，也不解除 G0～G6 阶段门禁。

## 二、经营模式重构：从“人人开店”到“公司拥有获客系统”

### 2.1 旧模型的隐含假设

```text
给会员店主资格
  → 给店铺和商品
  → 店主主动推广
  → 店主带来消费者
  → 商城自动分佣
  → 店主持续经营
```

这个链路隐含四个未经验证的条件：

1. 普通店主有可触达的潜在消费者。
2. 普通店主愿意持续生产内容和跟进咨询。
3. 商品有足够差异化，能穿透熟人关系和竞品比较。
4. 佣金到账足够快，能够形成正反馈。

线上数据只能证明“少数人最终获得佣金”，不能证明上述四个条件在多数店主上成立。

### 2.2 新模型不是“公司包办一切”

“公司集中获客”应理解为公司集中拥有以下能力，而不是所有动作都由公司员工亲自完成：

| 公司必须拥有 | 可以由外部角色执行 |
|---|---|
| 获客策略与预算 | 内容拍摄、KOC 分享、达人发布 |
| 商品与消费者价值主张 | 美容师体验、团长社群说明 |
| 内容资产与版本 | 不同渠道的适配发布 |
| 线索归因规则 | 达人/KOC/门店带来的具体触点 |
| 咨询知识与成交 SOP | 人工顾问、合作服务点执行 |
| 分佣计算和结算 SLA | 第三方支付或人工确认打款 |
| 实验设计与停止线 | 渠道伙伴按被冻结方案执行 |
| 订单、复购和经营证据 | 微信小程序承接交易和会员 |

目标结构：

```text
公司集中经营系统
  ├─ 内容与商品策略
  ├─ 公域/半公域获客实验
  ├─ 统一咨询与成交 SOP
  ├─ 渠道归因与分佣治理
  └─ 复购与客户关系策略
            │
            ▼
达人 / KOC / 社群 / 合作服务点（可替换执行节点）
            │
            ▼
微信小程序（成交、支付、履约、会员、复购真源）
```

### 2.3 小程序的角色重新定义

| 不再要求小程序承担 | 小程序应成为 |
|---|---|
| 自己产生稳定自然流量 | 交易和支付真源 |
| 让每个会员经营完整店铺 | 单品/组合 Offer 的承接页 |
| 替代内容平台完成种草 | 内容触点后的可信商品事实页 |
| 替代顾问完成复杂咨询 | 咨询结果的下单与权益确认 |
| 自动解决复购 | 会员身份、订单历史和复购触发器 |
| 自动证明渠道贡献 | 带归因 token 的订单结果记录 |

### 2.4 角色重构

| 角色 | 主要贡献 | 不再承担 | 结算方式 |
|---|---|---|---|
| 公司运营中心 | 策略、内容、预算、咨询、实验、复购 | 依赖个人关系盲推 | 经营毛利 |
| 达人/KOC | 可归因新客触点 | 经营完整商城 | 新客首单佣金 |
| 普通会员 | 真实体验、轻量推荐 | 每日运营店铺 | 推荐佣金/积分，限首单 |
| 美容店/服务点 | 体验、咨询、服务履约 | 作为唯一规模化获客渠道 | 获客佣金或固定服务费，二选一或受控组合 |
| 私域顾问 | 咨询、需求识别、成交协助 | 自行承诺价格和功效 | 内部绩效或明确服务费 |
| 消费者 | 购买、反馈、复购、转介绍 | 被默认转成店主 | 会员权益和合规推荐奖励 |

### 2.5 分佣规则重构原则

保留分佣系统，但将“身份分佣”改成“贡献分佣”。

```text
一笔订单
  → 1 个主要获客贡献者（可选）
  → 1 个真实服务履约者（可选）
  → 公司咨询/成交（内部职责，不自动对外分佣）
  → 佣金总额受贡献毛利上限约束
```

硬规则：

1. 一笔订单只有一个主要获客归因。
2. 服务费必须对应可验证服务，不与同一贡献重复计算。
3. 公司内容/投流获得且公司成交的订单，不产生店主主佣金。
4. 达人/KOC 的佣金原则上限首单或冻结窗口。
5. 客户维护佣金必须有维护证据、有效期和频控，不永久继承。
6. 自购、资格购买不算新增消费者，不发外部获客佣金。
7. 历史已产生权益按原规则结算；新规则设切换时间，不追溯取消。
8. 佣金、技术服务费和其他渠道费用必须一起过毛利护栏。

贡献毛利护栏：

```text
可分配激励上限
= 订单净实付
- 商品成本
- 履约与支付成本估计
- 售后风险准备
- 目标经营利润
```

### 2.6 新模式仍可能失败

公司集中获客不是逃避困难，而是把困难从“无法观察的个人推广”变成“公司可控制的经营系统”。它仍可能因以下原因失败：

- 商品差异不足，内容无法建立购买理由。
- 目标消费者和主商品不匹配。
- 咨询能力不足，流量无法转化。
- 获客成本高于 90 天贡献毛利。
- 产品缺少复购周期或消费体验不稳定。
- 归因缺失，团队无法判断哪个动作有效。

因此实验目标不是证明新模式必胜，而是**尽快、低成本、可解释地得到继续或停止的证据**。

## 三、Palantir 决策四组件在私域电商中的类比

### 3.1 私域经营不是 CRM 通讯录，而是动态决策系统

```text
┌─────────────────────────────────────────────────────────────────────┐
│                 私域电商 Palantir 决策四组件                          │
├─────────────────────────────────────────────────────────────────────┤
│ Data              Logic              Action             Security    │
│ ─────────         ─────────          ─────────          ─────────   │
│ Member/Customer   获客机会评分        创建实验 Draft      consent     │
│ Touch/Lead        商品-人群匹配       创建咨询任务         频控/退订   │
│ Content/Offer     归因与增量评估      生成 Offer Draft     PII Marking │
│ Consultation      毛利安全分佣        分佣提案/人工确认     审批/CAS    │
│ Order/Outcome     复购/流失判断       复盘与下一轮计划      Lineage     │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.2 四组件 × AOS 映射

| Palantir 组件 | 私域电商含义 | AOS 承载 | 当前状态边界 |
|---|---|---|---|
| Data | 订单、会员、商品、触点、线索、咨询、分佣、实验 | Dataset + Ontology Object/Link/Funnel | Niushop 只读接入方案已存在；不是全部已上线 |
| Logic | 获客、咨询、毛利、归因、复购、停止判断 | Logic Runtime + TAOR + Evals | 电商 G0～G6 尚未授权编码 |
| Action | 生成计划、任务、Offer、结算提案和复盘 | Drafts + Action Bus + Receipt/Lineage | 初期只允许 Draft/人工登记 |
| Security | consent、频控、退订、PII、审批、职责分离 | Marking + Principal + maker-checker + immutable evidence | 必须复用平台内核，不做栖月汇旁路 |

### 3.3 与常见工具的差异

| 工具形态 | 擅长回答 | 通常缺失 | Palantir/AOS 增量 |
|---|---|---|---|
| 商城后台 | 订单和商品发生了什么 | 为什么发生、下一步试什么 | 经营本体 + 跨对象 Logic |
| CRM/SCRM | 联系谁、发什么 | 增量价值、毛利、实验污染 | Experiment + Attribution + 护栏 |
| BI | 指标怎样变化 | 谁批准了哪个行动、结果如何 | Action + Decision Lineage |
| 营销自动化 | 自动触达 | consent 语义、真实增量和跨渠道证据 | ContactPolicy + 冻结实验 |
| 通用 Agent | 生成建议和内容 | 工具权限、事实版本、执行审计 | Ontology 约束下的 Agent |

本实验要验证的不是 AOS 能否生成一篇私域文案，而是：

> **AOS 能否把“这次为什么要找这群人、用哪个内容、由谁执行、花多少钱、带来多少增量、是否伤害毛利和客户关系”保存成一个完整决策对象。**

## 四、栖月汇私域经营薄本体（Ontology）

### 4.1 建模纪律：先闭环，后完备

不把 Niushop 302 张表全部建成 Object Type。第一期只建能跑通“获客→咨询→成交→激励→复购→复盘”的最小对象集。

| `Order` | orderId | buyer、netPay、status、attributionToken | `ns_order` | `ITransaction` |
| `OrderLine` | orderGoodsId | sku、quantity、net、cost | `ns_order_goods` | `ITransactionLine` |

```text
DecisionRecord ──used──▶ ExperimentRevision / Outcome / OfferRevision
```

### 4.4 三条核心 Funnel

**获客与成交 Funnel**

```text
touch_observed
  → lead_created
  → consent_verified
  → consultation_started
  → offer_presented
  → order_paid
  → fulfilled
  → repeat_eligible
  → repeated|inactive
```

**激励 Funnel**

```text
contribution_observed
  → eligible
  → calculated
  → margin_checked
  → approved
  → paid|voided|disputed
```

**实验 Funnel**

```text
draft
  → frozen
  → running
  → stopped|completed
  → reviewed
  → adopted|rejected|iterate
```

### 4.5 平台侧代理对象

内容平台、达人平台或社交平台的数据主权不属于栖月汇。未知能力不能被伪装成完整对象，统一使用 Proxy Object：

```text
ChannelAccountProxy
  · provider
  · account_token（opaque）
  · capability_snapshot

ContentPublicationProxy
  · provider_object_token
  · content_revision_ref
  · observed_metrics（平台允许回传的聚合指标）

AudienceProxy
  · audience_token
  · aggregate_profile
  · size
  · observed_at
```

本体边界画在数据主权边界上；跨过边界的动作通过 Connector 委托平台执行，而不是假装拥有平台内部数据。

### 4.6 PII 与身份边界

- `CustomerLite` 不携带手机号、地址、openid 和聊天原文。
- 联系方式由未来 Connector 在渠道边界内解析 token。
- 跨渠道身份无法可靠匹配时，只做聚合比较，不强行合并。
- 小样本人群低于阈值时，不展示细分明细。
- 咨询文本先脱敏和安全处理，再生成结构化标签。

## 五、Logic 层：把经营判断封装成可检验能力

### 5.1 Logic 目录

| ID | Logic | 输入 | 输出 | 关键护栏 |
|---|---|---|---|---|
| L01 | 获客机会评估 | 渠道、内容、商品、预算、历史结果 | 机会排序 + 不确定性 | 不把相关性当增量 |
| L02 | 内容-商品-人群假设 | 产品事实、受众需求、内容资产 | 冻结实验假设 | 功效与价格合规 |
| L03 | 线索质量判断 | 触点、意图、咨询行为 | lead score + 跟进优先级 | 不使用敏感属性 |
| L04 | 咨询建议 | 客户需求、商品事实、库存、服务能力 | recommendation Draft | 不承诺医疗功效 |
| L05 | 毛利安全 Offer | 净价、成本、履约、预算 | Offer + margin floor | 低于 floor 禁止提交 |
| L06 | 贡献型分佣 | 归因、角色、订单、成本 | entitlement Draft | 单一主归因、总额 cap |
| L07 | 结算时效巡检 | dueAt、paidAt、状态、异常 | overdue alert | 不自动修改台账 |
| L08 | 复购机会评估 | 商品周期、订单、服务反馈、consent | repeat cohort + 计划 Draft | 频控和退订优先 |
| L09 | 增量与归因评估 | assignment、touch、order、refund、窗口 | observed/estimated/unknown | 保存口径和置信区间 |
| L10 | 继续/调整/停止建议 | KPI、护栏、样本、污染 | DecisionProposal | 口径冻结后不可改 |

### 5.2 贡献型分佣 Logic

```text
输入：
  order.net_pay
  order_line.cost
  acquisition_touch.primary_contributor
  service_fulfillment.actor
  commission_policy_revision
  fulfillment/payment/after_sale_estimate
  target_profit_floor

处理：
  1. 验证订单有效且非自购获客
  2. 验证主要获客触点唯一
  3. 验证服务动作是否真实存在
  4. 计算可分配激励上限
  5. 按角色规则生成 entitlement
  6. 若总激励超过 cap，返回 MARGIN_GUARD_DENIED

输出：
  IncentiveEntitlement Draft
  calculation_evidence
  policy_revision
  denial_reason（如有）
```

### 5.3 增量价值 Logic

不能只看“归因成交额”。至少同时计算：

```text
增量新客 = 实验组新付费消费者 - 对照组基线新付费消费者

90天贡献毛利
= 90天净实付
- 商品成本
- 退款损失
- 履约/支付成本
- 渠道与服务激励

获客效率 = 增量90天贡献毛利 / 获客总投入
```

没有随机或可信对照时，只输出“观察相关性”，不输出“增量因果”。

### 5.4 证据等级

| 等级 | 定义 | 可用于 |
|---|---|---|
| E0 未知 | 无可靠数据或口径 | 仅列为问题 |
| E1 观察 | 单组、单渠道、无对照 | 方向性判断 |
| E2 对照 | 同期对照或可信历史基线 | 经营决策参考 |
| E3 实验 | 冻结分配、口径和停止规则 | 采用/停止决策 |
| E4 复现 | 至少两轮或跨商家复现 | 通用产品资产 |

### 5.5 Scenario 输出不是预测事实

每个模拟结果必须保存：

- 输入事实 revision；
- 参数假设及范围；
- 计算 Logic 版本；
- 敏感性范围；
- 未建模成本；
- 允许的行动范围；
- 谁批准将模拟变成真实实验。

## 六、Action Bus：从建议到受控行动

### 6.1 首批 Action 目录

| Action Type | 作用 | 当前实验执行方式 | 风险 |
|---|---|---|---|
| `CreateAcquisitionExperimentDraft` | 创建获客实验草稿 | AOS Draft/文档 | low |
| `FreezeExperimentRevision` | 冻结假设、分组、指标、窗口 | 人工批准 | medium |
| `GenerateContentBriefDraft` | 生成渠道无关内容简报 | Draft/人工制作 | low |
| `RegisterManualTouchEvidence` | 登记人工发布和触点证据 | 人工录入/批量导入 | medium |
| `CreateConsultationTask` | 创建咨询与跟进任务 | Inbox/人工领取 | medium |
| `GenerateOfferDraft` | 生成受毛利约束的 Offer | 人工确认 | medium |
| `CreateIncentiveEntitlementDraft` | 生成贡献型分佣提案 | 财务确认 | high |
| `AcknowledgePaymentEvidence` | 登记打款证据 | 双人复核 | high |
| `CreateRepeatPlanDraft` | 生成合规复购计划 | Draft-only | medium |
| `CloseExperimentWithReview` | 关闭实验并保存复盘 | 人工批准 | medium |

### 6.2 初期为什么必须 Draft/manual

- G3 规划私域活动与归因，但不允许外部发送。
- G5 社交平台 Connector 尚需逐平台能力核验。
- G6 才定义受控生产 Action。
- 当前 AOS 为 M3-1 GREEN、下一阶段 M3-2，M5 完成前不得编码 G0～G6。

因此本实验第一阶段的真实闭环是：

```text
AOS 生成冻结实验和任务 Draft
  → 人工在外部平台发布/咨询/结算
  → 人工登记最小证据或只读回流
  → AOS 连接订单结果并复盘
```

这仍然能验证 Ontology、Logic、Scenario、Task 和 Decision Lineage 的价值，不需要假装已经具备自动发布能力。

### 6.3 Action 六层防线

```text
L1 身份与租户：谁在为哪个组织/项目操作
L2 对象权限：能否读取目标对象和字段
L3 业务规则：consent、频控、毛利、库存、角色归因
L4 安全分类：PII、注入、违规功效、虚假承诺
L5 人工审批：高风险 Offer、分佣、付款、外部触达
L6 执行确认：外部回执/人工证据，不以 toast 作为成功
```

### 6.4 Decision Lineage

每次采用或停止一个策略，至少记录：

```yaml
decision_id: dec_...
hypothesis_revision: exp_...@r3
data_cutoff: 2026-08-02T09:06:54+08:00
metric_definitions: [new_paid_non_owner_customer, contribution_margin_90d]
logic_versions: [L01@v1, L05@v1, L09@v1]
proposal: continue|adjust|stop
approved_by: human_actor_ref
action_refs: [task_..., content_draft_..., offer_draft_...]
outcome_refs: [outcome_...]
uncertainty: small_sample|attribution_gap|none
```

## 七、AIP 数字同事：围绕集中获客重新分工

### 7.1 协作关系

| 数字同事 | 集中获客场景职责 | 禁止越界 |
|---|---|---|
| 电商增长参谋长 | 冻结目标、预算、节奏、停止线和跨角色 DAG | 不绕过审批执行 |
| 数据参谋 | 发现渠道/商品机会，维护归因、实验和复盘 | 不把估计说成因果 |
| 内容官 | 生成内容 brief、版本和素材事实清单 | 不直接发布、不编造功效 |
| 私域管家 | 合规分群、关系健康、复购窗口和频控 | 不持有联系方式、不群发 |
| 导购顾问 | 咨询任务、商品匹配和异议处理建议 | 不承诺未批准价格或疗效 |
| 活动策划师 | Offer、预算、毛利、库存、实验方案 | 不只优化 GMV |
| 客服专员 | 服务问题、退款风险和信任修复 | 不擅自改变财务状态 |

### 7.2 典型 Handoff

```text
数据参谋：发现某内容×商品组合值得测试
  → 活动策划师：冻结 Offer、预算和实验
  → 内容官：生成 A/B/C 内容资产 Revision
  → 私域管家：检查 consent/频控，形成触达 Draft
  → 导购顾问：领取咨询任务，记录结构化结果
  → 客服专员：处理服务/退款风险
  → 数据参谋：连接触点、订单、毛利和退款
  → 增长参谋长：提出继续/调整/停止 DecisionProposal
```

### 7.3 Agent 的价值判定

以下不是有效价值：

- 生成了多少条文案；
- 自动打了多少标签；
- 工作台被打开多少次；
- 发出了多少条消息。

首要产品健康度指标：

> **每周被人工采用并形成真实经营证据的 Action 数。**

辅助指标包括 Action 采用率、从异常到提案的时间、从批准到结果的时间、口径可复现率和建议停止后避免的无效投入。

## 八、Scenario 实验室：四个核心场景推演

### 8.1 场景一：公司集中获客的 14 天微实验

**问题**：公司统一商品、内容和咨询后，能否产生非店主新消费者？

```text
实验输入（需冻结）：
  · 1 个主商品 + 1 个复购商品
  · 3 个内容角度 A/B/C
  · 12 个执行节点：KOC/普通推荐者/公司账号的可行组合
  · 统一咨询 SOP
  · 每个内容唯一 touch/campaign token
  · 预算上限、毛利下限、库存与客服容量

分配：
  · 内容版本随机或准随机分配给执行节点
  · 公司咨询统一承接，避免成交能力差异污染
  · 自购和资格购买不计入主指标

主指标：
  · 非店主新付费消费者数
  · 每个活跃执行节点带来的新付费消费者

护栏：
  · 增量贡献毛利/CAC
  · 退款、投诉、取消关注/退订
  · 咨询容量和响应时长
  · 归因完整率
```

模拟只按每 10,000 次可观察曝光给出敏感性范围，不作为业绩承诺：

| 参数 | 保守 | 基准 | 乐观 |
|---|---:|---:|---:|
| 进入小程序/咨询率 | 1.0% | 2.0% | 3.0% |
| 进入后有效咨询率 | 8% | 15% | 20% |
| 有效咨询支付率 | 10% | 18% | 25% |
| 模拟有效订单 | 1 | 5 | 15 |

敏感性结论：如果内容不能带来有效咨询，提高咨询成交率也无济于事；如果咨询量足够但支付率低，应优先检查商品、价格和信任证明，而不是继续扩大流量。

### 8.2 场景二：小程序成交后的复购实验

**问题**：小程序是否能成为复购承接工具，而不是一次性下单页面？

```text
实验人群：
  正净实付且满足 consent 的历史买家

分组：
  A 组：基于商品使用周期的咨询型提醒
  B 组：普通促销提醒
  C 组：不做营销触达，仅保留服务通知

冻结：
  · 商品复购窗口
  · 触达频控和静默时段
  · 30/60 天复购、贡献毛利、退订和投诉指标
  · 污染规则：跨组领取同一活动、人工额外触达
```

当前正净实付买家只有 33 人，样本不足以做稳定显著性推断。因此首轮只用于验证事件闭环和方向，不得以一轮小样本宣布策略有效。

### 8.3 场景三：佣金结算信任修复

**问题**：佣金到账速度是否影响合作方继续行动？

伦理约束：不能故意延迟对照组的应得佣金，因此不做“快打款 vs 慢打款”随机实验。

```text
Step 1：一次性核查超过30天的待打款
Step 2：建立 dueAt、paidAt、异常原因和付款证据
Step 3：新规则设置首笔佣金 72 小时目标 SLA
Step 4：比较规则切换前后的：
  · 中位打款时长
  · 超 SLA 金额占比
  · 首笔到账后 14 天内再次产生有效触点的比例
  · 争议/咨询次数
```

这里 AOS 的价值不是替财务自动打钱，而是让“算了多少、为什么算、谁批准、何时应付、是否已付”可见且可审计。

### 8.4 场景四：美容店从经销渠道改为服务节点

**问题**：面对强竞品，美容店是否更适合提供体验服务，而不是主推完整商城？

```text
旧方案：美容店承担获客 + 讲解 + 成交 + 服务 + 复购

候选方案：
  公司内容获客
    → 对高咨询需求客户预约合作服务点体验
    → 美容店只完成可验证服务
    → 小程序统一下单和会员沉淀
    → 美容店获得服务费或明确的渠道佣金
```

比较指标：预约到店率、服务后支付率、单次服务成本、消费者满意度、竞品替换风险、90 天贡献毛利。该场景只验证“服务节点”价值，不把唯一美容店合伙人的结果外推为全国招商模式。

## 九、14/30/60/90 天验证路线

### 9.1 Day 0～7：先让经营事实可观测

| 任务 | 完成标准 |
|---|---|
| 冻结指标口径 | 新客、非店主、净实付、贡献毛利、CAC、复购定义明确 |
| 补充渠道标记 | 订单可关联 campaign/touch/actor token |
| 佣金状态核查 | 历史待打款有原因、dueAt 和处理结论 |
| 商品经济性 | 主商品具备成本、履约、退款准备和目标利润 |
| consent 盘点 | 没有同意的人不进入营销触达实验 |
| 实验登记 | 假设、分组、窗口、停止线冻结 |

### 9.2 Day 8～21：14 天集中获客微实验

- 只测 1 个主商品，不推广完整商城。
- 只用少量内容和执行节点，不先扩规模。
- 公司统一咨询承接，减少执行者能力差异。
- 每日只监控护栏，不因短期波动改主指标。
- 归因完整率不足时暂停结论，而不是补填“看起来合理”的渠道。

### 9.3 Day 22～30：第一次 Decision Review

| 结论 | 触发条件 | 下一步 |
|---|---|---|
| Continue | 产生可重复非店主新客，且贡献毛利/CAC 趋势可接受 | 扩一个内容角度或执行节点，不同时扩全部变量 |
| Adjust | 有咨询但支付弱，或有支付但毛利差 | 调整商品/Offer/咨询，保持渠道规模不变 |
| Stop | 无有效咨询、无非店主支付，或护栏持续失败 | 停止该组合，保存失败知识 |
| Inconclusive | 归因、样本、数据延迟或污染不足以判断 | 修复证据后重跑，不宣布成功 |

### 9.4 Day 31～60：复购与角色结算验证

- 对首轮新消费者验证 30/60 天复购。
- 验证达人/KOC 首单佣金、服务费和公司自有流量的分界。
- 比较首笔到账 SLA 改进前后合作方继续行动率。
- 输出第一版 `PrivateCommercePack` 的可复用对象、Logic 和 Action 清单。

### 9.5 Day 61～90：正交验证

不能只在同一批人、同一商品上重复。至少选择一个正交变量：

- 不同价格带商品；
- 不同内容渠道；
- 不同执行角色（KOC vs 公司账号 vs 服务点）；
- 不同消费者需求场景。

若核心对象和 Decision App 无需修改，仅通过 Adapter/Overlay 即可运行，才算出现产品化信号。

## 十、价值验证 KPI 与停止线

### 10.1 北极星指标

本实验不使用 GMV 作为唯一北极星指标，使用：

> **可归因非店主新消费者的 90 天增量贡献毛利。**

原因：它同时排除自购/资格购买，约束获客成本、分佣、退款和履约，并要求观察复购。

### 10.2 KPI 框架

| 层 | 指标 | 说明 |
|---|---|---|
| 获客 | 非店主新付费消费者、有效咨询率、CAC | 判断是否真正获得消费者 |
| 成交 | 咨询支付率、Offer 采用率、净实付 | 判断商品和咨询是否匹配 |
| 经济性 | 贡献毛利、激励占比、90 天毛利/CAC | 防止买增长 |
| 复购 | 30/60/90 天复购、复购贡献毛利 | 判断小程序是否产生留存价值 |
| 客户权益 | 退订、投诉、退款、触达负担 | 不能牺牲关系换成交 |
| 渠道 | 每个执行节点有效新客、集中度 | 防止再次依赖唯一关键人物 |
| 结算 | 中位打款时长、超 SLA 金额、争议率 | 判断激励是否可信 |
| AOS 产品 | Time to First Decision、Action 采用率、口径复现率 | 判断 Palantir 模式自身价值 |

### 10.3 必须预先冻结的停止线

具体数值由实验负责人在启动前结合商品毛利和预算冻结；以下是最低规则：

1. 归因完整率低于 90%，不得宣称渠道效果。
2. consent 或退订链路不完整，暂停营销触达。
3. 实际贡献毛利低于冻结 floor，停止该 Offer 扩量。
4. 连续两轮实验后，参与执行节点中仍少于 20% 能产生至少 1 名非本人有效买家，停止“分散节点获客”假设。
5. 退款、投诉或误导性宣传超过护栏，立即停止对应内容/Offer。
6. 两轮后 CAC 仍高于 90 天贡献毛利的可接受上限，停止该渠道×商品组合。
7. 样本太小或污染过高时结论必须是 `INCONCLUSIVE`，不能改指标求成功。

### 12.3 通用产品 8 模块

| 模块 | 核心能力 | 栖月汇实例 | 可复用边界 |
|---|---|---|---|
| 1. 商城事实连接器 | 订单、会员、商品、退款、分润 | Niushop MySQL | Adapter 差异最大 |
| 2. 私域经营本体 | Customer/Touch/Lead/Consult/Order/Incentive | 栖月汇薄本体 | Core 高复用 |
| 3. 集中获客实验室 | 内容×商品×渠道 Scenario/Experiment | 14 天微实验 | 行业通用 |
| 4. 咨询成交工作台 | 任务、知识、建议、结果 | 护肤咨询 | 品类知识差异大 |
| 5. 复购与关系工作台 | 生命周期、ContactPolicy、复购 Draft | 小程序老客 | Core 高复用 |

| 7. Action Bus | Draft→批准→执行→回执 | 初期人工执行 | Core 高复用 |
| 8. Decision Lineage 与学习 | 假设、证据、结果、复用经验 | Continue/Adjust/Stop | Core 高复用 |

### 12.4 Core / Pack / Overlay 边界

| 层 | 全商家通用 | 品类/模式扩展 | 每商家配置 |
|---|---|---|---|
| Object | Order、Touch、Lead、Experiment、Outcome | SkinNeed、ServiceAppointment | 会员等级、角色名称 |
| Logic | 归因、实验、毛利、停止规则 | 肤质匹配、使用周期 | 阈值、预算、目标利润 |
| Action | 创建任务、冻结实验、登记证据、关闭复盘 | 预约体验、样品领取 | 审批链、结算 SLA |
| Workbench | 获客实验、咨询、激励、复购、复盘 | 美妆咨询卡片 | 品牌和组织布局 |
| Connector | 调用信封、能力快照、回执 | Niushop/有赞/微盟适配 | 账号、权限、字段映射 |

### 12.5 私域电商成熟度模型

| 等级 | 状态 | 商家能回答的问题 | AOS 价值 |
|---|---|---|---|
| L0 不可知 | 订单有但渠道、触达和分佣断裂 | “为什么有单/没单？”答不出 | 事实接入和缺口显性化 |
| L1 可观测 | 触点、咨询、订单、分佣能连接 | 哪个动作带来结果 | Ontology + Lineage |
| L2 可辅助 | Logic 能提出下一步 Draft | 接下来试什么、风险是什么 | Agent + Workbench |
| L3 可行动 | 人工批准后受控执行并回读 | 谁在何时执行了什么 | Action Bus + Receipt |
| L4 可学习 | 实验复现并沉淀跨周期经验 | 哪些策略可复制、何时失效 | Scenario + Memory + Evals |

### 12.6 价值函数

```text
私域电商 Palantir 价值
≈ 决策频率
× 跨对象关联深度
× 失败成本
× 角色协同复杂度
× 可行动覆盖率
× 证据复用率
÷ 建模与运营成本
```

对于小商家，价值不来自“大数据计算”，而来自：

- 更快停止无效渠道和无效商品组合；
- 减少对少数关键个人的不可见依赖；
- 防止分佣、投放和优惠叠加侵蚀毛利；
- 让人工执行也留下可复用经营证据；
- 把一次栖月汇经验沉淀成下一个商家可安装的资产包。

### 12.7 通用方案不是什么

- 不是自动获得微信流量的工具；
- 不是爬取平台私有数据的系统；
- 不是批量骚扰客户的群发器；
- 不是替代商城、CRM、SCRM 或支付系统；
- 不是让 LLM 自主改价、发券、打款和发布内容；
- 不是承诺某个达人、店主或美容店一定能卖货；
- 不是用漂亮看板掩盖产品和获客模式没有成立。

## 十四、风险与局限

### 14.1 业务风险

| 风险 | 影响 | 处理 |
|---|---|---|
| 商品缺少差异化 | 集中获客仍不能转化 | 小规模测试，快速停止，不先扩渠道 |
| 公司缺少内容/咨询能力 | 新模式执行失败 | 把能力建设成本计入实验，不把失败全部归因渠道 |
| 美容店竞品强 | 服务点也可能拒绝或替换商品 | 不以美容店规模化为默认路径 |
| 复购周期不清 | 触达过早或过晚 | 商品级复购窗口实验 |
| 样本太小 | 结果不稳定 | 多轮复现，保持 `INCONCLUSIVE` 选项 |
| 核心人物集中 | 再次形成不可复制成功 | 报告集中度，单独标注特殊渠道节点 |

### 14.2 数据风险

| 风险 | 影响 | 处理 |
|---|---|---|
| 地推没有活动字段 | 无法比较渠道 | 增加 touch/campaign token |
| 历史会员缺失 | cohort 和生命周期偏差 | 保留 unknown，不静默丢弃 |
| 零金额/低价订单多 | 订单数夸大真实消费 | 同时报告订单数、净实付和正价敏感性 |
| `order_id` 跨业务非全局唯一 | 错误 Join | 主键包含 biz_type 或使用稳定复合键 |
| 外部平台指标延迟/不完整 | 归因误判 | 保存 observed_at、口径和 capability |

### 14.3 合规与组织风险

- 未取得 consent 的人不能进入营销触达。
- 退订和投诉优先于任何销售目标。
- 达人/KOC 内容需要事实、版权和宣传合规审核。
- 财务不能因 Agent 建议直接打款，必须 maker-checker。
- 公司集中运营可能增加人力成本，必须计入 CAC 和贡献毛利。
- 人工漏登记会破坏 Decision Lineage，需要任务和证据完整率监控。

### 14.4 技术与阶段风险

- 当前 AOS 尚未进入电商 G0～G6 实施阶段。
- G3/G5/G6 文档是目标方案，不是当前生产能力。
- 微信、企微、视频号等外部能力必须在实现时重新核验。
- 本文不得被解释为生产自动发送、打款或商城写回授权。

## 十六、核心结论

### 结论 1：Palantir 在中国私域电商的价值，不是“帮商家多发消息”，而是“经营假设的操作系统”

私域最危险的不是没有工具，而是无法判断一个订单为什么发生、一个动作是否增量、一个成功是否依赖特殊个人。Ontology 连接事实，Scenario 比较方案，Action 记录执行，Lineage 保存结论，四者共同形成可学习经营系统。

### 结论 2：微信小程序是交易、身份和复购锚点，不应独自承担获客

内容和流量可以来自多个外部节点，但订单、支付、履约、会员和复购必须有稳定真源。小程序的战略价值是把外部触点变成可持续的一方经营关系。

### 结论 3：公司集中获客是当前最值得测试的方向，但不是答案

旧店主模型已经暴露出高沉默和关键人物集中；美容店渠道又难以扩张。把获客能力收回公司能提高可控性，但仍需通过商品、内容、咨询、CAC 和复购实验来证明。

### 结论 4：佣金系统要保留，但必须从“身份分佣”升级为“贡献权益”

佣金不是删除，而是对象化：贡献证据、政策 revision、毛利 cap、审批、到期、打款和争议均可追溯。这样才能同时激励获客、保护利润并建立合作信任。

### 结论 5：栖月汇最有价值的产物，可能不是一个成功活动，而是一套可安装的 Private Commerce Decision OS

如果薄本体、集中获客实验、咨询工作台、激励治理和 Decision Lineage 能在第二个正交商家上复用，栖月汇就从“让人头疼的微商城”变成了验证中国私域电商通用解决方案的第一块试验田。

### 结论 6：失败也必须成为产品资产

如果集中获客实验失败，AOS 仍应明确告诉团队失败发生在曝光、咨询、商品、价格、信任、履约、复购还是经济性。**能快速、可信地证伪错误方向，本身就是 Palantir 模式的重要价值。**
