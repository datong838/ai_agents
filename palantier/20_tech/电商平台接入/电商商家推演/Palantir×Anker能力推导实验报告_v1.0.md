# Palantir × Anker 淘系运营
## 能力推导实验报告 v1.0
### —— 以真实业务负载压测 Palantir 范式的价值边界与实现模式

---

## 0. 实验设定

### 0.1 这不是一份方案，是一次压测

本文档的目的不是交付一个可执行的项目计划，而是**用一个具体、真实、复杂度足够的业务负载，把 Palantir 的产品原语逐个"跑"一遍**，看哪些原语在这个负载下产生了不可替代的价值、哪些是过剩能力、哪些暴露出结构性缺口。

Anker × 淘系运营在这里的角色是**测试台**，不是客户。最终产出应该是可迁移的结论，而不是这一个场景的答案。

### 0.2 边界条件（本次实验忽略的因素）

| 忽略项 | 说明 |
|---|---|
| 商务可行性 | 假设 Foundry + AIP 完整可用、可本地部署、无地域限制 |
| 数据合规 | 假设跨境、PIPL、平台协议问题均已解决 |
| 成本 | 不做 TCO 对比，只推导能力与价值 |
| **替代方案** | **不做"国产等价栈"类比，全程使用 Palantir 原生原语推导**——类比会掩盖原语之间的耦合关系，而耦合恰恰是本次要测的东西 |

### 0.3 为什么这个负载值得做实验载体

Palantir 的经典案例（空客供应链、药企研发、军事指挥）有一组共同的负载特征。淘系电商在其中三项高度吻合、一项显著背离——**这个背离正是本实验最有价值的部分**。

| 负载特征 | Palantir 经典场景 | 淘系电商 | 吻合度 |
|---|---|---|---|
| 数据源异构度 | 高（10–50 个系统） | 高（12–15 个：淘系 API、ERP、WMS、PLM、QMS、客服、财务、外部） | ✅ 吻合 |
| 跨源关联深度 | 深（4–6 跳） | 深（质量事件→批次→库存→订单→消费者 = 5 跳） | ✅ 吻合 |
| 决策频率 | 中（周/月） | **高（日/小时，大促期分钟级）** | ✅ 更极端 |
| 决策后果 | 高 | 高（单次召回千万级；断货损失百万级） | ✅ 吻合 |
| 数据规模 | 极大（PB） | **小（单店日订单 10³–10⁵）** | ❌ 背离 |
| **数据主权完整性** | **完整（数据都在自己手里）** | **不完整（核心流量数据在平台手里）** | ❌❌ **严重背离** |

最后一行是本实验的核心变量。Palantir 的所有成熟案例都建立在"组织拥有自身业务全部原始数据"这一隐含前提上。电商平台经济打破了这个前提。**这个前提被打破后，Ontology 范式还成立吗？成立到什么程度？** —— 这是本次实验真正要回答的问题。

### 0.4 五个待验证假设

| # | 假设 | 证伪条件 |
|---|---|---|
| **H1** | Palantir 的价值与数据量无关，与"异构度 × 关联深度 × 决策频率 × 后果严重性"正相关 | 若在小数据量下无法产生传统 BI 无法产生的价值，则证伪 |
| **H2** | Action（写回）是价值的主要承载，Ontology 是它的前提而非目的 | 若去掉 Action 后价值损失 < 40%，则证伪 |
| **H3** | Scenario（假设推演）在电商的使用频率远高于传统行业，应是一等公民 | 若推导不出周级以上的高频 what-if 场景，则证伪 |
| **H4** | Ontology + Action 构成 AI Agent 的权限边界，使 Agent 能真正进入生产执行 | 若 Agent 仍需绕过 Action 直调外部 API 才能完成任务，则部分证伪 |
| **H5** | 通过 Interface + Marketplace 机制，单客户方案可实现 ≥ 60% 向通用产品的复用 | 若复用率 < 40%，则产品化路径不成立，只能做项目制 |

## 1. 原语拆解：把 Palantir 还原成 19 个能力单元

推导前先做还原。把 Foundry + AIP 拆成不可再分的能力原语，并标注"若没有它，传统栈需要付出什么代价"。

### 语义层（Semantic）

| 原语 | 本质 | 传统栈等价物与代价 |
|---|---|---|
| **Object Type** | 把数据集映射为业务实体 | 数仓维度表 + 一份没人维护的数据字典 |
| **Link Type** | 实体间的关系，可双向遍历 | 每次关联都要写 JOIN；关系知识存在于 SQL 里，不可复用 |
| **Property / Shared Property** | 属性及其集中管理的元数据 | 字段散落各表，同名不同义 |
| **Interface** | 对象类型的抽象形状，提供多态 | **传统栈几乎无等价物**——这是产品化的关键，见第 7 节 |
| **Object Type Group** | 对象分类与检索 | — |

### 动力层（Kinetic）—— Palantir 与数据平台的分界线

| 原语 | 本质 | 传统栈等价物与代价 |
|---|---|---|
| **Action Type** | 对对象的一组变更，含校验、提交条件、副作用 | 自建工单系统 + 自写 API 调用 + 自建审批流，每个动作重复一遍 |
| **Function** | 挂在对象上的可复用逻辑（TS/Python） | 散落在各处的脚本，无统一调用入口 |
| **Automate** | 事件驱动：对象变化 → 触发动作/通知 | Airflow + 规则引擎 + 告警系统三件套 |
| **Dynamic Security / Markings** | 行列级、随对象流动的权限 | 每个应用各自实现一遍权限 |

### 推演层（Projective）—— 最被低估的一层

| 原语 | 本质 | 传统栈等价物与代价 |
|---|---|---|
| **Scenario** | 在 Ontology 分支上创建"沙盒宇宙"，改数据、跑下游、看后果，满意后合并为真实动作 | Excel 建模 + 人工录入。**这是传统栈最大的能力空洞** |
| **Modeling Objectives** | 模型集成、评估、对象绑定 | 模型和业务对象两张皮 |
| **Branching / Proposals** | 本体与管道的分支开发与合并 | 直接改生产，或维护两套环境 |

### 智能层（AIP）

| 原语 | 本质 | 关键约束 |
|---|---|---|
| **AIP Logic** | 无代码构建 LLM 驱动的功能，输出必须是 Ontology 编辑 | 输出受 Schema 约束，不能自由发挥 |
| **AIP Chatbot Studio**（原 AIP Agent Studio） | 构建 Agent，工具集 = Action / Object Query / Function / Command | **Agent 的工具只能是已注册的 Ontology 能力** |
| **AIP Evals** | Agent 评估集，可跨模型对比、检查执行方差 | — |
| **Agents as Functions** | Agent 可发布为 Function，被 Automate、Evals、代码库调用 | 使 Agent 可组合 |

### 交付层（Delivery）

| 原语 | 本质 | 对产品化的意义 |
|---|---|---|
| **Pipeline Builder / Code Repositories** | 数据加工 | 复用率最低的一层，见 7.4 |
| **Workshop** | 拖拽构建运营应用，原生支持 Scenario | 应用层复用的载体 |
| **Marketplace + Foundry DevOps** | 把对象类型、链接类型、动作类型、接口、管道、应用打包为可安装产品 | **产品化的唯一机制**。注意关键约束：**对象实例不可打包**，只有 Schema 和管道能被打包 |
| **Apollo** | 多环境部署与版本管理 | 多租户升级的基础 |

## 2. 正向推导：19 个原语 × 淘系负载

对每个原语提问：**在淘系运营中，它解决了什么传统栈解决不了或代价极高的问题？** 评级标准：

- ★★★ = 不可替代，价值主要来源
- ★★ = 显著优于传统栈
- ★ = 有用但非必需
- ○ = 在此负载下过剩或价值不明显

### 2.1 语义层推导

**Object Type + Link Type ★★★**

推导实例：质量团队问"3 月上旬那批充电宝，卖出去多少、还剩多少、退货率多高、涉及多少消费者"。

- 传统栈：需要 WMS（批次）、ERP（出库）、TOP（订单）、售后系统四方对数，跨 4 个团队，通常 2–3 天，且每次都要重来一遍。
- Ontology：`Batch` 对象点开 → 关联的 `InventoryPosition`、`OrderLine`、`ReturnCase`、`Customer` 全部可遍历，**耗时 30 秒，且第二次问的边际成本为零**。

**关键推导结论**：Ontology 的经济学本质是**把"跨源关联"从可变成本变成一次性固定成本**。传统栈里每问一个新问题都要重新付一次关联成本；Ontology 里关联被物化为 Link，问题数量趋于无限时边际成本趋于零。

由此得出一个可判定的适用性法则：

> **当"跨源关联问题的年提问次数 × 单次关联成本" > "建模成本"时，Ontology 成立。**

淘系运营的跨源提问频率极高（日级），因此即便数据量小，Ontology 依然成立。**这直接支持 H1。**

**Interface ★★★（但价值在本项目内不体现）**

在 Anker 单点项目里，Interface 是纯成本——多一层抽象，开发慢 10–15%。它的价值完全兑现在第二个客户身上。这是一个必须**在第一个项目里就付出、但要到第三个项目才收回**的投资。详见 7.2。

**Shared Property ★★**

淘系有一批天然跨对象的属性：`sku_code`、`shop_id`、`gmv`、`order_time`、`brand_code`。集中管理避免了"店铺ID在五个对象里三种格式"这类经典问题。价值实在但不惊艳。

### 2.2 动力层推导

**Action Type ★★★ —— 本实验判定的最大价值来源**

推导实例：库存指挥台发现某 SKU 将在 11 天后断货。

| | 只读版本（无 Action） | 带 Action 版本 |
|---|---|---|
| 运营动作 | 看到结论 → 打开 ERP → 查在途 → 算数量 → 填补货单 → 找主管审批 | 点击"提交补货建议"，系统已带入建议量、在途、提前期、大促排期 |
| 耗时 | 40 分钟 – 2 天（跨人） | 2 分钟 |
| 决策质量 | 手工填单时上下文丢失，容易漏算大促 | 上下文随动作传递，校验规则强制 |
| 可审计 | 无法追溯"为什么补这么多" | 动作日志含触发依据与执行人 |

**关键推导结论**：把 Action 从 Foundry 中拿掉，剩下的（Pipeline + Ontology + Workshop）本质上是**一个语义化极好的 BI**。市场上有替代品，价值大约损失 55–65%。**H2 成立。**

由此得出一个项目健康度判据：

> **评估任何 Palantir 项目，只看一个指标：每周 Action 执行次数。** 看板浏览量是虚荣指标——一个被每天打开但从不触发动作的决策台，等于失败。

淘系的 Action 清单具体化（每个都能对应到平台 API）：

| Action | 校验规则示例 | 副作用 |
|---|---|---|
| 调整 Listing 价格 | 不得低于 `PricePolicy.最低授权价`；变动 >15% 需审批 | 写回 TOP API + 通知渠道团队 |
| 调整计划预算 | 单次 ≤20%，日累计 ≤50% | 写回阿里妈妈 API |
| 提交补货单 | 金额分级审批；校验仓容 | 写回 ERP + 生成审批任务 |
| **冻结批次** | 需质量负责人角色 | 写回 WMS + 拦截在途 + 触发客服话术下发 |
| 发起召回工单 | 需高层+法务双签 | 触发多系统级联 |

**Automate ★★★**

推导实例：`Batch.质量退货率` 超过基线 2.5 倍 → 自动创建质量事件 → 通知质量负责人 → 暂存一个"冻结批次"Action 待审批。

传统栈需要：调度系统 + 规则引擎 + 告警平台 + 工单系统四件套拼装。Automate 把它们收敛为一个对象事件监听。且 AIP Logic 可直接生成 Automate 自动化，把 LLM 判断纳入触发条件。

**Function ★★**

淘系的复用逻辑：真实毛利计算、补货量算法、退货责任归因、评价情感打分。挂在对象上后，Workshop、Action、Agent 三处共用同一份实现——解决了"三个地方三种毛利口径"的经典问题。

**Dynamic Security / Markings ★★**

淘系的敏感字段有明确分层：SKU 标准成本（商业机密）、消费者标识（个人信息）、供应商报价（合同约束）。权限随对象流动，而非每个应用重实现一遍。价值稳定但不构成差异化。

### 2.3 推演层推导 —— 本实验的意外发现

**Scenario ★★★ —— 严重被低估**

推导实例：双 11 预算 800 万，分配到 5 个品牌 × 24 个主推 SKU。每个 SKU 有库存上限、毛利率、历史投放弹性、大促目标。

- 传统做法：运营用 Excel 建一版分配表 → 开会争论 → 定稿 → 到广告后台手工调 24 次 → 大促当天发现某 SKU 库存不够，再手工回滚。
- Scenario 做法：在 Ontology 分支上直接修改 24 个 `Campaign.日预算`，下游的预计 GMV、预计毛利、预计断货风险实时重算 → 拖动参数对比 3 套方案 → 选定后**一键合并为 24 个真实 Action**。

**关键推导结论**：Scenario 在淘系的使用频率远高于 Palantir 的传统行业。

| 行业 | 典型 what-if 场景 | 频率 |
|---|---|---|
| 制造/航空 | 产能规划、供应链中断推演 | 季度级 |
| 能源 | 电网负荷推演 | 月级 |
| **电商** | **促销力度、预算分配、清仓策略、调价影响、备货方案** | **周级，大促期日级** |

**H3 成立**，且推出一条产品建议：面向电商的通用解决方案中，**Scenario 必须是一等公民、默认出现在每个决策台里**，而不是留给高级用户的隐藏功能。这与 Palantir 在传统行业的产品重心不同。

**Branching / Proposals ★★**

具体价值场景：双 11 前两周需要给作战室加新功能，但不能动生产环境。分支开发 + 提案合并让本体和应用的变更具备与代码同级的管控。大促当天的应急改动也走分支，可快速回滚。

**Modeling Objectives ★**

销量预测、退货率预测、CLV 预测在这里都是常规模型，Foundry 的模型管理能力属于"够用但非差异化"。价值在于模型输出能直接成为对象属性并被 Action 消费——即模型不再是一张预测表，而是决策链的一环。

### 2.4 智能层推导

**AIP Chatbot Studio + Action as Tool ★★★**

推导实例：投放 Agent。

关键在于 Agent 的工具集**只能**是已注册的 Ontology 能力（Action、Object Query、Function、Command）。这意味着：

- Agent 不可能"手滑"把某个计划预算调成 10 倍——因为 `调整预算 Action` 的校验规则里写死了单次 ≤20%
- Agent 不可能查到它无权查看的成本数据——因为 Object Query 受 Markings 约束
- Agent 的每一步决策可回放审计

**关键推导结论**：**Agent 的安全性不应该建立在 Prompt 上，应该建立在 Action Schema 上。** 这是本实验最具跨行业迁移价值的结论之一。传统做法里"给 Agent 加个 API Key 让它调广告接口"是把安全性寄托在模型自觉；Ontology 范式把它变成了工程约束。

**H4 成立**，但有一个重要限定：见 3.2 的缺口 G4。

**AIP Logic + Automate 的"提案模式" ★★★**

淘系的动作有一个特点：**量大、单个后果小、但需要人把关**。例如每天可能产生 200 条否词建议、50 条出价调整建议。

- 全自动执行：风险不可控
- 全人工执行：运营做不完

提案模式正好匹配：LLM 生成提案 → 批量呈现给运营 → 运营可查看每条提案背后的推理日志 → 勾选批准 → 自动执行。这把运营从"决策者+执行者"变成"审核者"，是电商运营人效提升的正确形态。

**AIP Evals ★★**

淘系 Agent 的效果可量化（采纳率、采纳后 ROI 变化），Evals 让"Agent 是否值得信任"变成可测量问题。建议规则：连续两周采纳率 <30% 的 Agent 自动降级为只读。

### 2.5 交付层推导

**Workshop ★★★** —— 决策台的载体，且原生支持 Scenario，这个组合在电商场景价值极高。

**Marketplace + DevOps ★★★（对产品化）/ ○（对单项目）** —— 见第 7 节。

**Pipeline Builder ★★** —— 能力充分，但**这是复用率最低的一层**，见 7.4。

**Media Sets ★★（意外发现）**

淘系有大量被浪费的非结构化资产：商品主图、详情页、评价图片、直播切片。Media Set + 多模态模型可以做：

- 评价图片的缺陷自动识别 → 关联到 `Batch` → 补全质量归因链中最有说服力的证据
- 主图变更与转化率的关联分析（`Listing` 的主图版本作为时序属性）

这在传统电商数据栈里几乎没人做，因为图像和交易数据分属两个世界。Ontology 把它们连在同一个对象上。

| 交付 | Apollo | ★★ | 多租户升级基础 |
| 全局 | Data Lineage | ★★ | 终结指标口径争议 |

**过剩能力（○）**：超大规模分布式计算、Vertex（系统拓扑建模）、Map（地理空间，除非做区域仓配优化）、Gaia。淘系负载用不到 Foundry 的数据规模能力——**这恰恰印证 H1：价值不来自数据量。**

## 3. 反向推导：从最难的决策倒推能力缺口

正向推导容易得出乐观结论。反向推导——从业务中最难的决策出发，看 Palantir 能不能接住——才能暴露真实缺口。

### 3.1 十个最难决策的能力需求

| # | 决策 | 难在哪 | 所需原语 | Palantir 能接住吗 |
|---|---|---|---|---|
| 1 | 这批货该不该冻结 | 需 5 跳关联 + 后果推演 | Object/Link + Scenario + Action | ✅ 完全 |
| 2 | 双11 预算怎么分 | 多约束优化 + 高频调整 | Scenario + Function + Action | ✅ 完全 |
| 3 | 这个 SKU 补多少 | 多源输入 + 不确定性 | Object + Modeling + Action | ✅ 完全 |
| 4 | 差评是产品问题还是批次问题 | 需归因到供应链 | Link + Function + Media Set | ✅ 完全 |
| 5 | 该给 Anker 还是 eufy 加预算 | 需统一真实毛利口径 | Shared Property + Function | ✅ 完全 |
| 6 | 老品什么时候退市 | 库存×合规×毛利多目标 | Scenario + Action | ✅ 完全 |
| 7 | **这个流量下滑是搜索降权还是竞品挤压** | **依赖平台不开放的数据** | — | ❌ **不能** |
| 8 | **这个人群包为什么效果差** | **人群明细在平台侧** | — | ⚠️ **部分** |
| 9 | **实时竞价该出多少** | **毫秒级决策** | — | ❌ **不能** |
| 10 | 竞品明天会不会降价 | 外部信息不可得 | — | ❌ 不能（任何系统都不能） |

### 3.2 缺口清单

**G1 —— 数据主权缺口（结构性，最重要）**

淘系的核心流量数据不出平台：搜索词明细、曝光归因、人群明细、排序逻辑。这意味着 Ontology 中会出现两类残缺结构：

- **空心对象**：`AudienceSegment` 只有 ID、规模、聚合特征，没有成员明细
- **断链**：无法从"曝光"穿透到"人"，`Customer` 的上游链路是断的

这不是 Palantir 的产品缺陷，而是**平台经济对 Ontology 范式的结构性约束**，且在淘宝、京东、抖音、Amazon 全部成立。

**G2 —— 实时性缺口**

Foundry 的 Action 执行是秒到分钟级，适配运营决策；不适配毫秒级竞价。这条缺口是设计取舍，不是缺陷——但意味着通用方案必须明确声明"不做实时竞价引擎"。

**G3 —— 平台连接器缺口**

淘宝开放平台的授权机制、频控、权限等级需要定制 Connector；生意参谋数据不开放明细，只能走授权 + 聚合。这是每个电商客户都要重做一遍的工作——**因此它是产品化投资的最高优先级，见 7.4。**

**G4 —— Agent 的行动半径缺口（对 H4 的限定）**

Agent 只能调用已注册的 Action。这带来安全性，同时意味着：**任何一个没有被建模成 Action 的动作，Agent 都做不了。** 淘系运营的长尾动作极多（回复一条问大家、改一个 SKU 的属性、调整一个活动的报名）。如果只注册了 15 个 Action，Agent 的能力天花板就是这 15 个。

推论：**Ontology 范式下，Agent 的能力上限 = Action 目录的完备度。** 这把"提升 AI 能力"从模型问题转化为了建模工程问题——这是一个重要的、经常被误解的结论。

### 3.3 缺口 G1 的产品化应对 —— 从限制中提炼资产

面对数据主权不完整，有三种设计策略。推导后认为第三种才是正确答案：

| 策略 | 做法 | 判定 |
|---|---|---|
| A. 强行补全 | 爬取、逆向、第三方数据补明细 | ❌ 违规、脆弱、数据质量差 |
| B. 放弃前链路 | Ontology 只覆盖订单以后 | ❌ 丢掉营销决策，价值折半 |
| **C. 代理对象模式** | **为平台侧资产定义标准建模范式** | ✅ **正确解** |

**"平台侧代理对象"（Platform Proxy Object）范式定义：**

```
一个 Proxy Object 由三部分构成：
  1. 句柄     — 平台侧 ID（人群包 ID、计划 ID）
  2. 影子属性 — 平台允许回传的聚合特征（规模、花费、转化）
  3. 委托动作 — Action 不直接改数据，而是调用平台 API 委托平台执行
             （如"下发人群包"：本体只发 ID，圈人和触达在平台侧完成）
```

关键点：**Ontology 的边界应该画在"数据主权边界"上，而不是"业务边界"上。** 跨过主权边界的部分用 Proxy Object 建模，明确标注其为不完整对象，并在应用层对用户提示"此处为平台聚合数据，不可下钻"。

这个范式本身是可复用的产品资产——它在所有平台电商场景通用，应作为通用解决方案的标准构件。**从约束中提炼出的构件，往往比从能力中提炼出的更有价值，因为它不可绕过。**

## 4. 假设验证结论

| # | 假设 | 判定 | 关键证据 | 限定条件 |
|---|---|---|---|---|
| H1 | 价值与数据量无关 | ✅ **成立** | 淘系数据量对 Foundry 是极小负载，但因异构度高、关联深、决策频率高，价值充分兑现；Foundry 的大规模计算能力在此完全过剩 | 需重新定义价值函数，见 F1 |
| H2 | Action 是价值主承载 | ✅ **成立** | 去掉 Action 后价值损失 55–65%，剩余部分与语义化 BI 无本质差异 | — |
| H3 | Scenario 在电商是一等公民 | ✅ **成立且超出预期** | 推导出 5 类周级以上 what-if 场景，频率约为传统行业 10 倍 | 产品设计需相应调整重心 |
| H4 | Ontology+Action 是 Agent 的权限边界 | ✅ **成立，有限定** | 工具集受限于已注册 Action，安全性成为工程约束而非 Prompt 约束 | 但 Agent 能力上限 = Action 目录完备度（G4） |
| H5 | 可实现 ≥60% 复用 | ⚠️ **条件成立** | 综合复用率推算 ~60%，但**必须在第一个项目就采用 Interface-first 建模**，否则降至 25% 以下 | 见第 7 节，这是执行纪律问题而非技术问题 |

## 5. 关键发现

### F1 —— Palantir 的价值函数需要被重新表述

行业普遍认知是 `价值 ≈ f(数据量)`。本实验推导出的表述是：

```
价值 ≈ 数据源异构度 × 跨源关联深度 × 决策频率 × 决策后果严重性 × 协同角色数
       ────────────────────────────────────────────────────────────────
                              建模复杂度
```

**数据量根本不在分子上。** 淘系电商在分子的五项中全部得分很高（12–15 源 / 5 跳 / 日到小时级 / 千万级后果 / 5 类角色），因此价值成立。

这个表述的实用价值在于：它给出了一个**售前判断客户是否适合的可计算清单**，替代了"你数据够不够大"这种错误提问。

### F2 —— 项目健康度只需要一个指标

> **每周 Action 执行次数。**

看板浏览量、用户数、数据接入量都是虚荣指标。一个被每天打开但从不触发动作的决策台，说明它没有进入业务流程，只是一个更好看的报表。

推论出的立项纪律：**任何决策台在立项时必须先定义它能触发哪些 Action，否则不予立项。** 这一条规则能过滤掉大部分注定失败的需求。

### F3 —— Scenario 是电商场景的隐藏杀手锏

Palantir 在传统行业的产品重心是 Ontology + Action；在电商，Scenario 的相对权重显著更高，因为电商决策的特征是**高频、可逆、多方案对比**——这正是 Scenario 的最佳适用形态。

制造业一年做 4 次产能推演；电商一年做 200 次促销推演。

### F4 —— 平台经济是 Ontology 范式的边界压力测试（本实验最重要的发现）

Palantir 所有成熟案例的隐含前提是**数据主权完整**。电商平台生态第一次系统性地打破了这个前提。

结论不是"Ontology 在电商不成立"，而是：

> **Ontology 的边界必须画在数据主权边界上。跨过边界的部分用"平台侧代理对象"建模，并在产品层面显式标注不完整性。**

这个结论的迁移价值远超电商——所有依附于第三方平台的业务（SaaS 生态、支付、物流平台、医保系统、跨国合规环境）都面临同构问题。**Anker 淘系这个测试台的真正价值，是替 Palantir 范式测出了它在平台经济中的适用形态。**

### F5 —— AI Agent 的安全边界应该是 Schema，不是 Prompt

传统做法把 Agent 安全寄托在提示词和模型自觉。Ontology 范式把它变成工程约束：Agent 只能调用注册过的 Action，Action 自带校验、审批、幂等、日志。

代价是 **Agent 能力上限 = Action 目录完备度**。这把"让 AI 更能干"从模型问题转化为建模工程问题——对于要做通用产品的团队，这意味着**Action 目录本身就是核心产品资产**，其价值可能高于任何一个应用。

### F6 —— 交付模式不可与产品分离

Palantir 的 FDE（前向部署工程师）模式在电商场景的适配度**高于**传统行业，因为电商运营的迭代节奏是日级，与 FDE 的现场即时迭代天然匹配。

但这也意味着：**如果把 Foundry 当成软件卖而不配 FDE，在电商场景的失败率会更高**，因为电商业务变化快，一份三个月前写的需求文档在交付时已经失效。

## 6. 实现模式推导

### 6.1 关键时间指标

Palantir 式交付与传统实施的根本差异在前 4 周。推导 Anker 淘系场景的时间线：

| 里程碑 | Palantir 模式 | 传统实施模式 |
|---|---|---|
| 第一次业务对齐产出 | D1–D3：**Decision Inventory**（决策清单，不是需求文档） | W1–W4：需求调研报告 |
| **Time to First Ontology** | **D4–D10**（6 个对象类型：SKU / Listing / Order / OrderLine / InventoryPosition / Batch） | 数仓建模 W5–W10 |
| Time to First App | **D11–D15**（第一个 Workshop 决策台） | W11–W14 |
| **Time to First Action** | **≈ D16–D20（第 4 周）** | W15+（且多数项目根本没有写回） |
| 第一个 Agent | D30–D40 | 通常不在一期范围 |

**第 4 周产生第一个真实写回动作** —— 这是本实验推导出的、最应该被实证检验的数字。它也是 Palantir 交付模式与传统实施最尖锐的对比点。

### 6.2 Decision Inventory：替代需求文档的方法

不问"你想要什么功能"，而问四个问题：

1. 你每周要做哪些决策？
2. 每个决策现在需要多久、要问几个人？
3. 决策错了后果多严重？
4. **决策完成后，你要去哪个系统做什么操作？** ← 这一问直接产出 Action 清单

第 4 问是整个方法的核心。传统需求调研从不问它，因为传统交付物到"看到结论"为止。

### 6.3 建模纪律：薄本体优先

反模式：一次性建 40 个对象类型追求完备。

正确路径：**先建能跑通一条完整链路的最小对象集**。Anker 场景选择"质量归因链"：

```
Review / ReturnCase → Order → OrderLine → Batch → Supplier
```

6 个对象、5 条链接、2 个 Action，即可产出此前完全无法回答的问题（"哪个批次质量异常"）。跑通后再横向扩展。

### 6.4 大促期的分支策略

淘系特有的运行模式：大促是脉冲式高压期，且**不允许失败**。

- T-14 起，主分支冻结，所有变更走开发分支 + 提案合并
- 战时应急改动在分支上做，验证后合并，可秒级回滚
- Scenario 用于战前预演："如果某爆款 2 小时售罄会怎样"

这套机制在传统电商数据栈里基本不存在——大促当天改看板 SQL 是常态，出错就是事故。

## 7. 从 Anker 到通用：产品化架构推导

这是本次实验的最终交付目标。核心问题：**一个为 Anker 做的方案，如何变成任何淘系商家可安装的产品？**

### 7.1 三层产品架构

```
┌──────────────────────────────────────────────────────┐
│ L-Tenant  租户配置层（每客户必做，不可复用）            │
│ 数据源字段映射 · 组织与审批链 · 阈值 · 品牌结构         │
├──────────────────────────────────────────────────────┤
│ L-Pack    行业扩展包（按品类复用）                     │
│ 消费电子包 ← Anker 项目产出                            │
│ 服饰包 · 美妆包 · 食品生鲜包 · 大件家电包               │
├──────────────────────────────────────────────────────┤
│ L-Core    淘系商业本体（全商家通用）                    │
│ Interfaces · Core Actions · Core Apps · TOP Connector │
└──────────────────────────────────────────────────────┘
```

### 7.2 技术承载机制：Interface 是产品化的支点

这是整个产品化路径的技术关键，值得展开。

**问题**：Anker 的 `SKU` 带批次和认证状态；服饰品牌的 `SKU` 带尺码颜色矩阵和季节；生鲜的 `SKU` 带保质期和冷链等级。三者结构差异巨大。如果库存决策台直接依赖 `AnkerSKU` 这个具体对象类型，换客户就要重写应用。

**解法**：定义抽象接口，应用只依赖接口。

```
Interface: ISellableItem
  必填属性：item_code, item_name, standard_cost, lifecycle_stage
  选填属性：batch_tracked, size_matrix, shelf_life

  实现者：
    AnkerSKU        （额外：batch_no, certification_status）
    ApparelSKU      （额外：size, color, season）
    FreshSKU        （额外：expiry_date, cold_chain_level）
```

Workshop 应用和 Function 只引用 `ISellableItem`，因此**换客户时应用零改动，新增实现类型时应用自动兼容**。

两个关键工程细节：

1. **选填属性是版本演进的关键。** 接口新增属性时若设为必填，所有已安装客户都会被阻塞升级；设为选填则可平滑迭代。这是做 Marketplace 产品的必备纪律。
2. **对象实例不可打包。** Marketplace 只能打包 Schema（对象类型、链接类型、动作类型、接口）和管道、应用，不能打包数据。这恰好是 SaaS 产品想要的形态——交付的是"空壳 + 管道"，安装后由客户自己的数据填充。

**由此得出一条对当前 Anker 项目的强制执行纪律：**

> **所有 Workshop 应用和 Function 必须只依赖 Interface，不得直接依赖具体 Object Type。**

这条纪律会让 Anker 项目慢 10–15%，但它决定了 H5 能否成立——**不遵守则复用率从 60% 掉到 25% 以下，产品化路径直接消失。** 这是本报告中优先级最高的执行建议。

### 7.3 通用产品定义草案

**L-Core 接口层（全商家通用）**

| Interface | 说明 | 实现示例 |
|---|---|---|
| `ISellableItem` | 可售单元 | SKU（各品类实现不同） |
| `IListing` | 平台商品链接 | 淘宝 Item / 京东 SKU |
| `ITransaction` / `ITransactionLine` | 交易与交易行 | 订单 / 子订单 |
| `IReturnCase` | 退款退货 | — |
| `ICustomerProxy` | **消费者代理对象**（脱敏，主权受限） | — |
| `IStockPosition` | 库存位 | 各家 WMS 实现不同 |
| `IAdPlan` | **推广计划（平台侧代理对象）** | 万相台计划 |
| `IAudienceProxy` | **人群包（平台侧代理对象）** | 数据银行人群 |
| `IPromotionVehicle` | 促销载体 | 券 / 满减 / 直降 |
| `IFeedback` | 用户反馈 | 评价 / 问大家 |
| `IServiceCase` | 服务工单 | — |
| `ISupplyNode` | 供应节点 | 供应商 / 仓 |

**L-Core 动作层**

调价 · 上下架 · 改主图标题 · 调预算 · 调出价 · 加否词 · 暂停单元 · 发券 · 建活动 · 下发人群 · 建工单 · 提交库存计划 —— 12 个基础 Action，覆盖淘系日常运营 80% 的高频操作。

**L-Core 应用层**

生意指挥中心 · 投放优化台 · 库存指挥台 · VOC 反馈台 —— 4 个，全部只依赖接口。

**L-Pack 扩展包（Anker 项目的产出物）**

| 包 | 新增对象 | 新增 Action | 新增应用 |
|---|---|---|---|
| **消费电子/家电包** | Batch, Supplier, QualityIncident, Certification, RecallCampaign | 冻结批次、发起召回、拦截在途 | 召回与合规指挥台、批次质量归因台 |
| 服饰包 | SizeColorMatrix, Season, FitFeedback | 尺码建议调整、季末清仓 | 尺码退货归因台、上新节奏台 |
| 美妆包 | ShelfLife, Ingredient, MemberTier | 临期处理、会员权益调整 | 效期管理台、复购运营台 |
| 生鲜包 | ColdChainSegment, ExpiryBatch | 临期降价、损耗登记 | 损耗控制台 |

### 7.4 复用率推算与一个反直觉结论

| 层 | Core 可复用 | Pack 可复用 | Tenant 必须定制 |
|---|---|---|---|
| Interface / Object 层 | 60% | 25% | 15% |
| Action 层 | 55% | 30% | 15% |
| **Application 层** | **70%** | 20% | 10% |
| **Pipeline 层** | **40%** | 10% | **50%** |

综合复用率约 **60%**，H5 条件成立。

**但注意 Pipeline 层是唯一低于 50% 的一层。** 拆开看：

- 淘系侧管道（TOP API、阿里妈妈）：**可 100% 复用**——所有淘宝商家的接口是同一套
- 内部系统侧管道（ERP / WMS / PLM / QMS）：**几乎 0% 复用**——每家的系统和字段都不同

由此得出一个反直觉的资源分配结论：

> **产品化投资的第一优先级不是做更多决策台，而是建"内部系统适配器库"。**

即：为主流 ERP（用友、金蝶、SAP）、主流电商 ERP（旺店通、聚水潭、管易）、主流 WMS 预先构建标准适配器。这决定了新客户上线周期是 2 周还是 8 周，是产品化能否规模化的真正瓶颈。

做第二个客户时，你会发现应用层几乎不用改（因为用了 Interface），但 80% 的时间花在接数据上。**瓶颈在 Pipeline，不在 Ontology。**

### 7.5 从项目到产品的三阶段路径

| 阶段 | 载体 | 目标 | 关键动作 | 判定标准 |
|---|---|---|---|---|
| **S1 深挖** | Anker 淘系 | 验证价值与实现模式 | **强制 Interface-first**；建立 12 个 Core Action；沉淀消费电子包 | 第 4 周产生第一个 Action；每周 Action 执行 ≥50 次 |
| **S2 抽象** | 第 2–3 个客户 | 验证抽象是否成立 | 抽出 L-Core；构建第一批适配器；封装 Proxy Object 范式 | 新客户上线周期 ≤6 周；应用层改动 <15% |
| **S3 产品化** | Marketplace | 规模化 | 打包 Core 产品 + 行业包；适配器库；交付方法论固化 | 新客户上线 ≤3 周；FDE 投入下降 50% |

**S2 客户选择标准（重要）**：应选择与 Anker **在关键维度上正交**的客户，才能真正检验抽象。

| 维度 | Anker | 理想的 S2 对照客户 |
|---|---|---|
| 批次重要性 | 极高（召回） | 低 |
| SKU 结构复杂度 | 低（颜色/容量） | 高（尺码×颜色矩阵） |
| 客单价 | 中高 | 低 |
| 退货率 | 低 | 高 |
| 上新频率 | 低（季度） | 极高（周） |

**结论：服饰类目是最佳 S2 对照组。** 如果 L-Core 的接口能同时容纳 Anker 和一个女装品牌，抽象基本成立；如果选一个同为 3C 的客户，等于没做验证。

## 8. 本次实验未覆盖的部分与下一步

诚实标注实验边界，避免过度外推：

| 未验证项 | 风险 | 建议验证方式 |
|---|---|---|
| Interface 抽象在跨品类下是否成立 | **高** — H5 的核心依赖 | S2 选服饰客户做正交验证 |
| 适配器库的边际成本曲线 | **高** — 决定规模化经济性 | 做完 3 个客户后统计 Pipeline 工时曲线 |
| 多租户下的 Ontology 隔离与批量升级 | 中 | 用 Private / Shared Ontology 机制做压测 |
| Agent 在中文电商语料下的实际采纳率 | 中 | 用 AIP Evals 建评估集，目标采纳率 >50% |
| Time to First Action = 4 周 是否可复现 | 中 | 这是本报告最该被实证的数字 |
| Proxy Object 范式在其他平台（抖音、京东）的普适性 | 中 | 第二平台接入时验证 |

### 结语：这次实验真正测出了什么

三条结论按迁移价值排序：

1. **Palantir 的价值函数与数据量无关，与决策密度有关。** 这改变了目标客户的筛选逻辑——不应该问"数据够不够大"，应该问"跨源决策够不够频繁、后果够不够严重"。

2. **平台经济是 Ontology 范式的边界压力测试，答案是"边界画在数据主权线上"。** 这个结论的适用范围远超电商，覆盖所有依附第三方平台的业务形态。从这个约束中提炼出的"平台侧代理对象"范式，是本次实验最有产品价值的副产品。

3. **产品化的支点是 Interface，瓶颈是 Pipeline。** 前者决定了能不能复用，后者决定了复用的速度。而 Interface-first 这条纪律必须在**第一个项目就开始执行**——它是一个无法追溯补救的架构决策。
