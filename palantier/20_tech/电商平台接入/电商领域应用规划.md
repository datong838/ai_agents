## 三、优先级排序

### 3.1 排序原则

基于 `电商领域数字同事初探.md` 的判断标准：

> **可靠性 > 灵活性，可预测性 > 创造性**
> **生产环境的 Agent 由最坏情况定义，不是最好情况**

排序依据：
1. **商业价值** — 私域是所有电商的蓄水池，没有私域一切免谈
2. **技术依赖** — 下层为上层提供能力，必须先打通
3. **实施成本** — 最小更改原则，复用已有代码

## 八、护城河分析

### 8.1 什么不是护城河

- 数据接入（管道工谁都能做）
- 通用技能引擎（逻辑可复制）
- 种子知识导入（管道1+5谁都能做）

### 8.2 真正的护城河

> **管道2（自学习）+ 管道6（客户反哺）—— 运营越久，数据越多，Wiki越深，别人越追不上。**

AOS 运营6个月的美妆客户，其行业 Wiki 积累了：
- 数千次推荐的成功/失败经验
- 数万条客户行为关联规则
- 数百个经过验证的话术模板
- 实时更新的竞品情报

这些是**时间换不来的**。新竞品即使拿到同样的代码，也没有这个知识积累。

### 11.4 客情维护平台设计方案

#### 11.4.1 设计哲学：任务驱动，不是聊天驱动

> 来源：Claude Code 产品哲学 — **"Agent 是同事，不是工具/自动售货机"**

**为什么不是聊天框？**

| 对话产品（错误） | 工作流产品（正确） |
|---------------|-----------------|
| 聊天框是唯一入口 | 任务列表是入口，聊天只是辅助 |
| 进度条转圈不说话 | Plan Mode 展示方案，用户可编辑 |
| 全文件覆盖式修改 | Diff 视图精确呈现变更 |
| 演示永远是 happy path | 失败处理是第一优先级 |

**核心数据模型**：`Task + Artifact + Action`，不是 `Conversation + Message`

**客情维护平台要做的事**：
- 展示私域管家当前在做什么（任务状态）
- 展示产出了什么（Artifact：话术列表、客户分层结果）
- 展示需要什么确认（权限门控：话术确认、导入确认）
- 展示历史（Checkpoint 追溯）

#### 11.4.3 三个核心区域

**区域一：任务列表（左侧，25%宽度）**

## 十二、LLM 选型方案

### 12.1 选型结论：智谱 GLM-5.2（PaaS）

| 维度 | 评估 |
|------|------|
| **模型** | 智谱 GLM-5.2 |
| **接口** | PaaS：`https://open.bigmodel.cn/api/coding/paas/v4` |
| **协议** | OpenAI-compatible（`/v1/chat/completions`） |
| **架构** | MoE 稀疏混合专家，744B 总参数 / 40B 激活参数 |
| **上下文** | **1M tokens** 无损长上下文 |
| **特长** | Coding + Agent 能力强化，适合长时程任务 |
| **兼容度** | 与现有 `llm_gateway.py` 的 `_openai_chat()` 函数完全兼容 |
| **成本** | 待用户提供 API Key 后确认（Token Plan 计费） |

### 12.2 集成方案

现有 `llm_gateway.py` 的 `_openai_chat()` 函数已支持任意 OpenAI-compatible 端点，只需在环境变量中配置：

```bash
# .env 配置
AGNES_BASE_URL=https://open.bigmodel.cn/api/coding/paas/v4
AGNES_API_KEY=<用户提供>
AGNES_TEXT_MODEL=glm-5.2
```

无需修改 `llm_gateway.py` 代码，通过环境变量切换即可。

`aip_llm_adapter.py` 中指定 `model="private-medium"` 别名，在模型路由层映射到 `glm-5.2`。
