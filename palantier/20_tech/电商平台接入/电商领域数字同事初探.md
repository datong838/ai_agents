## 一、为什么电商接入是 FDE 最佳验证场景

电商接入有三个特征天然适合自动化：

1. **流程高度重复** — 每个商家接入都是同一套步骤（认证→拉API→建映射→配同步→测试→上线），换 100 个商家流程几乎不变
2. **决策点明确** — 每一步的"成功标准"是清晰的（API 通了？映射对不对？同步跑起来没有？）
3. **人力成本极高** — 现在 Palantir 的 FDE 是人，一个商家接入少说几天，8 个平台 × N 个商家 = 巨量人力

**结论**：这是 FDE 最有商业价值、最可标准化的场景。

## 二、核心认知转变：数据接入只是开始

### 23 篇方案 vs FDE 需要的东西

**关键认知**：23 篇电商方案只解决了"数据进系统"，但电商运营的真正战场在数据进来之后。


| 维度    | 23 篇方案                       | FDE 需要的                    |
| ----- | ---------------------------- | -------------------------- |
| 回答的问题 | **What & Why**（支持什么、为什么这么设计） | **How to execute**（怎么自动干完） |
| 形态    | 静态文档                         | 可编排的技能链                    |
| 消费者   | 产品经理 / FDE 工程师               | AOS 引擎本身                   |
| 覆盖范围  | 数据基础设施（管道工）                  | 电商运营全貌（运营团队）               |


中间缺了一层 — **Plan Mode 层**：

> 用户说"接入淘宝商家" → AOS 理解任务 → 生成执行计划 → 用户确认 → 逐步执行 → 每步有 checkpoint



### 真实案例印证

微商城案例证明：**数据接入只是修了管道，但管道里流什么、往哪流、谁在接——这些才是电商运营的本质。**

> 微商城现状：私域裸奔——企微有但空、老客没进、种子池 30 个还没用起来、分销链条断了、没有内容获客通道。
> **这不是"做活动"能解决的问题，是从 0 搭的问题。**

## 三、电商运营的六层全景


| 层级      | 名称       | 说明                           | FDE 价值         |
| ------- | -------- | ---------------------------- | -------------- |
| **第一层** | 数据基础设施   | API 接入、字段映射、数据同步、Ontology 物化 | 地基，但不直接产生商业价值  |
| **第二层** | 商品运营     | 上架流程、定价策略、SKU/库存、商品优化        | 基础运营自动化        |
| **第三层** | 客户运营（私域） | 客户沉淀、分层、1V1 导购、触达通道、生命周期     | **最大 FDE 价值区** |
| **第四层** | 营销推广     | 1V1 促单、分销裂变、内容营销、直播、活动策划     | 获客和转化引擎        |
| **第五层** | 售后服务     | 效果回访、好评促进、复购提醒、差评预警          | 复购引擎           |
| **第六层** | 数据驱动     | 运营看板、异常检测、智能推荐、归因分析          | 全局的眼睛          |


**原 23 篇方案只覆盖了第一层。上面五层才是"数字同事"的真正战场。**

## 四、电商跑起来需要的 6 个数字同事



### 判断标准：工具 vs 同事

- **工具**：你给它指令，它执行，不需要判断
- **同事**：它有主动性，能判断、能决策、能"建议你怎么做"

真正叫"数字同事"的，是后者——能**替你做运营判断**。

---



### 数字同事 1：私域管家 — 最核心

**80% 的电商痛点都指向这个角色。**


| 职责       | 具体能力                       |
| -------- | -------------------------- |
| 客户沉淀     | 把老客分批导入企微（话术个性化、防封频控）      |
| 客户打标     | 肤质、消费力、偏好、互动频次             |
| **主动提醒** | "王姐 5 天没互动了，上次买了精华，该推搭配面霜" |
| 跟进排期     | 加粉第几天该说什么、首单破冰用什么钩子        |
| 客户分层     | 谁是高价值、谁该重点维护、谁适合做分销        |


**为什么是最核心**：私域是所有电商的"蓄水池"。没有私域管家，后面所有同事都巧妇难为无米之炊。

### 数字同事 2：导购顾问 — 促单引擎


| 职责    | 具体能力                       |
| ----- | -------------------------- |
| 个性化推荐 | 基于客户画像自动生成推荐方案             |
| 搭配建议  | 体验装引流 → 正装复购 → 套装提客单，自动算阶段 |
| 聊天话术  | 生成 1V1 聊天草稿（人工审核后发送）       |
| 破冰钩子  | 自动从商品池挑低客单做引流款             |


**和私域管家的区别**：私域管家管"关系"（谁、什么时候、怎么触达），导购顾问管"卖什么"（推荐什么、怎么搭配、怎么聊）。

**核心洞察**：美妆促单不是优惠券驱动，是"你帮我选对了"驱动。1V1 推荐的转化率是商城自己逛的 5-10 倍。

### 数字同事 3：内容官 — 获客和种草


| 职责    | 具体能力                                    |
| ----- | --------------------------------------- |
| 多平台文案 | 同一产品生成 4 个平台版本（小红书种草风/抖音带货风/朋友圈风/社群团购风） |
| 短视频脚本 | 产品 → 自动出脚本（钩子→展示→信任→促单）                 |
| 内容日历  | 什么时候发什么、发哪个平台、频次控制                      |
| 素材库管理 | 产品图、好评截图、效果对比图自动归类和复用                   |


**价值**：解决"没有内容获客通道"的问题。但顺序要对——先有私域沉淀，内容拉来的人才有地方接住。

### 数字同事 4：客服专员 — 售前售后


| 职责         | 具体能力                                     |
| ---------- | ---------------------------------------- |
| 售前咨询       | 自动回复常见问题、转人工提醒                           |
| 售后回访       | 买了 7 天后问效果、15 天后促好评                      |
| **消耗周期计算** | 精华 30ml 日均 0.5ml → 用完约 60 天 → 第 50 天提醒复购 |
| 差评预警       | 检测差评 → 立即提醒 + 生成安抚话术                     |
| 退换货处理      | 自动化流程 + 人工确认                             |


**和导购顾问的区别**：导购顾问主动出击"卖"，客服专员被动响应"接"。售后回访是二者交叉地带。

### 数字同事 5：活动策划师 — 节奏掌控


| 职责   | 具体能力                     |
| ---- | ------------------------ |
| 时机推荐 | "近 7 天转化率下降 15%，建议做限时闪购" |
| 方案生成 | 选品、定价、满减规则、页面文案          |
| 效果预测 | 基于历史数据估转化                |
| 活动复盘 | 自动出报告（ROI、转化漏斗、客户反馈）     |


**为什么排第 5**：没有私域池子，活动做了没人看。活动策划师在前面 4 个同事跑顺后才有价值。

### 数字同事 6：数据参谋 — 全局的眼睛


| 职责       | 具体能力                          |
| -------- | ----------------------------- |
| 运营看板     | 日活、加粉数、转化率、客单价、复购率            |
| 异常检测     | 订单突降？某客户流失？库存不足？              |
| **归因分析** | 这个客户为什么买了？内容种草、1V1 推荐、还是活动推动？ |
| 决策支持     | 选品建议、定价建议、人群圈选                |


**特殊定位**：不直接对客户，但给其他 5 个同事提供"眼睛"。

---



### 六个数字同事的协作关系

```
                    数据参谋（眼睛）
                   ╱              ╲
         发现机会 ╱                ╲ 反馈效果
              ╱                    ╲
     ┌──────────┐            ┌──────────┐
     │ 私域管家  │──分发任务──→│ 导购顾问  │
     │（管关系）  │            │（管卖什么）│
     └────┬─────┘            └─────┬────┘
          │                        │
     触达客户                  促单转化
          │                        │
     ┌────┴─────┐            ┌─────┴────┐
     │ 内容官    │            │ 客服专员  │
     │（管获客）  │            │（管售后）  │
     └──────────┘            └──────────┘

               活动策划师（管节奏）
              在数据参谋建议下介入所有环节
```



### 优先级排序


| 优先级    | 数字同事  | 理由                   |
| ------ | ----- | -------------------- |
| **P0** | 私域管家  | 30 个老客是第一桶金，没有私域一切免谈 |
| **P0** | 导购顾问  | 私域建起来后，马上要促单变现       |
| **P1** | 数据参谋  | 数据是其他同事的眼睛，越早有越好     |
| **P1** | 客服专员  | 售后回访 = 复购引擎，不能等      |
| **P2** | 内容官   | 私域跑顺后再开内容获客通道        |
| **P2** | 活动策划师 | 池子养活了再做活动放大          |

## 五、架构决策：通用框架 + 行业外挂 Wiki



### 为什么不选垂直版

**垂直版的死穴**：每进一个行业就要重写一遍导购逻辑、客服逻辑、内容逻辑。美妆版做完，做食品版又是一年。而且行业知识会变——平台规则更新、新品类兴起、消费趋势变化——写死在代码里就永远在追。

**通用框架的优势**：导购顾问的"推荐逻辑"是通用的（客户画像 + 商品池 → 匹配 → 排序 → 推荐方案），换行业只是换"画像维度"和"商品属性"。美妆的画像维度是肤质/年龄/预算，食品的画像维度可能是口味/过敏/家庭人数——**逻辑一样，参数不同**。

但通用框架有一个致命陷阱：**如果行业知识只是配置参数，那它就太浅了。** 真正的行业知识是非结构化的经验、规律、禁忌、节奏。

### 解决方案：行业外挂 Wiki 库

**行业知识不是代码的一部分，而是 AOS 的一个"知识器官"，可以热插拔。**

```
AOS 平台
├── 通用技能引擎（6 个数字同事）
│   ├── 私域管家（通用逻辑）
│   ├── 导购顾问（通用逻辑）
│   ├── 内容官（通用逻辑）
│   ├── 客服专员（通用逻辑）
│   ├── 活动策划师（通用逻辑）
│   └── 数据参谋（通用逻辑）
│
├── 行业 Wiki 基础设施
│   ├── Wiki 存储层（文档/媒体/数据/视频）
│   ├── Wiki 检索层（RAG + 语义搜索）
│   ├── Wiki 写入门控（HugAgentOS 写型四闸门）
│   ├── Wiki 版本管理
│   └── Wiki 置信度系统
│
├── 行业知识包（可插拔）
│   ├── 美妆行业包
│   │   ├── 美妆 Wiki（成分/肤质/品牌/话术/平台规则）
│   │   ├── 美妆画像 Schema
│   │   └── 美妆内容调性库
│   ├── 食品行业包（未来）
│   ├── 母婴行业包（未来）
│   └── ...
│
├── 数据管道层（G1+G2 解锁）
│   └── 电商平台适配器（淘宝/微商城/抖音...）
│
└── 编排层（Claude 哲学：从对话到工作流）
    ├── Plan Mode（理解任务→生成执行计划）
    ├── Checkpoint 系统（分段确认）
    └── Task 数据模型（任务是一等公民）
```

**与 Palantir 的对齐**：Foundry 是通用平台，行业 Foundry（Government Foundry、Healthcare Foundry）是行业知识包。AOS 走同一条路——不卖"美妆 SaaS"，卖"能学会任何行业的数字同事平台"。

## 六、行业 Wiki 的知识来源 — 全渠道七条管道

行业 Wiki 的内容来源是**全渠道**的，七条管道各有分工：

### 管道 1：种子知识导入（冷启动）

**来源**：

- 现有 23 篇电商接入方案（平台规则、API 限制、数据结构）
- 行业 SOP 手册（门店运营手册、客服话术库）
- 人工编写的领域知识（资深运营的经验结构化录入）

**特点**：质量高但慢，适合做 Wiki 的"骨架"。

### 管道 2：运营实践自学习（持续长大）

这是 Claude 哲学的 Self-correction Loop——**Wiki 会长大**。

- 导购顾问推了面霜，客户买了 → 记录"这个搭配成功"→ 置信度+
- 客服专员处理了 10 次同类投诉 → 自动总结"这类问题的处理模式"
- 活动策划师做了 3 次闪购 → 总结"什么选品+什么折扣转化最高"

**关键设计**：参考 HugAgentOS 写型门控——低风险经验自动积累（标记"经验级"），高风险结论必须人工确认后才进正式 Wiki。

### 管道 3：网络学习（最"活"的管道）


| 学什么    | 从哪学                    | 怎么用                 |
| ------ | ---------------------- | ------------------- |
| 平台规则变化 | 淘宝/抖店/小红书官方公告          | 自动更新 Wiki 的"平台规则"章节 |
| 热门品类趋势 | 电商平台热销榜、搜索趋势           | 内容官知道"最近什么火"        |
| 消费者讨论  | 小红书/抖音评论区、知乎问答         | 理解客户真实痛点和话术         |
| 行业报告   | 艾瑞/QuestMobile/CBNData | 宏观趋势注入决策            |


**技术实现**：定时爬取 + LLM 摘要 + 人工审核入库。

### 管道 4：竞品分析

**专门盯着竞争对手。**

- 竞品在卖什么、什么价格、什么活动
- 竞品的内容策略（小红书、抖音、文案风格）
- 竞品的客户反馈（他们商品评价区就是金矿——客户在骂什么就是你的机会）
- 定时抓取竞品店铺数据 → 对比自身 → 生成"竞品周报" → 高价值洞察自动入 Wiki



### 管道 5：专业知识库（第三方数据源）


| 领域   | 数据源         | 示例               |
| ---- | ----------- | ---------------- |
| 美妆成分 | CosDNA、美丽修行 | 成分安全评级、致敏风险、搭配禁忌 |
| 食品营养 | 薄荷健康、FDA    | 营养成分、过敏原、法规限制    |
| 法规合规 | NMPA（国家药监局） | 产品备案、禁用成分、广告红线   |
| 供应链  | 1688、工厂数据   | 成本参考、MOQ、交期      |


**特点**：结构化程度高，可以做成 API 对接，定期同步。

### 管道 6：客户数据反哺（最有价值）

**被忽略但最有价值的一条。**

- 客户的购买行为 → "买 A 的人 60% 也买了 B"（关联推荐知识）
- 客户的咨询记录 → "最近问得最多的问题是 XXX"（FAQ 自增长）
- 客户的评价 → "好评：保湿、不油腻；差评：瓶口设计差"（产品优化方向）
- 客户的退换货 → "退货原因集中在 XX"（风险预警）

**特殊性**：这是**你独有的**。竞品分析谁都能做，但你的客户行为数据别人没有。这是 Wiki 的差异化壁垒。

### 管道 7：人工经验注入（不可替代）

- 定期跟资深运营做访谈 → 结构化录入
- 月度运营复盘会 → AOS 自动记录关键决策和理由
- 客户成功案例拆解 → "这单为什么成功了"变成可复用的经验模板

## 七、行业 Wiki 的知识治理 — 三层过滤

七条管道往 Wiki 里灌东西，如果不治理就是垃圾堆。

### 第一层：可信度分级


| 等级        | 来源             | 示例           | 使用方式      |
| --------- | -------------- | ------------ | --------- |
| **L1 权威** | 官方文档、法规、API 规范 | NMPA 禁用成分列表  | 直接使用，不需确认 |
| **L2 专业** | 第三方专业数据库、行业报告  | CosDNA 成分评级  | 使用但标注来源   |
| **L3 经验** | AOS 自学习、运营复盘   | "敏感肌推这个转化率高" | 参考但需置信度标注 |
| **L4 推测** | 网络爬取的碎片信息      | 论坛里某用户说XX好   | 仅作线索，需验证  |




### 第二层：写入门控（HugAgentOS 模式）


| 写入类型 | 来源          | 门控级别            |
| ---- | ----------- | --------------- |
| 直接写入 | L1 权威数据     | 无门控，自动入库        |
| 待审核  | L3 经验、L4 推测 | 写入草稿区，人工审核后转正   |
| 紧急标记 | 管道6客户投诉激增   | 立即标记预警 + 推送人工确认 |




### 第三层：时效性管理

知识会过期。每条知识需要：

- **生效时间**：什么时候开始有效
- **失效检查**：多久复查一次（平台规则每月复查、成分知识每年复查）
- **版本追溯**：改了什么、谁改的、什么时候改的

## 九、FDE 数据接入的技能分解



### 完整的电商 FDE 数据接入任务



### Step 1 — 对话理解

- 用户："帮我接入淘宝天猫"
- AOS 澄清门（Clarification Gate）：商家ID？API密钥？同步哪些数据？
- 低置信度时暂停问，高置信度（已有模板）直接做



### Step 2 — 认证配置（依赖 G2 OAuth Token Manager）

- AOS 调用 OAuth 技能 → 配置 Token → 测试连通
- 敏感操作挂起确认（HugAgentOS 写型门控思想）



### Step 3 — API 探索（依赖 G1 REST API Connector）

- AOS 自动拉取平台 API schema
- LLM 理解接口 → 匹配 AOS 数据模型



### Step 4 — 字段映射

- AOS 生成映射建议
- Diff 审核（用户看到"将要做什么"）



### Step 5 — 同步配置 + Ontology 物化

- 配置频率/增量/重试策略 → 物化到 Ontology



### Step 6 — 测试验证

- 拉测试数据 → 验证映射 → 输出报告
- 失败自动重试 + 记忆写入（Self-correction Loop）



### 核心原则：分段式 checkpoint 模型

**FDE 数字同事不是"一键全自动"，而是 90% 自动 + 10% 人工确认。**


| Claude 哲学机制            | 电商 FDE 对应         |
| ---------------------- | ----------------- |
| **Clarification Gate** | API 密钥、商家信息必须人工确认 |
| **过程透明**               | 字段映射、配置变更展示 Diff  |
| **Self-correction**    | 映射失败时重试，下次更聪明     |
| **Abort & Escalate**   | API 限流、认证失败时优雅退场  |


每一段执行完都可以暂停、审核、回滚。

## 十一、护城河分析



### 什么不是护城河

- 数据接入（管道工谁都能做）
- 通用技能引擎（逻辑可复制）
- 种子知识导入（管道 1 + 5 谁都能做）



### 什么是真正的护城河

**管道 2（自学习）+ 管道 6（客户反哺）——运营越久，数据越多，Wiki 越深，别人越追不上。**

AOS 运营 6 个月的美妆客户，其行业 Wiki 积累了：

- 数千次推荐的成功/失败经验
- 数万条客户行为关联规则
- 数百个经过验证的话术模板
- 实时更新的竞品情报

这些是**时间换不来的**。新竞品即使拿到同样的代码，也没有这个知识积累。
