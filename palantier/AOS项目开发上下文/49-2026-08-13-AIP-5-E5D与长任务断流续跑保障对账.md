## 3. 断流续跑机制

### 3.1 能力边界

`stream disconnected before completion` 会终止当前响应。被终止的响应不能在自身内部继续计时或重新建立连接，因此“断流后由同一响应立即重试两次”不是可真实保证的能力。

可执行的等价保障拆成两层：

1. **活动响应内即时重试**：命令、浏览器动作或工具调用遇到临时网络/通道错误时，最多即时重试 2 次；两次仍失败则停止重复副作用并写入检查点。
2. **外部 Watchdog 兜底续跑**：`launchd` 每 30 秒检查一次同一任务的 rollout transcript；当最新用户 turn 尚无 final、连续静默满 5 分钟且没有恢复锁时，立即尝试恢复两次，失败后每 5 分钟再尝试一次，直到成功或被禁用。

### 3.2 防重复执行

Watchdog 必须遵守以下门禁：

- transcript 在最近 300 秒仍在增长时不启动第二执行链；尚未返回的工具调用只在该 300 秒心跳窗口内视为活跃，超过窗口后按疑似残留调用进入恢复判定。
- `06-当前执行检查点.md` 显示完成、暂停、待评审、待授权或外部阻塞时，只报告状态，不擅自越门。
- 开始状态变更前先运行 `memory-gate`，并检查共享记忆 Lease；Lease 冲突时不执行。
- 只执行检查点中的“下一步”，不重新运行已经有 commit 和新鲜验证的步骤。
- Git 工作树出现未归属改动时精确避让；不执行 reset、清理、强推或整仓暂存。
- 写操作继续遵守幂等键、CAS、Receipt 和租户边界；无法证明幂等的动作只做只读核查。

### 3.3 外部 Watchdog 恢复任务

Watchdog 通过 `codex exec resume <同一 session-id>` 发送固定恢复指令：

1. 第一条用户可见消息必须先明确输出：`外部 Watchdog 检测到任务中断并已恢复本任务。`
2. 读取 `01-当前项目状态.md`、`06-当前执行检查点.md`、本文件。
3. 运行两个仓库的 `git log -8 --oneline --decorate` 与 `git status --short --branch`。
4. 运行共享记忆 `memory-validate`、`memory-status`、`memory-gate`；记忆 RED 时先修复投影，不推进依赖状态变更。
5. 若存在活动执行、完成/暂停/评审门或 Lease 冲突，则 no-op 并简短记录原因。
6. 否则从 `06` 的首个未完成步骤继续；临时错误即时重试不超过 2 次。
7. 完成一个可验证子步骤后更新 `01/06`，运行对应测试并形成安全提交。

### 3.4 验收标准

- Watchdog 绑定当前任务；`launchd` 每 30 秒巡检，首次疑似断流后即时恢复两次，后续失败按 5 分钟退避。
- Watchdog 不创建新 thread，不在 transcript 活跃时重复编码。
- 守护进程依赖本机开机、网络恢复和有效 Codex 登录；关机期间不执行，开机后由 `RunAtLoad` 恢复巡检。
- 续跑后的第一条用户可见消息必须先说明 Watchdog 已发挥作用；同一条状态随后说明读取到的 revision、两个 Git HEAD、未完成项和实际继续步骤。
- 当前长任务全部完成后停用 Watchdog，避免永久空转。

### 3.5 2026-08-13 真实断流复盘与结论修正

本次只能判定为 **Watchdog 触发链有效，但自动恢复未成功**，不能表述为“第二次恢复成功”。北京时间时间线如下：

| 时间 | 事件 | 判定 |
|---|---|---|
| 15:32:23 | 原任务 `stream disconnected before completion`，`last_agent_message=null` | 原任务失败 |
| 15:37:56 | Watchdog 发起第 1 次同任务 `resume` | 初始 300 秒静默门槛已到，巡检触发正常 |
| 15:41:55 | 第 1 次恢复任务再次断流，未产生用户可见消息 | 恢复失败 |
| 15:42:08 | Watchdog 发起第 2 次 `resume` | 双尝试机制正常 |
| 15:47:29 | 第 2 次恢复任务再次断流，未产生用户可见消息 | 恢复失败 |
| 15:47:39 | 记录 `retry-scheduled`，下一次为 15:52:39 | 进入失败后 300 秒退避 |
| 15:50:57 | 用户人工发送“Watchdog 起作用了吗” | 比下一次自动重试早 1 分 42 秒 |

因此，用户没有看到 Watchdog 主动“喊起来”的直接原因有两个：两次自动恢复都在输出首条助手消息前再次断流；用户人工唤醒又发生在第三次计划重试之前。`launchd` 的 30 秒 `--once` 调度正常，`not running` 只是两次巡检之间的静止状态。

先前回答把旧事件遗留的 `last_recovered_at` 和旧成功退出码当成了本次结果，并声称“第二次恢复成功”，这是错误结论。当前事件的权威字段是 `last_exit_code=1`、`consecutive_failures=2`，两次 task 均为 `last_agent_message=null`。以后判定恢复成功必须同时满足：

1. 当前恢复 episode 的退出码为 0；
2. transcript 中出现当前 episode 的助手可见恢复声明或后续完成证据；
3. 不得读取上一个 episode 遗留的 `last_recovered_at` 代替当前结果。

后续 Watchdog 补强建议单独实施：为状态增加 `recovery_episode_id`、`last_recovery_outcome`、`visible_ack_at`，新 episode 开始时清理旧 `last_recovered_at`；在满足可见 ACK 前只报告“已触发/恢复尝试中”，不得报告“已恢复”。
