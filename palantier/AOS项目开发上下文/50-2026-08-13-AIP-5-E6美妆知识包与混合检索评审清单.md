## 使用的 Rules

1. 先方案、清单和权威边界，再编码；本文件通过后才进入 E6 实现。
2. 只在 `aos-platform/m1` 开发；最小变更，保留所有非本波工作树改动。
3. 行业知识是可安装的 `VerticalPack`，不是 AOS 核心代码，也不是前端 fixture。
4. 外部资料默认不可信；来源、许可、版本、新鲜度、内容哈希任一未知即 fail closed。
5. 所有知识先进入 E5 Candidate/治理链；禁止 crawler、LLM 或 adapter 直写正式 Wiki/Memory。
6. 索引是可重建投影，不是授权真源；授权、scope、marking 和 freshness 必须在 payload 解析前生效。
7. 不用 Mock、预测数量或静态页面冒充真实知识、真实召回或 Eval GREEN。
8. 每个子门完成后更新 `01-当前项目状态.md`、`06-当前执行检查点.md`，测试并形成安全提交。

## 一、实时事实

- E5 已具备七类知识管道 Policy、Schedule/Run/Receipt/checkpoint、可信 adapter 空注册表和控制面；真实租户当前为 7 条 Policy、0 Schedule、0 Run。
- AIP 当前检索只支持 subject/object-ref 精确解析；尚无面向自然语言查询的全文/向量融合检索。
- PostgreSQL 当前安装 `pgcrypto/plpgsql`；`pg_trgm/unaccent` 可用但未安装，`pgvector` 不可用。因此首期全文通道可落地，向量通道必须以 capability 状态诚实降级，不能伪造 embedding。
- 现有 `BundleKind` 已支持 `VerticalPack`，但 `BundleExports` 尚无知识资产出口；仓库中没有美妆 VerticalPack、获授权种子包或经审核的 50 条金标集。
- 本地 `smart_lab` 话术文件、历史示例和 CosDNA 抓取设想均不是本波可直接发布的权威知识。

## 二、方案复审发现

### P0：必须整改

1. 旧 14-Wiki 文档允许 L1/L2 或管道直接写 Semantic，与 E0-E5 唯一 Candidate 治理链冲突。
2. 旧冷启动方案把“预计 353 条”写成目标数据，缺少逐条来源、许可、hash、freshness 和回滚凭证，不能作为真实交付。
3. 旧专业库方案包含未获授权的 CosDNA 自动抓取；不得启动，也不得保存未授权全文。
4. 旧检索方案把向量库视为既有能力；当前开发 PostgreSQL 无 pgvector，必须显式区分 `ready/degraded/blocked`。
5. 旧 50 查询仅给出少量示例，缺 reviewer、gold citation、负向权限/过期/撤回/冲突用例，不能宣告 Top-1 指标。

### P1：本轮补强

1. 冻结知识包 `manifest -> source inventory -> candidate import -> governance -> install projection -> rollback` 全链路。
2. 新增自然语言 `KnowledgeSearch` 契约，保留现有 `KnowledgeQuery` 精确 subject 路径，避免破坏 E3。
3. 全文、向量、重排为独立 capability；仅 ready lane 参与融合，所有结果必须装配 citation。
4. Eval 同时覆盖检索质量、六角色依赖、租户/marking/新鲜度/撤回和引用正确性。

## 四、外部数据门

### 允许进入代码的内容

- 数据结构、导入器、验证器、索引和 Eval 执行器。
- 官方来源的 URL、版本和抓取日期清单；只有确认使用政策后，其内容才可成为 Candidate payload。
- 不含知识正文的测试 fixture，以及专用于权限/状态机的合成测试数据。

### 当前保持阻断

- CosDNA：没有已核验授权与使用政策，保持 `license_unknown / disabled`。
- NMPA：可作为官方权威来源候选，但 2021 目录已被 2025 动态清单机制更新；需逐项登记当前 List I/II 版本、公告日期和可使用范围。
- 353 条美妆内容：只是旧方案容量预测，不是现有资产；没有逐条 Receipt 前计数为 0。
- 50 条检索金标：没有专家审核和精确 gold citation 前，Eval 状态为 `blocked_gold_set_unapproved`。
- 向量通道：本机无 pgvector/本地 embedding authority，状态为 `degraded_vector_unavailable`；全文通道不得伪装成混合 GREEN。

## 六、验收矩阵

- Contract：未知字段、未知 scope/kind/capability、路径穿越、hash 漂移全部拒绝。
- Migration：disposable PostgreSQL upgrade/downgrade、单 head、RLS/FORCE、无 scope 零可见、既有行数守恒。
- Bundle：安装/卸载/回滚不改核心包；同一 VerticalPack 可按组织/工作区形成独立投影。
- Ingestion：同 Receipt 重放得到同一 Candidate；异 hash 冲突；失败不推进 checkpoint。
- Retrieval：权限、marking、freshness、revoked、conflict 在 payload 前过滤；全文索引清空后不改变 canonical authority。
- Degrade：向量/重排不可用时响应清楚说明 degraded lane 和未参与原因。
- Eval：只有审核通过且不少于 50 条的 gold set 才计算 Top-1；六角色映射按语义依赖检查，不按数量凑数。
- Browser：只在 `org-org/dev-project` 验证知识包、索引 capability、阻断来源、Eval 状态、空态/错误态；控制台错误 0。

## 七、评审结论

经过“评审 -> 整改 -> 复审”对账，架构边界、子门、真实数据原则、降级语义和验收矩阵已经闭合，结论为：

**方案通过；E6A 已实现并复审通过，可进入 E6B；外部知识正文、50 条金标和向量 GREEN 仍受外部数据门约束。**

这不是 E6 完成声明。只有 E6A-E6F 的实现证据和外部数据门分别满足后，才能改变 E6 总状态；其余时点必须分别报告 `CODE_GREEN`、`DATA_BLOCKED`、`EVAL_BLOCKED` 或 `DEGRADED`。
