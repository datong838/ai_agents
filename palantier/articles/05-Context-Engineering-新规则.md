## 一、核心发现

### 1.1 实验结果

Anthropic 在 Claude 5 代模型发布后，做了一个实验：**删掉了 80% 的 Claude Code 系统提示词**。

结果：

> "We removed over 80% of Claude Code's system prompt for more advanced models with no measurable loss on our coding evaluations."

**没有任何可测量的性能下降。**

### 1.2 原因分析

新一代模型（Claude 5 代）具备更强的**判断力**，不再需要大量的硬规则来约束行为：

| 旧模型需要 | 新模型不再需要 |
|-----------|--------------|
| 大量示例才能学会模式 | 理解接口设计即可推断 |
| 硬规则列表才能约束行为 | 给判断边界就能自主判断 |
| 重复强调才不会遗忘 | 工具描述清晰就足够 |
| 全量上下文才能理解任务 | 按需加载效果更好 |

### 1.3 范式转变

这不是简单的"删规则"，而是**从 Prompt Engineering 到 Context Engineering 的范式转变**：

```
Prompt Engineering（旧）        Context Engineering（新）
══════════════════════          ════════════════════════════
精心设计系统提示词                精心管理上下文生命周期
给大量规则和示例                  给判断边界 + 设计接口
一次性塞满上下文                  渐进式披露（Progressive Disclosure）
人工维护记忆                      系统自动记忆
```

## 二、六条新旧规则对照

### 2.1 规则一：从"给规则"到"用判断力"

| 旧规则（Then） | 新规则（Now） |
|---------------|--------------|
| Give Claude rules | Let Claude use judgment |

**旧做法**：

```
你是一个代码助手。遵守以下规则：
1. 永远不要使用 var
2. 优先使用 const 而非 let
3. 函数名用 camelCase
4. 类名用 PascalCase
5. 文件名用 kebab-case
6. 不要使用 any 类型
7. ...（几十条规则）
```

**新做法**：

```
你是一个代码助手。
用你的判断力写出高质量的 TypeScript 代码。
遵守项目已有的代码风格。
```

**原理**：新模型见过足够多的代码，已经知道什么是"好的代码"。过度约束反而会导致冲突（如"留文档"vs"不加注释"的矛盾）。

**边界**：仍然需要**不可妥协的硬规则**（安全/合规/隐私），但不需要穷举所有情况。

### 2.2 规则二：从"给示例"到"设计接口"

| 旧规则（Then） | 新规则（Now） |
|---------------|--------------|
| Give Claude examples | Design interfaces |

**旧做法**：

```
工具用法示例：
示例1：search("手机") → ["iPhone 15", "华为 Mate60"]
示例2：search("笔记本") → ["MacBook Pro", "ThinkPad"]
示例3：search("耳机") → ["AirPods Pro", "Sony WH-1000"]
```

**新做法**：

```typescript
const searchTool = {
  name: "search",
  description: "搜索商品库",
  inputSchema: {
    type: "object",
    properties: {
      query: {
        type: "string",
        description: "搜索关键词。支持模糊匹配。"
      },
      category: {
        type: "string",
        enum: ["electronics", "clothing", "food"],
        description: "商品类别。可选。"
      },
      limit: {
        type: "number",
        default: 10,
        description: "返回数量上限。默认10。"
      }
    },
    required: ["query"]
  }
}
```

**原理**：好的接口设计（清晰的参数名、类型、描述、枚举值）比示例更有效。模型从接口定义就能推断正确用法，不需要看例子。

### 2.3 规则三：从"全部放前面"到"渐进式披露"

| 旧规则（Then） | 新规则（Now） |
|---------------|--------------|
| Put it all up front | Use progressive disclosure |

**旧做法**：

```
System Prompt:
  你是一个电商运营助手。
  以下是客户A的完整信息：[5000字]
  以下是产品库的完整信息：[10000字]
  以下是历史订单：[8000字]
  以下是行业知识：[6000字]
  ...（总计 30000+ 字一次性塞入）
```

**新做法**：

```
System Prompt:
  你是一个电商运营助手。
  当前任务：推荐产品
  客户ID：12345

  # 记忆系统按需加载：
  Think阶段 → 加载客户画像（3条最相关）
  Act阶段 → 加载产品库（按需查询）
  Observe阶段 → 加载历史订单（2条最相似）
```

**原理**：新模型擅长**按需加载上下文**。一次性塞满会导致：
- 注意力分散（关键信息被淹没）
- Token 浪费（加载了用不上的信息）
- 成本增加（Token = 钱）

**Progressive Disclosure 三层策略**：

```
始终加载              按需加载              触发加载
─────────           ──────────           ──────────
当前任务上下文         客户画像（Think时）    历史订单（Observe时）
系统角色定义          产品库（Act时）       行业知识（Branch时）
当前步骤信息          工具定义（使用时）     竞品情报（分析时）
```

### 2.4 规则四：从"重复强调"到"工具描述写清楚"

| 旧规则（Then） | 新规则（Now） |
|---------------|--------------|
| Emphasize repeatedly | Clear tool descriptions |

**旧做法**：

```
System Prompt:
  重要：使用 search 工具搜索商品。
  提醒：search 工具需要传入 query 参数。
  再次提醒：不要忘记 search 工具的存在。
  强调：搜索时用 search 工具，不要用其他方式。
```

**新做法**：

```typescript
const searchTool = {
  name: "search",
  description: "搜索商品库。当用户询问产品信息、价格、库存时使用此工具。",
  // 描述清晰，模型自然会在正确时机使用，不需要在 Prompt 里重复
}
```

**原理**：如果工具的描述写得清楚，模型会**自然在正确的时机使用它**。在 System Prompt 里反复强调反而：
- 浪费 Token
- 可能误导模型在不该用时使用
- 降低其他信息的权重

### 2.5 规则五：从"记忆存 CLAUDE.md"到"自动记忆"

| 旧规则（Then） | 新规则（Now） |
|---------------|--------------|
| Store in CLAUDE.md | Automatic memory |

**旧做法**：

```
用户：# 记住，客户A 喜欢简约风格的包装
  ↓
人工写入 CLAUDE.md：
  - 客户A偏好：简约风格包装
```

**新做法**：

```
用户：客户A 喜欢简约风格的包装
  ↓
Agent 执行任务时自动判断：
  - 这条信息有长期价值？→ 是
  - 与当前任务相关？→ 是
  - 已有类似记忆？→ 否
  ↓
自动存储到记忆系统：
  type: Semantic
  title: "客户A偏好"
  content: "简约风格包装"
  confidence: L2
  source: "conversation_auto_save"
```

**原理**：新模型可以**自己判断什么值得记**。不需要用户主动 `# 存记忆`，系统自动：
- 识别有长期价值的信息
- 判断是否与已有记忆冲突
- 自动更新或新建记忆
- 在合适时机主动检索

### 2.6 规则六：从"简单规格"到"丰富引用"

| 旧规则（Then） | 新规则（Now） |
|---------------|--------------|
| Simple spec docs | Rich grounding (HTML, tests, functions) |

**旧做法**：

```
# 需求规格
创建一个用户列表页面：
- 显示用户名、邮箱、注册时间
- 支持按注册时间排序
- 支持分页
```

**新做法**：

```
# 需求规格（丰富引用）

## 设计参考
- HTML 模板：`/templates/user-list.html`
- 设计稿：`/designs/user-list.png`

## 代码引用
- 现有列表组件：`/components/DataTable.tsx`
- 用户类型定义：`/types/user.ts`
- 排序工具函数：`/utils/sort.ts`

## 测试引用
- 集成测试：`/tests/user-list.test.tsx`
- E2E 测试：`/tests/e2e/user-list.spec.ts`

## API 引用
- 用户列表接口：`GET /api/users?page=1&sort=created_at`
- 用户详情接口：`GET /api/users/:id`

## 需求
创建一个用户列表页面：
- 显示用户名、邮箱、注册时间
- 支持按注册时间排序
- 支持分页
```

**原理**：新模型擅长**从代码/测试/设计稿中提取信息**。丰富的引用比纯文本描述更精确：
- HTML 模板 → 了解布局结构
- 代码引用 → 了解现有组件能力
- 测试引用 → 了解预期行为
- API 引用 → 了解数据格式

## 三、`claude doctor` 命令

### 3.1 功能

Anthropic 提供了 `claude doctor` 命令，自动帮助：

1. **精简 CLAUDE.md** — 删除过时的、冗余的规则
2. **精简 Skills** — 合并重复的验证技能
3. **分析上下文使用** — 哪些上下文被加载了但从没用到
4. **建议优化** — 哪些规则可以改为工具描述

### 3.2 工作流

```
运行 `claude doctor`
  ↓
分析当前 System Prompt
  ↓
识别冗余规则（被工具描述覆盖的、过时的、冲突的）
  ↓
生成精简建议：
  - 删除规则 #3（已被工具描述覆盖）
  - 合并规则 #7 和 #12（功能重复）
  - 规则 #5 与 #9 冲突，建议保留 #9
  ↓
用户确认后自动应用
```

### 3.3 效果

| 指标 | 精简前 | 精简后 | 变化 |
|------|--------|--------|------|
| System Prompt Token 数 | 5000+ | 1000- | -80% |
| 规则数 | 50+ | 10- | -80% |
| 评估成绩 | 基准 | 基准 | 0% |
| 响应速度 | 基准 | +15% | 更快 |

## 四、Progressive Disclosure 深度解析

### 4.1 什么是 Progressive Disclosure

**定义**：上下文不是一次性全部加载，而是**根据当前需要，动态加载最相关的信息**。

类比：图书馆
- 旧方式：把所有书搬到桌上再开始找（全量加载）
- 新方式：先查目录，再去书架取需要的书（按需加载）

### 4.2 三层加载策略

```
┌──────────────────────────────────────┐
│  Layer 1: 始终加载（Always-on）       │
│  ─────────────────────────────       │
│  · 系统角色定义（"你是XXX助手"）      │
│  · 当前任务上下文（任务ID/类型/状态）  │
│  · 当前步骤信息（步骤编号/动作类型）   │
│  · Working Memory（当前任务动态上下文）│
│  Token 成本：低（通常 < 500）         │
├──────────────────────────────────────┤
│  Layer 2: 按需加载（On-demand）       │
│  ─────────────────────────────       │
│  · Semantic Memory（行业知识/RAG）   │
│    触发条件：LLM 调用、分支判断       │
│  · 工具定义（当前可用工具的Schema）   │
│    触发条件：需要使用工具时           │
│  Token 成本：中（每次加载 500-2000）  │
├──────────────────────────────────────┤
│  Layer 3: 触发加载（Event-driven）    │
│  ─────────────────────────────       │
│  · Episodic Memory（历史经验）        │
│    触发条件：LLM 调用、写回操作       │
│  · 外部数据（API 响应/数据库查询）    │
│    触发条件：工具调用返回             │
│  · 竞品情报                           │
│    触发条件：分析/对比任务             │
│  Token 成本：高（每次加载 1000-5000） │
└──────────────────────────────────────┘
```

### 4.3 加载决策矩阵

| 步骤类型 | Semantic | Episodic | 工具定义 | 外部数据 |
|---------|----------|----------|---------|---------|
| LLM 调用 | ✅ 加载（top 3） | ✅ 加载（top 2） | ✅ 加载 | ❌ |
| 工具调用 | ❌ | ❌ | ✅ 加载 | ✅ 加载 |
| 分支判断 | ✅ 加载（top 1） | ❌ | ❌ | ❌ |
| 数据写回 | ❌ | ✅ 加载（top 2） | ❌ | ❌ |
| 只读查询 | ❌ | ❌ | ✅ 加载 | ✅ 加载 |

### 4.4 指针策略

当上下文超出限制时，用**指针**代替内容：

```
全量内容（不使用指针）：
  客户A的完整信息：[2000字描述]

指针策略（推荐）：
  客户A → ref:customer:12345
  （需要时通过 ref 检索完整信息）
```

**原理**：
- 指针只占几个 Token
- 需要时才检索完整内容
- 上下文窗口保持精简
- 支持更长的对话/任务

## 五、自动记忆机制

### 5.1 什么是自动记忆

**定义**：系统自动判断什么信息值得存储，不需要用户主动触发。

> "Claude now automatically saves memories that are relevant to the work and to you."

### 5.2 自动记忆的判断标准

```
信息出现
  ↓
判断1：有长期价值？
  ├── 否 → 丢弃（如"今天天气不错"）
  └── 是 → 判断2
  ↓
判断2：与当前任务相关？
  ├── 否 → 存入 Episodic（情景记忆，低优先级）
  └── 是 → 判断3
  ↓
判断3：已有类似记忆？
  ├── 是 → 更新已有记忆（补充/修正）
  └── 否 → 新建记忆
  ↓
判断4：出现频率高？
  ├── 是（>5次）→ 提升到 Semantic（长期语义记忆）
  └── 否 → 保留在 Episodic
```

### 5.3 三种记忆类型的自动流转

```
Episodic（情景记忆）          Semantic（语义记忆）
═════════════════════         ═══════════════════
"上次给客户A推荐成功了精华液"   "美妆客户常买：精华液+面霜+爽肤水"
     ↓                            ↑
     ↓  出现5次以上模式            ↑
     └────────────────────────────┘
        自动提升到 Semantic

Working（工作记忆）
═════════════════════
"当前任务：给客户B推荐产品"
     ↓
     ↓  任务完成后
     ↓  有可复用经验？
     ↓  ├── 是 → 存入 Episodic
     ↓  └── 否 → 丢弃
```

### 5.4 冲突处理

当新记忆与已有记忆冲突时：

```
新信息："客户A 喜欢浓烈香型"
已有记忆："客户A 喜欢清淡香型"
  ↓
冲突检测：
  · 是否时间变化导致偏好改变？
    ├── 是 → 更新记忆，标注时间
    └── 否 → 判断2
  · 来源可信度？
    ├── 新信息来源更可信 → 更新
    └── 旧信息来源更可信 → 标注矛盾，保留两者
```

## 六、工具接口设计原则

### 6.1 接口设计 > 示例

> "Designing interfaces is more effective than providing examples."

**好的接口设计**包含：

| 元素 | 说明 | 示例 |
|------|------|------|
| **清晰的参数名** | 见名知意 | `customer_id` 而非 `cid` |
| **类型标注** | 明确数据类型 | `age: number` 而非 `age: any` |
| **参数描述** | 说明用途和约束 | `description: "客户ID。必须是正整数。"` |
| **枚举值** | 限制取值范围 | `enum: ["electronics", "clothing"]` |
| **默认值** | 可选参数的默认行为 | `default: 10` |
| **必填标记** | 哪些参数必须提供 | `required: ["query"]` |

### 6.2 接口设计示例

```typescript
// ❌ 坏的接口设计（需要示例才能理解）
const badTool = {
  name: "do",
  description: "做一些事情",
  inputSchema: {
    type: "object",
    properties: {
      x: { type: "string" },
      y: { type: "string" },
      z: { type: "string" }
    }
  }
}

// ✅ 好的接口设计（不需要示例）
const goodTool = {
  name: "search_customers",
  description: "搜索客户库。当需要查找客户信息、分析客户画像、或给客户打标签时使用。",
  inputSchema: {
    type: "object",
    properties: {
      query: {
        type: "string",
        description: "搜索关键词。支持姓名、手机号、邮箱的模糊匹配。"
      },
      filters: {
        type: "object",
        properties: {
          skin_type: {
            type: "string",
            enum: ["干性", "油性", "混合性", "敏感性", "中性"],
            description: "肤质筛选。可选。"
          },
          ltv_min: {
            type: "number",
            description: "最低 LTV 筛选。可选。"
          }
        },
        description: "筛选条件。全部可选。"
      },
      limit: {
        type: "number",
        default: 10,
        description: "返回数量上限。默认10，最大100。"
      }
    },
    required: ["query"]
  }
}
```

### 6.3 接口设计检查清单

```
□ 参数名是否见名知意？
□ 每个参数都有类型标注？
□ 每个参数都有描述？
□ 枚举值是否完整？
□ 默认值是否合理？
□ 必填参数是否最小化？
□ 描述是否说明了"什么时候使用"？
□ 描述是否说明了"参数的约束"？
```

## 七、System Prompt 极简原则

### 7.1 核心理念

> **"Less is more" — 更少的规则，更好的效果。**

### 7.2 什么应该保留

```
必须保留的硬规则：
  ───────────────────
  1. 安全规则（不可妥协）
     · PII 保护（手机/身份证/银行卡必须脱敏）
     · SQL 注入防护
     · Prompt 注入防护

  2. 合规规则（法律要求）
     · GDPR 数据处理规则
     · 行业监管要求

  3. 品牌规则（不可妥协）
     · 品牌名正确拼写
     · 禁止提及竞品名

  4. 系统边界（架构约束）
     · 可用工具列表
     · 数据访问范围
```

### 7.3 什么应该删除

```
可以删除的软规则：
  ───────────────────
  1. 风格规则（模型有判断力）
     · "用简洁的语言"
     · "保持专业语气"
     · "段落不要太长"

  2. 格式规则（接口设计已覆盖）
     · "返回 JSON 格式"
     · "字段名用 camelCase"
     · "日期格式用 ISO 8601"

  3. 流程规则（工具描述已覆盖）
     · "先搜索再推荐"
     · "查询前先检查权限"
     · "修改前先备份"

  4. 重复规则（已在别处定义）
     · 在 System Prompt 重复工具说明
     · 在 System Prompt 重复业务规则
```

### 7.4 极简 System Prompt 模板

```
你是 {角色}。

你的职责是 {核心职责}。

## 不可妥协的规则
1. {安全规则}
2. {合规规则}
3. {品牌规则}

## 判断边界
- {高风险操作} → 需人工确认
- {只读操作} → 自动放行
- 其他情况 → 用你的判断力

## 可用工具
（工具定义由工具系统自动注入，不在此重复）
```

## 十、最佳实践检查清单

### 10.1 System Prompt 检查

```
□ 是否只保留不可妥协的硬规则？
□ 是否删除了风格/格式/流程规则？
□ 是否没有重复工具说明？
□ Token 数是否控制在 1000 以内？
□ 是否给了"判断边界"而非"规则列表"？
```

### 10.2 工具接口检查

```
□ 参数名是否见名知意？
□ 每个参数都有类型和描述？
□ 枚举值是否完整？
□ 描述是否说明了"什么时候使用"？
□ 必填参数是否最小化？
□ 是否不需要示例就能理解用法？
```

### 10.3 上下文加载检查

```
□ 是否采用渐进式披露（非全量加载）？
□ Semantic 层是否按需检索（非预加载）？
□ Episodic 层是否触发加载（非始终加载）？
□ 是否有指针策略（超出限制时用指针代替内容）？
□ Token 成本是否优化？
```

### 10.4 记忆系统检查

```
□ 是否有自动记忆机制（非手动存储）？
□ 是否有冲突检测（新记忆 vs 已有记忆）？
□ 是否有频率检测（高频模式提升到 Semantic）？
□ 是否有按需检索（非全量加载记忆）？
```

## 十一、总结

### 核心要点

1. **删掉 80% 的 System Prompt** — 新模型有判断力，不需要硬规则
2. **设计接口 > 给示例** — 好的 propsSchema 比例子有效
3. **渐进式披露** — 按需加载，不一次性塞满
4. **工具描述写清楚** — 不在 Prompt 里重复
5. **自动记忆** — 系统自己判断什么值得存
6. **丰富引用** — HTML/测试/函数比纯文本规格更有效

### 范式转变

```
Prompt Engineering              Context Engineering
════════════════════            ══════════════════════════
"给模型更多规则"                "给模型更好管理的上下文"
"给更多示例"                    "设计更好的接口"
"一次性加载所有"                "按需加载最相关的"
"人工维护记忆"                  "系统自动记忆"
"简单文本规格"                  "丰富多源引用"
```

### 一句话总结

> **"用判断力代替规则，用接口代替示例，用按需加载代替全量塞入，用自动记忆代替手动存储。"**
