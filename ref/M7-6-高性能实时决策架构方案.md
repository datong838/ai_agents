## 0. 一句话定位

> **站在巨人的肩膀上：** L1（离线本体）和 L3（交互界面）直接对标 Palantir 全球最佳实践；L2 采用 **「双引擎并行」**——左边 Palantir 原生 AIP（K-LLM）走主路，右边自研实时决策引擎（PPR+ANN+EGB）走应急车道。**不是替代，是补充**；平时 AIP 是主力，流量洪峰时 L2 自动补位，双保险。

## 1. 三层架构总览（对标用户示意图）

```text
┌─────────────────────────────────────────────────────────────────┐
│  L3 交互界面（对标 Palantir Apollo）                              │
│  数字孪生大屏 · 运营操作后台 · 本体展示层                          │
│  ← 最顶层：负责把能力可视化，给客户/运营用                          │
├─────────────────────────────────────────────────────────────────┤
│  L2 决策层（双引擎并行）                                          │
│  ┌──────────────────────────┬──────────────────────────┐         │
│  │ Palantir 原生 AIP        │ 自研实时决策引擎           │         │
│  │ (K-LLM)                  │ (PPR + ANN + EGB)         │         │
│  │ 通用场景标准化决策         │ 高并发场景加速             │         │
│  │ 检索 → 生成 【主路】      │ 过滤 → 提纯 → 快决策【应急车道】│         │
│  └──────────────────────────┴──────────────────────────┘         │
│  ← 中间层：两个模块并列，互不冲突，互为备份                          │
├─────────────────────────────────────────────────────────────────┤
│  L1 离线本体层（对标 Palantir Ontology）                          │
│  OKF Bundle · 知识底座 · 对象/链接/规则沉淀                        │
│  ← 最底层：老板熟悉的「知识底座」                                   │
└─────────────────────────────────────────────────────────────────┘
```

**金句：**

> 我们不重复造轮子，我们只造更强的引擎。  
> **Palantir AIP 负责「稳」的主路决策，自研引擎负责「快」的洪峰补位——稳快结合，双引擎并行。**

## 2. 各层定义（术语拉齐）

| 层 | 对外名称 | 对标 Palantir | 职责 | 谛听实现 |
|----|----------|---------------|------|----------|

## 3. L2 双引擎并行（核心 · 第 4 页重点）

### 3.1 为什么并列，不替代？

| 维度 | Palantir 原生 AIP（左引擎） | 自研实时决策引擎（右引擎） |
|------|----------------------------|---------------------------|
| **定位** | 全球最佳实践 · **主路** | 国产补充 · **应急车道** |
| **链路** | 检索 → 生成 | 过滤 → 提纯 → 快速决策 |
| **擅长** | 政策查询、常规客服、标准化决策 | 直播间弹幕、订单洪峰、毫秒分流 |
| **典型场景** | 环科院政策查询、常规咨询 | 马帮跨境电商直播间（一秒几千条弹幕） |
| **关系** | 平时主力 | 洪峰自动补位 · 互为备份 |

```text
         流量入口（弹幕 / 咨询 / 订单）
                    │
         ┌──────────┴──────────┐
         │   智能路由 / 分流      │
         └──────────┬──────────┘
                    │
      ┌─────────────┴─────────────┐
      ▼                           ▼
┌─────────────┐           ┌─────────────────┐
│ AIP 主路     │           │ 自研引擎 应急车道  │
│ K-LLM       │           │ PPR → ANN → EGB  │
│ 检索→生成    │           │ 过滤→提纯→快决策  │
│ 通用·稳      │           │ 高并发·快         │
└──────┬──────┘           └────────┬────────┘
       │                           │
       └───────────┬───────────────┘
                   ▼
            L1 本体（共享知识底座）
                   ▼
            L3 交互界面（统一展示）
```

### 3.2 右引擎三件套（去术语化）

| 技术 | 中文名 | 角色 | 一句话 |
|------|--------|------|--------|
| **PPR** | 并行模式识别 | 交通指挥官 | 多车道分流，「下单」和「哈哈哈」瞬间分开 |
| **ANN** | 特征萃取引擎 | 读心神探 | emoji/方言/新梗 → 愤怒/退货/急件 |
| **EGB** | 动态调优机制 | 进化引擎 | 记录结果，淘汰差策略，越跑越准 |

### 3.3 双引擎协作规则

1. **互不干扰**：两条链路独立运行，不互相阻塞  
2. **互为备份**：AIP 过载时，路由自动把流量切到右引擎  
3. **共享 L1**：两引擎都读同一套本体，决策有共同「世界模型」  
4. **统一 L3**：无论哪条引擎产出，都在交互界面可视化 + 溯源  

---

## 4. 痛点：为什么需要右引擎补位？（第 3 页）

| 痛点 | 表现 | 左引擎（AIP）局限 | 右引擎补位 |
|------|------|-------------------|------------|
| **高并发** | 直播间每秒上万弹幕 | 检索链路长，易卡顿 | PPR 多车道毫秒分流 |
| **新场景** | 「绝绝子」「City不City」 | 规则库更新慢 | ANN 语义萃取兜底 |
| **成本高** | 全量走重型 AI | Token 费用高 | 99% 噪音先过滤，仅高价值下沉 AIP |

**结论：** 不是放弃 Palantir AIP，而是在 L2 **并列**加一条加速链路，各走各的，反而能分流压力。

## 5. L2 右引擎运作逻辑（第 5 页）

```text
输入：弹幕 · 订单流 · 库存（洪水涌入）
        ↓
① 并行模式识别（PPR）— 多车道分流
        ↓
② 特征萃取引擎（ANN）— 模糊人话 → 精确指令
        ↓
③ 动态调优机制（EGB）— 试错迭代，越跑越准
        ↓
输出：回复 · 报警 · 改价 · 转人工 · 写回 L3
```

**与左引擎对比：**

| 步骤 | AIP 主路 | 自研应急车道 |
|------|----------|--------------|
| 1 | Ontology 检索对象 | PPR 并行分类分流 |
| 2 | K-LLM 生成回答 | ANN 特征萃取 |
| 3 | HITL 审批写回 | EGB 策略调优 + 快输出 |
